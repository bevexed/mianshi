# 用户反馈偶发 Bug 怎么查

> **这题最能体现工程成熟度**——
> 因为偶发问题没法靠"我本地跑一下"解决。
> 你的 mi8 项目就是「客户反馈驱动的修复节奏」，
> 有真实素材，一定要用上。

## 第一步：把"偶发"变成"可复现"

**能复现就成功一半了。**

### 尽可能收集环境信息

| 维度 | 为什么重要 |
|---|---|
| 设备 / 系统版本 | iOS 和安卓的行为差异（日期格式、键盘、webview 内核） |
| 浏览器 / webview 版本 | 低版本不支持某些语法或 API |
| 网络环境 | 弱网、切换网络时的竞态 |
| 账号 / 角色 | 权限不同导致数据结构不同 |
| 操作路径 | 从哪进来的、之前做了什么 |
| 时间点 | 能对上发版时间或某个定时任务吗 |

**最有用的一句追问**：
> 「你能回忆一下出问题之前做了哪几步吗？」

用户说"就是突然不行了"的时候，
往往是**前一步的操作留下了脏状态**。

---

## 第二步：靠监控还原现场

**这是自建 Sentry 的价值所在，你有实战经验。**

- **错误堆栈 + sourcemap 还原** → 定位到具体代码行
- **面包屑（breadcrumbs）** → 用户出错前的操作序列、
  接口调用、路由跳转
- **用户上下文** → 哪个账号、哪个租户
- **tag / extra** → 自定义的业务标识

**没有监控时**：只能靠日志上报或者复现。
所以「先把监控接上」本身就是解法的一部分。

## 偶发问题的常见根因分类

### 1. 竞态（最常见）

- 快速切换 tab / 翻页，**先发的请求后回来覆盖了新数据**
- 重复点击提交，两次请求都成功
- 组件卸载后异步回调还在执行

**特征**：手快的用户容易遇到，手慢的遇不到。

**排查**：看是否有未取消的请求、未清理的定时器。

### 2. 缓存/状态残留

- localStorage 里的旧数据结构，新版本代码读不了
- 单例状态在页面间没重置
- 你踩过的「**邀请人被固定**」就是这类

**特征**：新用户没问题，老用户有问题；清缓存就好了。

> 见 [13-项目深挖/工程汇微信H5-授权与构建优化.md](../13-项目深挖/工程汇微信H5-授权与构建优化.md)

### 3. 环境差异

- iOS 的 `new Date('2025-01-01 10:00')` 返回 Invalid Date
- 不同 webview 内核的 CSS 差异
- 时区导致的日期错一天

**特征**：只有某类设备/地区的用户遇到。

### 4. 数据边界

- 空数组、null、超长字符串、特殊字符
- 数值精度（金额）
- 权限导致某个字段缺失

**特征**：只有特定数据的用户遇到。

### 5. 并发/时序

- 多个 tab 同时操作
- 审批流中另一个人同时改了状态

## 第三步：加日志缩小范围

如果还是定位不了，**主动加埋点**：

```js
// 在可疑路径上打点，带上足够的上下文
Sentry.addBreadcrumb({
  category: 'order',
  message: 'submit clicked',
  data: { orderId, status, retryCount }
})
```

**关键**：
- 打点要带**状态快照**，不只是"到这里了"
- 灰度放量，收集一段时间
- 注意脱敏

## 答题结构（把 mi8 经历用上）

> 我在 mi8 那个项目里处理过很多这类问题，
> 因为是交付给工程企业的 ERP，客户的问题描述往往很模糊，
> 比如"产值填报送审失败"，没有报错、没有步骤。
>
> 我的顺序是：
> 先问清环境和操作路径，把范围缩小；
> 然后去 Sentry 看有没有对应的错误和面包屑；
> 如果监控里没有，说明不是抛异常而是逻辑问题，
> 这时我会**去对比 PC 端的行为**——
> 因为移动端很多问题的本质是和 PC 端的业务口径不一致，
> 不是技术 bug。
>
> 实在定位不了就在可疑路径加埋点，灰度收集。
>
> 【需确认】举一个你真实查出来的例子。

**「很多问题的本质是业务口径不一致而不是技术 bug」
这句话很成熟**，显示你不是只会盯着代码看。
