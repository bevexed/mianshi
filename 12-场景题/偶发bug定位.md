# 偶发 Bug 定位

偶发问题的核心不是立即猜根因，而是保存证据、缩小变量并把问题转化为可重复验证的假设。

## 1. 先确定影响与止损

- 影响哪些版本、设备、地区、账号、角色和业务数据？
- 从什么时间开始，是否与发版、配置、数据任务或依赖故障重合？
- 是功能不可用、数据错误还是体验退化？是否需要回滚、关开关或暂停入口？
- 是否涉及资金、权限、数据破坏等高风险影响？高风险问题先隔离和保全日志。

不要为了复现继续污染生产数据。必要时复制脱敏数据到隔离环境，或只增加只读观测。

## 2. 收集最小复现信息

| 维度 | 示例                                           |
| ---- | ---------------------------------------------- |
| 环境 | 设备、系统、浏览器/WebView、应用版本、网络     |
| 身份 | 匿名用户标识、租户、角色、实验组；敏感字段脱敏 |
| 路径 | 入口、操作顺序、刷新/返回/多标签页等前置状态   |
| 数据 | 业务对象 ID、状态版本、空值和边界数据          |
| 时间 | 带时区的精确时间、请求 ID、trace ID            |

用户录屏和 HAR 可能包含令牌、个人数据，应经过同意并安全传输、限时保存。

## 3. 用观测还原现场

- 错误堆栈配合对应版本的 source map；生产 source map 访问权限要受控。
- breadcrumbs 记录路由、用户动作和请求结果，但不要记录密码、令牌或完整表单。
- 前后端使用 request/trace ID 串联浏览器、网关、服务和数据库日志。
- 对比成功与失败样本，而不是只盯失败日志。
- 记录版本、feature flag、配置和 API schema，避免只知道“同一页面”。

没有抛异常不等于没有证据：状态转换、关键分支和业务结果也需要结构化事件。

## 4. 常见假设分类

### 竞态与生命周期

- 旧请求后返回覆盖新请求；
- 重复提交或多标签页并发修改；
- 组件卸载后回调继续写状态；
- 乐观更新失败后回滚顺序错误。

可用请求序号、`AbortController`、幂等键和状态机版本号验证。

### 缓存与持久状态

- 旧版本 `localStorage` 数据与新 schema 不兼容；
- service worker、CDN、接口缓存处于不同版本；
- 单例状态、连接或订阅未在边界重置。

“清缓存后恢复”只是线索，不是修复。应加入 schema 版本、迁移或失效策略。

### 环境与时间

- 依赖非标准日期字符串解析；
- 时区、夏令时、语言和数字格式差异；
- 低版本 WebView 不支持语法或 API；
- 弱网、离线恢复和网络切换触发重试竞态。

### 数据与权限边界

- `null`、空集合、超长文本、特殊 Unicode、精度溢出；
- 权限裁剪导致字段缺失；
- 历史数据没有满足新约束。

## 5. 设计实验

每次只改变少量变量：固定数据更换设备、固定设备更换账号、限制网速、重复快速操作、切换旧版本数据。为每个假设写出“如果成立会看到什么证据”，再决定是否加日志或开调试构建。

```js
monitor.addBreadcrumb({
	category: 'order.submit',
	data: {
		orderId,
		stateVersion,
		requestId,
		retryCount
	}
});
```

新增观测要有采样、脱敏、容量限制和下线时间，避免临时日志永久留在生产。

## 6. 修复与复盘

1. 用自动化测试或最小脚本固化复现条件。
2. 修根因并验证相邻路径，避免只增加 `try/catch` 隐藏问题。
3. 灰度观察原指标和副作用，保留回滚能力。
4. 复盘发现、影响、时间线、根因、修复和预防项，明确负责人和截止时间。
