# 发版安全

安全发布依赖可重复构建、分阶段验证、兼容性、观测和可演练的回退，而不是发布人的记忆。

## 分支与集成策略

| 策略        | 适用倾向                   | 主要代价                    |
| ----------- | -------------------------- | --------------------------- |
| GitHub Flow | 短生命周期分支、持续交付   | 需要主干始终可发布          |
| Trunk-Based | 高频集成、小批量发布       | 强依赖自动化和 feature flag |
| Git Flow    | 明确版本列车、维护多个版本 | 长分支和回合并成本较高      |

名称不是重点。团队应明确受保护分支、评审要求、紧急修复、版本标记和谁有发布/回滚权限。

## 质量门禁

```text
本地快速反馈 → PR/CI → 集成或预发布验证 → 灰度/金丝雀 → 全量
```

- CI 至少按项目风险运行格式、lint、类型、单元/集成测试、构建和安全检查。
- 测试环境使用生产相似的配置，但不直接连接生产数据；需要真实分布时使用脱敏副本或受控影子流量。
- 构建一次、逐环境提升同一不可变制品；环境配置在部署时注入并校验。
- 对制品生成版本、来源提交和依赖清单，确保能追溯。

## 发布兼容性

- API 遵循先兼容后端、再发布消费者、最后清理旧字段的 expand-contract 流程。
- 数据库迁移优先小步、在线和向后兼容；“回滚代码”不一定能回滚已变更数据。
- 静态资源使用内容 hash，并让旧资源保留超过 HTML、service worker 和活跃会话的最大存活期。
- feature flag 要有负责人、默认值、监控和清理日期；开关本身也需要测试。

## 灰度与观测

灰度可按内部用户、租户、稳定 hash 或比例分流。发布前定义继续/停止条件，例如：

- JS 错误率、白屏率和资源加载失败率；
- API 错误率与 p95/p99；
- 登录、提交、支付等核心流程成功率；
- 容量、成本和客服反馈。

灰度组必须具有代表性；只让内部高速网络用户试用，不能覆盖真实环境。

## 回退与前滚

- 保存最近可用制品和部署配置，回退操作应自动化、限权并审计。
- 严重影响先止损；数据迁移不可逆或安全漏洞场景可能更适合前滚修复。
- 动态导入失败可提示刷新或单次自动重载，但要防止循环刷新。
- 定期演练回退，记录恢复时间；“文档上能回滚”不等于实际能回滚。

## 发布清单

### 发布前

- 变更范围、风险、依赖顺序和回退方案已评审；
- migration、配置、feature flag 和资源已验证；
- 值班人、观察窗口和沟通渠道明确。

### 发布中

- 分阶段提升流量，每阶段等待足够观测窗口；
- 自动比较基线与新版本指标；
- 不在异常未解释时继续放量。

### 发布后

- 确认核心业务与技术指标；
- 记录版本、时间和异常；
- 清理过期开关和临时兼容代码；
- 事故转化为测试、门禁或可观测性改进。
