# 如何保证发版安全

> 你简历里写「负责团队的分支管理与版本发布，把控上线节奏与发版质量」，
> **这题几乎必被问**，而且会问得很细。

## 分支策略

| 策略 | 适用 | 说明 |
|---|---|---|
| **Git Flow** | 有明确版本周期、需要维护多版本 | 分支多（develop/feature/release/hotfix），重 |
| **GitHub Flow** | 持续部署 | 只有 main + feature，简单 |
| **Trunk Based** | 高频发布、有完善自动化 | 直接往主干提，用 feature flag 控制 |

【需确认】你们团队实际用哪种？
**答这题要说清「为什么适合我们」**，而不是背定义。

> 我们是按版本节奏发布的 B 端产品，
> 用的是接近 Git Flow 的模式——
> 有 release 分支做提测和修复，hotfix 直接从 main 拉。
> 这个模式重，但适合我们这种要给客户交付确定版本的场景。

## 上线前的卡口

```
本地       → husky + lint-staged（快反馈）
PR         → CI: lint / type-check / test / build
            + code review（人看设计，不看格式）
提测       → 测试环境验证
预发布     → 预发环境（和生产同配置，连生产数据或影子库）
生产       → 灰度 → 全量
```

**关键原则**：
- **本地卡口能被 `--no-verify` 绕过，所以 CI 必须有同样的检查**
- **构建产物只构建一次**——
  测试环境验过的产物直接推生产，
  而不是在生产重新构建（避免"测试环境好的，生产构建出来不一样"）

> 见 [07-工程化/规范与卡口.md](../07-工程化/规范与卡口.md)

## 灰度发布

**怎么灰度前端？**

| 方式 | 说明 |
|---|---|
| **按用户分流** | 网关/Nginx 按 userId hash 或 cookie 决定返回哪个版本的 html |
| **按比例分流** | 先放 5%，观察指标，逐步放量 |
| **feature flag** | 代码全量发布，但功能开关控制是否生效——**回滚最快** |

**feature flag 的优势**：
出问题时**关开关即可**，不需要重新发版回滚，秒级生效。
代价是代码里会积累开关，需要定期清理。

## 回滚

**回滚要能在几分钟内完成，这是发版安全的底线。**

- **静态资源**：保留旧版本产物，切换 html 指向即可
- **⚠️ 关键**：**旧版本的静态资源不能立刻删**——
  否则已经加载了旧 html 的用户会拿不到 chunk 而白屏
- **数据库变更**：这是最难回滚的部分。
  原则是**向前兼容**——
  加字段而不是改字段、先发兼容代码再改结构

### 前端资源加载失败的兜底

```js
// Vite
window.addEventListener('vite:preloadError', e => {
  e.preventDefault()
  location.reload()   // 拿到新 html 重新加载
})

// 通用：动态导入失败时提示刷新
import('./Page').catch(() => {
  if (confirm('页面有更新，是否刷新？')) location.reload()
})
```

**这个细节很能体现你真的经历过发版事故。**

## 发版后要做什么

**发完就走是最常见的问题。**

> 我要求发完版后至少盯 30 分钟：
> - **Sentry 错误曲线**——有没有新增的高频错误
> - **接口错误率**
> - **核心链路的埋点**——下单量有没有异常下跌
>
> 有异常立刻回滚，先止损再查原因。
> 不要在用户受影响的时候慢慢定位。

## 常见发版事故清单

| 事故 | 原因 | 预防 |
|---|---|---|
| **白屏** | CDN 缓存不一致，html 引用了已删除的 chunk | html no-cache + 旧资源保留 |
| **样式错乱** | CSS 文件缓存 | 内容 hash |
| **接口 404** | 前后端不同步发布 | 后端先发（向前兼容），前端后发 |
| **配置漏改** | 环境变量、域名 | 配置纳入代码管理，CI 校验 |
| **依赖版本漂移** | lockfile 没提交 | 强制提交 lockfile |

## 作为负责人的视角（加分）

> 我的判断是**发版安全靠机制不靠人**。
>
> 早期我们是"发版前群里喊一声大家注意"，
> 这种约定一忙就忘。后来我把它变成卡口——
> CI 不过不能合、发版走固定流程、回滚脚本提前准备好。
>
> **能自动化的就别靠自觉**，
> 这是我带团队之后最大的一个转变。
