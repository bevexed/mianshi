# 开发流程与任务分配

> **题目**：如果让你负责一个跨前后端需求，你会怎样推动开发流程并分配任务？有人延期时怎么办？

这道题考察的不是能否背出“需求、开发、测试、上线”，而是能否把目标变成可验收任务，识别依赖和风险，并对交付结果负责。

## 1. 从需求到上线的完整闭环

```text
需求澄清
  → 技术与风险评估
  → 任务拆分、依赖和排期
  → 接口/数据契约先行
  → 小步开发与持续集成
  → Code Review、联调和测试
  → 灰度/发布与观察
  → 复盘和行动项关闭
```

每一步都应有退出条件：

- 需求评审明确用户目标、范围、异常和验收标准；
- 技术评估列出数据迁移、兼容、安全、性能和外部依赖；
- 任务拆分到可独立验收的结果，不按“前端三天、后端三天”粗切；
- 发布前明确负责人、观察指标、回退方案和沟通渠道；
- 上线完成以业务与技术指标正常为准，不以流水线变绿为终点。

## 2. 任务如何拆分

先按用户流程和交付结果拆，再决定由谁负责。例如一个“企业认证申请”可以拆为：

- 规则与状态：哪些主体可申请，重复提交和历史状态如何处理；
- 接口与数据：请求/响应、错误码、幂等、权限和迁移；
- 前端交互：表单、回填、上传、失败恢复和埋点；
- 后端处理：校验、事务、文件事实、通知和审计；
- 测试与发布：契约测试、端到端路径、开关、灰度和回退。

每个任务写清：输入输出、依赖、完成标准、owner、评审人和风险。任务太大无法独立验收时继续拆；拆得只剩机械步骤、需要多人频繁同步时则可能过细。

## 3. 如何分配，而不是平均分

分配时同时考虑：

| 维度       | 判断                                               |
| ---------- | -------------------------------------------------- |
| 业务优先级 | 哪些任务决定最小可交付范围，哪些可以延后           |
| 依赖关系   | 关键路径、外部团队、接口和数据是否阻塞             |
| 能力匹配   | 成员的技术、业务熟悉度和当前负载                   |
| 风险       | 高风险任务是否有经验负责人、提前验证和备份         |
| 成长       | 非关键路径是否可以给成员成长机会，并提供评审或结对 |
| 连续性     | 关键模块是否只有一个人知道，是否需要备份和交接     |

不是所有难题都交给最强的人，也不是为了“公平”平均分任务。目标是让关键路径可控，同时避免形成永久单点。

## 4. 怎样让前后端并行

先确认契约而不是等后端全部完成：

- 字段语义、类型、空值和枚举；
- 权限、租户和身份来源；
- 状态码、业务错误和部分失败；
- 分页、排序、幂等和版本兼容；
- 示例数据、Mock 与契约测试。

前端可以基于已确认契约和 Mock 开发，后端实现接口与持久化；联调验证真实序列化、权限和异常。Mock 能帮助并行，不能证明真实链路正确。

## 5. 进度跟踪与延期处理

进度不是问“做完百分之几”，而是看可验证产物、剩余风险和关键路径。出现延期时：

1. 先确认根因：需求变化、估算错误、技术阻塞、依赖等待还是人员容量；
2. 重新计算对关键路径和上线范围的影响；
3. 按风险选择缩范围、调整顺序、增加结对/评审、协调依赖或修改日期；
4. 尽早同步影响和新承诺，不到最后一天才报告；
5. 事后把重复问题改成拆分规则、技术预研、测试或流程卡口。

临时加人并不一定更快；新成员需要上下文，且多人同时修改同一边界可能增加沟通和集成成本。

## 6. Code Review 和测试放在哪里

- 高风险方案在编码前评审，避免 PR 末尾才推翻方向。
- 自动化负责格式、类型、基础测试和构建；人工评审关注业务行为、边界、数据、安全和可维护性。
- 小 PR 尽早合并，配合 feature flag 隔离未完成能力，减少长期分支。
- 测试覆盖正常、失败、权限、重复提交、兼容与回退路径。
- 发布后继续观察错误率、延迟和核心流程成功率。

## 7. 60 秒口语答案

> 我会先把需求目标、范围、异常路径和验收标准讲清，再评估接口、数据、兼容和发布风险。任务不是简单按前端后端平分，而是按可独立验收的结果拆，标出关键路径和依赖，每项明确 owner、完成标准和评审人。
>
> 分配时会结合优先级、个人能力、业务熟悉度和当前负载。关键任务由有经验的人负责并设置备份，非关键路径可以安排成长任务，通过结对和评审降低风险。前后端要先确认接口和错误契约，用 Mock 并行推进，再通过真实联调和契约测试收口。
>
> 开发中我看的是可验证产物和剩余风险，不只是完成百分比。发现延期会先定位是范围、估算、技术还是依赖问题，再调整范围、顺序、资源或日期，并尽早同步。上线后还要看业务指标和错误率，复盘行动项真正关闭才算完成。

## 8. 回答边界

如果实际工作中是技术负责人分配任务，自己只参与了估时、接口设计或模块交付，就按真实职责回答：

> 我没有独立负责过整个团队排期，但参与过需求拆分、工作量评估、接口确认和自己模块的推进。如果让我负责，我会按关键路径和验收结果组织，并通过负责人评审和风险同步保证交付。

不要为了显得资深，把“参与评审”说成“负责整个团队”，也不要虚构人数、工期和结果。

## 9. 高频追问

### 两个人都想做同一个核心模块怎么办？

以交付风险和成长目标决定 owner，另一人可以负责设计评审、相邻模块或结对；把决策标准公开，不用职位和个人偏好作为唯一理由。

### 成员能力不足但任务必须按时完成怎么办？

缩小其独立负责边界，提供模板、结对和更密集检查点；关键路径由能兜底的人共同负责。长期则通过复盘和训练补能力，不能每次都临时把任务收回。

### 产品中途改需求怎么办？

先说明对范围、兼容、测试和日期的影响，再让业务方在范围、时间和资源之间做显式取舍。不能口头答应后靠团队无声加班消化。
