# RAG 项目落地与效果排查

> **题目**：请介绍一个 RAG 项目。如果用户能搜到资料，但召回结果不准或 AI 仍然答错，你怎样定位？

先说明项目边界，再讲链路。使用了 AI 对话不等于做过 RAG；做了检索服务也不等于自己训练了模型或控制了最终生成。

## 1. 先用一分钟讲清项目

以 `ng-design-mcp` 为例，可按这个结构回答：

> 团队的 UI 规范和组件文档很多，直接全部塞进 prompt 成本高，也容易稀释当前任务需要的信息。我把 Markdown 文档和组件类型解析成可检索片段，使用 ChromaDB 做语义检索、MiniSearch 做关键词检索，再把结果提供给 AI 编码工具。关键词适合组件名、prop 和错误码，向量适合同义表达；项目还用查询—期望文档用例评估检索质量。
>
> 这个项目的边界是提供上下文和校验工具，最终代码生成由外部 AI 客户端完成，所以我能直接控制的是资料解析、索引、召回、融合和工具契约，不能把模型最终回答全部包装成自己的 RAG 生成服务。

这段先讲“为什么做、链路是什么、自己负责哪一段”，再接受细节追问。

## 2. 画出完整链路

```text
文档 / 类型定义
  → 解析与清洗
  → 按结构切分并补 metadata
  → 关键词索引 + 向量索引

用户问题
  → 查询规范化与权限/版本过滤
  → 多路召回
  → 融合、去重与必要的重排
  → 上下文组装
  → AI 客户端生成或校验
```

每个阶段都要能观测输入、输出、版本和耗时。只记录“最终回答错了”，无法区分是文档、索引、检索、上下文还是模型使用出了问题。

## 3. 回答错误时先做故障分层

| 层次       | 先检查什么                                                     |
| ---------- | -------------------------------------------------------------- |
| 原始资料   | 正确答案是否存在，版本是否过期或互相矛盾                       |
| 解析与切分 | 标题、正文、表格、代码和 props 是否被拆散或丢失                |
| 索引       | 内容 hash、embedding 模型、索引版本和删除/更新是否同步         |
| 召回       | 正确 chunk 是否进入 top-k，精确术语是否被语义结果挤掉          |
| 融合/过滤  | 关键词与向量权重、去重、权限、租户、版本过滤是否错误           |
| 上下文组装 | 证据是否超出上下文预算、被重复片段挤占或缺少来源与章节路径     |
| 工具与生成 | 模型是否调用了工具，是否忽略证据、混入常识或在证据不足时仍猜测 |

复现时保存同一个查询、身份/租户、索引版本、检索参数、top-k 结果和最终上下文。没有这些条件，前后两次答案不同不一定是代码回归。

## 4. 常见失败与验证方法

### 精确组件名搜不到

可能是向量模型不擅长专有名词，或组件名在切分后丢失。验证同一查询的关键词与向量结果；修复可补组件名/章节 metadata、保留关键词召回并调整融合，而不是盲目提高 top-k。

### 语义相近但答案来自旧规范

检查索引更新、版本字段、失效标记和源删除同步。大规模资料可以按内容 hash 增量更新，并通过索引别名或版本切换避免用户读到半成品；还要定期做源与索引对账。

### 正确文档召回了，模型仍答错

检查最终上下文中是否真的包含关键句、是否被截断、指令是否要求依据证据回答，以及引用是否对应。证据不足时应拒答或提示缺少资料，不能用“再多召回十条”掩盖生成约束问题。

### AI 根本没有调用 MCP 工具

MCP Server 只能提供能力，不能保证模型一定调用。需要让工具名称、description、输入 schema 和返回值清晰表达使用时机，并在项目规则中约定“生成组件代码前先查询规范”。事后 validate 工具可以兜底，但不能替代检索质量。

## 5. 用评测代替凭感觉调参

评测集至少覆盖：

- 组件名、prop、错误码等精确查询；
- 同义改写和自然语言需求；
- 多个相似组件的区分；
- 无答案、过期资料和权限不可见资料；
- 中文、英文和代码混合文本。

常用指标：

| 层次   | 指标/检查                                |
| ------ | ---------------------------------------- |
| 检索   | Recall@k、MRR、NDCG、过滤正确率          |
| 上下文 | 证据覆盖、重复率、来源完整性、token 成本 |
| 生成   | 忠实度、引用正确性、拒答质量、任务成功率 |

调整 chunk、top-k、融合权重或 embedding 模型时，用同一版本评测集做前后对比并保留失败样本。平均分提升也可能掩盖关键组件名查询退化。

## 6. 60 ～ 90 秒口语答案

> 我会先把 RAG 问题拆成资料、索引、召回、上下文和生成五层。以 UI 规范 MCP 为例，资料来自 Markdown 和组件类型，按标题和组件语义切分，关键词检索处理组件名和 prop，向量检索处理自然语言需求，两路结果融合后提供给 AI 客户端。
>
> 如果结果不准，我会固定查询、索引版本和用户权限，先看正确 chunk 是否进入 top-k。没进说明是解析、索引、召回或过滤问题；进了但最终上下文没有，查去重和 token 预算；上下文有但回答错，再查工具调用、生成约束和拒答策略。这样不会把所有问题都归因于 embedding。
>
> 参数调整必须用查询—期望文档评测集比较 Recall@k、MRR 和失败样本。对实际项目我也会明确边界：检索和工具服务是我能控制的部分，最终生成由外部 AI 客户端完成，不能把完整模型能力都说成自己实现。

## 7. 高频追问

### 为什么不只用向量检索？

组件名、prop 和错误码需要精确匹配，自然语言需求又需要语义泛化。混合检索是由查询分布决定的，不是“向量加关键词一定更高级”。

### chunk 越小越好吗？

过小会把语义、表格和代码示例拆散；过大则降低定位精度并浪费上下文。先按文档结构建立基线，再用评测确定上限和 overlap。

### top-k 越大召回越好吗？

可能提高召回，但也会带来重复、冲突、延迟和上下文噪声。要同时观察正确证据是否进入、排序位置、上下文预算和最终任务成功率。

### 如何处理权限？

检索前按可信用户、租户和文档权限过滤，不能先召回敏感内容再提示模型不要泄露；缓存键、评测和日志同样要包含权限边界并脱敏。
