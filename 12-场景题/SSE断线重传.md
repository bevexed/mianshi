# SSE 断线重传

> **题目**：业务使用 SSE 推送订单状态、任务进度或 AI 流式结果。用户短暂断网后浏览器虽然自动重连，但页面出现消息缺失或重复。如何设计可靠的断线恢复？

这里的“重传”是指连接中断后的**应用层事件补发**，不是 TCP 连接内部的丢包重传。

## 90 秒回答

`EventSource` 的自动重连只负责重新建立 HTTP 连接，不等于自动补发断线期间的业务事件。可靠恢复至少需要四部分：

1. 服务端为每条事件生成流内有序且唯一的 `id`，先写入可回放的事件日志，再向客户端推送。
2. 浏览器收到带 `id` 的事件后会记录最后事件 ID；同一个 `EventSource` 重连时会通过 `Last-Event-ID` 请求头把游标带回服务端。`retry` 只控制重连等待时间。
3. 服务端从游标之后补发历史事件，并无缝切换到实时流；客户端按事件 ID 去重，让状态更新保持幂等。因此更现实的目标是“至少一次投递 + 幂等消费”，不要轻易承诺端到端恰好一次。
4. 如果游标已超出日志保留窗口，服务端明确通知客户端重新获取快照，再从快照版本继续订阅，不能静默跳过缺失数据。

同时要处理鉴权、多实例共享日志、代理缓冲、心跳、慢消费者和重连风暴，并通过断网和竞态测试验证没有丢事件。

## 1. 先分清协议能力

一条 SSE 消息可以写成：

```text
retry: 3000
id: 106
event: order-status
data: {"orderId":"A1001","version":106,"status":"paid"}

```

- 空行表示一条事件结束。
- `id` 会更新 `EventSource` 保存的最后事件 ID；重连时，非空的最后事件 ID 会放入 `Last-Event-ID` 请求头。
- `retry` 是浏览器再次连接前的等待时间，单位为毫秒；它不是消息保留时间，也不会让服务端自动保存事件。
- `event` 是事件类型，客户端通过 `addEventListener('order-status', handler)` 监听。
- `: ping\n\n` 这类注释可作为心跳，不会产生业务消息或推进事件游标。

如果服务端从未发送可恢复的 `id`，或只把消息放在当前进程内存里，那么浏览器即使自动重连，也没有可靠游标和历史数据可供补发。

## 2. 服务端如何补发

### 事件 ID 与日志

- ID 应在同一业务流内稳定、有序且唯一，例如数据库序列、Redis Streams ID 或消息日志 offset。不要只依赖客户端时间或单机 `Date.now()`。
- 先持久化事件，再发布 SSE；否则“已推送但未入日志”会导致断线后无法恢复。业务状态和事件写入需要一致性时，可使用事务消息或 outbox。
- 日志必须定义保留数量或保留时间，并监控最老可用游标。保留窗口应覆盖真实的离线时长，而不是随意设置。
- 多实例部署不能只保存在某个 Node 进程的数组里。重连可能命中另一实例，应使用共享的数据库、消息日志或流存储。

### 建连与恢复流程

```text
1. 校验身份，并确认用户有权订阅目标 streamId
2. 读取 Last-Event-ID；页面刷新后的首次恢复也可使用受校验的 after 查询参数
3. 判断游标是否仍在保留窗口内
4. 从 lastEventId 之后按顺序回放事件
5. 无缝切换到实时订阅，后续每条消息继续携带 id
```

最容易漏掉的是第 4、5 步之间的竞态：回放历史时新事件仍在产生，如果“先查历史，再订阅实时”，两步之间的消息会丢失。可选做法是：

- 直接使用支持“从 offset 开始并持续 tail”的有序日志；或
- 先建立实时订阅并暂存新事件，记录高水位，再回放至高水位，最后排空暂存队列并进入实时模式。

若连接恰好在服务端写出事件后、客户端提交本地状态前断开，该事件可能再次送达。因此服务端补发与客户端去重必须配套，不能用“不重复发送”的假设换取表面上的恰好一次。

## 3. 客户端如何消费

- 同一业务流只维护一个 `EventSource`。不要在 `error` 回调里立即再 `new EventSource()`，原对象本身可能正在自动重连，否则容易产生重复连接。
- 用 `event.lastEventId` 或业务 `version` 去重。状态变更应设计成幂等，例如只有 `version` 大于当前版本时才应用，而不是收到一次就无条件累加。
- 先成功应用状态，再持久化已处理游标；反过来可能造成“游标已推进，但业务状态尚未落地”。
- 组件卸载、用户退出或切换订阅对象时调用 `source.close()`，防止旧连接继续消费。
- `error` 事件用于显示“正在重连”等状态并记录诊断信息，不要把每次网络抖动都提示成永久失败。

同一个 `EventSource` 的网络重连能自动携带 `Last-Event-ID`；但页面刷新后创建的是新对象，不能假设浏览器还会替应用恢复旧游标。需要跨刷新恢复时，可在本地保存已提交游标，并通过 `after` 查询参数传给服务端；服务端必须校验它属于当前用户和业务流。

原生 `EventSource` 不能任意设置 `Authorization` 等请求头。优先使用安全的同源、HttpOnly Cookie；若必须使用自定义 Bearer 请求头，可选支持流式响应的 `fetch` 或经过审查的兼容实现，并自行补齐解析、游标和退避逻辑。不要把长期访问令牌直接放进 URL。

## 4. 游标过期时不要静默丢数据

当 `Last-Event-ID` 早于最老可用事件时，服务端可在 SSE 流中发送明确的控制事件：

```text
event: resync-required
data: {"reason":"cursor_expired","snapshotUrl":"/api/orders/A1001"}

```

客户端收到后：

1. `close()` 当前连接，停止自动重连。
2. 获取带当前版本的完整快照，原子替换本地状态。
3. 使用快照返回的版本作为 `after`，创建新的 SSE 连接。

初始化也应使用“快照 + 对应高水位”的一致性协议，否则先查快照、后订阅期间同样可能漏事件。快照接口和事件流必须使用同一套版本语义。

## 5. 网关、心跳与背压

- 响应至少设置 `Content-Type: text/event-stream` 和合适的禁止缓存策略；在 Nginx、CDN 或应用网关中关闭会聚合 SSE 响应的缓冲。
- 心跳间隔应小于链路中最短的空闲超时，并结合移动网络和服务容量实测。心跳只能帮助发现死连接，不能替代业务事件补发。
- 为每个连接设置发送队列上限。慢客户端积压过多时主动断开，让它通过游标恢复，避免单连接拖垮进程内存。
- 服务恢复时使用退避、抖动和容量保护，避免大量客户端同时重连形成惊群。浏览器可能自行调整重连等待，服务端也要限流和分批恢复。

## 6. 排查与验证

先记录 `streamId`、连接 ID、客户端最后已应用 ID、服务端收到的游标、补发范围、当前高水位和断开原因，再判断是客户端重复连接、服务端日志缺口、恢复竞态还是代理提前断流。

至少覆盖以下测试：

1. 连续产生事件时切换离线/在线，最终状态与服务端快照一致。
2. 在“服务端已写出、客户端尚未提交”时断开，验证重复事件不会重复生效。
3. 回放期间持续产生新事件，验证从补发切到实时流时不丢、不乱序。
4. 重连命中另一服务实例，验证仍可从共享日志恢复。
5. 使用过期或伪造游标，验证会触发安全的全量同步且不能越权读取其他流。
6. 大量客户端同时重连，验证限流、退避和发送队列不会击穿服务。

监控至少包括活跃连接数、重连率、异常断开率、补发条数与耗时、游标延迟、游标过期次数、客户端去重次数、慢消费者数量和发送队列水位。

## 常见追问

**为什么不能保证恰好一次？**

连接可能在“服务端发送成功”与“客户端确认应用成功”之间断开，双方无法仅凭断开的连接判断客户端是否已经处理。工程上通常采用至少一次补发，再由事件 ID、业务版本或幂等键消除重复影响。

**`Last-Event-ID` 能防止越权吗？**

不能。它只是客户端游标，服务端仍要从当前身份和订阅目标推导允许访问的流，并校验游标范围；不能把客户端传来的 ID 直接拼成任意日志查询条件。

**只做心跳够吗？**

不够。心跳只能减少中间设备因空闲关闭连接并更快发现断线，无法保存或补发断线期间的业务事件。
