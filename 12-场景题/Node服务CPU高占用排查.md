# Node 服务 CPU 高占用排查

> **题目**：线上 Node.js 服务 CPU 突然接近满载，接口延迟和错误率同时上升。你如何判断是流量、攻击、代码还是容器资源问题？前五分钟做什么？

这道题不应从“先看日志”开始，也不能看到高 CPU 就直接扩容。回答主线是：**先止损并确认影响，再对齐实例、流量和代码证据，最后用 CPU profile 证明热点。**

## 1. 前五分钟：影响、止损和证据并行

先回答四个问题：

1. 影响是单 Pod、单节点还是全部实例？
2. CPU 上升是否与发版、配置变更、定时任务或流量突增重合？
3. 错误率、p95/p99、事件循环延迟和核心业务成功率是否同时恶化？
4. 当前容量还有多少，是否需要暂停发布、限流、摘除异常实例或回滚？

止损动作按证据选择：

- 新版本实例独有：暂停放量，必要时回滚，并保留故障实例或 profile。
- 单实例异常：先从负载均衡摘除，再在不扩大影响的前提下采样。
- 明确的高成本接口或异常来源：在网关/CDN/WAF 和应用层收紧速率、并发与请求体上限。
- 合法流量超过容量：按下游承载能力扩容，同时限制队列生产速度，不能只增加 Worker。

不要为了“保现场”放任核心业务持续不可用，也不要重启全部实例后才发现证据已经丢失。

## 2. 先确认“谁在高”，不要只看一个百分比

| 观察层级      | 要确认的内容                                                |
| ------------- | ----------------------------------------------------------- |
| 宿主机 / Node | 哪个进程或容器占用 CPU，是否还有系统进程、steal 或 I/O 等待 |
| 容器 / Pod    | 是用量高、触及 CPU limit 被 throttling，还是节点整体争用    |
| Node.js 进程  | 主线程、Worker Thread、子进程还是原生扩展在消耗 CPU         |
| 业务          | 哪个路由、任务、租户、输入和版本与峰值同时出现              |

常用只读检查：

```bash
kubectl top pod -n <namespace> --containers
kubectl top node
kubectl describe pod <pod> -n <namespace>
kubectl logs <pod> -n <namespace> --since=30m

docker stats --no-stream
docker top <container>

ps -eo pid,ppid,%cpu,%mem,etime,command --sort=-%cpu
```

`kubectl top` 依赖 Metrics API，只提供基础 CPU/内存视图，不等于历史监控或完整根因分析。还要对照监控系统中的 request/limit、throttling、节点压力和同时间窗口趋势。

## 3. 把 CPU、流量和事件循环放到同一时间线

至少对齐这些信号：

- 请求量、并发数、状态码、路由、请求体大小、租户和来源分布；
- 队列 waiting/active 数、任务耗时、重试和失败率；
- Node.js 事件循环利用率与延迟、GC 次数和暂停时间；
- 数据库、Redis、外部接口的延迟与超时；
- 发布版本、配置、定时任务和流量活动时间点。

典型判断：

- **CPU 与请求量同比上涨**：可能是正常流量，也可能是恶意请求；继续看来源、路由、业务成功率和单位请求成本。
- **请求量稳定但新版本 CPU 上涨**：优先比较新旧版本热点、输入和配置。
- **CPU 高且事件循环延迟高**：主线程很可能被同步计算、超大序列化或循环占住。
- **CPU 高但主线程不忙**：继续检查 Worker Thread、子进程、压缩/加密库或其他原生工作。
- **CPU 不算高但延迟很高**：可能是 throttling、锁/连接池排队、下游等待或事件循环被间歇长任务阻塞。

## 4. 分层建立假设

| 类型         | 常见原因                                                    | 关键证据                                        |
| ------------ | ----------------------------------------------------------- | ----------------------------------------------- |
| 流量与攻击   | 突发活动、爬虫、撞库、超大请求体、高成本查询、ReDoS 输入    | 来源与路由分布、请求大小、4xx/5xx、WAF/网关日志 |
| 应用计算     | 大 JSON 解析/序列化、图片/OCR、压缩、加密、同步 API、死循环 | CPU profile、火焰图、事件循环延迟               |
| 任务系统     | 队列并发过高、批量任务同时触发、失败后无退避重试            | 队列深度、任务耗时、重试时间线                  |
| 内存与 GC    | 大对象频繁创建、缓存增长、堆接近上限导致频繁 GC             | heap/GC 指标、内存趋势、profile                 |
| 容器与节点   | CPU limit 太小、同节点争用、HPA 指标或 request 配置不合理   | cgroup/容器指标、调度分布、HPA 状态             |
| 可观测性自身 | 同步格式化大量日志、异常风暴、日志字段过大                  | 日志速率、序列化热点、关闭采样后的对比实验      |

“日志很多”只是线索；没有 CPU 热点或对比实验时，不能直接断言日志就是根因。

## 5. 用 profile 证明热点

先在可控副本或可复现环境采集。`--cpu-prof` 会从进程启动时开启 V8 CPU profiler，并在退出时写出 profile：

```bash
node --cpu-prof --cpu-prof-dir ./profiles dist/main.js
```

生产在线实例可使用经过评审的 APM/profiler、Inspector 或系统级采样；先评估额外开销、端口暴露、磁盘空间和敏感函数参数风险。不要为了抓 profile 同时重启全部实例。

分析时重点看：

- 哪些函数的 self time 和 total time 高；
- 热点是否只出现在特定路由、任务或输入；
- 是业务代码、JSON/正则、GC、框架中间件还是原生调用；
- 同一压测输入下，修复前后 profile 和吞吐是否变化。

如果某个输入能触发正则灾难回溯或超大计算，除了优化实现，还要增加长度、复杂度、超时和并发边界，避免同类输入再次耗尽资源。

## 6. 修复与预防

- 将 CPU 密集计算移到 Worker Thread、子进程或独立计算服务，并设置队列和并发上限。
- 对大列表、批处理和序列化分批处理；避免同步 API 和无界循环。
- 网关与应用共同限制速率、并发、请求体、查询复杂度和执行时间。
- 为重试增加上限、退避与抖动，防止下游故障被放大成 CPU 风暴。
- 根据压测设置 requests/limits 和 HPA 指标；队列 Worker 优先结合积压与任务耗时，不只看 CPU。
- 监控 CPU、事件循环延迟、GC、路由耗时、队列等待和核心业务成功率。
- 将触发输入、回归压测和发布观察阈值固化下来。

扩容只能缓解可并行且下游有容量的负载。死循环、单请求超高成本或共享数据库瓶颈不会因为盲目加 Pod 自动消失。

## 7. 60 秒口语答案

> 我不会先猜是日志、队列还是攻击，而是先确认影响范围和止损条件。先看是单实例、单节点还是全量，是否和发版、定时任务或流量突增重合，同时对齐错误率、延迟和业务成功率。需要时暂停发布、摘除异常实例或对高成本入口限流，但会保留一个可控现场。
>
> 定位时我会把宿主机、容器、Node 进程和业务请求放在同一时间线：看 CPU limit 和 throttling、路由和来源分布、事件循环延迟、GC、队列积压与重试。如果请求量稳定但新版本 CPU 上涨，就比较新旧版本；如果流量和某个高成本接口一起上涨，再区分正常活动和恶意调用。
>
> 最后用 CPU profile 或火焰图证明热点，而不是只凭日志猜。修复可能是优化同步计算、限制输入和并发、把 CPU 工作移出主线程，或者修正重试和资源配置；完成后再用相同流量回放验证 CPU、p99 和错误率。

## 8. 高频追问

### 怀疑被攻击，是否直接封 IP？

先确认来源、账号、设备、租户、路径和行为序列。共享出口、代理和移动网络会让大量正常用户共用 IP；应组合速率限制、身份/设备维度、请求成本、验证码或挑战、WAF/CDN 和业务风控，并保留误伤回退能力。应用层资源耗尽和网络层流量攻击也不是同一种处置。

### CPU 高时直接加 Pod 对吗？

只有负载可并行、调度资源和下游容量充足时才可能有效。若根因是单请求死循环、共享数据库瓶颈、无限重试或节点整体资源不足，扩容可能无效甚至放大故障。

### 只看日志能定位吗？

日志能帮助关联请求和任务，但不能展示函数级 CPU 时间。需要把日志、指标、trace 和 profile 组合起来；临时增加日志还要控制采样、字段大小和脱敏。
