# 接口慢与前端应对

先建立端到端时间线，再决定是减少网络开销、优化服务端还是改善交互。只看浏览器的一次请求无法代表整体分布。

## 1. 定位慢在哪里

浏览器 Network Timing 可以提供线索：

| 阶段                   | 可能原因                                   |
| ---------------------- | ------------------------------------------ |
| Queueing / Stalled     | 请求优先级、连接复用、客户端并发或代理等待 |
| DNS / Connection / TLS | 首次连接、网络路径、证书握手               |
| Waiting / TTFB         | 网络往返、网关、服务端计算和首字节生成     |
| Content Download       | 响应体积、带宽、丢包和流式方式             |

TTFB 不等于纯后端执行时间。通过 `Server-Timing`、trace ID 和分布式链路追踪继续拆分网关、应用、数据库与下游服务。比较 p50/p95/p99、地区和版本，不只看平均值。

## 2. 前端减少不必要工作

- 对相同身份和参数的请求做安全去重；不同权限或租户不能共用缓存键。
- 没有依赖的请求并行，有依赖的请求避免伪并行。
- 按视口和用户路径延后非关键请求。
- 搜索、联想等高频请求防抖并取消旧请求。
- 对大列表分页或增量加载，避免一次下载和渲染全部数据。

```js
const [profile, permissions] = await Promise.all([getProfile(), getPermissions()]);
```

聚合接口/BFF 可以减少往返和前端编排，但也可能成为耦合和容量瓶颈，应按页面边界和复用需求设计。

## 3. 缓存、预取与体验

- 缓存必须定义 key、过期、失效、权限隔离和允许陈旧的时长。
- 只预取高概率会用且成本可控的数据，考虑用户流量和服务端容量。
- 骨架屏结构应接近最终内容以降低布局偏移；很快的请求不必强制闪现 loading。
- 乐观更新仅适合易回滚、冲突可处理的操作。
- 关键内容优先，非关键区域可独立失败或流式显示。

## 4. 超时、取消与重试

超时应真正取消底层请求，而不是只用 `Promise.race` 放弃等待：

```js
const controller = new AbortController();
const timer = setTimeout(() => controller.abort(), 5000);

try {
	return await fetch(url, { signal: controller.signal });
} finally {
	clearTimeout(timer);
}
```

- 只自动重试幂等且暂时失败的请求，并设置上限、退避和抖动。
- 429 尊重 `Retry-After`；离线或页面隐藏时避免持续重试。
- 提交类操作使用幂等键，不能简单把 POST 重发多次。
- 超时阈值来自用户目标和真实延迟分布，不应全站固定一个值。

## 5. 服务端协作

- 用 trace 找慢查询、锁等待、N+1、连接池排队和下游超时。
- 对热点只读数据评估缓存，同时解决失效、穿透和一致性。
- 返回必要字段并分页；压缩不等于可以无限返回数据。
- 将不影响同步结果的耗时工作异步化，并提供可查询的任务状态。

最终应记录基线、瓶颈、改动和前后 p95/错误率，确认优化没有把压力转移到其他环节。
