# 线上接口慢怎么办

## 先分清：是谁慢

**这是这题的关键——很多人一上来就讲前端优化，
但接口慢首先要定位是哪一段慢。**

用 DevTools Network 面板的 Timing 分解：

```
Queueing      → 浏览器排队（同域并发数限制、优先级低）
Stalled       → 代理协商、连接复用等待
DNS Lookup    → DNS 解析
Initial connection / SSL → 握手
Request sent  → 发送
Waiting (TTFB)→ ⭐ 服务端处理时间
Content Download → 响应体下载
```

| 哪段大 | 说明 | 归谁 |
|---|---|---|
| **Waiting (TTFB)** | 服务端慢 | **后端**（数据库、下游服务） |
| **Content Download** | 响应体太大 | 后端（字段冗余）+ 网络 |
| **Queueing / Stalled** | 并发数打满、连接复用问题 | 前端（请求太多）/ 运维 |
| **DNS / SSL** | 首次连接开销 | 运维（preconnect 可缓解） |

**先拿这个分解去和后端对齐**，
而不是一上来说"接口慢，你们优化下"。

## 前端能做什么

### 1. 减少请求数量

- **合并请求**——多个小接口合成一个（推动后端提供聚合接口/BFF）
- **去重**——同一个请求短时间内发多次（react-query 自带请求去重）
- **按需请求**——首屏只请求首屏需要的，其余滚动到再请求

### 2. 改变请求时机

- **预请求（prefetch）**——hover 列表项时预取详情
- **并行化**——避免请求瀑布流

```js
// ❌ 串行，总耗时 = a + b
const a = await getA()
const b = await getB()

// ✅ 并行，总耗时 = max(a, b)
const [a, b] = await Promise.all([getA(), getB()])
```

**React 里最容易产生瀑布流的场景**：
父组件 useEffect 请求完，子组件才开始请求。
→ 用 RSC 或把请求提到共同的上层。

### 3. 让用户感觉不慢（体验优化）

| 手段 | 效果 |
|---|---|
| **骨架屏** | 比 spinner 感知更快，且能减少 CLS |
| **乐观更新** | 点赞/收藏立刻反馈，后台再同步 |
| **分页/虚拟滚动** | 不用等全部数据 |
| **流式渲染** | 先出快的部分（Suspense） |
| **缓存优先** | 先展示缓存再后台刷新（react-query 默认行为） |

**「感知性能」是很好的答题角度**——
用户抱怨的是"慢"，不是"接口耗时 800ms"。

### 4. 超时与降级

```js
// 超时控制
Promise.race([request(), timeout(5000)])

// 但要注意：race 只是不再等待，请求本身没取消
// 真正取消要用 AbortController
const ctrl = new AbortController()
fetch(url, { signal: ctrl.signal })
ctrl.abort()
```

**降级策略**：
- 非核心接口失败不阻塞页面（`Promise.allSettled`）
- 提供兜底数据或"稍后重试"

## 如果是你能改的后端（你有 NestJS 经验）

这是你的加分点——**能跨端定位**：

- 慢查询：加索引、避免 N+1
- 缓存：Redis 缓存热点数据
- 异步化：耗时操作丢队列（你的 BullMQ 经验）
- 分页：别一次返回全量

## 答题结构

> 我会先看 Network 的 Timing 分解，确认是 TTFB 慢还是下载慢，
> 因为这决定了是后端问题还是传输问题。
>
> 如果是 TTFB，我会带着具体数据去找后端，
> 而不是笼统说"接口慢"——比如"这个接口 P95 是 3 秒，
> 主要卡在 waiting 阶段"。
>
> 同时前端侧我会做两件事：
> 一是看有没有不必要的串行请求可以并行；
> 二是做感知优化，骨架屏和缓存优先，
> 让用户不至于对着 loading 干等。
>
> 如果后端短期改不动，就上缓存和降级兜底。
