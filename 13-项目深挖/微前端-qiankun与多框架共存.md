## 一、动机（必问，且是筛人题）

### Q1：为什么要用微前端？

**⚠️ 最差的答法是「为了技术栈无关」——这是宣传语，不是理由。**

**真实且有力的答法（你的场景恰好是最正当的两个）**：
1. **存量老项目迁移不动**——选购下单前台是纯 Angular，
   完全重写成本高、风险大、业务不会给这个时间。
   微前端让**新功能用新技术写，老代码原地不动**，是一种渐进式迁移策略
2. **团队/发布解耦**——不同业务域由不同人维护，独立发布，
   不用因为改一个模块全量回归

**必须补的一句**：
> 微前端的正当理由基本只有「组织和存量」，不是技术先进性。
> 如果是一个从零开始的新项目、一个团队维护，用微前端纯属自找麻烦。

### Q2：微前端的代价是什么？

**能主动说出代价，是资深和初级的分界线：**
- **复杂度大幅上升**——调试、部署、本地开发环境都变复杂
- **公共依赖重复加载**——每个子应用带一份 React/Vue，体积膨胀
- **样式和全局变量污染**——最主要的坑（下面详述）
- **通信成本**——主子应用之间传数据比组件间 props 麻烦得多
- **用户体验割裂**——子应用切换时的白屏、loading、路由状态丢失

## 二、qiankun 原理（技术深度区）

### Q3：qiankun 是怎么工作的？

**答题骨架——三步**：
1. **基于 single-spa 做应用生命周期管理**（bootstrap / mount / unmount）
2. **HTML Entry**——这是 qiankun 相比 single-spa 的主要改进。
   single-spa 要你手动配置子应用的 JS 入口；
   qiankun 直接请求子应用的 `index.html`，
   解析出里面的 JS/CSS 并执行，接入成本低得多
3. **沙箱隔离**——JS 沙箱 + CSS 沙箱，防止子应用互相污染

### Q4：JS 沙箱是怎么实现的？

**这是 qiankun 最核心的技术点，必须能讲：**

| 沙箱类型 | 原理 | 限制 |
|---|---|---|
| **SnapshotSandbox**（快照沙箱） | 子应用挂载前给 `window` 拍快照，卸载时对比并还原被修改的属性 | 只支持**单实例**（同时只能有一个子应用），且遍历 window 有性能开销。用于不支持 Proxy 的老浏览器 |
| **LegacySandbox** | 记录子应用对 window 的新增/修改/删除，卸载时精确还原 | 仍是单实例，但不用全量遍历，性能好于快照 |
| **ProxySandbox**（代理沙箱） | 用 `Proxy` 给每个子应用一个 **fakeWindow**，读走原型链、写只写进自己的副本 | **支持多实例**，qiankun 默认方案。依赖 Proxy |

**关键理解**：ProxySandbox 让子应用的 `window.xxx = 1` 实际写到了自己的假 window 上，
读的时候先查自己的、再回退到真 window。所以多个子应用可以同时存在互不干扰。

**加分**：提一句它是怎么让子应用代码用上假 window 的——
把子应用脚本包在 `with(proxyWindow) { ... }` 里执行（本质是改变作用域链）。

### Q5：CSS 隔离有哪几种方案？各自的问题？

**这题和你「Angular + React 样式冲突」的经历直接对应，必答好：**

| 方案 | 原理 | 问题 |
|---|---|---|
| **Shadow DOM**（qiankun `strictStyleIsolation`） | 子应用挂在 shadow root 里，天然隔离 | **弹窗类组件会挂到 body 上，跑到 shadow 外面就失去样式**；第三方 UI 库大量踩雷。实际很少能用 |
| **Scoped CSS**（qiankun `experimentalStyleIsolation`） | 给子应用所有选择器加上 `div[data-qiankun="app"]` 前缀 | 动态插入的样式、body 上的元素仍然管不到 |
| **约定前缀 / 命名空间** | 手动给类名加前缀，UI 库配置 prefixCls | 需要人工约束，但**最可控、副作用最小** |
| **CSS Modules / CSS-in-JS** | 编译期生成唯一类名 | 只能管自己写的样式，管不了第三方库和全局样式 |

**你的实际做法**（简历原文：「Angular 侧样式隔离、为 antd 添加类名前缀、防止主应用污染子应用」）：
- 走的是**约定前缀路线**——antd 配 `prefixCls`，
  Angular 侧用它自带的 ViewEncapsulation
- **可以讲一个观点**：我试过 Shadow DOM，但 antd 的 Modal/Select 下拉都挂在 body 上，
  隔离直接失效；最后回到给 UI 库配前缀 + 约束全局样式的写法，
  虽然土但可控。**「土但可控」是生产环境的正确选择。**

【需确认】你是否真的试过 Shadow DOM？没试过就别说试过，改成
「了解 Shadow DOM 方案但因为弹窗挂载问题没有采用」。

### Q6：Angular 的样式隔离是怎么回事？

- Angular 默认 `ViewEncapsulation.Emulated`——
  编译时给组件模板元素加 `_ngcontent-xxx` 属性，样式选择器也加上对应属性选择器，
  **模拟出 Shadow DOM 的效果但不真的用 Shadow DOM**
- 另外两种：`None`（完全不隔离，样式全局泄漏）、`ShadowDom`（真 Shadow DOM）
- **坑**：`::ng-deep` 会穿透隔离，用多了等于没隔离——老项目里这个满天飞

### Q7：主子应用怎么通信？

- **qiankun 官方**：`initGlobalState` + `onGlobalStateChange`，本质是发布订阅
- **props 传递**：主应用注册子应用时传入，适合传初始配置和方法
- **自定义事件 / 共享 store**：可以，但**要警惕耦合**——
  通信越多，微前端的解耦收益就越少
- **最好的通信是不通信**——能通过 URL 传的（比如 tenant id、页面参数）就走 URL，
  无状态、可刷新、可分享

### Q8：主子应用的路由怎么调度？

- 主应用负责一级路由（决定加载哪个子应用），子应用负责自己内部的路由
- **坑**：子应用要配 `base`（Vue Router 的 base / React Router 的 basename），
  否则子应用内部跳转会丢掉主应用的路径前缀
- **坑**：浏览器前进后退时，主子应用的路由状态要能同步
- 【需确认】你提到「新增门户设计页面路由」「集成 portal 微应用」，有没有踩过路由相关的坑？

## 三、你的特殊场景：Angular + React 双应用并存

### Q9：这个改造具体是怎么做的？为什么不用 qiankun？

【需确认，这段很重要——简历写的是「双应用并存结构」，
**没说是不是用了 qiankun**。选购下单前台这个项目里，你到底是：
- (a) 用 qiankun 把 React 作为子应用挂进 Angular 主应用？
- (b) 只是仓库层面拆成两个 app，构建产物合并部署，运行时其实是两个独立页面？
- (c) 在 Angular 组件里直接手动 mount React 组件？

**这三种的技术含量和追问方向完全不同，务必确认后重写这一节。**】

如果是 (c)，要能讲：
- 在 Angular 组件的 `ngAfterViewInit` 里拿到 DOM 节点，
  用 `createRoot().render()` 挂 React 组件
- `ngOnDestroy` 里 `root.unmount()`，**否则内存泄漏**
- 两套框架的变更检测是独立的——Angular 的 zone.js 和 React 的状态更新互不知情，
  跨框架传数据要手动触发对方更新

### Q10：px2rem 和 rem 换算问题是什么？

- px2rem 是构建时把 px 转成 rem 的插件，配合根字号动态设置做移动端适配
- **典型坑**：
  - 第三方 UI 库的样式也被转了，导致组件尺寸错乱 → 需要配 `exclude`
  - 1px 边框被转成很小的 rem 值，渲染成 0 → 需要配置最小转换阈值
  - 两个应用共存时，**根字号是全局的**，一个应用改了 `html { font-size }`
    会影响另一个应用 → 这大概率就是你踩的坑

## 四、PMS：Vue2 / Vue3 共存

### Q11：Vue2 和 Vue3 子应用共存有什么问题？

- 两个版本的 Vue 同时存在，**bundle 体积翻倍**
- Vue2 用 `Object.defineProperty` 做响应式，Vue3 用 `Proxy`——
  数据不能直接共享，跨应用传对象会丢响应性
- element-ui（Vue2）和 element-plus（Vue3）**类名前缀都是 `el-`**，
  样式冲突非常严重 → 必须改前缀或严格隔离
- 【需确认】你实际是怎么处理 element-ui / element-plus 类名冲突的？

### Q12：i18n 在微前端下怎么统一？

（这条呼应你 PMS 的 i18n 经历，见 [PMS 酒店管理系统](PMS酒店管理系统-国际化.md)）
- 语言状态应该由**主应用持有**，通过 props 或全局 state 下发给子应用
- 每个子应用维护自己的语言包（避免主应用变成翻译文件的垃圾场），
  但共享公共词条
- 切换语言时要通知所有已挂载的子应用
