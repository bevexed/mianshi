## 0. 一句话自述（开场 60 秒版）

> 这是一个面向住建部「四库一平台」的企业资质数据采集服务，为资质到期预警和合规判断提供数据底座。
> 技术栈是 NestJS 11 + Fastify + TypeScript，用 BullMQ + Redis 做任务编排，TypeORM + MySQL 存储，
> Playwright 拿会话凭证，Docker + K8s 部署。整个服务由我从 0 到 1 独立设计和实现。
> 核心难点有三块：**队列驱动的任务编排怎么保证幂等和不丢任务**、**有状态代理池的并发竞态**、
> **翻页采集的数据一致性怎么对账**。

## 一、架构与选型

### Q1：为什么要用队列？直接写个循环慢慢抓不行吗？

**答题骨架**：
1. **任务量与耗时不匹配同步模型**——企业详情 → 资质翻页 → 人员列表分页 → 人员详情，是一棵展开后量级很大的树，同步跑完可能几小时，HTTP 请求撑不住。
2. **需要失败重试与断点续跑**——采集必然遇到风控、超时、代理失效，循环里一挂就得从头再来，队列天然支持单个任务重试而不影响整体。
3. **需要限流**——目标站有风控，必须控制并发和速率，队列的 concurrency + rate limit 是现成的。
4. **需要可观测**——每个任务的状态、失败原因、重试次数可查。

### Q2：为什么选 BullMQ，不用 Kafka / RabbitMQ / 数据库轮询？

| 方案 | 为什么没选 |
|---|---|
| 数据库轮询 | 简单但要自己实现锁、重试、延时、优先级，等于重写一遍队列 |
| RabbitMQ / Kafka | 能力过剩，引入额外中间件运维成本；且我需要的是**任务队列**语义（重试/延时/优先级/进度），不是消息流 |
| BullMQ | 项目已有 Redis；Node 生态一等公民，NestJS 有官方集成；重试、指数退避、延时任务、Repeatable Job、并发控制开箱即用 |

**加分补充**：BullMQ 相比老的 Bull，用 Lua 脚本保证原子性、有独立的 Worker/Queue 分离、支持 Flow（父子任务），我的四级编排正好用得上。
【需确认】你是否真用了 FlowProducer，还是自己在 Worker 里手动派生子任务？两种答法完全不同，别答错。

### Q3：为什么 NestJS 用 Fastify 而不是默认的 Express？

- Fastify 的 JSON 序列化基于 schema 编译，吞吐明显高于 Express
- 内置 schema 校验，和 TS 类型配合好
- 这是纯服务端项目，没有 Express 中间件生态的历史包袱

**反问陷阱**：面试官可能追问"那你实测提升多少？"——如果没测过，**诚实说没做基准对比，是基于社区数据和无历史包袱做的默认选择**。硬编数字是自杀。

## 二、任务编排与幂等（最高频追问区）

### Q4：四类队列是怎么编排的？父任务怎么派生子任务？

**答题骨架**（画出来讲，最好在白板上画）：

```
企业详情队列 ──► 资质翻页队列 ──► 人员列表分页队列 ──► 人员详情回填队列
    │                │                    │                    │
    └────────────────┴────────────────────┴────────────────────┘
                        任务事实表（幂等 + 状态追踪）
```

关键点：**每一级任务完成后，把下一级要做的任务先写入「任务事实表」，再入队**。
写表和入队不是一个原子操作，所以顺序很重要——先落库再入队，最坏情况是「库里有、队列没有」，
可以靠补偿扫描捞回来；反过来「队列有、库里没有」就是幽灵任务，没法追溯。

### Q5：幂等具体怎么保证的？

**这是必问题，答不好整个项目的可信度就没了。**

**答题骨架**：
1. **业务唯一键**——每个任务有一个由业务字段拼出的确定性 key【需确认：你的 key 是什么？企业统一社会信用代码 + 抓取轮次？+ 页码？】
2. **任务事实表加唯一索引**——插入用 `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE`，重复派生直接被数据库挡掉
3. **BullMQ 的 jobId 用同一个 key**——BullMQ 对相同 jobId 的任务会去重，这是第二道防线
4. **消费侧幂等**——即使任务真的执行两次，写入业务表也用 upsert（按 RowKey），保证结果一致

强调"**幂等不是靠一个机制，是派生侧 + 队列侧 + 消费侧三道**"，这句话很能体现设计水平。

### Q6：什么是"孤儿任务"？你怎么恢复的？

**定义**：任务已经被 Worker 领走（状态是 active），但 Worker 进程崩了 / Pod 被 K8s 驱逐了，
任务既没成功也没失败，永远卡在 active 状态——这就是孤儿任务（BullMQ 里叫 **stalled job**）。

**BullMQ 的机制**：Worker 会定期续租（renew lock），`stalledInterval` 内没续上就判定 stalled，
自动搬回 wait 队列重试，超过 `maxStalledCount` 才标记失败。

**我额外做的**【需确认，这段是你的差异化，务必按真实情况写】：
- 定时扫描任务事实表，捞出「状态是 running 且 updated_at 超过阈值」的任务，重新派生
- 因为光靠 BullMQ 的 stalled 机制覆盖不了「任务事实表写了但入队失败」的情况

### Q7：失败重试策略是怎么设计的？所有失败都重试吗？

**关键在于区分错误类型**——一律重试是新手做法：

| 错误类型 | 处理 |
|---|---|
| 网络超时、代理失效、5xx | 重试，指数退避（如 3 次，1s/4s/16s）|
| 验证码失败 | 重试，但换代理 / 换 token |
| 目标数据不存在（404、企业已注销）| **不重试**，直接标记为终态 |
| 解析异常（页面结构变了）| **不重试**，告警——重试解决不了代码问题 |
| 被风控封禁 | 不立即重试，触发止损逻辑，延时后重新调度 |

**加分**：可重试错误和不可重试错误在代码里用不同的异常类型区分，Worker 捕获后决定
`throw`（触发 BullMQ 重试）还是 `return`（标记完成）。

## 三、代理池与竞态（简历里写了"IP 已回收仍在使用"，必被追问）

### Q8：代理出口和身份池是怎么设计的？

**答题骨架**：
- 每个出口维护 `accessToken` + IP 槽位，是**有状态资源**
- 采集任务开始前**借**一个槽位，结束后**还**回去
- 槽位有租约（lease）和 TTL，按剩余 TTL 主动轮换，避免用到快过期的凭证

### Q9：「IP 已回收仍在使用」这个问题是怎么发现的、根因是什么？

**这题是整个项目的技术高光，务必讲成一个完整故事。**

**故事结构**：
1. **现象**——【需确认】日志里出现某个 IP 已经被标记回收/轮换，但仍有请求带着它发出去，导致目标站返回异常 / 触发风控
2. **排查**——加日志把「借出时刻 / 归还时刻 / 实际发请求时刻 / 租约过期时刻」四个时间戳打出来对齐
3. **根因**——典型的 **TOCTOU（检查与使用之间的时间差）竞态**：
   任务在 T0 拿到槽位并通过了有效性检查，但请求真正发出是在 T1，中间租约到期被回收线程收走了，
   而任务手里还持有那个已失效的对象引用
4. **修复方向**：
   - 借还操作用 **Redis Lua 脚本**保证原子性（检查 + 占用 一次完成）
   - 引入 **fencing token / 版本号**——归还和使用时校验版本，版本不匹配直接拒绝
   - 回收前先判断槽位是否处于 in-use 状态，in-use 的走**软回收**（等归还）而不是硬抢
   - 使用侧在真正发请求前**再校验一次租约剩余时间**，不足阈值就主动换
5. **教训**（简历里你自己写了，直接用）——"大量 bug 来自分布式 + 有状态资源的竞态，倒逼我先画状态机再写代码"

**面试官大概率追问**：
- "为什么 Lua 脚本能保证原子性？"→ Redis 单线程执行 Lua，脚本执行期间不会插入其他命令
- "为什么不用 Redlock？"→ 单 Redis 实例场景没必要，Redlock 有争议且复杂度高；诚实说明你的部署是单实例还是集群
- "如果 Worker 拿着锁挂了呢？"→ 靠租约 TTL 自动释放，这也是为什么租约必须有过期时间而不能是永久锁

### Q10：并发度是怎么定的？

**别答"试出来的"**，要有方法论：
- 上界受**目标站风控**约束，不是受本机 CPU 约束——这是采集类服务和普通服务最大的区别
- 从低并发起步，观察「请求成功率 / 验证码触发率 / 封禁率」三条曲线，找拐点
- 【需确认】你最终定的是多少？企业详情和人员详情是分开控制的吗？简历写了"企业与人员详情并行拉取"

## 四、数据一致性（简历写了对账方案，这是加分项）

### Q11：怎么保证抓下来的数据是完整的、没漏页？

**答题骨架——四层校验**：
1. **抓取轮次（batch/round）**——每次全量采集打一个轮次号，同一轮次内的数据自洽，不同轮次可对比
2. **分页对账**——每页抓完记录实际条数，最后校验 `Σ每页条数 == 首页返回的 total`
3. **预期总数核对**——和目标站声明的总数比对，不一致则触发补漏
4. **人员 RowKey**——每条人员记录有稳定唯一键，用于跨轮次比对

### Q12：人员离职 / 企业注销了怎么处理？为什么用软删除？

- **软删除**（标记 `deleted_at` / 状态位）而不是物理删除，因为：
  - 资质合规判断需要**历史快照**——去年这个人在不在这家企业，是有业务意义的
  - 采集数据可能因为漏抓而"看起来消失了"，物理删除会造成不可逆的数据丢失
  - 【需确认】你的判定逻辑：连续 N 轮没抓到才判定离职，还是单轮没抓到就标记？
    **单轮就标记是危险的**——一次采集失败就会误判一批人离职。如果你做了 N 轮确认，这是很好的加分点。

## 五、验证码与风控（敏感区，答法要注意）

### Q13：GeeTest 点选和滑块是怎么做的？

**答题骨架**：
- Playwright 驱动真实浏览器拿会话凭证，规避纯 HTTP 请求的指纹检测
- 滑块：canvas 取图 → 找缺口位置 → 生成带加速度的拟人轨迹（匀速直线必被识别）
- 点选：需要图像/文字识别能力【需确认：你是接了第三方打码平台还是自己做的识别？这两个答案技术含量差别很大，别含糊】
- **辅助判定**：换题、reload、协议返回结果三路交叉验证，单次失败不代表方案失效

**简历里"验证码截图改事件就绪等待，固定延时降级为兜底上限"这句要能展开**：
原来用 `waitForTimeout(3000)` 死等，既慢又不稳；改成等待具体的 DOM/网络事件就绪
（`waitForSelector` / `waitForResponse`），固定延时只作为最长兜底。这是个很典型的
「把不确定的等待变成确定的信号」优化，能讲清楚很加分。

### Q14：这个项目的合规性怎么考虑的？

**⚠️ 这题有相当概率被问，尤其是稍微正规一点的公司。答不好会被认为风险意识差。**

**安全答法**：
- 采集对象是**住建部公开的政务数据**，本身面向公众查询，不涉及个人隐私的非公开信息
- 采集频率做了控制，没有对目标站造成压力（这就是"受控并发"和"日消耗分级保护"的另一层意义）
- 数据用途是内部资质预警，不对外二次分发
- 【需确认】公司层面是否有法务评估？如果有，一定要提

**不要说**：「我们绕过了他们的风控」这种表述。要说「为了保证采集稳定性，处理了会话与验证环节」。
同样的事，表述方式决定面试官的观感。

### Q15：什么是"直连三信号诊断"、"日消耗分级保护"、"人工熔断"？

【需确认，这三个是你自己的设计，我按字面推测，请按真实情况改写】
- **代理探活**：定时发探测请求，剔除失效出口
- **直连三信号诊断**：怀疑代理有问题时，用直连做对照，通过三个信号（如状态码 / 响应体特征 / 耗时）
  判断是「代理挂了」还是「目标站挂了」还是「我们被封了」——避免误判乱切代理
- **日消耗分级保护**：代理是按量计费的，设置日消耗阈值，到 50% / 80% / 100% 分级降速或停机，防止跑飞烧钱
- **人工熔断**：提供手动开关，出事时能立刻停

**这组东西的价值在于体现"成本意识 + 生产责任心"**，别只讲技术，讲一句
「因为代理是花钱的，跑飞一次成本很直接，所以做了分级保护」，比任何技术细节都打动人。

## 六、可能被问到的"你其实没做过"的题

面试官验真的常用手段是问一些"真做过一定会遇到"的问题：

1. **BullMQ 的 Job 数据存在 Redis 里，跑久了 Redis 内存会不会爆？**
   → 要答 `removeOnComplete` / `removeOnFail` 配置，只保留最近 N 条
2. **MySQL 那张任务事实表现在多大？有没有分区或归档？**
   → 【需确认】真实量级
3. **TypeORM 批量插入几万条时的性能问题遇到过吗？**
   → 分批 chunk、关闭 listener、必要时走原生 SQL
4. **服务部署在 K8s，Pod 缩容时正在跑的任务怎么办？**
   → 优雅停机：监听 SIGTERM，Worker 停止领新任务、等待在途任务完成，
     配合 `terminationGracePeriodSeconds`；未完成的靠 stalled 机制回收
5. **怎么知道服务是健康的？**
   → 队列积压量、失败率、采集成功率这三个指标 + Sentry 告警【需确认你实际有没有做监控面板】

## 七、这个项目要讲出的三个"我的成长"

面试后半程一定会问"这个项目你最大的收获是什么"，简历里写了三条，加工一下：

1. **从"写页面"到"设计系统"的思维转变**——前端做业务时状态是局部的、单机的；
   做这个服务逼我第一次认真面对分布式下的状态一致性问题
2. **先画状态机再写代码**——被竞态坑够了之后形成的习惯，现在写复杂前端状态（比如你简历里
   工程汇后台的"套餐版本切换数据还原"）也在用同一套思路
3. **生产责任心**——代理要花钱、目标站会封禁、数据错了会影响资质判断，
   这些约束让我第一次把"能跑"和"能上生产"区分开

**第 2 点特别重要**——它把后端经验反哺回前端，回答了面试官心里那个问题：
"你一个前端做后端，对我招前端有什么用？"
