## 一、RSC 与 App Router（核心必问区）

### Q1：Server Components 和 Client Components 的区别？

**答题骨架**：

| | Server Component | Client Component |
|---|---|---|
| 运行位置 | 只在服务端运行 | 服务端预渲染 + 客户端水合 |
| 能做 | 直接读数据库/文件、用密钥 | 用 hooks、事件、浏览器 API |
| 不能做 | `useState`/`useEffect`/事件处理 | 直接访问服务端资源 |
| 打包体积 | **不进 JS bundle** | 进 bundle |
| 默认 | App Router 里**默认是 Server Component** | 需要 `'use client'` |

**最关键的一句**：RSC 的核心收益是 **把组件代码本身从客户端 bundle 里去掉**。
一个用 markdown 解析库渲染的服务端组件，那个库根本不会下发给浏览器——
这是 SSR 做不到的（SSR 只是把渲染提前，代码照样下发）。

### Q2：`'use client'` 加在哪？它的边界是怎么传染的？

**这题很多人答错，答对很加分：**
- `'use client'` 标记的是**边界，不是单个组件**——一旦某个文件加了它，
  **它 import 的所有模块都会被拉进客户端 bundle**
- 所以要**把 `'use client'` 尽量往叶子节点推**，
  而不是图省事加在页面顶层（那样整棵树都变成客户端组件，RSC 收益归零）
- **反直觉的点**：Server Component 可以通过 `children` prop 传给 Client Component，
  这样交互壳是客户端的、内容仍是服务端的。这是保住 RSC 收益的关键模式

```tsx
// ❌ 整棵树都变客户端
'use client'
export default function Page() {
  return <Accordion><HeavyServerContent /></Accordion>
}

// ✅ 只有 Accordion 是客户端，内容仍在服务端渲染
export default function Page() {
  return <Accordion><HeavyServerContent /></Accordion>  // Accordion 内部才有 'use client'
}
```

### Q3：你说踩了水合（hydration）问题，具体是什么？

**必须有具体案例，泛泛而谈会被识破。**

**水合不匹配的典型成因**（挑你真遇到的讲）：
1. **服务端和客户端渲染出的 HTML 不一致**——最常见是用了
   `Date.now()`、`Math.random()`、`new Date().toLocaleString()`（时区不同）
2. **访问了只有浏览器有的东西**——`window`/`localStorage`，
   服务端渲染时是 undefined，客户端又有值
3. **第三方脚本改了 DOM**——浏览器插件、翻译插件注入节点
4. **HTML 嵌套非法**——比如 `<p>` 里套 `<div>`，浏览器会自动纠正结构，导致对不上

**解决手段**：
- `useEffect` 里再设置只有客户端才有的状态（首屏渲染一致，之后再更新）
- `suppressHydrationWarning`（**只用于确实无法避免的，如时间戳**，不是万金油）
- `dynamic(() => import(...), { ssr: false })` 对完全不该 SSR 的组件

【需确认】你实际遇到的是哪一种？**登录态判断**很可能是重灾区——
服务端不知道用户登没登录，客户端从 localStorage 读到了，一渲染就不匹配。
如果是这个，讲清楚你怎么解决的（cookie + 服务端读取？还是客户端兜底渲染？）。

### Q4：Next.js 的几种渲染/缓存策略，你怎么选的？

| 策略 | 适用 | 你的项目里对应 |
|---|---|---|
| **SSG**（静态生成） | 内容不变、人人相同 | 官网产品介绍页 |
| **ISR**（增量静态再生成） | 内容偶尔变，能容忍短暂陈旧 | 产品套餐列表（运营后台改了，几分钟后生效可接受）|
| **SSR**（每次请求渲染） | 内容随用户/请求变 | 需要登录态的页面 |
| **CSR**（客户端渲染） | 强交互、SEO 无所谓 | 选购配置页的实时价格计算 |

**答题要点**：官网这个项目**同时用到了多种**——这正是 App Router 的优势，
可以按路由甚至按组件粒度选择，而不是整个应用一刀切。

【需确认】你实际配了 `revalidate` 吗？多少秒？

### Q5：SEO 做了什么？

官网的核心诉求就是获客，SEO 必问：
- App Router 的 **Metadata API**（`export const metadata` 或 `generateMetadata`）
  生成 title/description/og 标签
- 用 SSG/SSR 保证爬虫拿到的是完整 HTML，而不是空 div
- `sitemap.ts` / `robots.ts`
- 结构化数据（JSON-LD）
- 【需确认】有没有做 Core Web Vitals 优化？`next/image` 的自动优化算一个

## 二、交易链路（业务深度区）

### Q6：折扣是怎么算的？为什么在前端算？

**⚠️ 这题是陷阱。「按订阅策略计算购买折扣」如果只在前端算，是严重的安全问题。**

**正确答法**：
> 前端算是为了**实时展示**——用户改套餐、改年限、加购时要立刻看到价格变化，
> 每次都请求后端体验太差。但**下单时的最终价格一定以后端为准**，
> 前端算出来的价格只是展示，提交时后端会重新计算并校验，不一致就拒绝。

【需确认】你的项目实际是不是这样？**如果不是，这是个真实的漏洞，值得回去看一眼。**
面试时如果确实没做后端校验，诚实说「当时前端算完直接提交，
现在回头看这里应该做服务端校验」——**主动指出自己项目的问题，反而是加分项**。

### Q7：价格计算这种逻辑，你怎么保证不出错？

- 抽成**纯函数**（输入：套餐/年限/加购项/订阅策略 → 输出：价格明细），
  和 UI 解耦，可单测
- **金额不要用浮点数直接算**——`0.1 + 0.2 !== 0.3`，
  用整数分为单位，或用 decimal.js
  （你 mi8 项目里就修过"小数精度问题"，可以呼应）
- 边界用例：0 元、最大值、折扣叠加、年限跨档

### Q8：版本对照表的分组与子项折叠交互，难点在哪？

这题看起来是纯 UI，但可以答出深度：
- **数据结构决定交互复杂度**——对照表是「分组 → 子项 → 每个版本的值」的三维结构，
  渲染成表格时行是分组+子项，列是版本
- 折叠状态该放哪：放在数据里还是单独的 UI state？
  （**放单独的 state**——折叠是纯视图状态，混进业务数据会污染）
- 移动端怎么办？三列以上的对照表在窄屏必然放不下——【需确认】你怎么处理的？
  横向滚动？还是切换成按版本分卡片？

## 三、状态与数据层

### Q9：为什么用 Zustand 而不是 Redux / Context？

| 方案 | 为什么没选 |
|---|---|
| Context | 无法细粒度订阅，一个值变化导致所有消费组件重渲染；多个 Provider 嵌套地狱 |
| Redux(Toolkit) | 样板代码多，这个项目的全局状态很少（主要是用户信息、选购配置），杀鸡用牛刀 |
| Zustand | API 极简、支持 selector 细粒度订阅、不需要 Provider、体积小 |

**加分**：说清楚 **Zustand 在 Next.js 里的坑**——
Server 端不能用模块级单例 store，因为服务端是多请求共享同一进程，
一个用户的数据会串到另一个用户。正确做法是**每个请求创建新 store，用 Provider 传下去**。
【需确认】你踩过这个吗？踩过一定要讲，这是很硬的细节。

### Q10：Zustand 和 react-query 怎么分工？

**这题答得清楚说明你真的想过架构：**
- **react-query 管服务端状态**——请求、缓存、失效、重试、后台刷新
- **Zustand 管客户端状态**——用户当前选了哪个套餐、UI 状态、跨页面的选购配置
- **最常见的错误是把服务端数据也塞进全局 store**，
  然后自己手写缓存和失效逻辑——那就是在重新实现一遍 react-query

### Q11：react-query 的 staleTime 和 gcTime 区别？

- **staleTime**：数据多久后被认为「陈旧」。陈旧前，组件重新挂载**不会**重新请求
- **gcTime**（旧名 cacheTime）：数据没有任何组件使用后，多久被回收出缓存
- 关系：`staleTime` 控制**要不要重新请求**，`gcTime` 控制**缓存留多久**
- 默认 `staleTime: 0` 意味着每次挂载都会后台重新请求——很多人不知道，
  以为 react-query 默认就缓存了

## 四、性能与工程

### Q12：官网首屏性能怎么保证的？framer-motion 那些动效不会拖慢吗？

- framer-motion 体积不小，**应该按需引入 / 用 `LazyMotion`**，
  或者简单动效直接用 CSS
- 首屏入场动画要注意：**不能让动画阻塞 LCP**——
  如果主视觉元素初始 `opacity: 0` 等动画才显示，LCP 会被严重拖后
  【需确认】这是个很常见的坑，你的首页产品区入场动画有没有踩到？
- 图片用 `next/image`（自动 WebP/AVIF、尺寸适配、懒加载）
- 字体用 `next/font`（自托管，避免 FOUT 和外部请求）

### Q13：重构验证码组件和登录注册流程，改了什么？

【需确认，简历只写了一句，需要展开】可能的方向：
- 验证码的倒计时状态、防重复发送、多端复用
- 登录/注册/找回密码的流程状态机
- Token 存储位置的选择（**localStorage vs httpOnly cookie**）——
  这个必被追问：httpOnly cookie 防 XSS 但要处理 CSRF，
  localStorage 反之。在 Next.js 里因为有服务端渲染，**cookie 方案还能让服务端直接读到登录态**，
  避免上面 Q3 说的水合不匹配

## 五、"第一次用 App Router" 的诚实答法

简历里写了「第一次用 Next.js App Router 做生产项目」——
**这句话面试官一定会抓住问"那你觉得它好用吗 / 有什么坑"**。

**准备一个有观点的回答**（有观点比全是优点更可信）：

> 好的地方是渲染策略可以按路由甚至组件粒度选，
> 官网这种「大部分静态 + 少量强交互」的场景特别合适。
>
> 但坑也不少：一是 `'use client'` 的边界传染，一开始没意识到，
> 图省事加在页面顶层，等于白用 RSC；二是水合问题排查起来很痛苦，
> 报错信息经常只说 hydration mismatch，不告诉你是哪个节点；
> 三是缓存行为在版本之间变化比较大，文档和实际行为对不上的情况遇到过。
>
> 整体我认为对官网这类项目是正收益，但如果是一个纯后台管理系统，
> 我会更倾向于用普通的 SPA，App Router 的复杂度换不来价值。

**最后那句"什么情况下我不会用它"是关键**——
能说清技术的适用边界，比能背优点重要得多。
