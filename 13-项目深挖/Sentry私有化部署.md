# Sentry 私有化部署与前端接入

> 简历定位：**基建能力的直接证据**。绝大多数前端只会 `Sentry.init()`，你把它拆开部署了一遍，
> 这是很稀缺的差异化。但也正因为稀缺，面试官会怀疑"是不是照着文档跑了个 docker-compose up"，
> 所以**必须能讲清数据链路**，这是真假的分水岭。
>
> 标注说明：`【需确认】` 表示取决于你的真实部署，回去翻部署脚本确认后填写。

## 一、为什么私有化（动机题，必问）

### Q1：为什么不直接用 Sentry SaaS？

**答题骨架**（按重要性排序）：
1. **数据合规**——错误上报会带上用户 ID、请求参数、页面路径，属于业务数据，公司要求不出内网
2. **成本**——SaaS 按事件量计费，多个项目接入后量不小；自建只有服务器成本
3. **内网环境**——【需确认】部分系统本身部署在客户内网/政务网，根本连不上公网 SaaS

**反问陷阱**："自建的运维成本不是更高吗？"
→ 诚实承认：**是的，Sentry 自托管的组件复杂度很高**（十几个容器），这也是我踩坑最多的地方。
但一次性投入换来长期的数据可控，对我们这种交付政企客户的场景是划算的。
**承认 trade-off 比假装没有 trade-off 可信得多。**

## 二、数据链路（分水岭题，必须能背下来）

### Q2：一个前端错误从浏览器到 Sentry 界面，中间经过了什么？

```
浏览器 SDK
   │  （捕获异常 → 组装 event → beforeSend 过滤 → 上报 /api/{id}/store/ 或 /envelope/）
   ▼
Relay          ← 接入层：鉴权、限流、采样、PII 清洗、事件规范化
   │
   ▼
Kafka          ← 缓冲：削峰，保证突发流量不打垮下游
   │
   ├──► Sentry Worker (Celery)  ← 事件处理：分组(grouping)、sourcemap 还原、告警触发
   │           │
   │           ▼
   │       Postgres            ← 元数据：项目、用户、issue、告警规则
   │
   ▼
Snuba          ← 查询抽象层：把 Sentry 的查询翻译成 ClickHouse SQL
   │
   ▼
ClickHouse     ← 事件明细存储：列式、适合海量事件的聚合查询
```

**必须能解释"为什么是这套组合"**：
- **为什么要 Relay**——把鉴权/限流/清洗前置，脏数据和超量数据在最外层就被挡掉，不浪费下游资源
- **为什么要 Kafka**——事件是突发的（一次线上事故可能瞬间几万条），需要缓冲层保护下游
- **为什么事件用 ClickHouse 而不是 Postgres**——事件是海量、只写不改、查询以聚合为主的时序数据，
  列式存储压缩比和聚合性能远超行式；而项目配置、告警规则这类关系型元数据仍然放 Postgres
- **为什么要 Snuba**——上层不直接写 ClickHouse SQL，通过 Snuba 抽象，便于查询优化和 schema 演进

> 这一段能流畅讲出来，基本就证明你真的部署过。建议**手画一遍**练熟。

## 三、离线部署的实际难点（体现"真的踩过坑"）

### Q3：离线环境部署有什么特别的坑？

**答题骨架**：
1. **镜像获取**——离线机器拉不到 Docker Hub，需要在有网环境 `docker save` 打包，
   拷贝进内网 `docker load`；镜像总量不小，要处理版本对齐
2. **官方安装脚本依赖外网**——`install.sh` 会做联网检查、拉取 geoip 数据库等，
   离线环境会卡住或超时失败，必须裁剪
3. **启动超时**——多个服务会尝试连外网（版本检查、错误上报给 Sentry 官方、geoip 更新），
   离线环境下这些请求要等到超时才继续，导致启动极慢甚至健康检查失败
   → **禁用外网相关功能**（`SENTRY_BEACON=False`、关闭 geoip 更新等）
4. **服务依赖顺序**——ClickHouse / Kafka / Postgres 起来之前，Snuba 和 Relay 会反复重启

### Q4：你裁剪了哪些服务？依据是什么？

【需确认，请按真实裁剪情况填写。以下是常见可裁项，仅供对照】
- **移动端/原生符号化相关**（symbolicator）——只接前端 JS 项目，用不到 native 符号还原
- **Profiling / Replay 相关消费者**——没有开这些功能就不需要对应的 consumer
- **邮件服务**——如果用企业内部邮件网关，可以替换掉自带的 smtp

**答题要点**：强调裁剪依据是**"我们实际用到哪些功能"**，而不是"随便关掉几个省内存"。
面试官想听的是决策依据，不是操作步骤。

### Q5：ClickHouse 磁盘持续增长是怎么回事？怎么解决的？

**这是简历里最具体的一个技术问题，一定会被问。**

**根因**：
1. **事件数据本身没有过期策略**——Sentry 默认保留期不一定符合你的磁盘容量
2. **ClickHouse 的系统日志表**（`system.query_log`、`system.part_log`、`system.trace_log` 等）
   默认开启且**没有 TTL**，长期运行后这些日志表本身能占掉大量磁盘——很多人只盯业务表，忽略了这个

**解决**：
- 给 ClickHouse 系统日志表配置 TTL，或直接关闭不需要的系统日志
- 设置事件数据的保留天数（`SENTRY_EVENT_RETENTION_DAYS`），让清理任务定期删除过期分区
- 【需确认】你写的"ClickHouse 日志配置与 TTL 自动设置脚本"具体做了什么？
  是改配置文件还是执行 `ALTER TABLE ... MODIFY TTL`？

**加分**：提一句 ClickHouse 按分区删除（`DROP PARTITION`）比按行删除高效得多，
所以保留策略设计成按天分区 + 删旧分区。

### Q6：资源限制是怎么调的？

- 不能照搬官方默认——官方配置面向的是大流量场景，我们的实际事件量小得多
- 【需确认】你的实际做法：观察各容器稳态内存占用，给 Kafka / ClickHouse / Postgres
  这三个吃内存的大户按实测值加余量设 limit，其余压缩
- **加分点**：讲一句"没设 limit 的容器会互相挤，某个服务内存泄漏会拖垮整机；
  设了 limit 至少故障是局部的"——这是容器编排的核心思维

## 四、前端接入侧（这块问得更细，因为是你的主场）

### Q7：sourcemap 是怎么关联的？为什么有时候还原不出来？

**流程**：
1. 构建时生成 sourcemap，但**不部署到线上**（避免源码泄露）
2. 通过 `sentry-cli` 或构建插件上传 sourcemap 到 Sentry，绑定一个 **release** 版本号
3. SDK init 时配置**相同的 release**，Sentry 才能把事件和 sourcemap 对应上

**还原失败的常见原因**（能列出来说明真踩过）：
- release 不一致——上传时用 commit hash，运行时用 package version，对不上
- `dist` 参数缺失——同一 release 下有多套产物（比如多环境）时需要 dist 区分
- 文件路径不匹配——上传时的路径前缀和运行时 `//# sourceMappingURL` 里的路径对不上，
  需要配置 `urlPrefix`
- sourcemap 没上传成功但构建流程没报错——CI 里要检查上传结果

### Q8：错误是怎么分组的？为什么有些错误被合并成一个 issue 了？

- Sentry 按 **fingerprint** 分组，默认由异常类型 + stacktrace 的关键帧计算
- 常见问题：**动态信息进了错误消息**（比如 `用户 12345 不存在`），导致本该合并的错误炸成上千个 issue
  → 解决：用 `beforeSend` 归一化 message，或手动指定 `fingerprint`
- 反过来也有本该分开却被合并的，同样用自定义 fingerprint 解决

### Q9：`Script error.` 是怎么回事？

- 跨域脚本抛出的错误，浏览器出于安全策略**不暴露详情**，只给一个 `Script error.`
- 解决：
  1. 脚本标签加 `crossorigin="anonymous"`
  2. CDN 响应头配置 `Access-Control-Allow-Origin`
- 【需确认】你的项目静态资源走 CDN，大概率遇到过这个，能讲一个具体案例最好

### Q10：用户信息上报，隐私怎么处理？

- `Sentry.setUser()` 上报用户标识，但**不应该上报手机号、身份证、密码等敏感字段**
- 手段：SDK 侧 `beforeSend` 清洗 + Relay 侧配置 PII 清洗规则（服务端兜底，防止前端漏改）
- **加分**：讲"两侧都做"——前端可能有遗漏或老版本没更新，服务端清洗是最后一道防线

### Q11：错误量太大怎么办？

- **采样**：`sampleRate`（错误采样）与 `tracesSampleRate`（性能追踪采样）分开配置，
  性能数据量远大于错误数据，采样率应该更低
- **过滤**：`ignoreErrors` 过滤掉已知噪音（浏览器插件报错、`ResizeObserver loop limit exceeded`、
  网络取消引起的 AbortError 等）
- **限流**：Relay 侧配置 rate limit，防止某个项目打爆整个系统

1. **"之前只会用 Sentry，这次把它拆开部署了一遍"**——从 API 使用者变成了理解数据链路的人。

后来我接入官网、工程汇后台、微信 H5 时，成本几乎是零。
这句话会让面试官觉得你有平台思维，而不只是做需求。
