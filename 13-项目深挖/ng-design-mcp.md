# ng-design-mcp：UI 规范 MCP 服务（MCP + RAG）

> 简历定位：**2026 年最稀缺的一段经历**。绝大多数前端只会「用 AI 写代码」，
> 你是「给 AI 造工具」的那一类。面试官对这段的兴趣通常最高，因为几乎所有公司都在做同一件事。
>
> 但也最容易翻车——因为体量小（简历只写了三条责任描述），如果只能讲三句话就没了，
> 反而暴露"蹭热点"。**这篇的目标是把一个小项目讲出系统性思考。**

---

## 0. 一句话自述

> 公司有自己的 UI 规范和组件库，但 AI 编码工具不知道这些，生成的代码经常不符合设计系统——
> 用错组件、造轮子、样式硬编码。我把内部 UI 规范和组件库文档做成了一个 MCP 服务，
> 让 AI 在生成代码前能查询和校验。技术上是 MCP SDK + Express，
> 检索用 ChromaDB 向量 + MiniSearch 关键词的混合方案，
> 文档解析用 unified/remark 处理 Markdown、react-docgen-typescript 提取组件类型，
> 还写了 evals 用例来验证检索质量。

## 一、动机与价值（这块比技术更重要）

### Q1：为什么要做这个？不能把规范贴在 prompt 里吗？

**这是最核心的一问，答好了整段经历就立住了。**

**答题骨架**：
1. **上下文窗口装不下**——完整的组件库文档 + 设计规范体量很大，全塞进 prompt 既超限又贵
2. **塞进去也会被稀释**——大量无关内容会降低模型对关键信息的注意力，
   给 100 个组件的文档不如精准给出当前需要的那 3 个
3. **规范会变**——组件库在迭代，硬编码在 prompt 里的规范会过期，
   而 MCP 服务读的是**当前**的文档和类型定义
4. **需要的是「按需检索」而不是「一次性灌输」**——这正是 RAG 的适用场景

**升华一句**（简历里你自己写的，很好，一定要说）：
> 「给 AI 提供什么上下文，比怎么问 AI 更能决定产出质量。」

### Q2：解决了什么实际问题？有效果数据吗？

【需确认】如果有数据（比如 AI 生成代码的返工率下降、组件复用率提升）一定要说。
**如果没有，不要编**，改成讲具体现象：

> 接入前，AI 生成表单经常自己写一个 `<input>` 加样式，而不是用我们封装的组件；
> 接入后能正确查到组件名和 props 再生成。

具体现象比虚假数字有说服力。

## 二、MCP 协议（必问，且很多人答不上来）

### Q3：MCP 是什么？解决了什么问题？

**答题骨架**：
- MCP（Model Context Protocol）是 Anthropic 提出的开放协议，
  用来标准化**「AI 应用」和「外部上下文/工具」之间的连接**
- **解决的是 M×N 问题**：过去每个 AI 客户端要对接每个数据源都得写一套适配，
  N 个工具 × M 个客户端 = M×N 份集成代码；
  有了 MCP，工具只实现一次 Server，所有支持 MCP 的客户端都能用——变成 M+N
- 常被类比为「**AI 应用的 USB-C 接口**」

### Q4：MCP 里的 Tools / Resources / Prompts 有什么区别？

**这题能筛掉 90% 只是听说过 MCP 的人。**

| 原语 | 谁来触发 | 类比 | 典型用途 |
|---|---|---|---|
| **Tools** | **模型**决定调用 | POST 接口 / 函数调用 | 查询规范、校验代码——有副作用或需要模型判断时机 |
| **Resources** | **应用/用户**选择 | GET 接口 / 文件 | 把某份文档作为上下文附加进去 |
| **Prompts** | **用户**主动触发 | 快捷命令 / 模板 | 预设好的工作流，如「按规范审查这段代码」 |

【需确认】你的服务主要暴露的是 Tools 吧？简历写「实现 UI 规范查询与验证工具」——
那就是两个 Tool：一个 query、一个 validate。**能说出你具体定义了哪几个 tool、
每个的入参出参是什么，可信度立刻上一个台阶。**

### Q5：MCP 的传输层有哪些？你用的哪种？

- **stdio**——本地进程，客户端直接启动 Server 子进程通信。最简单，适合本地工具
- **Streamable HTTP**（较新）/ 早期的 **HTTP + SSE**——远程服务，适合团队共享部署

你用了 Express，说明是 HTTP 方式。**要能解释为什么**：
> 因为这是给团队用的服务，规范文档在服务端统一维护和更新，
> 不需要每个同事本地跑一份、也不用各自同步文档。

### Q6：工具描述（description）该怎么写？

**这是 MCP 实践里最容易被忽略、但最影响效果的一环，答出来很加分：**
- 模型是**靠 tool 的 name 和 description 决定要不要调用、怎么传参**的，
  description 写得含糊，模型就不调用或者传错参数
- 所以工具描述本质上是**写给模型看的 prompt**，不是写给人看的 API 文档
- 实践：描述里要写清楚「什么时候该用这个工具」，而不只是「这个工具做什么」

## 三、RAG 与检索（技术深度区）

### Q7：为什么用向量 + 关键词的混合检索？只用向量不行吗？

**答题骨架——两者各自的失效场景**：

| | 擅长 | 失效场景 |
|---|---|---|
| 向量检索（ChromaDB） | 语义相似，「怎么做一个下拉选择」能匹配到 Select 组件 | **精确名词**——查 `NgTable` 这种专有组件名时，向量相似度未必把它排第一 |
| 关键词检索（MiniSearch） | 精确匹配组件名、prop 名、错误码 | 语义泛化能力为零，换个说法就查不到 |

UI 规范这个场景**两种查询都很常见**——既有"我要做个带搜索的下拉"（语义），
也有"NgSelect 的 mode 属性有哪些值"（精确），所以必须混合。

**加分**：提一句结果融合方式——【需确认】你是用 RRF（Reciprocal Rank Fusion）
还是加权打分？说不清就诚实说是加权合并后去重。

### Q8：文档是怎么切分（chunking）的？

**RAG 的效果七成取决于切分，这题问得很细：**
- **不能按固定字符数暴力切**——会把一个组件的说明和它的 props 表格切散
- Markdown 文档按**标题层级**切（unified/remark 解析出 AST，按 heading 分块），
  保证一个 chunk 是语义完整的一节
- 组件类型（react-docgen-typescript 提取的 props）单独成块，
  并**带上组件名作为前缀**，否则一张纯 props 表脱离上下文后检索不到
- 【需确认】你是否给 chunk 加了 metadata（组件名、分类、文档来源）用于过滤？
  如果做了，这是很专业的做法，一定要讲

### Q9：evals 是怎么做的？为什么要做？

**这条是简历里最能体现工程素养的一句，很多做 RAG 的人根本不做评测。**

**答题骨架**：
- **为什么要做**：RAG 系统的调参（chunk 大小、top-k、混合权重）如果靠人工抽查，
  改一个参数不知道是变好还是变坏，纯凭感觉。必须有可重复的评测集
- **怎么做**：构造一批「查询 → 期望命中的文档」的用例，
  跑检索后看期望文档有没有进 top-k
- **指标**：命中率 / Recall@k、MRR（期望结果的排名倒数）
- 【需确认】你实际构造了多少条用例？指标是什么？

**加分**：说一句「**RAG 的评测要分两层——检索层和生成层**。
我这个场景重点评的是检索层，因为生成是交给 AI 编码工具的，我控制不了；
我能控制的是给它的上下文准不准。」这句话显示你想清楚了系统边界。

## 四、可能被追问的硬问题

### Q10：文档更新了，索引怎么同步？

【需确认】是手动重建还是有自动化？
- 最简单：CI 里组件库发版时触发重新索引
- 增量更新：按文档 hash 判断变更，只重新 embed 变化的部分

**如果你没做自动化，诚实说「目前是手动触发重建，量不大还能接受，
如果要推广到更多团队，这是首先要补的」**——承认边界比吹牛安全。

### Q11：embedding 模型用的什么？中文效果怎么样？

【需确认】ChromaDB 默认用的是 all-MiniLM-L6-v2（英文为主）。
如果你的文档是中文，用默认模型效果会明显打折——**这是个真实的坑**，
如果你换了中文/多语言 embedding 模型，一定要讲；如果没换，
可以说「这是我知道但还没优化的点，中文语义检索的效果确实不如英文」。

### Q12：这个服务怎么保证 AI 一定会调用它？

**诚实答**：保证不了。MCP 只提供能力，调不调是模型决定的。
提升调用率的手段：
- 工具描述写清楚触发时机
- 在项目的规则文件（如 `CLAUDE.md` / `.cursorrules`）里明确要求「写组件前先查规范」
- 这也是为什么我除了 query 还做了 **validate 工具**——事后校验能兜住事前没查的情况

### Q13：这个东西的天花板在哪？如果让你继续做，下一步做什么？

**准备好这题，它是给「有产品思维」加分的机会：**
- 从「查规范」延伸到「查代码实现」——把组件的实际用法示例也索引进来
- 双向打通：结合 Code Connect 之类的方案，让设计稿也能关联到组件
- 从被动查询到主动检查——做成 lint 规则或 CI 卡口，而不只依赖 AI 自觉

## 五、防守：如果面试官觉得"这项目太小"

**大概率会遇到的质疑**："这不就是个包了层皮的检索服务吗？"

**别辩解，正面接**：
> 是的，从代码量看它不大，两三周的东西。但它的价值不在代码量，
> 在于它是我们团队第一次把「AI 产出质量」当成一个可以被工程化解决的问题，
> 而不是靠每个人自己调 prompt。我做完之后最大的收获是意识到，
> AI 编码工具的效果瓶颈往往不在模型，在于我们喂给它的上下文是不是结构化的、可检索的。

**把小项目讲出方法论，比把小项目吹成大项目有效得多。**
