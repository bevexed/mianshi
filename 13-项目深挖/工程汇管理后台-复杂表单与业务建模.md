## 一、业务建模（最能出彩的部分）

### Q1：介绍一下这套配置模型

**准备一张图**，面试时画出来。大意（【需确认】按真实模型修正）：

```
产品线（mi8 / i8c / 云产品 / AI_CLAW）
   └─ 产品
        └─ 套餐（版本：基础版/专业版/旗舰版）
             ├─ 套件（功能模块的打包）
             ├─ 指标（用量限制：用户数/存储/表单数…）
             └─ 订阅策略（年限 → 折扣规则）
                  └─ 订单
```

**答题要点**：讲清楚**为什么要分这么多层**，而不是罗列有哪些层：
- 套件和指标分开，是因为一个是**功能有无**（布尔），一个是**用量多少**（数值），
  售卖和校验逻辑完全不同
- 订阅策略独立出来，是因为**同一个套餐在不同年限/活动下价格不同**，
  策略变化频率远高于套餐本身

### Q2：这种嵌套配置的表单，你是怎么组织的？

**答题骨架**：
1. **表单结构跟随数据结构，但不等于数据结构**——
   直接把嵌套 JSON 铺成嵌套表单，运营会疯掉。
   要按**操作频率和心智模型**分组、分步
2. **用 antd 的 `Form.List` 处理动态数组**（套件列表、指标列表）
3. **拆子表单组件**，每个子组件只关心自己那部分，通过受控 props 通信——
   而不是所有字段挤在一个巨型 Form 里
4. **配置项的元数据化**——如果指标项本身是后端可配的，
   前端就不能写死字段，要按后端返回的 schema 动态渲染

【需确认】第 4 点你做了吗？如果做了动态表单/schema 驱动渲染，这是很强的加分项。

### Q3：「产品类型扩展（定制接口、云产品、AI_CLAW）」怎么做的扩展性？

**这题在考你有没有把「加需求」变成「加配置」的意识：**
- **差的做法**：`if (type === '云产品') {...} else if (type === 'AI_CLAW') {...}`
  ——每加一个产品类型改一遍所有页面
- **好的做法**：把类型差异收敛成一份配置（每种类型有哪些字段、走哪个提交接口、
  支付成功后跳哪里），页面读配置渲染。**新增类型 = 加一条配置**
- 简历里「支付成功后按商品类型分流引导」就是典型的策略分发场景

【需确认】你实际是哪种？**如果当时写的是 if-else，诚实说「当时是 if-else，
加到第三种类型的时候明显感觉不对，如果重构我会抽成策略配置」——
这种反思比假装一开始就设计好更可信。**

## 二、表单状态（简历金句，必被追问）

### Q4：「表单状态该由谁持有」，你的判断是什么？

**这是整篇最重要的一题。答题骨架：**

| 状态类型 | 该由谁持有 | 理由 |
|---|---|---|
| 字段值、校验状态 | **Form 实例**（antd 的 `useForm`） | 表单库就是干这个的，自己再存一份必然不同步 |
| 服务端来的初始值 | **react-query / 请求层** | 它是服务端状态，不是表单状态 |
| 跨字段联动的派生值 | **计算出来，不存** | 存了就要维护同步，能算就别存 |
| 跨页面/跨步骤的暂存 | 外部 store（Zustand） | 超出单个表单生命周期 |
| 弹窗开关、折叠状态 | 组件局部 `useState` | 纯视图状态，别污染表单数据 |

**核心原则一句话**：
> **同一份数据只能有一个权威来源。** 我踩的坑基本都是同一个原因——
> 一份数据在 Form 里有一份、在 useState 里又存了一份，
> 某个路径下只更新了其中一个，就出 bug。

### Q5：「版本切换数据还原」这个问题具体是什么？

**这是你简历里点名的难点，必须能讲清：**

**场景**：套餐有多个版本（基础版/专业版/旗舰版），运营在表单里切换版本时，
下面的套件、指标配置要跟着换成该版本的数据。

**难点**：
1. **切走之前用户改了但没保存的内容怎么办**——丢弃？暂存？提示？
2. **切回来的时候要还原成什么**——服务端的原始值，还是用户上次编辑到一半的值？
3. **antd Form 的 `initialValues` 只在首次挂载生效**，
   后续改它不会更新表单——这是最经典的坑，必须用 `form.setFieldsValue()`
4. 异步数据回来时表单可能还没挂载，`setFieldsValue` 打空

**你的解法**【需确认】：
- 常见方案是给 Form 加 `key={version}` 强制重新挂载（简单粗暴但有效，代价是丢失编辑态）
- 或者维护一个 `Record<version, formData>` 的草稿 map，切换时存/取

**答题要点**：讲清你**权衡了什么**——
「运营的实际操作习惯是先定版本再填内容，跨版本反复横跳的场景很少，
所以我选了切换即重置 + 二次确认，而不是做复杂的草稿管理」。
**基于真实用户行为做的简化，比技术上更"完备"的方案更值得讲。**

### Q6：受控组件和非受控组件，表单里怎么选？

- antd Form 内部是**非受控**思路（值存在 form 实例里，靠 `getFieldValue` 读），
  这样能避免每次输入都触发整个表单重渲染
- 强行给每个 `Input` 加 `value` + `onChange` 变成受控，
  会导致大表单输入卡顿
- 需要联动时用 `Form.Item` 的 `shouldUpdate` 或 `dependencies` 做**局部**订阅，
  而不是让整个表单重渲染——**这是 antd 大表单性能优化的核心手段**

## 三、权限

### Q7：「按后端权限控制按钮」是怎么实现的？

- **原则：前端权限只是体验，后端权限才是安全。** 前端隐藏按钮只是为了不让用户点了才报错，
  真正的校验必须在接口层——**这句话一定要说，不说会被认为安全意识不足**
- 实现：后端返回权限码列表，前端封装 `<Auth code="xxx">` 组件或 `usePermission` hook
- 菜单级权限：路由表按权限过滤
- 【需确认】你还参与了 Java 侧的「菜单权限」开发，可以讲讲权限模型是 RBAC 吗？
  角色-权限-用户怎么关联的？**前端做过后端权限模块，这是个亮点，别浪费**

## 四、订单与支付

### Q8：退款审核这类操作，前端要注意什么？

- **防重复提交**——审核类操作重复提交后果严重，
  按钮 loading + 请求去重 + 后端幂等（要提幂等，说明你知道前端防不住）
- **二次确认 + 拒绝原因必填校验**
- **操作后的状态同步**——列表要刷新，且要考虑其他人同时操作导致的状态过期
  （乐观锁 / 版本号）
- **金额展示**——精度、千分位、币种

### Q9：付款回执上传，大文件怎么处理？

- 类型/大小前端先校验（省一次无效上传）
- 上传中的进度、失败重试
- 【需确认】走的是直传 OSS 还是经过自己后端？
  直传要处理签名获取；经后端要注意网关的 body 大小限制

## 五、这段经历怎么讲出高度

B 端后台最容易讲得很平淡（「我负责了 XX 模块的增删改查」）。
**把它讲成「业务复杂度的工程化应对」**：

> 这个后台我最大的收获不是技术，是意识到 B 端的复杂度来自业务模型本身，
> 而不是技术选型。同样一套 antd，把套餐配置做成一个 30 个字段的大表单，
> 和做成按运营操作路径分步的表单，维护成本差好几倍。
>
> 我现在写复杂表单会先做两件事：一是画清楚数据模型和它的变化频率，
> 二是明确每一份状态的权威来源在哪。这两件事想清楚了，代码写起来反而很快；
> 想不清楚就会一直在补同步逻辑的窟窿。
