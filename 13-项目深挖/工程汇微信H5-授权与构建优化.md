## 一、微信授权（必问核心）

### Q1：微信网页授权的完整流程是什么？

**答题骨架——必须能背下来：**

```
1. 前端跳转微信授权页
   https://open.weixin.qq.com/connect/oauth2/authorize
     ?appid=APPID
     &redirect_uri=URLEncode(回调地址)
     &response_type=code
     &scope=snsapi_base | snsapi_userinfo
     &state=自定义参数
     #wechat_redirect          ← 这个 hash 必须带，否则微信不认

2. 用户同意后，微信 302 回 redirect_uri，URL 上带 code 和 state

3. 前端把 code 传给后端

4. 后端用 code + appid + appsecret 换 access_token 和 openid
   （⚠️ 必须后端换，appsecret 绝不能出现在前端）

5. 后端签发自己的登录态（token/session）返回前端
```

### Q2：`snsapi_base` 和 `snsapi_userinfo` 的区别？

| | snsapi_base | snsapi_userinfo |
|---|---|---|
| 用户感知 | **静默授权**，无感跳转 | 弹出授权确认页 |
| 能拿到 | 只有 openid | 昵称、头像等公开信息 |
| 是否需要关注公众号 | 否 | 否（但关注后体验更好）|

**实践**：只需要识别用户身份就用 `snsapi_base`，静默无感；
只有确实要展示昵称头像才用 `snsapi_userinfo`——**能不打扰用户就不打扰**。

### Q3：`code` 有什么坑？

**这题是分水岭，真踩过的人才知道：**
1. **code 只能用一次**，用过即失效
2. **有效期 5 分钟**
3. **用户刷新页面时，URL 上还挂着旧 code**，
   前端再拿它去换就会报 `invalid code`
   → 解决：**换取成功后立即把 code 从 URL 上清掉**（`history.replaceState`）
4. **React 18 StrictMode 下 useEffect 会执行两次**，
   开发环境会导致 code 被消费两次，第二次必然失败
   → 这个坑非常经典，能说出来很加分
5. **并发请求**：如果页面同时有多个地方触发换取，会互相踩

### Q4：redirect_uri 有什么限制？

- **必须在公众号后台配置「网页授权域名」**，且是**域名**不是路径
- 必须 URL encode
- **不支持 hash 路由的 hash 部分**——微信回调时 hash 后面的内容处理不可靠，
  这就是为什么很多微信 H5 项目被迫用 history 路由
- 【需确认】你简历写「修复登录跳转、登录失败兜底页问题」——
  是不是就是回跳后原目标路径丢失的问题？

### Q5：授权后怎么回到用户原本想去的页面？

**这是"登录跳转"问题的本质**：
- 把原目标路径存进 `state` 参数带过去（**注意 state 有长度限制且会被微信透传，
  不要放敏感信息**）
- 或者授权前存 sessionStorage，回来后读取
- **坑**：如果用 sessionStorage，微信内置浏览器某些版本跳转后 sessionStorage 会丢

### Q6：iOS 和 Android 在微信里的差异？

**这题能看出是不是真做过移动端：**
- **iOS 微信的 SPA 路由问题**：iOS 上 `wx.config` 的签名要用**首次进入页面的 URL**，
  而 Android 用当前 URL。SPA 路由跳转后 iOS 签名会失效
  → 解决：进页面时记录初始 URL，iOS 一直用它签名
- **iOS 日期格式**：`new Date('2025-01-01 10:00:00')` 在 iOS Safari 上返回
  `Invalid Date`，因为它只认 ISO 格式（`2025-01-01T10:00:00`）
  → **这就是你简历里"修复 iOS 日期格式兼容问题，统一改用 dayjs"的原因**，
  能说清成因比说"我用了 dayjs"强十倍

## 二、微信支付

### Q7：微信 JSAPI 支付的流程？

```
1. 前端下单 → 后端调微信统一下单接口，拿到 prepay_id
2. 后端用 prepay_id 生成支付参数并签名，返回前端
3. 前端调 wx.chooseWXPay / WeixinJSBridge.invoke('getBrandWCPayRequest')
4. 用户支付
5. 前端拿到 res.err_msg 判断结果，但 ⚠️ 这只是"用户操作结果"
6. 真正的支付结果以微信的异步回调通知后端为准
```

### Q8：为什么前端的支付回调结果不能作为最终依据？

**必答题，答不好说明没做过支付：**
- 前端返回 `get_brand_wcpay_request:ok` 只代表**用户完成了支付动作**，
  不代表钱到账、订单已更新
- 用户可能支付成功后立刻关闭页面，前端回调根本没执行
- 用户可能篡改前端逻辑
- **正确做法**：前端拿到 ok 后跳转到「支付结果页」，
  该页面**轮询后端订单状态**，后端以微信异步通知为准
- 还要处理「支付中」的中间态——微信通知有延迟，不能立刻判失败

### Q9：支付要注意的其他坑？

- **重复下单**：同一订单重复调统一下单，要用商户订单号保证幂等
- **金额单位**：微信是**分**，不是元
- **支付目录/授权目录**要在商户后台配置

## 三、邀请函二维码那个 bug（简历点名，必被问）

### Q10：「扫过一次后邀约人被固定」是什么问题？

**这题要讲成完整的排查故事。**

**现象**：A 分享邀请函给用户，用户扫码报名，邀约人正确记录为 A；
之后用户扫 B 的邀请函，邀约人却还是 A。

**根因**（【需确认】按你实际情况修正，以下是最可能的两种）：
1. **邀约人被持久化存储后没有覆盖逻辑**——
   首次扫码时把 inviterId 存进 localStorage，
   后续扫码时代码写的是「如果没有才存」，导致永远是第一次的值
2. **URL 参数被登录跳转吞掉**——扫码进来带 `?inviter=B`，
   但走了一遍微信授权跳转后 URL 参数丢了，
   于是回退到读缓存里的旧值

**修复思路**：
- 明确优先级：**URL 参数 > 缓存**，每次有新的 inviter 就覆盖
- 授权跳转时把 inviter 一起带进 `state` 或存到跳转前的暂存里
- 加上时效——邀约关系不应该永久绑定

**答题加分**：说一句「这个 bug 的本质是**同一份数据有两个来源且优先级没定义清楚**」——
和你在工程汇后台总结的「状态权威来源」是同一个教训，**两段经历能互相呼应，
显示你的认知是成体系的，不是零散的。**

## 四、构建优化（简历金句：「优化要先量再改」）

### Q11：chunk 分割是怎么优化的？

**流程要讲成"先量后改"：**
1. **量**：接 `rollup-plugin-visualizer`，生成体积可视化，找出大头
2. **常见的大头**：
   - moment（体积大且默认打包全部 locale）→ 换 dayjs
   - lodash 全量引入 → 按需引入 / lodash-es + tree shaking
   - antd-mobile 图标全量引入
   - **react-pdf**（你项目里有）——这个库非常大，
     应该 **`React.lazy` 动态导入**，只在真正要预览 PDF 时加载
   - echarts 全量 → 按需引入图表类型
3. **改**：Vite 里配 `build.rollupOptions.output.manualChunks`
   - 把稳定的第三方库单独成 chunk（**利用长期缓存**，业务代码更新时 vendor 不失效）
   - 路由级代码分割（`React.lazy` + `Suspense`）

### Q12：manualChunks 分得越细越好吗？

**这题是深度题，答"越细越好"就掉坑了：**
- **不是**。chunk 过多会导致 HTTP 请求数暴增，
  在移动端弱网下，请求开销可能超过体积节省的收益
- 也会削弱 gzip 效果（小文件压缩率低）
- **原则**：按「变更频率」分组——
  很少变的第三方库合成一个大 vendor chunk（缓存命中率高），
  业务代码按路由分割

### Q13：你优化后效果怎么样？

【需确认】**这里必须有数字**，哪怕是粗略的。
「首屏 JS 从 X MB 降到 Y MB」。如果真没记录，就说
「当时主要解决的是首屏加载明显偏慢的问题，
把 react-pdf 这类只在特定页面用的大库改成动态导入后，

### Q14：为什么引入 Vitest 而不是 Jest？

- 项目是 Vite，**Vitest 直接复用 Vite 的配置和转换管线**——
  不用再维护一套 Jest 的 babel/ts 配置
- 原生 ESM 支持，Jest 对 ESM 一直很别扭
- API 兼容 Jest，迁移成本低
- 启动快（Vite 的按需编译）

### Q15：pre-commit 卡口具体卡什么？为什么不放到 CI？

- husky + lint-staged：**只对暂存区的文件**跑 ESLint/Prettier，快
- **为什么本地卡**：反馈越早成本越低，代码推上去再被 CI 打回来，
  上下文已经切走了
- **但不能只有本地卡**——husky 可以被 `--no-verify` 绕过，
  CI 必须有同样的检查作为兜底。**两层都要有**

### Q16：单测你都测什么？

**B/C 端业务项目的单测最容易流于形式，答出取舍才可信：**
- **值得测的**：纯函数（价格计算、日期处理、数据转换）、
  自定义 hooks、关键工具函数
- **性价比低的**：UI 组件的快照测试（改个样式就挂，维护成本高）
- 【需确认】你实际写了多少？如果只是接入了框架 + 少量用例，
  **诚实说「接入了框架并覆盖了核心工具函数，
  组件层面的覆盖还很少」**——B 端项目单测覆盖率低是常态，不丢人，
  假装覆盖率很高才危险。

## 六、附：`useSearchParams` 替换 `useUrlState`

简历里这条小改动可以答出深度：
- `useUrlState`（ahooks）是自己维护一份 state 再同步到 URL，
  **URL 和 state 是两份数据**——又是"双来源"问题
- `useSearchParams`（React Router）**直接以 URL 为唯一来源**，
  读的就是当前 URL，天然和浏览器前进后退同步
- **收益**：分享链接、刷新页面、前进后退行为都正确了

**又一次呼应「同一份数据只能有一个权威来源」这个主线。**
把三段经历（工程汇后台的表单状态、邀请函 bug、这条）串成同一个方法论，
是这份简历最有说服力的讲法。
