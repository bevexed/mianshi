# qiankun 原理与 JS 沙箱

本文解释 qiankun 的核心机制。具体实现可能随版本变化，排障时应以当前源码和官方文档为准。

## qiankun 是怎么工作的

可拆成三部分：

**1. 基于 single-spa 做应用生命周期管理**
（`bootstrap` / `mount` / `unmount`）

**2. HTML Entry**——这是 qiankun 相比 single-spa 的主要改进

- single-spa 要你手动配置子应用的 JS 入口
- qiankun 直接请求子应用的 `index.html`，
  解析出里面的 JS/CSS 并执行
- **接入成本低得多**，子应用改动最小

**3. 沙箱隔离**——JS 沙箱 + CSS 沙箱，防止子应用互相污染

---

## JS 沙箱的三种实现

| 沙箱类型                            | 原理                                                                       | 限制                                                                  |
| ----------------------------------- | -------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| **SnapshotSandbox**<br>（快照沙箱） | 子应用挂载前给 `window` **拍快照**，卸载时对比并还原被修改的属性           | 只支持**单实例**；遍历 window 有性能开销。用于不支持 Proxy 的老浏览器 |
| **LegacySandbox**                   | 记录子应用对 window 的**新增/修改/删除**，卸载时精确还原                   | 仍是单实例，但不用全量遍历，性能好于快照                              |
| **ProxySandbox**<br>（代理沙箱）    | 用 `Proxy` 给每个子应用一个 **fakeWindow**，读走原型链、写只写进自己的副本 | **支持多实例**，qiankun 默认方案。依赖 Proxy                          |

### ProxySandbox 的关键理解

子应用的 `window.xxx = 1` 实际写到了**自己的假 window** 上，
读的时候先查自己的、再回退到真 window。
所以多个子应用可以同时存在互不干扰。

### 子应用代码怎么用上假 window

把子应用脚本包在 `with(proxyWindow) { ... }` 里执行——
**本质是改变作用域链**，让脚本里的全局变量访问落到 proxy 上。

```js
// 简化示意
const code = `with(proxyWindow) { ${subAppCode} }`;
new Function('proxyWindow', code)(proxyWindow);
```

> `with` 的作用域机制见 [JavaScript 作用域](../../01-JavaScript/作用域.md)。这段代码只用于说明思路，并非 qiankun 完整实现。

## 主子应用通信

| 方式                                          | 说明                         | 注意                                   |
| --------------------------------------------- | ---------------------------- | -------------------------------------- |
| **`initGlobalState` + `onGlobalStateChange`** | qiankun 官方，本质是发布订阅 | 状态多了会变成隐式耦合                 |
| **props 传递**                                | 主应用注册子应用时传入       | 适合传初始配置和方法                   |
| **自定义事件 / 共享 store**                   | 灵活                         | **警惕耦合**——通信越多，解耦收益越少   |
| **URL**                                       | 可刷新、可分享               | 只适合可序列化且适合暴露在地址中的状态 |

能通过 URL 表达的页面定位和筛选条件优先放在 URL；敏感信息和大对象不应放入 URL。

## 主子应用的路由调度

- **主应用负责一级路由**（决定加载哪个子应用），
  子应用负责自己内部的路由
- **坑 1**：子应用要配 `base`
  （Vue Router 的 `base` / React Router 的 `basename`），
  否则子应用内部跳转会丢掉主应用的路径前缀
- **坑 2**：浏览器前进后退时，主子应用的路由状态要能同步
- **坑 3**：两个路由实例同时监听 `popstate`，
  可能互相触发导致重复渲染

---

## 子应用卸载要清理什么

沙箱能回收 `window` 上的污染，
但**这些需要子应用自己在 `unmount` 里清理**：

- 定时器
- 事件监听（挂在 document/window 上的）
- 第三方 SDK 实例（地图、图表、播放器）
- 动态插入的 DOM

反复切换子应用后内存持续上涨时，应重点检查这些资源，同时用堆快照和引用链确认，不能仅凭现象下结论。
