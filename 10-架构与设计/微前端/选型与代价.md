# 微前端：什么时候该用，代价是什么

微前端首先是组织和系统治理方案。采用它之前，应明确要解决的是存量迁移、团队自治还是独立发布，并用可验证的约束来评估收益。

## 为什么要用微前端

### 技术栈无关不是充分理由

允许不同技术栈可以帮助渐进迁移，但同时也会增加依赖、招聘、监控和调试成本。对于由一个团队维护的新系统，统一技术栈往往更简单。

### 真实且有力的理由

**1. 存量老项目迁移不动**
比如一个跑了几年的 Angular 项目，
完全重写成本高、风险大、业务不会给这个时间。
微前端让**新功能用新技术写，老代码原地不动**——
这是一种**渐进式迁移策略**。

**2. 团队/发布解耦**
不同业务域由不同人维护，独立发布，
不用因为改一个模块全量回归。

组织边界和存量治理是常见动机，但不是唯一条件。还要验证子应用能否形成稳定业务边界，以及独立交付是否真能抵消运行时集成成本。

## 代价是什么

**能主动说出代价，是资深和初级的分界线。**

| 代价                   | 具体表现                                         |
| ---------------------- | ------------------------------------------------ |
| **复杂度大幅上升**     | 调试、部署、本地开发环境都变复杂                 |
| **公共依赖重复加载**   | 每个子应用带一份 React/Vue，体积膨胀             |
| **样式和全局变量污染** | 最主要的坑，见 [CSS 隔离方案.md](CSS隔离方案.md) |
| **通信成本**           | 主子应用之间传数据比 props 麻烦得多              |
| **用户体验割裂**       | 子应用切换时的白屏、loading、路由状态丢失        |
| **内存泄漏风险**       | 子应用卸载不彻底                                 |

## 有哪些替代方案

**在上微前端之前应该先问一遍：**

| 方案                  | 适用                     | 相比微前端                                           |
| --------------------- | ------------------------ | ---------------------------------------------------- |
| **路由懒加载**        | 只是想拆分包体积         | 仍保留单应用模型，改造成本较低                       |
| **Monorepo + 包拆分** | 只是想代码解耦、复用组件 | 仍是单应用，无运行时开销                             |
| **Module Federation** | 运行时共享模块或独立交付 | 粒度灵活，但版本协调和运行时依赖治理复杂             |
| **iframe**            | 强隔离、低集成           | 浏览上下文隔离强，但路由、通信、尺寸和体验集成成本高 |
| **微前端**            | 存量迁移 + 组织解耦      | 最重                                                 |

Module Federation 通过构建配置声明、在运行时加载远程模块，
粒度比 qiankun 的"整个应用"更细，
但需要各方都用兼容的构建工具（Webpack 5 / Vite 插件）。

## 决策检查表

1. 子应用是否对应稳定、可独立负责的业务边界？
2. 是否确有独立发布、存量迁移或组织自治诉求？
3. 主子应用的路由、鉴权、错误处理和监控由谁负责？
4. 共享依赖如何定版本，失败时如何回滚？
5. 本地联调、端到端测试和跨应用问题如何复现？
6. 是否用模块化单体、包拆分或 iframe 就能满足需求？

只有收益和长期维护责任都明确，微前端才是可持续方案。
