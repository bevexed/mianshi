# 微前端：什么时候该用，代价是什么

> **这是筛人题。** 面试官问微前端，考的不是"你会不会用 qiankun"，
> 而是"你有没有想清楚为什么要用"。
> 微前端是一个被过度使用的技术，**能说清它的坏处才显得成熟**。

## 为什么要用微前端

### ⚠️ 最差的答法

「为了技术栈无关」——这是**宣传语，不是理由**。

真实世界里，一个团队同时维护 React + Vue + Angular 三套栈
本身就是问题，不是优点。

### 真实且有力的理由

**1. 存量老项目迁移不动**
比如一个跑了几年的 Angular 项目，
完全重写成本高、风险大、业务不会给这个时间。
微前端让**新功能用新技术写，老代码原地不动**——
这是一种**渐进式迁移策略**。

**2. 团队/发布解耦**
不同业务域由不同人维护，独立发布，
不用因为改一个模块全量回归。

### 必须补的一句

> 微前端的正当理由基本只有「**组织**」和「**存量**」，
> 不是技术先进性。
> 如果是一个从零开始的新项目、一个团队维护，
> 用微前端纯属自找麻烦。

## 代价是什么

**能主动说出代价，是资深和初级的分界线。**

| 代价 | 具体表现 |
|---|---|
| **复杂度大幅上升** | 调试、部署、本地开发环境都变复杂 |
| **公共依赖重复加载** | 每个子应用带一份 React/Vue，体积膨胀 |
| **样式和全局变量污染** | 最主要的坑，见 [CSS隔离方案.md](CSS隔离方案.md) |
| **通信成本** | 主子应用之间传数据比 props 麻烦得多 |
| **用户体验割裂** | 子应用切换时的白屏、loading、路由状态丢失 |
| **内存泄漏风险** | 子应用卸载不彻底 |

---

## 有哪些替代方案

**在上微前端之前应该先问一遍：**

| 方案 | 适用 | 相比微前端 |
|---|---|---|
| **路由懒加载** | 只是想拆分包体积 | 成本几乎为零 |
| **Monorepo + 包拆分** | 只是想代码解耦、复用组件 | 仍是单应用，无运行时开销 |
| **Module Federation** | 想运行时共享模块、独立部署 | 比 qiankun 轻，但对构建工具有要求 |
| **iframe** | 隔离要求极高、集成度要求低 | 隔离最彻底，但体验最差（弹窗、路由、通信都难） |
| **微前端** | 存量迁移 + 组织解耦 | 最重 |

**Module Federation 现在是很常被追问的对比项**，
要能说清：它是**构建期约定 + 运行时加载远程模块**，
粒度比 qiankun 的"整个应用"更细，
但需要各方都用兼容的构建工具（Webpack 5 / Vite 插件）。

## 如果被问"你会推荐用微前端吗"

**准备一个有立场的回答：**

> 分情况。如果是我现在这种场景——
> 一个跑了好几年的 Angular 项目，团队想用 React 写新功能，
> 重写不现实——微前端是我能想到的最合理的方案。
>
> 但如果是新项目，或者只是想「按业务拆一拆」，
> 我会先问一句：是不是 monorepo + 模块联邦，
> 甚至就是普通的路由懒加载，就够了？
> 微前端带来的运维和调试复杂度，是要长期付利息的。
>
> 我踩过的坑里有九成跟样式和全局状态有关，
> **这些成本在做技术选型的 PPT 上是看不见的。**

**最后一句是杀手锏**——面试官会觉得你是真做过而不是看文档来的。
