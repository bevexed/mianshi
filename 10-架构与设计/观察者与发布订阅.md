# 观察者模式 vs 发布订阅模式

> ⚠️ **原 `发布订阅模式.md` 有三处错误，本篇重写并修正**：
>
> 1. **标题写「发布订阅」，代码实现的却是「观察者模式」**——两者不是一回事
> 2. **注释写「不需要中间人」**——这恰恰是**观察者模式**的特征，
>    发布订阅**必须有**中间人（事件中心）
> 3. **代码有 bug**：构造函数里是 `this.observers = []`，
>    `attach` 里却写 `this.list.push(...)` —— **`this.list` 是 undefined，会直接报错**

## 两者的核心区别（面试常混）

|                      | 观察者 Observer                        | 发布订阅 Pub/Sub                                   |
| -------------------- | -------------------------------------- | -------------------------------------------------- |
| **有没有中间人**     | ❌ **没有**，Subject 直接持有 Observer | ✅ **有**，通过事件中心（Event Bus）转发           |
| **双方是否知道对方** | Subject 知道有哪些 Observer            | **互相不知道**，只认识事件中心                     |
| **耦合度**           | 松耦合（但仍有直接引用）               | 发布者和订阅者互相解耦，但都依赖事件契约和事件中心 |
| **典型场景**         | Vue2 Dep/Watcher、DOM EventTarget      | EventBus、跨模块事件中心、消息代理的主题订阅       |

**一句话记忆**：

> **观察者是"我盯着你"，发布订阅是"我们都听广播"。**

```
观察者：  Subject ──直接通知──► Observer

发布订阅：Publisher ──► EventBus ──► Subscriber
                     （互不认识）
```

## 观察者模式（修正版）

```js
class Subject {
	constructor() {
		this.state = {};
		this.observers = new Set();
	}

	getState() {
		return this.state;
	}

	setState(state) {
		this.state = state;
		this.notifyAll();
	}

	attach(observer) {
		if (!observer || typeof observer.update !== 'function') {
			throw new TypeError('observer 必须实现 update()');
		}
		this.observers.add(observer); // ← 原代码这里写成 this.list，是 bug
		return () => this.detach(observer);
	}

	detach(observer) {
		// ← 原代码缺少解绑，会内存泄漏
		return this.observers.delete(observer);
	}

	notifyAll() {
		// 复制快照，避免 update() 内解绑影响本轮遍历
		for (const observer of [...this.observers]) observer.update();
	}
}

class Observer {
	constructor(name, subject) {
		this.name = name;
		this.subject = subject;
		subject.attach(this);
	}

	update() {
		console.log(`${this.name} update, state:`, this.subject.getState());
	}
}

// 使用
const subject = new Subject();
new Observer('A', subject);
new Observer('B', subject);
subject.setState({ count: 1 }); // A、B 都收到通知
```

> ⚠️ **`detach` 是原版缺的**——
> Subject 生命周期长于 Observer 时，只订阅不解绑会让 Observer 持续被引用，
> 是常见的内存泄漏来源。
> 见 [08-性能优化/内存泄漏排查.md](../08-性能优化/内存泄漏排查.md)

## 发布订阅模式（EventEmitter 手写题）

**这个是高频手写题**，要能默写：

```js
class EventEmitter {
	constructor() {
		this.events = new Map();
	}

	on(event, callback) {
		if (typeof callback !== 'function') throw new TypeError('callback 必须是函数');
		if (!this.events.has(event)) this.events.set(event, new Set());
		this.events.get(event).add(callback);
		return () => this.off(event, callback); // 返回取消订阅函数（好设计）
	}

	once(event, callback) {
		if (typeof callback !== 'function') throw new TypeError('callback 必须是函数');
		const wrapper = (...args) => {
			this.off(event, wrapper);
			callback.apply(this, args);
		};
		wrapper.raw = callback; // 存原函数，便于 off 时匹配
		return this.on(event, wrapper);
	}

	off(event, callback) {
		if (callback === undefined) return this.events.delete(event); // 不传就全清
		const set = this.events.get(event);
		if (!set) return;
		for (const cb of set) {
			if (cb === callback || cb.raw === callback) set.delete(cb);
		}
		if (!set.size) this.events.delete(event);
	}

	emit(event, ...args) {
		const set = this.events.get(event);
		if (!set) return false;
		// ⚠️ 复制一份再遍历——防止回调里 off 导致遍历出错
		for (const cb of [...set]) cb.apply(this, args);
		return true;
	}
}
```

**四个能体现水平的细节**（面试官会看）：

1. **`on` 返回取消订阅函数**——用起来方便，不用自己存引用
2. **`once` 存 `raw`**——否则用户拿原函数 `off` 时匹配不上
3. **`once` 先解绑再执行**——回调里递归触发同一事件时不会执行第二次
4. **`emit` 时复制一份再遍历**——本轮通知不受回调增删监听器影响
5. **用 `Set` 而不是数组**——本实现约定同一函数不重复注册，平均删除 O(1)

这个轻量实现是**同步**的：监听器抛错会中断后续监听器；它也没有实现
Node.js `EventEmitter` 的 `error` 事件、最大监听器告警等语义。

## 在前端里的实际应用

| 场景                          | 用的哪个                                           |
| ----------------------------- | -------------------------------------------------- |
| **Vue2 响应式**               | 观察者（Dep 持有 Watcher）                         |
| **DOM EventTarget**           | 观察者风格；作为共享事件中心时也可形成发布订阅用法 |
| **Vue2 EventBus**             | 发布订阅                                           |
| **Redux 的 subscribe**        | 观察者                                             |
| **跨标签页 BroadcastChannel** | 发布订阅                                           |
| **消息代理的 topic/fan-out**  | 发布订阅                                           |
| **BullMQ Queue/Worker**       | 默认是任务队列/竞争消费，不等于发布订阅            |

## 面试怎么答

**被问"观察者和发布订阅有什么区别"**：

> 核心区别是**有没有中间人**。
>
> 观察者模式里，Subject 直接持有 Observer 的引用，
> 状态变了直接调用它们的 update——**双方是认识的**。
> Vue2 的响应式就是这样，Dep 里存着 Watcher。
>
> 发布订阅多了一个事件中心，发布者和订阅者**互相不知道对方存在**，
> 都只和事件中心打交道——**耦合度更低**，但也更难追踪
> 「这个事件到底是谁发的、被谁消费了」。
>
> 实践中应优先使用能显式表达数据流的 props、callback 或状态容器；
> EventBus 使用过多会让事件来源、消费方和执行顺序难以追踪。

回答到事件契约、调试和生命周期成本，比只说“耦合度更低”更完整。
