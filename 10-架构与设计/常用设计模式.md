# 常用设计模式（前端视角）

> 设计模式是对**反复出现的设计问题**的命名，不是必须套用的代码模板。
> 使用时应说明：它解决了什么变化、为什么比朴素实现更合适、代价是什么。
>
> 观察者和发布订阅容易混淆，单独见
> [观察者与发布订阅.md](观察者与发布订阅.md)。
>
> 设计原则与编程范式另见：[SOLID 设计原则](SOLID设计原则.md)、
> [AOP 面向切面编程](AOP面向切面编程.md)。二者都不是 GoF 设计模式。

## 先建立分类

| 类型       | 关注点       | GoF 模式                                                                           |
| ---------- | ------------ | ---------------------------------------------------------------------------------- |
| **创建型** | 对象怎么创建 | 单例、工厂方法、抽象工厂、建造者、原型                                             |
| **结构型** | 对象怎么组合 | 适配器、桥接、组合、装饰器、外观、享元、代理                                       |
| **行为型** | 职责怎么协作 | 责任链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法、访问者 |

分类是帮助记忆的，不要为了“用了模式”而增加抽象层。只有变化反复出现、
条件分支开始散落或第三方接口需要隔离时，抽象才通常值得。

---

## 一、单例模式

**解决的问题**：某个作用域内只需要一个共享实例，并提供统一访问入口。

```js
class RequestClient {
	constructor(baseURL) {
		this.baseURL = baseURL;
	}
}

let client;

function getRequestClient() {
	if (!client) client = new RequestClient('/api');
	return client;
}
```

ES Module 的同一模块实例通常会被缓存，因此直接导出实例也能实现
“模块作用域内共享”。但这不保证跨 iframe、Web Worker、重复安装的依赖副本
或多份 bundle 仍只有一个对象。

**前端场景**：请求客户端、WebSocket 连接管理器、弹窗调度器、客户端 store。

**代价与边界**：

- 全局共享状态会隐藏依赖，使测试隔离和并发推理更困难。
- SSR 进程可能同时处理多个请求；包含用户状态的模块级实例会造成跨请求污染。
  服务端 store 应按请求创建，只有无请求状态的配置或客户端实例才适合共享。
- Spring Bean 默认是单例作用域，同样不应在 Service 实例字段里保存请求状态。

> 关联：[状态库选型.md](../05-React生态/状态管理/状态库选型.md)、
> [Spring 核心概念.md](../16-后端常识/Spring核心概念.md)

## 二、工厂模式

**解决的问题**：调用方只描述“要什么”，把创建细节和具体类型选择集中管理。

```js
class JsonClient {
	constructor() {
		this.contentType = 'application/json';
	}
}

class FormClient {
	constructor() {
		this.contentType = 'application/x-www-form-urlencoded';
	}
}

function createRequestClient(type) {
	if (type === 'json') return new JsonClient();
	if (type === 'form') return new FormClient();
	throw new TypeError(`不支持的客户端类型: ${type}`);
}
```

上面是**简单工厂**，严格说不属于 GoF 23 种；GoF 的工厂方法通常把创建步骤
延迟给子类，抽象工厂则创建一组相互配套的产品。前端面试多数讲清简单工厂即可。

**前端场景**：按 schema 创建表单控件、按环境创建存储适配器、
按文件类型创建解析器。

**代价**：类型很少且不会扩展时，工厂只是额外跳转；一个巨大 `switch`
也会成为新的修改中心，可以在类型持续增加后再改为注册表。

## 三、策略模式

**解决的问题**：同一目标有多种可替换算法，让调用方选择策略，
避免同一组条件分支散落到多个页面和流程。

```js
const pricingStrategies = new Map([
	['normal', (price) => price],
	['vip', (price) => price * 0.8],
	['svip', (price) => price * 0.6]
]);

function getPrice(type, price) {
	const strategy = pricingStrategies.get(type);
	if (!strategy) throw new TypeError(`不支持的价格策略: ${type}`);
	return strategy(price);
}
```

**前端场景**：表单校验规则、排序算法、不同产品类型的展示或提交规则、
埋点上报渠道。

**代价与边界**：

- 策略模式没有消灭分支，只是把“选择哪个行为”和“行为怎么实现”分开。
- 价格、权限等安全敏感规则必须由服务端最终校验；前端策略只能负责展示或预估。
- 只有两条稳定分支时直接写条件往往更清晰。

---

## 四、适配器模式

**解决的问题**：把已有接口转换成调用方期望的接口，隔离不兼容的数据结构。

```js
function adaptToTreeSelect(items) {
	return items.map((item) => ({
		value: item.id,
		label: item.name,
		children: item.subs ? adaptToTreeSelect(item.subs) : undefined
	}));
}
```

**前端场景**：API DTO 转组件 ViewModel、兼容不同版本的 SDK、
统一多个第三方地图或支付接口。

**代价**：适配层需要维护字段映射和错误处理，但它能避免服务端结构渗透到所有组件。
如果应用内部模型和外部 DTO 本来就一致，不需要为了模式再复制一层对象。

**和外观的区别**：适配器重点是**接口不兼容**；外观重点是
**把多个复杂步骤收敛成一个简单入口**。

## 五、代理模式

**解决的问题**：代理和真实对象暴露相同接口，在访问前后增加缓存、权限、
延迟加载或远程访问等控制。

```js
function createCachedLoader(load) {
	const cache = new Map();
	return {
		async get(id) {
			if (cache.has(id)) return cache.get(id);
			// 先缓存进行中的 Promise，合并同一 id 的并发请求；失败后允许再次加载
			const pending = Promise.resolve().then(() => load(id));
			cache.set(id, pending);
			try {
				return await pending;
			} catch (error) {
				if (cache.get(id) === pending) cache.delete(id);
				throw error;
			}
		},
		clear(id) {
			cache.delete(id);
		}
	};
}
```

**前端场景**：请求缓存代理、图片懒加载（虚拟代理思想）、权限代理；
Vue 3 使用 JavaScript `Proxy` 拦截对象操作来实现响应式，qiankun 的部分沙箱实现
也利用代理对象隔离全局访问。

这个版本缓存 Promise，从而合并同一 `id` 的并发加载；失败结果不会保留，下一次调用可以重试。
`clear()` 只移除缓存，不能取消已经开始的加载，取消仍需由底层配合 `AbortSignal`。

**代价**：访问链路变得隐式；缓存还会引入失效、一致性和内存上限问题。

> 关联：[Proxy 与 Reflect.md](../01-JavaScript/Proxy与Reflect.md)、
> [qiankun 原理.md](微前端/qiankun原理.md)

## 六、装饰器模式

**解决的问题**：保持原接口不变，用包装对象或包装函数按需叠加能力。

```js
function withRetry(request, maxRetries = 2) {
	return async function requestWithRetry(...args) {
		let lastError;
		for (let attempt = 0; attempt <= maxRetries; attempt++) {
			try {
				return await request.apply(this, args);
			} catch (error) {
				lastError = error;
			}
		}
		throw lastError;
	};
}
```

示例只展示包装结构。生产重试还要限制为幂等操作和暂时性错误，设置退避、抖动、
总超时与取消；支付、创建订单等非幂等写操作不能在没有幂等键时直接套用。

**前端场景**：给请求函数叠加重试、日志和指标；高阶组件或高阶函数在结构上
也常体现装饰思想。

TypeScript / NestJS 的 `@Decorator` 是**装饰器语法和元数据机制**；
它可能用于配置守卫、拦截器等功能，但“使用了 `@`”不自动等于采用了经典装饰器模式。
React `memo`、`forwardRef` 是高阶 API，也不必机械贴成 GoF 装饰器。

**和代理的区别**：代理主要控制“如何访问原对象”，装饰器主要叠加“额外能力”；
两者结构相似，真实代码里可能同时出现，不必只凭一段包装代码强行分类。

## 七、外观模式

**解决的问题**：为多个子系统提供一个更简单、稳定的入口。

```js
function createCheckoutFacade({ inventory, payment, tracker }) {
	return {
		async checkout(order) {
			await inventory.reserve(order.items);
			const receipt = await payment.pay(order.total);
			tracker.track('checkout_success', { orderId: order.id });
			return receipt;
		}
	};
}
```

**前端场景**：统一封装登录流程、支付流程、监控 SDK、多种浏览器存储能力。

**代价**：外观如果不断吸收业务规则，会变成“万能 Service”。它应负责协调稳定步骤，
而不是拥有所有领域逻辑。

---

## 八、组合模式

**解决的问题**：让叶子节点和容器节点通过同一接口组成树，调用方可以统一递归处理。

```js
function totalSize(node) {
	if (node.type === 'file') return node.size;
	return (node.children || []).reduce((sum, child) => sum + totalSize(child), 0);
}

const directory = {
	type: 'directory',
	children: [
		{ type: 'file', size: 2 },
		{ type: 'directory', children: [{ type: 'file', size: 3 }] }
	]
};

totalSize(directory); // 5
```

**前端场景**：组件树、菜单树、虚拟 DOM、权限节点。

**代价**：统一接口可能掩盖叶子和容器的真实差异；只有一种固定层级时，
直接的数据结构通常更简单。

---

## 九、责任链模式

**解决的问题**：让多个处理器按顺序尝试处理请求，发送方不需要知道最终由谁处理。

```js
const handlers = [
	(request) => (request.role === 'admin' ? '进入管理台' : undefined),
	(request) => (request.role === 'member' ? '进入会员页' : undefined),
	() => '进入访客页'
];

function handleRequest(request) {
	for (const handler of handlers) {
		const result = handler(request);
		if (result !== undefined) return result;
	}
}
```

Axios 拦截器、表单校验流水线和中间件体系常体现责任链思想。
Koa 的洋葱模型还包含 `next()` 前后的双向控制，不能只用“责任链”概括其全部语义。

**代价**：处理顺序会影响结果；链过长时很难定位哪个处理器拦截了请求，
应提供清晰的命名、日志和顺序约定。

## 十、状态模式与状态机

**解决的问题**：同一个对象在不同状态下允许不同操作，避免到处判断状态字符串。

```js
const uploadTransitions = {
	idle: { start: 'uploading' },
	uploading: { success: 'success', fail: 'failed', cancel: 'cancelled' },
	failed: { retry: 'uploading', cancel: 'cancelled' },
	success: {},
	cancelled: {}
};

class UploadTask {
	constructor() {
		this.state = 'idle';
	}

	send(event) {
		const next = uploadTransitions[this.state]?.[event];
		if (!next) throw new Error(`状态 ${this.state} 不允许事件 ${event}`);
		this.state = next;
		return this.state;
	}
}
```

这是数据驱动的有限状态机，也体现了状态模式“行为随状态改变”的核心思想。
如果每个状态的行为很多，可以把状态拆成对象；状态较少时，转换表更直观。

**前端场景**：上传、支付、审批、播放器、复杂表单和请求生命周期。

**代价**：状态和事件组合会快速膨胀；必须明确非法转换、终态以及失败恢复路径。

## 十一、命令模式

**解决的问题**：把一次操作封装成对象，便于排队、记录、重放或撤销。

```js
function createSetTitleCommand(model, nextTitle) {
	const previousTitle = model.title;
	return {
		execute() {
			model.title = nextTitle;
		},
		undo() {
			model.title = previousTitle;
		}
	};
}

const model = { title: '旧标题' };
const command = createSetTitleCommand(model, '新标题');
command.execute();
command.undo();
```

**前端场景**：编辑器撤销/重做、快捷键映射、离线操作队列、批处理任务。

**代价**：每个动作都创建命令会增加对象和样板代码；只有需要操作历史或调度时才值得。

---

## 十二、迭代器模式

**解决的问题**：调用方通过统一协议遍历集合，而不依赖集合的内部结构。

```js
function range(start, end) {
	return {
		*[Symbol.iterator]() {
			for (let value = start; value <= end; value++) yield value;
		}
	};
}

[...range(2, 4)]; // [2, 3, 4]
```

JavaScript 的 `Array`、`Map`、`Set`、字符串和 Generator 都实现了可迭代协议。
迭代器适合惰性序列，但一次性迭代器被消费后不能自动重来，需要区分
“可迭代对象”和“迭代器对象”。

---

## 十三、依赖注入与控制反转（不是 GoF 模式）

**控制反转（IoC）**是原则：对象不再自己决定依赖怎么创建；
**依赖注入（DI）**是实现手段：从构造函数、参数或容器把依赖传进来。

```js
class OrderService {
	constructor({ orderApi, logger }) {
		this.orderApi = orderApi;
		this.logger = logger;
	}

	async getOrder(id) {
		this.logger.info('load order', { id });
		return this.orderApi.get(id);
	}
}
```

NestJS 容器根据 provider token 创建对象并完成构造器注入；测试时可以换成 fake API。
工厂关注“如何创建一个对象”，DI 关注“对象从哪里获得依赖”，两者可以一起使用。

**代价**：容器和装饰器可能隐藏真实创建链；token 配置错误通常到启动或运行时才暴露。
小型纯函数不需要引入容器，直接传参数最清楚。

## 十四、其他模式知道用途即可

| 模式         | 适合记住的用途             | 边界提醒                                       |
| ------------ | -------------------------- | ---------------------------------------------- |
| **建造者**   | 分步骤组装复杂对象         | 链式 API 不一定就是建造者                      |
| **模板方法** | 父类固定流程，子类覆盖步骤 | React 生命周期只能算相似思想，不是必须这样归类 |
| **享元**     | 共享大量相同的细粒度对象   | 虚拟列表主要是窗口化和复用，不应直接等同于享元 |
| **备忘录**   | 保存并恢复快照             | 大状态快照要考虑内存和结构共享                 |
| **中介者**   | 集中协调多个对象的交互     | 中介者容易膨胀成上帝对象                       |
| **桥接**     | 抽象与实现可以独立变化     | 只有一个变化维度时通常不需要                   |
| **抽象工厂** | 创建一组彼此匹配的对象     | 产品族很少变化时可能只是额外间接层             |
| **原型**     | 从已有对象复制出新对象     | 浅拷贝、原型链继承与 GoF 原型模式不要混为一谈  |
| **解释器**   | 为小型语言定义语法和求值   | 复杂语言应使用成熟 parser，不宜手写分支堆叠    |
| **访问者**   | 不改节点类就增加一组操作   | 增加节点类型成本高，适合节点结构稳定的 AST     |

## 容易混淆的模式

| 对比               | 判断问题                                          |
| ------------------ | ------------------------------------------------- |
| 工厂 vs DI         | 是在封装创建过程，还是把依赖交给外部提供？        |
| 适配器 vs 外观     | 是转换不兼容接口，还是简化多个子系统？            |
| 代理 vs 装饰器     | 是控制访问，还是叠加职责？                        |
| 策略 vs 状态       | 是调用方选择算法，还是对象行为随内部状态迁移？    |
| 观察者 vs 发布订阅 | Subject 是否直接持有 Observer？是否存在事件中心？ |

真实实现可能同时满足两种意图。分类是沟通工具，不是代码验明正身的规则。

## 面试回答方式

建议只准备 2 ～ 3 个**确实用过**的模式，按下面顺序回答：

1. 原来遇到什么变化或维护问题。
2. 最初的朴素实现为什么开始变难维护。
3. 抽象后职责和数据流怎么变化。
4. 这个模式带来了什么新成本，什么时候不会用它。

例如不同产品类型的计算规则可以作为策略或工厂的候选场景，
但只有代码确实把变化收敛到策略表或创建入口时才形成对应模式；
如果实际仍是集中式条件分支，应先判断变化是否稳定，再决定是否抽象。

成熟的结论不是“我熟悉 23 种模式”，而是：
**先写清楚的朴素实现，等变化方向稳定后再抽象，并能说出抽象的代价。**
