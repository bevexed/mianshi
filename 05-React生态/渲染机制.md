# React 渲染机制

> 原 `虚拟DOM的key.md` 已并入本篇。

## 虚拟 DOM

虚拟 DOM 的本质是**对象**——用 JS 对象描述真实 DOM 结构。

**它的价值不是"快"**（直接操作 DOM 往往更快），而是：

1. **让 UI 变成状态的函数**，开发者不用手动操作 DOM
2. **批量化和跨平台**——同一套描述可以渲染到 DOM、Native、Canvas

---

## 组件为什么会重新渲染

常见原因有：

1. **自身 state 变化**（setState / useReducer dispatch）
2. **父组件重新渲染**（默认级联，**与 props 是否变化无关**）
3. **订阅的 Context value 变化**
4. **订阅的外部 store 变化**（例如 `useSyncExternalStore`、Redux、Zustand）

---

## 父组件 render，子组件一定 render 吗

**默认会重新调用子组件，但有以下常见边界：**

**1. 子组件被 `React.memo` 包裹**且 props 浅比较相等

**2. 子 element 作为稳定的 `children` / prop 传入**——
如果包装组件更新时收到的 element 引用没变，React 可以复用该 element。

```jsx
// Wrapper 重渲染时，Heavy 不会重渲染（element 引用没变）
<Wrapper>
	<Heavy />
</Wrapper>
```

这是组件组合带来的 element 复用，不等于为任意子组件自动加了 `memo`。

> 关联：[Next.js/RSC 与水合.md](Next.js/RSC与水合.md)

## React.memo 的原理与失效

- **原理**：对 props 做**浅比较**，相等就复用上次的渲染结果
- **失效的常见原因**：
  - props 里有每次都新建的对象/数组/内联函数 → 浅比较必然不等
  - props 里有 `children`（JSX 每次都是新对象）
  - **组件内部订阅了 Context，Context 变了照样重渲染**（memo 管不了）
- 第二个参数可以自定义比较函数，
  但**深比较的成本可能超过重渲染本身**

## key 的作用

key 是**追踪列表中哪些元素被添加、修改、移除的辅助标志**。
它让 diff 时能识别「这是同一个节点」，
从而只替换真正变化的元素，而不是整块重建。

### 为什么不能用 index

用 index 时，**列表增删或排序后，同一个 index 对应的数据变了**，
React 会认为节点没变而只更新内容 → 导致：

- **组件内部 state 错位**（比如输入框的值跟错了行）
- 非受控组件的 DOM 状态残留
- 动画/焦点错乱

**经典复现**：一个带输入框的列表，在头部插入一项，
用 index 做 key 会导致所有输入框的值往下错一位。

**什么时候可以用 index**：
列表纯静态、不排序不增删、且项内无状态。

### key 的另一个用途：强制重新挂载

```jsx
<Form key={userId} /> // userId 变化时整个 Form 重新挂载，state 全部重置
```

这是 React 官方推荐的「props 变化时重置 state」的做法，
比在 useEffect 里手动重置干净得多。

这适合“实体身份已变，整棵子树应视为新实体”的场景，
不要用随机 `key` 强制每次重建。

---

## Diff 算法的三个策略

React 把 O(n³) 的树 diff 降到 O(n)，靠三个假设：

1. **同层比较**——只比较同一层级的节点，
   跨层级移动会被当成「删除 + 新建」
2. **类型不同直接重建**——`<div>` 变 `<span>`，整棵子树重建，
   不做细粒度对比
3. **同层列表用 key 标识**——有 key 才能识别移动，
   没有 key 只能按顺序逐个比

**实践含义**：不要做跨层级的 DOM 结构变化
（比如条件渲染时把节点从一层挪到另一层），代价是整棵子树重建。
