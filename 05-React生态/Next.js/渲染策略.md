# Next.js 渲染与缓存策略

> 本文以 App Router 为主。Next.js 的缓存语义跨大版本变化较大，
> 回答时应先说明项目版本与是否启用 Next.js 16 的 `cacheComponents`。

## 先分清概念

| 概念                   | 发生时机                                  | 适合场景                                |
| ---------------------- | ----------------------------------------- | --------------------------------------- |
| **CSR**                | 浏览器加载 JS 后获取数据并渲染            | 强交互、无 SEO 要求的局部界面           |
| **静态预渲染**         | 构建或后台重新生成时输出 HTML/RSC Payload | 所有用户相同的内容                      |
| **动态渲染**           | 请求到达服务端时执行                      | 依赖 cookie、header、实时数据或用户身份 |
| **ISR / revalidation** | 复用已生成结果，按时间或事件重新验证      | 允许短暂陈旧的公共内容                  |
| **Streaming**          | 服务端逐段发送已就绪的 UI                 | 页面各区域数据耗时差异大                |

Streaming 是传输/展示方式，不是和静态/动态渲染互斥的第五种模式。

## 选型示例

| 页面                   | 起点策略                    | 理由                       |
| ---------------------- | --------------------------- | -------------------------- |
| 产品介绍页             | 静态预渲染                  | 内容公共、变更少、需要 SEO |
| 可由内容系统更新的列表 | 带 revalidation 的预渲染    | 能容忍可控的陈旧窗口       |
| 账户中心               | 动态渲染                    | 内容依赖当前身份           |
| 报表编辑器             | 服务端输出外壳 + 客户端交互 | 首屏可见与高交互需求并存   |

选择不是整个应用一刀切。App Router 可以把服务端和客户端组件组合，
Next.js 16 Cache Components 还允许在同一路由中混合预渲染外壳、显式缓存区域和请求时动态区域。

## Streaming 与 Suspense

```jsx
export default function Page() {
	return (
		<>
			<Header />
			<Suspense fallback={<Skeleton />}>
				<SlowDataSection />
			</Suspense>
		</>
	);
}
```

`loading.tsx` 会为对应路由段建立加载边界。Streaming 能让外壳先到达，
但不会自动消除慢查询；仍需要避免服务端数据瀑布和过粗的 Suspense 边界。

## App Router 与 Pages Router

| 维度       | Pages Router                                         | App Router                                 |
| ---------- | ---------------------------------------------------- | ------------------------------------------ |
| 数据获取   | 主要是页面级 `getServerSideProps` / `getStaticProps` | Server Component 中直接读数据              |
| 布局       | `_app` 和手动布局模式                                | 嵌套 `layout` 约定                         |
| 服务端组件 | 不支持 App Router 的 RSC 模型                        | 默认为 Server Component                    |
| 加载/错误  | 通常手动组织                                         | `loading`、`error`、`not-found` 等文件约定 |
| 迁移成本   | 存量稳定，仍被支持                                   | 新心智模型与缓存边界需重新学习             |

## Next.js 16 缓存边界

### 未启用 Cache Components

- `fetch` 默认不跨请求缓存；用 `cache: 'force-cache'` 显式缓存。
- 可用 `next.revalidate`、`next.tags`、`revalidatePath` 和 `revalidateTag`
  建立时间或事件失效策略。
- 同一渲染过程中的请求去重，不等于结果已跨用户持久缓存。

### 启用 `cacheComponents`

- 缓存是显式 opt-in，用 `'use cache'` 为页面、组件或函数建立缓存边界。
- 请求时 API 与非缓存工作保持动态，可在 Suspense 边界中流式输出。
- 不要把旧版本“四层缓存”的口诀不加区分地套到 Cache Components 模型。

## 回答时的检查项

1. 先问数据是否因用户、请求或时间而变。
2. 说明允许多久的陈旧窗口，以及用时间还是业务事件失效。
3. 说明负载、TTFB、SEO、客户端 JS 和操作复杂度的取舍。
4. 最后落到项目确切版本与官方文档，不依赖跨版本默认值。
