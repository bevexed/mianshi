# Next.js 渲染与缓存策略

> 本文以 App Router 为主。Next.js 的缓存语义跨大版本变化较大，
> 回答时应先说明项目版本与是否启用 Next.js 16 的 `cacheComponents`。

## 先分清概念

| 概念                   | 发生时机                                  | 适合场景                                |
| ---------------------- | ----------------------------------------- | --------------------------------------- |
| **CSR**                | 浏览器加载 JS 后获取数据并渲染            | 强交互、无 SEO 要求的局部界面           |
| **静态预渲染**         | 构建或后台重新生成时输出 HTML/RSC Payload | 所有用户相同的内容                      |
| **动态渲染**           | 请求到达服务端时执行                      | 依赖 cookie、header、实时数据或用户身份 |
| **ISR / revalidation** | 复用已生成结果，按时间或事件重新验证      | 允许短暂陈旧的公共内容                  |
| **Streaming**          | 服务端逐段发送已就绪的 UI                 | 页面各区域数据耗时差异大                |

Streaming 是传输/展示方式，不是和静态/动态渲染互斥的第五种模式。

## 选型示例

| 页面                   | 起点策略                    | 理由                       |
| ---------------------- | --------------------------- | -------------------------- |
| 产品介绍页             | 静态预渲染                  | 内容公共、变更少、需要 SEO |
| 可由内容系统更新的列表 | 带 revalidation 的预渲染    | 能容忍可控的陈旧窗口       |
| 账户中心               | 动态渲染                    | 内容依赖当前身份           |
| 报表编辑器             | 服务端输出外壳 + 客户端交互 | 首屏可见与高交互需求并存   |

选择不是整个应用一刀切。App Router 可以把服务端和客户端组件组合，
Next.js 16 Cache Components 还允许在同一路由中混合预渲染外壳、显式缓存区域和请求时动态区域。

### 场景追问：SSR、CSR、SSG、ISR 有什么区别，怎么选？

**面试官：** 更新很少的官网、几分钟更新一次的新闻、登录后台，分别选什么？SSR 一定更快吗？

**口语参考答案：**

> SSR 在请求时生成页面，CSR 主要在浏览器执行脚本获取数据和渲染，SSG 提前生成静态内容，ISR 在静态生成基础上按时间或事件重新验证。公共且少变的官网适合静态生成，允许短暂陈旧的新闻适合重新验证，后台则按身份动态获取数据并结合客户端交互。SSR 可能更早展示内容，但服务端查询慢、JS 多和水合重仍会拖慢体验，需结合 TTFB、LCP 和交互成本分析。App Router 还要区分组件边界和缓存策略。

**追问与易错点：** 后台也能结合服务端渲染；CSR、SSR 与 Server/Client Component 不一一对应。Next.js 缓存默认值应按项目版本确认。

## Streaming 与 Suspense

```jsx
export default function Page() {
	return (
		<>
			<Header />
			<Suspense fallback={<Skeleton />}>
				<SlowDataSection />
			</Suspense>
		</>
	);
}
```

`loading.tsx` 会为对应路由段建立加载边界。Streaming 能让外壳先到达，
但不会自动消除慢查询；仍需要避免服务端数据瀑布和过粗的 Suspense 边界。

## App Router 与 Pages Router

| 维度       | Pages Router                                         | App Router                                 |
| ---------- | ---------------------------------------------------- | ------------------------------------------ |
| 数据获取   | 主要是页面级 `getServerSideProps` / `getStaticProps` | Server Component 中直接读数据              |
| 布局       | `_app` 和手动布局模式                                | 嵌套 `layout` 约定                         |
| 服务端组件 | 不支持 App Router 的 RSC 模型                        | 默认为 Server Component                    |
| 加载/错误  | 通常手动组织                                         | `loading`、`error`、`not-found` 等文件约定 |
| 迁移成本   | 存量稳定，仍被支持                                   | 新心智模型与缓存边界需重新学习             |

## Next.js 16 缓存边界

### 未启用 Cache Components

- `fetch` 默认不跨请求缓存；用 `cache: 'force-cache'` 显式缓存。
- 可用 `next.revalidate`、`next.tags`、`revalidatePath` 和 `revalidateTag`
  建立时间或事件失效策略。
- 同一渲染过程中的请求去重，不等于结果已跨用户持久缓存。

### 启用 `cacheComponents`

- 缓存是显式 opt-in，用 `'use cache'` 为页面、组件或函数建立缓存边界。
- 请求时 API 与非缓存工作保持动态，可在 Suspense 边界中流式输出。
- 不要把旧版本“四层缓存”的口诀不加区分地套到 Cache Components 模型。

### 场景追问：数据库更新了，Next.js 页面为什么还是旧数据？

**面试官：** 关注人数从一百更新到一百零一，页面没变。revalidatePath、revalidateTag 和 router.refresh 各解决什么？

**口语参考答案：**

> 我会沿响应检查是 NestJS 已返回旧值、Next.js 服务端缓存未失效，还是客户端路由和本地状态没更新。revalidatePath 针对路径，revalidateTag 针对事先打标签的数据，可以影响多个页面；router.refresh 重新获取当前路由的 RSC 结果，但不会自动使服务端数据缓存失效。关注成功后要同步按钮和人数的状态，同时按数据来源处理缓存，再刷新需要的服务端内容。接口写库成功和页面拿到新数据，是两个需要衔接的动作。

**追问与易错点：** Next.js 16 中 `revalidateTag(tag, 'max')` 采用 stale-while-revalidate，允许暂时返回旧值。需要“写后立即读到新值”的 Server Action 可用 `updateTag`；外部回调和 Route Handler 需按官方 API 选择立即过期策略。还要区分是否启用 `cacheComponents`，不能沿用旧版默认缓存结论。

参考：[Next.js revalidateTag](https://nextjs.org/docs/app/api-reference/functions/revalidateTag)、[updateTag](https://nextjs.org/docs/app/api-reference/functions/updateTag)、[useRouter](https://nextjs.org/docs/app/api-reference/functions/use-router)。

## 回答时的检查项

1. 先问数据是否因用户、请求或时间而变。
2. 说明允许多久的陈旧窗口，以及用时间还是业务事件失效。
3. 说明负载、TTFB、SEO、客户端 JS 和操作复杂度的取舍。
4. 最后落到项目确切版本与官方文档，不依赖跨版本默认值。
