# Next.js 渲染策略

## 五种渲染方式

| 策略 | 何时生成 HTML | 适用 | 缺点 |
|---|---|---|---|
| **CSR** | 浏览器端 | 强交互、SEO 无所谓的后台 | 首屏白屏、SEO 差 |
| **SSR** | **每次请求**时在服务端 | 内容随用户/请求变化 | 服务器压力大、TTFB 受后端影响 |
| **SSG** | **构建时** | 内容不变、人人相同 | 内容更新要重新构建 |
| **ISR** | 构建时 + **按需重新生成** | 内容偶尔变，能容忍短暂陈旧 | 有陈旧窗口 |
| **Streaming** | 服务端**分块**逐步发送 | 页面有快有慢的部分 | 需要 Suspense 配合 |

---

## 怎么选（按你的项目举例）

| 页面 | 策略 | 理由 |
|---|---|---|
| 官网产品介绍页 | **SSG** | 内容固定，人人相同，要 SEO |
| 产品套餐列表 | **ISR** | 运营后台改了，几分钟后生效可接受 |
| 需要登录态的页面 | **SSR** | 内容随用户变 |
| 选购配置页的实时价格计算 | **CSR** | 强交互，且不需要 SEO |

**答题要点**：
> App Router 的优势是**可以按路由甚至按组件粒度选择**，
> 而不是整个应用一刀切。官网这个项目就同时用到了多种。

## ISR 怎么配

```jsx
// 基于时间的重新验证
export const revalidate = 60          // 60 秒后下一个请求触发重新生成

// 按需重新验证（推荐，运营改了立刻生效）
import { revalidatePath, revalidateTag } from 'next/cache'
revalidatePath('/products')
revalidateTag('products')
```

**ISR 的工作方式（stale-while-revalidate）**：
过期后的第一个请求**仍然拿到旧页面**，
同时后台触发重新生成，**下一个**请求才拿到新的。
所以它不是"立刻更新"——这点常被追问。

## Streaming 与 Suspense

```jsx
export default function Page() {
  return (
    <>
      <Header />                        {/* 立刻发给浏览器 */}
      <Suspense fallback={<Skeleton />}>
        <SlowDataSection />             {/* 数据好了再补发 */}
      </Suspense>
    </>
  )
}
```

**价值**：不用等最慢的数据就绪才发首字节，
TTFB 和 FCP 都能显著改善。

**loading.tsx** 本质就是给整个路由段自动包一层 Suspense。

## App Router 比 Pages Router 好在哪

| | Pages Router | App Router |
|---|---|---|
| 数据获取 | `getServerSideProps` / `getStaticProps`，**只能在页面级** | 任意 Server Component 里直接 `await` |
| 渲染粒度 | 整页 SSR 或整页 SSG | **组件级**混合 |
| 布局 | `_app.js` 全局，切换路由会重新渲染 | **嵌套布局**，切换时布局不重新渲染 |
| Bundle | 所有组件都进客户端 | **Server Component 不进 bundle** |
| Loading/Error | 手写 | `loading.tsx` / `error.tsx` 约定 |
| 流式渲染 | 有限支持 | 原生支持 |

### 但要有立场地说出代价

> App Router 的复杂度也更高：
> `'use client'` 的边界传染很容易踩、
> 水合错误排查困难、缓存行为在版本之间变化比较大。
>
> 我的判断是：官网这种「大部分静态 + 少量强交互」的场景是正收益。
> 但如果是一个纯后台管理系统，全是登录后的动态页面、不需要 SEO，
> 我会更倾向于普通 SPA——App Router 的复杂度换不来价值。

**「什么情况下我不会用它」是这题的加分句。**

## Next.js 的缓存层（v15 有重大变化）

Next.js 有四层缓存，**面试容易问混**：

1. **Request Memoization**——单次渲染中相同的 fetch 去重
2. **Data Cache**——跨请求的 fetch 结果缓存
3. **Full Route Cache**——整个路由的渲染结果
4. **Router Cache**——客户端的路由缓存

**⚠️ 版本差异**：Next.js 14 默认激进缓存（`fetch` 默认 `force-cache`），
**Next.js 15 起默认不缓存**（`no-store`），需要显式 opt-in。
这个变化坑了很多人，**能说出来说明你跟着版本走**。

【需确认】你用的 Next.js 16，默认行为按 15 之后的算。
