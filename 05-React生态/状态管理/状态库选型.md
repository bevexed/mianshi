# 状态库选型：Zustand / Redux / Mobx / Context

> 前置：[服务端状态与客户端状态.md](服务端状态与客户端状态.md)
> 原 `Redux管理状态的机制.md` 的机制部分已并入本篇。

## 为什么后来用 Zustand

### Redux Toolkit 的取舍

- 需要 slice、store 和 Provider 等明确结构，小型局部状态可能不值得引入。
- action / reducer / dispatch 带来了间接层，也带来可追踪的变更和一致规范。
- `useSelector` 按选择结果订阅；返回每次新建的对象时，
  需要稳定 selector 或选择合适的比较策略，而不是简化成“Redux 会全量重渲染”。
- Redux 的核心价值是大型应用的**可预测状态流转**
  （时间旅行、中间件、严格的单向数据流）。
  一旦服务端状态被 react-query 拿走，
  剩下的客户端状态往往简单到用不上这套重型机制

### Zustand 的优势

- API 极简，一个 `create` 就完事，**不需要 Provider**
- 天然支持 **selector 细粒度订阅**：`useStore(s => s.count)`，
  只有 count 变才重渲染
- 运行时轻量，API 面积小（确切体积随版本和构建方式变化）
- 可以**在 React 外部读写** store（`store.getState()`），
  在工具函数、请求拦截器里很方便

### 但要能说出 Zustand 的代价（不然像背通稿）

- 调试体验不如 Redux DevTools 成熟（虽然有中间件）
- **没有强约束，规模变大后容易出现随意写入**。
  需要自行约定 slice/领域边界、action 命名、持久化与调试策略

## Redux 的核心机制（仍要会）

**原理**：发布订阅模式。

```
store
 ├─ getState()          读取状态
 ├─ dispatch(action)    派发动作
 └─ subscribe(listener) 订阅变化

action   = { type, payload }        描述"发生了什么"
reducer  = (state, action) => next  纯函数，描述"状态怎么变"
```

**三大原则**：

1. 单一数据源（一个 store）
2. state 只读（只能通过 dispatch 修改）
3. 用纯函数（reducer）来修改

**生态**：

- `react-redux`——连接 React
- `redux-thunk` / `redux-saga`——处理异步
- `redux devtools`——时间旅行调试
- **Redux Toolkit (RTK)**——官方推荐，
  内置 immer（可以"直接改"）、简化 slice 定义

## Mobx

- **响应式 / 可变数据模型**，用 Proxy 追踪依赖，自动精确更新
- **优点**：写起来最像"普通 JS"，不需要手动优化重渲染
- **缺点**：
  - 可变数据 + 隐式依赖追踪，debug 时"数据从哪变的"不直观
  - 可变对象与隐式跟踪需要额外约束，否则状态边界容易模糊

**诚实答法**：

> 我用过但不是现在的首选。
> 它在「大量细粒度更新的复杂表单/表格」这类场景仍有优势，
> 因为不需要手动 memo 就能做到精确更新。

## Context 能替代状态管理库吗

**能处理简单低频共享状态，但不等价于具备 selector、中间件和调试能力的 store。**

**1. 无法细粒度订阅**——Context value 变化时，
**所有消费该 Context 的组件都会重渲染**，
哪怕它只用了 value 里的一个字段。

**2. 能力边界**——Context 本身不提供 action 日志、中间件、持久化、
开发者工具或细粒度 selector。可以拆分 Context，但要评估可维护性。

> **Context 的正确定位是「依赖注入」，不是「状态管理」。**
> 适合传很少变化的东西——主题、语言、当前用户、配置。

### 常见的 Context 性能坑

```jsx
// ❌ 每次渲染都是新对象，所有消费者重渲染
<Ctx.Provider value={{ user, setUser }}>

// ✅ 用 useMemo 稳定引用
const value = useMemo(() => ({ user, setUser }), [user])
<Ctx.Provider value={value}>
```

## Zustand 在 Next.js（SSR）里的坑

模块级单例 store 在服务端是**跨请求共享**的——
Node 进程常驻，**A 用户的数据会串到 B 用户**。

**正确做法**：每个请求创建新的 store 实例，
用 Provider 传下去；客户端则复用同一个实例。

```js
let clientStore;
const getStore = () => {
	if (typeof window === 'undefined') return createStore(); // 服务端：每次新建
	return (clientStore ??= createStore()); // 客户端：单例
};
```

**react-query 的 QueryClient 也有完全一样的问题。**

## 选型决策树

```
是服务端数据吗？
├─ 是 → react-query / SWR
└─ 否 ↓
   需要跨组件共享吗？
   ├─ 否 → useState / useReducer
   └─ 是 ↓
      变化频繁吗？
      ├─ 否（主题/语言/用户信息）→ Context
      └─ 是 ↓
         项目规模大 + 需要严格约束和调试能力？
         ├─ 是 → Redux Toolkit
         └─ 否 → Zustand
```
