# Server State vs Client State

> **这是整个状态管理话题的地基，答清楚了后面所有题都好答。**

## 核心区别

|              | Client State                             | Server State                       |
| ------------ | ---------------------------------------- | ---------------------------------- |
| 归属         | 前端**拥有**它                           | 前端只是**缓存**了远端的一份副本   |
| 例子         | 弹窗开关、表单草稿、当前选中的 tab、主题 | 用户列表、订单详情、商品数据       |
| 是否会过期   | 不会                                     | **会**——别人改了，你手里的就是旧的 |
| 是否需要同步 | 不需要                                   | 需要重新请求、后台刷新、失效       |
| 是否异步     | 通常同步                                 | 异步，有 loading / error 状态      |
| 归谁管       | Zustand / useState / Context             | **react-query / SWR**              |

---

## 一句话结论

> 把服务端数据塞进 Redux/Zustand，
> 就等于要自己实现缓存、失效、重试、去重、竞态处理——
> **那是在重写一遍 react-query。**

---

## 这是过去几年前端状态管理最大的认知变化

以前 Redux store 里 **70% 的代码是在管接口数据**——
`FETCH_USERS_REQUEST` / `SUCCESS` / `FAILURE` 三个 action，
loading 和 error 各存一份。

现在这部分被 react-query 拿走了，
**剩下的真正的客户端状态很少**，
所以 Zustand 这种轻量方案就够用了。

**能讲出这段演进，比会用十个库更有说服力。**

---

## 判断一份状态属于哪类

问三个问题：

1. **这份数据的权威来源在哪？** 在服务端 → server state
2. **别人改了会不会影响我？** 会 → server state
3. **刷新页面后需要保留吗？** 需要且来自服务端 → server state；
   需要但纯本地（如主题）→ client state + 持久化

### 灰色地带

- **表单草稿**——虽然最终要提交到服务端，
  但编辑期间的权威来源是前端 → client state
- **购物车**——看实现。存服务端就是 server state，
  纯本地就是 client state（例如尚未提交的选购配置）

---

## 一个通用原则

> **能算就别存。**
>
> 价格由套餐、年限、加购项算出来——两边都不存。
> 一旦存了，套餐变了、年限变了都要记得同步，
> 迟早会漏掉一条路径。

这条原则和「同一份数据只能有一个权威来源」是一回事，
它适用于任何派生状态：能从当前权威状态可靠计算的值，优先在读取时计算或使用带依赖的 memo，而不是维护第二份可漂移状态。
