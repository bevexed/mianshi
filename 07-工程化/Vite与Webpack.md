# Vite 与 Webpack

> 构建链变化很快。当前 Vite 官方文档以 Rolldown/Oxc 工具链为主；
> 阅读旧版本资料时，会看到开发预构建使用 esbuild、生产使用 Rollup 的旧架构。
> 回答具体项目时应以锁定版本为准。

## Vite 开发体验为什么通常较快

- 开发服务器可按浏览器请求转换应用模块，无需先输出完整生产 bundle。
- 第三方依赖会预处理，目标包括统一模块格式、减少过多细碎请求和建立可缓存结果。
- HMR 沿模块图更新受影响的边界，不需每次重做完整构建。
- 浏览器原生 ESM 与按需转换减少了冷启动工作；
  但超大模块图也可能遭遇过多请求或 transform 瓶颈。

“Vite 启动时间与项目规模无关”是过度结论。
插件、别名解析、依赖数量、类型检查和框架编译都会影响启动与 HMR。

## 当前 Vite 的构建链

Vite 最新官方指南将生产构建描述为 **Rolldown** 驱动，
并与 Oxc 协同完成解析、转换和压缩等工作。
因此不要再把“Vite 生产永远是 Rollup”或“为什么生产不用 esbuild”
当作不带版本的固定题。

仍然有价值的底层问题是：

- 开发与生产对反馈速度、兼容性、代码分割和产物稳定性的要求不同。
- 插件生态、框架集成和存量配置兼容性，往往比单次基准成绩更重要。
- 生产构建要用真实项目度量耗时、chunk 图、体积、sourcemap 与运行兼容性。

## Webpack 构建流程

```text
1. 读取并合并配置，创建 Compiler
2. 从 entry 出发解析模块与依赖
3. 使用 loader 将非 JavaScript 或新语法转换成可处理模块
4. 生成模块图并根据动态 import、入口和优化规则划分 chunk
5. 代码生成和优化，得到 assets
6. 通过输出文件系统写入或交给 dev server
```

### Loader 与 Plugin

- **Loader** 是模块转换管道。配置为 `use: ['style-loader', 'css-loader']`
  时，常规 normal loader 从右到左执行；还有 pitch 阶段，不应只死记一句顺序。
- **Plugin** 订阅 compiler/compilation 的 hooks，可在解析、分块、优化、
  资产生成等生命周期扩展行为。

## 何时仍选 Webpack

- 存量大型项目已有稳定 loader/plugin 与部署链，迁移收益不足。
- 依赖 Webpack 特有或已充分验证的集成，例如某些 Module Federation 架构。
- 团队对现有调试、缓存、构建分析和事故恢复路径更熟悉。

也可评估 Rspack 等兼容 Webpack 生态的方案，但“配置兼容”不等于
所有 loader、plugin 和运行行为零成本迁移，必须用实际项目验证。

## 选型方法

1. 列出必需能力：框架、SSR、浏览器范围、联邦、特殊资产。
2. 用真实仓库度量冷启动、HMR p95、生产构建、峰值内存和产物差异。
3. 验证测试、sourcemap、错误监控、长缓存和回滚。
4. 把迁移成本、插件风险和团队学习成本纳入决策，不只看 demo 启动时间。
