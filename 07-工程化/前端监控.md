# 前端监控体系

> 监控系统要完成“采集 → 清洗 → 聚合 → 告警 → 定位 → 复盘”闭环，
> 接入 SDK 只是第一步。

## 监控三大类

| 类型         | 监控什么                                        | 手段                                           |
| ------------ | ----------------------------------------------- | ---------------------------------------------- |
| **错误监控** | JS 异常、Promise 未捕获、资源加载失败、接口错误 | `window.onerror`、`unhandledrejection`、拦截器 |
| **性能监控** | Core Web Vitals、接口耗时、白屏时间             | `PerformanceObserver`、`web-vitals` 库         |
| **行为监控** | PV/UV、点击、路由变化、用户轨迹                 | 埋点、录屏                                     |

## 错误怎么采集

```js
// 1. JS 运行时错误
window.addEventListener('error', e => { ... })

// 2. 资源加载错误（注意：不冒泡，必须用捕获阶段）
window.addEventListener('error', e => {
  if (e.target !== window) { /* 资源错误 */ }
}, true)   // ← 第三个参数 true

// 3. Promise 未捕获的 rejection
window.addEventListener('unhandledrejection', e => { ... })

// 4. React 组件错误
class ErrorBoundary extends React.Component {
  static getDerivedStateFromError(e) { ... }
  componentDidCatch(error, info) { report(error, info) }
}
```

**⚠️ 关键细节**：

- 资源加载错误**不冒泡**，必须在捕获阶段监听
- **ErrorBoundary 捕获不到**：事件处理函数、异步代码、SSR、
  以及它自己抛的错——这些要靠 `window.onerror` 兜底

## `Script error.` 是怎么回事

跨域脚本抛出的错误，浏览器出于安全策略**不暴露详情**，
只给一个 `Script error.`，没有行号没有堆栈。

**解决**：

1. 脚本标签加 `crossorigin="anonymous"`
2. CDN 响应头配置 `Access-Control-Allow-Origin`

**这是接入 CDN 后必踩的坑**，也是监控接入的第一个拦路虎。

## 错误分组（fingerprint）

- Sentry 按 **fingerprint** 分组，
  默认由异常类型 + stacktrace 的关键帧计算
- **常见问题：动态信息进了错误消息**
  ```js
  throw new Error(`用户 ${userId} 不存在`); // ❌ 每个用户一个 issue
  throw new Error('用户不存在'); // ✅ 用 extra 带 userId
  ```
  当分组算法需要借助 message（例如缺少有效栈）时，
  动态值可能导致过度分组；具体结果仍取决于平台的分组算法
- 解决：`beforeSend` 归一化 message，或手动指定 `fingerprint`

## 上报策略

### 采样

```js
Sentry.init({
	sampleRate: 1.0, // 示例值：应按错误量、严重度和成本调整
	tracesSampleRate: 0.1 // 示例值：应用环境和采样函数实现更精细策略
});
```

### 过滤已知噪音

```js
beforeSend(event, hint) {
  // 只在已用数据证明是无行动价值的噪音时过滤，
  // 避免按宽泛字符串隐藏真实故障。
  return scrubAndClassify(event, hint)
}
```

### 上报方式

- 页面卸载附近的小批量数据可用 `navigator.sendBeacon`，它不阻塞卸载；
  需意识到 payload 大小、请求方法/头和可观察响应的限制
- `fetch(url, { keepalive: true })` 可作为另一选项，也有体积和生命周期限制。
  高频事件应先聚合、批量、采样和限流，不要每次交互都单独发请求

## 性能数据怎么采

```js
import { onLCP, onINP, onCLS } from 'web-vitals';
onLCP((m) => report('LCP', m.value));
onINP((m) => report('INP', m.value));
onCLS((m) => report('CLS', m.value));
```

**为什么用 web-vitals 库而不是自己写 PerformanceObserver**：
指标定义有很多边界情况（LCP 要在用户首次交互后停止记录、
CLS 要按会话窗口聚合），自己实现很难和 Chrome 的口径一致。

> 指标定义见 [08-性能优化/CoreWebVitals 指标.md](../08-性能优化/CoreWebVitals指标.md)

## 隐私

- **默认不上报密码、token、身份证件、完整请求体等敏感数据**；
  手机号、地址等个人信息只在有合法依据、明确用途和最小化处理后使用
- **两侧都做清洗**：
  - SDK 侧 `beforeSend` 过滤
  - **服务端（Relay）侧配置 PII 清洗规则**作为兜底
    前端可能有遗漏或老版本未更新，服务端清洗是最后一道防线。
    还应定义保留期、访问控制、删除流程和供应商数据边界。

## 有了监控之后怎么用

接入后至少要有：

1. 按版本、环境、路由和用户范围建立告警，避免只看绝对数。
2. 发版标记与前后对比，严重回归进入自动或人工回滚流程。
3. 为 issue 设置负责人、严重度、SLA 和处理状态，定期治理长尾噪音。
4. 故障修复后补回归测试或监控规则，形成闭环。
