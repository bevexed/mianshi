# 代码规范与提交卡口

> 规范的重点不只是配置工具，还包括反馈速度、存量迁移、
> CI 兜底、例外管理和团队共识。

## ESLint 为什么要放 pre-commit

- **反馈越早成本越低**——推上去被 CI 打回时，
  开发者的上下文可能已经切走
- **保证仓库里的代码始终是规范的**，
  而不是"CI 会帮我们发现"

### 但不能只有 pre-commit

`--no-verify` 能绕过，**CI 必须有同样的检查作为兜底**。

常用设计是**本地快反馈 + CI 可复现兜底**。
两层应尽量调用同一组项目脚本，避免规则漂移。

## husky 的原理

- Git 支持在 `.git/hooks/` 下放脚本，
  在特定时机（pre-commit、commit-msg 等）执行
- 但 **`.git` 目录不会被提交**，
  所以团队成员各自的 hook 无法同步
- **husky 的做法**：把 hook 脚本放在项目里的 `.husky/` 目录（可提交），
  然后通过 `git config core.hooksPath .husky` 把 Git 的 hook 目录指过去
- 常见配置是在 `prepare` 脚本中初始化 Husky；
  团队要用仓库锁定的包管理器安装，并在 CI 中不依赖本地 hook

## lint-staged 为什么快

- **只对 `git diff --cached` 里的文件跑检查**，
  而不是全量 lint 整个项目
- 大项目全量 lint 可能几十秒，
  改两个文件却要等全量——这是不可接受的

### 附带的关键好处

**不会因为存量代码的历史问题阻塞你这次提交**，
规范可以**渐进式落地**。

**这点对老项目接入规范特别重要**，
可以讲你是怎么在存量项目里推的：

> 老项目一开就是几千个 error，全量修不现实。
> 可以用 lint-staged 先只卡新改动的文件，
> 存量问题单独排期分批清理。
>
> **规范要能落地，就不能一上来要求完美。**

## ESLint 和 Prettier 怎么配合

- **职责分工**：ESLint 管**代码质量**（未使用变量、错误用法），
  Prettier 管**代码格式**（缩进、引号、换行）
- **冲突处理**：用 `eslint-config-prettier` 关掉与 Prettier 可能冲突的格式规则，
  让 Prettier 全权负责格式
- 不推荐用 `eslint-plugin-prettier` 把 Prettier 当 ESLint 规则跑——
  会拖慢 lint 速度且错误提示混乱

**ESLint 9 将 flat config（`eslint.config.js`）作为默认配置系统**。
`.eslintrc` 属于旧配置系统，维护存量仓库时应按实际 ESLint 版本和插件兼容性迁移，
不要只改文件名。

## commit message 规范有必要吗

**有，但价值不在"好看"**：

- 可以**自动生成 changelog**
- 按类型筛选提交
- 配合语义化版本自动发版

工具：`commitlint` + Conventional Commits
（`feat:` / `fix:` / `chore:` / `refactor:`）

如果接入 `commitlint`，应让本地 `commit-msg` 和 CI 使用同一规则，
并明确 revert、merge commit 和自动化 bot 的例外。Conventional Commits 的类型后使用英文冒号，
例如 `feat: 增加导出功能`。

## 单元测试推不动怎么办

**这题作为 leader 很可能被问。**

**诚实且有方法的答法**：

> B 端业务项目的单测覆盖率低是常态，
> 一上来要求 80% 覆盖率只会让大家写一堆无意义的测试来凑数。
>
> 可以**先划出值得测的部分**：
> 纯函数（价格计算、日期处理、数据转换）、自定义 hooks、关键工具函数。
> 这些投入产出比最高——逻辑密集、不依赖 UI、改动频繁。
>
> **性价比低的是 UI 组件的快照测试**——改个样式就挂，
> 维护成本高于收益。
>
> 可以从纯函数、关键业务规则、自定义 hooks/composables 和事故回归用例开始，
> 再根据缺陷风险扩展到组件与端到端流程。

**承认覆盖率低不丢人，假装很高才危险**——
一追问细节就露馅。

## 团队规范怎么达成共识

（管理向的追问）

> **可自动化的风格问题交给工具**。
> 缩进用几个空格、单引号还是双引号，
> 这类讨论是纯消耗——直接上 Prettier，
> 用默认配置，谁都别改。
>
> 真正需要讨论的是**架构层面的约定**——
> 目录结构、状态放哪、组件拆分粒度。
> 这些写进文档，在 code review 里执行。
