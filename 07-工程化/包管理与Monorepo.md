# 包管理与 Monorepo

## pnpm 相比 npm / yarn 的优势

- **硬链接 + 内容寻址存储**：
  同一个包在磁盘上**只存一份**，多项目共享，省空间省安装时间
- **非扁平的 node_modules**：严格遵守依赖声明，
  **不能引用没在 package.json 里声明的包**（幽灵依赖）

### 幽灵依赖为什么是问题

npm/yarn 的扁平化 `node_modules` 会把间接依赖也提升到顶层，
于是你 `import lodash` 能跑——即使你没装它。

**后果**：哪天上游依赖不再依赖 lodash 了，
你的代码突然就挂了，而且是在别人的机器/CI 上挂。
典型的"我本地能跑"。

**pnpm 用符号链接构造严格的依赖树，从根上杜绝这个。**

## 多个项目怎么共享代码

【需确认】你们有官网、工程汇后台、新云汇、微信 H5、mi8 多个前端项目，
**面试官很可能问「公共组件和工具怎么复用」**。

| 方案 | 优点 | 缺点 |
|---|---|---|
| **复制粘贴** | 零成本 | 改一处要改 N 遍，必然发散 |
| **npm 私有包** | 版本可控、边界清晰 | 改一次要发版升版本，链路长；调试要 link |
| **Monorepo** | 改了立刻生效，统一依赖版本和构建流程 | 仓库变大，需要工具链支持 |

**如果你们目前是复制粘贴，诚实说**：
> 目前公共组件是各项目各自维护，有重复。
> 这是我识别到但还没推动的事——
> 主要卡在几个项目的构建工具不统一（umi/max、Vite、Next.js），
> 直接上 monorepo 成本不低。

**能识别问题并说清阻碍，比假装做过更可信。**

## Monorepo 工具

- **pnpm workspace**——最轻量，只解决依赖管理和 link
- **Turborepo**——加上任务编排和**构建缓存**
  （改了 A 包只重新构建 A 和依赖 A 的）
- **Nx**——功能最全，但也最重

### Monorepo 的核心价值不是"代码放一起"

而是：
1. **原子提交**——改公共组件和改用它的业务代码在同一个 commit 里，
   不会出现中间不一致状态
2. **统一依赖版本**——避免 A 项目 React 17、B 项目 React 18
3. **增量构建缓存**——CI 只跑受影响的包

## 版本管理

- **语义化版本（SemVer）**：`主版本.次版本.修订号`
  - 主版本：破坏性变更
  - 次版本：新增功能，向后兼容
  - 修订号：bug 修复
- **changesets**——monorepo 下管理多包版本和 changelog 的主流方案
- **lockfile 必须提交**——保证团队和 CI 装到完全一样的依赖树

### `^` 和 `~` 的区别

```
^1.2.3  → 允许 1.x.x（不改主版本）
~1.2.3  → 允许 1.2.x（只改修订号）
1.2.3   → 锁死
```

**为什么有了 `^` 还需要 lockfile**：
`^` 是范围，不同时间安装可能装到不同版本；
lockfile 记录的是**实际安装的确切版本**。
