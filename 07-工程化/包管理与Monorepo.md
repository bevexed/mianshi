# 包管理与 Monorepo

## pnpm 相比 npm / yarn 的优势

- **内容寻址存储 + 链接布局**：
  相同包内容可在 store 中复用，再链接到项目，通常能节省磁盘和复制开销。
  并不保证所有环境和 peer dependency 组合在磁盘上永远只有一份
- **非扁平的 node_modules**：严格遵守依赖声明，
  **不能引用没在 package.json 里声明的包**（幽灵依赖）

### 幽灵依赖为什么是问题

npm/yarn 的扁平化 `node_modules` 会把间接依赖也提升到顶层，
于是你 `import lodash` 能跑——即使你没装它。

**后果**：哪天上游依赖不再依赖 lodash 了，
业务代码可能在上游依赖变更后突然失败，并且只在全新安装或 CI 中暴露。
典型的"我本地能跑"。

pnpm 的默认布局能更早暴露许多幽灵依赖，
但 hoist 配置、工具适配和工作区根依赖会改变可见性，
仍要靠 lint/检查和正确的 `package.json` 声明约束。

## 多个项目怎么共享代码

| 方案           | 优点                                 | 缺点                                    |
| -------------- | ------------------------------------ | --------------------------------------- |
| **复制粘贴**   | 零成本                               | 改一处要改 N 遍，必然发散               |
| **npm 私有包** | 版本可控、边界清晰                   | 改一次要发版升版本，链路长；调试要 link |
| **Monorepo**   | 改了立刻生效，统一依赖版本和构建流程 | 仓库变大，需要工具链支持                |

是否选 Monorepo 不取决于项目数量。只有当仓库间变更需要频繁原子协调、
工具链能统一，且团队愿意承担权限、CI 和发布编排成本时，它才可能是收益。

## Monorepo 工具

- **pnpm workspace**——最轻量，只解决依赖管理和 link
- **Turborepo**——加上任务编排和**构建缓存**
  （改了 A 包只重新构建 A 和依赖 A 的）
- **Nx**——功能最全，但也最重

### Monorepo 的核心价值不是"代码放一起"

而是：

1. **原子提交**——改公共组件和改用它的业务代码在同一个 commit 里，
   不会出现中间不一致状态
2. **统一依赖版本**——避免 A 项目 React 17、B 项目 React 18
3. **增量构建缓存**——CI 只跑受影响的包

## 版本管理

- **语义化版本（SemVer）**：`主版本.次版本.修订号`
  - 主版本：破坏性变更
  - 次版本：新增功能，向后兼容
  - 修订号：bug 修复
- **changesets**——monorepo 下管理多包版本和 changelog 的主流方案
- **lockfile 应提交**——记录解析结果并支持 CI 的 frozen install。
  操作系统、CPU、包管理器版本、registry 和 optional dependency 仍可能导致差异，
  所以还要锁定工具版本与构建环境

### `^` 和 `~` 的区别

```
^1.2.3  → 允许 1.x.x（不改主版本）
~1.2.3  → 允许 1.2.x（只改修订号）
1.2.3   → 锁死
```

**为什么有了 `^` 还需要 lockfile**：
`^` 是范围，不同时间安装可能装到不同版本；
lockfile 记录的是**实际安装的确切版本**。
