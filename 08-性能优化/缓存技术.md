# 缓存技术概览

缓存用空间、陈旧风险和失效复杂度换取更低延迟与源站负载。
回答任何缓存题，都要同时说清 **key、价值、TTL、失效、一致性和观测**。

## 前端常见层次

| 层次                           | 典型能力                                         | 主要风险                               |
| ------------------------------ | ------------------------------------------------ | -------------------------------------- |
| 浏览器 HTTP 缓存               | `Cache-Control`、ETag、304                       | 入口和 hash 资产策略不匹配导致旧版白屏 |
| Service Worker / Cache Storage | 可编程离线与请求策略                             | 双缓存、版本升级、过期与无限增长       |
| CDN/反向代理                   | 边缘共享缓存、减少回源                           | 缓存 key/Vary 错误导致串用户数据       |
| 客户端数据缓存                 | TanStack Query/SWR 等的 stale、retry、invalidate | 把缓存当成真相源、乐观更新回滚错误     |
| 应用/数据库缓存                | Redis、进程内缓存、查询结果                      | 穿透、击穿、雪崩、多副本不一致         |

## 读写策略

- **Cache Aside**：读先查缓存，miss 查数据库再回填；
  写数据库后删缓存。常用但仍存在并发窗口。
- **Read/Write Through**：应用只和缓存层交互，缓存层负责后端存储读写。
- **Write Behind**：先写缓存，异步批量落库，吞吐高但丢失/一致性风险更大。
- **stale-while-revalidate**：先返回可接受的旧值，后台更新，适合允许陈旧窗口的读多场景。

## 失效比写入更难

1. 用内容 hash 让不可变静态资产可长缓存，新内容换 URL。
2. 可变数据定义可容忍的 stale window，再决定 TTL 或事件失效。
3. 为 TTL 增加 jitter 避免大量 key 同时过期；热点 key 用请求合并/互斥回源防击穿。
4. 负面缓存/布隆过滤器可减少不存在 key 的穿透，但要处理误判、更新和攻击输入。

## 安全边界

- 共享缓存的 key 必须包含所有会影响响应的授权、语言、设备等维度，
  或直接将个性化响应标记为 private/no-store。
- 不要缓存密码、token 和无必要的完整个人数据。
- 缓存不能绕过授权；命中缓存后仍必须确保当前请求有权读取。
