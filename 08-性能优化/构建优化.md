# 构建优化

## 先区分两个目标

| 目标         | 关心指标                                | 主要手段                                       |
| ------------ | --------------------------------------- | ---------------------------------------------- |
| 构建过程更快 | 冷/热构建耗时、HMR、CPU/内存、CI 等待   | 缓存、缩小输入、并行任务编排、更合适的工具链   |
| 运行产物更好 | 初始 JS/CSS、chunk 数、长缓存、执行时间 | Tree Shaking、代码分割、去重、目标浏览器、压缩 |

构建更快不等于产物更快，两者必须分别度量。

## 构建耗时定位

1. 固定 Node.js、包管理器、lockfile、机器和缓存条件建立基线。
2. 区分 install、typecheck、lint、test、bundle、minify、sourcemap 和上传耗时。
3. 使用构建器 profiler/stats 查找慢 loader、plugin、transform 和大模块。
4. 分别测冷缓存与热缓存，防止只报好看的第二次结果。

## 常见优化

- 缩小解析范围：正确配置 include/exclude，不重复转换已符合目标的依赖。
- 用工具内建持久化缓存，并把配置、lockfile、环境和输入纳入缓存 key。
- 在 Monorepo 中只运行受影响任务，但要正确声明输入/输出，避免错误命中。
- 并行执行相互独立的任务，但不要让并行度超过 CI CPU/内存容量导致抢占。
- 把 typecheck 与纯 transpile 分开可改善反馈速度，但 CI 仍必须完成类型检查。

`DllPlugin` 和 HappyPack 是历史上的 Webpack 优化方案，
现代工具通常已有更完整的缓存、并行化或更快编译链。
存量项目可以继续维护，新项目不应把它们作为默认答案。

## 产物优化

- 通过 bundle visualizer/stats 先找到最大的首屏贡献者和重复模块。
- 保留 ESM 供打包器分析，正确标注 `sideEffects`，检查第三方包发布格式。
- 按使用时机和变更频率分包，少见重依赖用动态 import，避免一个巨型 vendor。
- 确认现代浏览器 target 与 legacy 需求，不对全部用户发送不必要 polyfill。
- minify 不等于保密。客户端代码不能包含密钥，不要依赖混淆建立安全边界。

## 回归防护

- CI 上报关键路由初始 chunk 和总产物 diff，阈值要允许经审查的例外。
- 不只比 raw 体积；同时比 gzip/brotli、请求时序和主线程执行成本。
- 构建优化后运行完整测试和 sourcemap 还原验证，防止代码转换导致运行回归。
