# Core Web Vitals 指标体系

> Core Web Vitals 是真实用户指标体系的核心部分。
> 阈值应在真实用户数据的第 75 百分位评估，并按移动/桌面与关键页面类型分组。

## 三个核心指标

| 指标    | 全称                      | 衡量什么                         | 好     | 需改进    | 差     |
| ------- | ------------------------- | -------------------------------- | ------ | --------- | ------ |
| **LCP** | Largest Contentful Paint  | **加载**：最大内容元素渲染完成   | ≤2.5s  | 2.5-4s    | >4s    |
| **INP** | Interaction to Next Paint | **响应**：交互到下一帧绘制       | ≤200ms | 200-500ms | >500ms |
| **CLS** | Cumulative Layout Shift   | **视觉稳定**：意外布局偏移累积分 | ≤0.1   | 0.1-0.25  | >0.25  |

### ⚠️ 关键更新

**INP 在 2024 年 3 月已经正式取代 FID** 成为 Core Web Vitals 之一。

因此当前应围绕 LCP、INP 和 CLS 回答；FID 可作为指标演进背景。

---

## 为什么 FID 被 INP 取代

- **FID 只测第一次交互的输入延迟**，
  而且只测「延迟」不测「处理完成」
- 结果是：很多页面 FID 很好看，
  但用户实际点按钮后卡半天——因为卡在处理和渲染阶段，FID 测不到
- **INP 测的是整个交互周期**
  （输入延迟 + 处理时间 + 下一帧绘制），
  且取的是**整个会话中接近最差的那次**，更接近真实体验

---

## 其他常用指标

| 指标     | 含义                   | 用途                            |
| -------- | ---------------------- | ------------------------------- |
| **TTFB** | Time to First Byte     | 服务端响应速度，是 LCP 的第一段 |
| **FCP**  | First Contentful Paint | 首次有内容绘制                  |
| **TBT**  | Total Blocking Time    | 实验室里 INP 的替代指标         |
| **TTI**  | Time to Interactive    | 可交互时间（已不在核心指标里）  |

## 实验室数据 vs 真实用户数据

**这个区分很重要，能答出来说明你真的在用：**

- **Lab（实验室）**：Lighthouse、本地跑分。
  环境可控、可重复，适合**开发时对比优化前后**
- **RUM（真实用户监控）**：从真实用户浏览器采集。
  反映真实设备和网络，适合**判断线上到底好不好**

**为什么两者常常对不上**：
实验室的模拟设备、网络、冷缓存和固定交互，
无法覆盖真实用户的设备分布、缓存状态、后台任务、会话长度和交互路径。

> 采集方式见 [07-工程化/前端监控.md](../07-工程化/前端监控.md)

## 答题框架（比背手段重要）

性能题最容易答成"背了一堆优化手段"。**加上这个框架会显得专业得多**：

> 我做性能优化的顺序是：
> **先定指标，再定位瓶颈，最后才谈手段**。
>
> 定指标是因为"页面卡"这种描述没法优化——
> 要先明确是首屏慢（LCP）、交互卡（INP）还是跳动（CLS），
> 三者的优化方向完全不同。
>
> 定位瓶颈用 Lighthouse 看整体、Performance 面板看长任务、
> React Profiler 看组件。
>
> 改动后要在相同条件下做实验室对比，再用灰度版本的 RUM 分位数验证，
> 同时观察错误率、流量和业务指标副作用。
