# 资源加载优化

## 先看 Network 时序

资源加载问题常分为：发现太晚、优先级不对、资源太大、
连接/服务端慢、过多不必要请求。先确认瓶颈，再选 resource hint。

## 资源发现与优先级

| 能力            | 作用                             | 常见边界                                          |
| --------------- | -------------------------------- | ------------------------------------------------- |
| `preload`       | 要求浏览器尽早获取当前页必需资源 | `as`/CORS/字体类型必须正确；过度 preload 会抢带宽 |
| `modulepreload` | 提前获取并处理 ESM 及依赖        | 用于确实即将执行的模块图                          |
| `preconnect`    | 提前建立跨源 DNS/TCP/TLS 连接    | 连接数有成本，只用于关键且很快请求的 origin       |
| `dns-prefetch`  | 只提前解析 DNS                   | 成本较低，收益也小于 preconnect                   |
| `prefetch`      | 为后续导航低优先级获取           | 是提示，可被浏览器忽略；要考虑数据流量与过期      |
| `fetchpriority` | 提示已发现资源的相对优先级       | 不会自动提前发现，也不是强制指令                  |

```html
<link rel="preconnect" href="https://static.example.com" crossorigin />
<link rel="preload" as="image" href="/hero.avif" fetchpriority="high" />
<img src="/hero.avif" fetchpriority="high" width="1200" height="675" alt="" />
```

同一资源的 preload 和真实请求必须在 URL、`as`、CORS 模式等关键属性上对齐，
否则可能重复下载。

## 懒加载

```html
<img src="below-fold.webp" loading="lazy" decoding="async" width="800" height="600" alt="..." />
<video controls preload="metadata" poster="poster.webp"></video>
```

- 原生 `loading="lazy"` 已是现代浏览器的常用能力；
  需精细控制预加载距离或其他元素时用 Intersection Observer。
- 首屏 LCP 图片不要懒加载。“首屏”应按真实 viewport 与 RUM 数据判断，
  不是固定前几张。
- 为媒体保留 `width`/`height` 或 `aspect-ratio`，避免懒加载导致 CLS。
- `decoding="async"` 是解码提示，不是“延迟加载”，也不保证解码不占用主线程。

## JavaScript 加载

- 普通脚本可用 `defer`，ES module 默认具有类似 defer 的执行时机。
- `async` 适合独立且不依赖 DOM/其他脚本顺序的代码，下载完就执行。
- 按路由和业务能力使用 `import()` 分割，但要防止过多细碎 chunk 和加载瀑布。
- 第三方脚本要度量主线程耗时、网络竞争与隐私成本，不只看传输体积。

## 验证

1. DevTools Network 检查发现时间、Initiator、Priority、缓存命中与重复请求。
2. Performance 检查资源完成后是否仍被 JS、样式或字体阻塞渲染。
3. 分别使用首次访问、二次缓存访问、弱网与低端设备验证。
4. 上线后看 RUM 分位数，防止本地快机器掩盖真实瓶颈。
