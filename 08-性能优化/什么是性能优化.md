# 什么是性能优化

性能优化是在明确的用户场景、设备和网络分布下，
改善可度量的加载、交互响应和视觉稳定性，并防止指标再次回退。

## 不要从优化清单开始

```text
定义用户与业务目标
        ↓
采集真实用户基线（RUM）
        ↓
按页面/设备/网络/版本分组
        ↓
用实验室工具复现并定位瓶颈
        ↓
改一个主要瓶颈并做前后对比
        ↓
灰度发布、监控副作用、设置性能预算
```

## 指标和工具

| 问题               | 主要指标                      | 常用定位工具                                     |
| ------------------ | ----------------------------- | ------------------------------------------------ |
| 主内容出现慢       | LCP，辅助看 TTFB/FCP          | DevTools Network/Performance、Lighthouse、RUM    |
| 点击后响应慢       | INP，辅助看长任务/TBT         | Performance、Long Animation Frame、框架 Profiler |
| 页面会跳           | CLS                           | Layout Shift 轨道、RUM attribution               |
| 长时间使用越来越卡 | 内存、DOM 节点、订阅/任务数   | Heap Snapshot、Allocation Timeline、Profiler     |
| 构建或下载过重     | chunk 体积、初始 JS、缓存命中 | bundle visualizer、coverage、network waterfall   |

Core Web Vitals 应在**第 75 百分位**按页面类型和关键维度观察，
不要只看一次本地 Lighthouse 总分或全站平均值。

## 性能预算

性能预算要对应真实风险，例如：

- 关键路由初始 JavaScript gzip/brotli 体积上限。
- 首屏高优先级图片的字节数和数量上限。
- CI 中的 bundle diff 和 Lighthouse 趋势阈值。
- 线上 LCP/INP/CLS p75 回归告警，并按版本对比。

预算不应只给一个全局数字。后台编辑器、内容首页和移动端弱网的目标不同，
要按关键用户任务分组。

## 常见误区

- “所有图片都懒加载”：会延迟 LCP 图片。
- “打分越高越好”：单次实验室分数不代表真实用户分布。
- “用 `memo`/`useMemo` 就能解决卡顿”：先确认时间花在哪个任务和组件。
- “上 CDN 就快”：需要验证命中率、回源、缓存 key、连接和地域分布。
- “优化完就结束”：没有预算和线上回归监控，指标会随功能迭代退化。
