# 浏览器缓存与 CDN 配置

> 协议机制见 [04-浏览器与网络/浏览器缓存问题.md](../04-浏览器与网络/浏览器缓存问题.md)；
> 多层缓存策略见 [缓存技术.md](缓存技术.md)。

## 静态前端产物的常用策略

| 资源                            | 建议起点                                         | 原因                                         |
| ------------------------------- | ------------------------------------------------ | -------------------------------------------- |
| HTML 入口                       | `Cache-Control: no-cache`，并提供 ETag           | 可存储但使用前重新验证，便于发现新版资产 URL |
| 带内容 hash 的 JS/CSS/字体/图片 | `public, max-age=31536000, immutable`            | 内容变化则 URL 变化，可长期缓存              |
| 不带 hash 且可覆盖的静态资源    | 短 TTL 或 `no-cache`                             | 同 URL 内容会变，不能使用 immutable          |
| 公共 GET API                    | 按陈旧容忍设 `s-maxage`/`stale-while-revalidate` | 可用 CDN 减少回源，但必须正确设计 key/Vary   |
| 个性化或敏感 API                | `private, no-store` 作为安全起点                 | 防止共享缓存跨用户泄漏；具体仍按数据性质决定 |

`no-cache` 不是“不存储”；它要求重新验证后才可使用。
`no-store` 要求缓存不存储该响应，对降低敏感数据残留风险更合适，
但也会失去 304/本地复用收益。

## CDN 缓存 key

至少审查：

- host、path、query 的哪些部分进入 key，无关营销参数是否需要归一化。
- `Vary` 中的 `Accept-Encoding`、`Accept`、语言或设备维度是否真正影响响应。
- `Authorization`、Cookie 或用户权限会影响内容时，是否已禁止共享缓存
  或把必需维度安全地纳入 key。
- 图像转换参数是否白名单化和限宽/质量，防止无界变体穿透缓存。

## 发版、灰度与回滚

1. 先上传带 hash 的不可变资产，确认 CDN 可访问，再发布 HTML 入口。
2. 旧 hash 资产的保留时间要覆盖长会话、bfcache、离线页和回滚窗口，
   不能只按“一个发布周期”判断。
3. HTML 如果使用 `no-cache`，CDN 必须真正尊重重新验证；
   如果中间层额外设 TTL，发布时要做精确 purge。
4. 回滚需同时恢复入口和对应资产，不要只回滚应用服务。

## chunk 加载失败

旧页面引用的 chunk 被提前删除、CDN 节点未同步或网络短暂失败都可能触发。

- 首选是保留旧资产与原子发布，不是把刷新当作根治。
- 需要刷新兜底时，只自动重试一次，用 sessionStorage 等记录防止刷新循环。
- Vite 可监听 `vite:preloadError`；Webpack/框架有各自的 chunk error 路径，
  不要把 Vite 事件当成通用浏览器 API。

## 跨域脚本错误详情

要从跨源脚本获得完整错误栈，资源响应需允许 CORS，
且 `<script>`/module 的 `crossorigin` 模式要与服务端响应对齐。
否则脚本可能仍能执行，但错误信息可能被裁剪成 `Script error.`。
