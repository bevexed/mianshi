# 内存泄漏排查

## 怎么确认是泄漏

**1. Performance 面板录制**
勾选 Memory，反复执行可疑操作（进出页面、开关弹窗），
看 JS Heap 曲线：

```
正常：锯齿状，GC 后回落到基线
泄漏：阶梯状上升，GC 后回不到原来的基线
```

**2. Memory 面板拍快照对比**

- 操作前拍一次 heap snapshot
- 反复操作 N 次
- 再拍一次
- 切到 **Comparison 视图**，看新增了哪些对象没被回收
- 看 **Retainers**（谁在引用它），顺藤摸瓜找到源头

## 前端常见泄漏源

| 泄漏源                     | 说明                                                     | 修法                             |
| -------------------------- | -------------------------------------------------------- | -------------------------------- |
| **定时器没清理**           | `setInterval` 一直跑，闭包持有组件引用                   | effect 里 return `clearInterval` |
| **事件监听没移除**         | `addEventListener` 到 window/document                    | return `removeEventListener`     |
| **Observer 没断开**        | IntersectionObserver / ResizeObserver / MutationObserver | return `observer.disconnect()`   |
| **闭包持有大对象**         | 一个小回调把整个大数组留住了                             | 只捕获需要的字段                 |
| **全局 Map/数组不断 push** | 缓存永不清理                                             | 用 **WeakMap** 或加淘汰策略      |
| **detached DOM**           | JS 还持有已从文档移除的节点                              | 清空引用                         |
| **微前端子应用卸载不彻底** | 全局变量、样式、监听残留                                 | unmount 时彻底清理               |

### React 里的标准写法

```js
useEffect(() => {
  const t = setInterval(tick, 1000)
  const onResize = () => {...}
  window.addEventListener('resize', onResize)
  const ob = new ResizeObserver(cb)
  ob.observe(el)

  return () => {                    // ← 这个 return 是关键
    clearInterval(t)
    window.removeEventListener('resize', onResize)
    ob.disconnect()
  }
}, [])
```

## WeakMap 为什么能防泄漏

普通 `Map` 持有**强引用**——
以 DOM 节点为 key 缓存数据，节点从文档移除后
**只要该 Map 本身仍然可达，节点就不会因离开文档而被回收**。

`WeakMap` 的 key 是**弱引用**，
对象没有其他引用时会被 GC，条目自动消失。

> 详见 [01-JavaScript/Map 与 WeakMap.md](../01-JavaScript/Map与WeakMap.md)

## 微前端场景的特殊性

子应用卸载时如果清理不彻底，会残留：

- 挂在 `window` 上的全局变量
- 未移除的事件监听
- 未清理的定时器
- **动态插入的 `<style>` 标签**
- 第三方 SDK 的实例（地图、图表、播放器）

qiankun 的沙箱主要隔离全局属性写入，不应把它当成所有副作的自动垃圾回收器。
定时器、DOM 事件、订阅、第三方实例和动态样式需由子应用在 `unmount` 中对称清理。

反复切换子应用后内存持续上涨，基本就是这个问题。

> 关联：[10-架构与设计/微前端/qiankun 原理.md](../10-架构与设计/微前端/qiankun原理.md)

## Node 侧的内存排查

- `node --inspect` + Chrome DevTools 拍快照
- `process.memoryUsage()` 打点监控
- **常见泄漏源**：全局缓存 Map、
  未关闭的数据库连接、事件监听累积、
  闭包持有大 Buffer

长时间运行的队列 Worker 需额外监控 heap/RSS、任务处理量、
队列滞留和容器 OOM 事件。内存增长不一定都是 JS heap 泄漏：
Buffer/native addon、文件映射和 allocator 行为也可能使 RSS 上升，应分指标定位。
