# 项目复盘方法

项目深挖的目标是证明判断过程和结果可验证，而不是堆叠技术名词。推荐用下面的结构组织文档或面试表达。

## 1. 背景与目标

- 谁遇到了什么问题？不解决会造成什么影响？
- 成功指标是什么：时延、错误率、交付周期、成本还是业务转化？
- 时间、人员、兼容性、合规和存量系统有哪些硬约束？

目标要区分业务结果与技术代理指标。例如“首屏 p75 LCP 低于目标”是技术指标，“核心流程完成率提升”才是业务结果；二者可以关联，但不能互相替代。

## 2. 现状与证据

- 用架构图或数据流说明当前边界，不从最终方案倒推问题。
- 记录基线数据、样本范围和采集方式。
- 区分已确认事实、合理推断和待验证假设。
- 列出过去方案为什么失效，避免重复踩坑。

## 3. 备选方案与决策

| 维度   | 示例问题                             |
| ------ | ------------------------------------ |
| 正确性 | 并发、失败、重复执行时会怎样？       |
| 性能   | 瓶颈在哪，扩容是否有效？             |
| 复杂度 | 谁维护，排障需要哪些能力？           |
| 兼容性 | 老版本、旧数据和灰度期间如何共存？   |
| 成本   | 开发、迁移、基础设施和长期运维成本？ |
| 安全   | 权限、隐私、审计和供应链风险？       |

至少写出一个被放弃的方案和放弃理由。不存在“零代价最佳方案”，只有在当前约束下更合适的取舍。

## 4. 实施与风险控制

- 将大变更拆为可独立验证、可回退的小阶段。
- 先补观测和基线，再优化；否则无法判断效果。
- 数据和协议变化采用兼容迁移，明确回滚/前滚边界。
- 高风险路径用灰度、feature flag、影子流量或双写对账。
- 记录关键决策和负责人，避免只有某个人理解系统。

## 5. 验证结果

```text
基线 → 改动 → 同口径对比 → 副作用 → 是否达到目标
```

结果应说明时间窗口、分位数、样本量和异常因素。只写“提升 50%”而不说明从什么到什么、如何测量，结论不可复核。

## 6. 复盘与后续

- 哪个假设错误，哪一步返工最多？
- 暴露了哪些组织、流程或可观测性问题？
- 新方案引入了什么技术债和维护成本？
- 哪些动作已完成，哪些有负责人和截止时间？
- 如果重新做一次，会在哪个决策点改变做法？

## 一页摘要模板

```text
背景：
目标与指标：
范围与约束：
现状证据：
备选方案：
选择与取舍：
我的贡献：
上线与风险控制：
结果：
不足与后续：
```
