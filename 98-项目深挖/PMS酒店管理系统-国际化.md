## 一、国际化（简历唯一点名的收获，必被追问）

### Q1：i18n 你踩了什么坑？

**⚠️ 只答"用了 vue-i18n 配置语言包"会非常单薄。国际化的真正难点在文案之外。**

**答题骨架——分五层讲**：

**1. 文案层**

- **变量插值和复数**——英文 `1 room / 2 rooms`，中文不变复数。
  硬拼字符串必然出错，要用 i18n 的 pluralization
- **语序不同**——「预订 3 间房」vs「Book 3 rooms」，
  拼接顺序不同，所以**绝不能用字符串拼接，必须用带占位符的模板**
- **文案长度差异**——德语/俄语通常比中文长 2-3 倍，
  按中文设计的按钮宽度到了德语会撑破 → **UI 要按最长语言留余量或允许换行**

**2. 时区**（酒店系统的重灾区）

- 酒店在不同国家，**入住/退房日期必须按酒店所在地时区**，
  不能按用户浏览器时区
- 一个中国用户订东京的酒店，"今天"是哪天？→ 必须以酒店时区为准
- **原则**：**存储用 UTC，展示按目标时区转换**，
  转换发生在展示层而不是数据层

**3. 日期/数字格式**

- 美国 `MM/DD/YYYY`，欧洲 `DD/MM/YYYY`——`03/04` 到底是三月四号还是四月三号
- 数字分隔符：`1,234.56`（英美）vs `1.234,56`（德国）
- → 用 `Intl.DateTimeFormat` / `Intl.NumberFormat`，别自己写格式化

**4. 货币**

- 币种符号位置、小数位数（日元没有小数位）
- **汇率换算的时机**——展示时换算还是下单时锁定？必须下单时锁定

**5. 布局（如果涉及阿拉伯语）**

- RTL 从右到左，`margin-left` 要变成 `margin-inline-start`
- 【需确认】你们支持阿拉伯语吗？不支持就别提，会被追问细节

### Q2：翻译文件怎么维护？

**简历里单独列了「翻译文件维护」，说明这事占了你不少时间，
可以讲成一个工程化问题：**

- **痛点**：文案散在各处、key 命名混乱、加一个语言要人肉对齐、
  删了组件但 key 还留着（死翻译）
- **可讲的改进**：
  - key 按模块命名空间组织（`order.list.title`）而不是扁平
  - 脚本扫描代码里用到的 key，和语言包对比，找出缺失和冗余
  - 【需确认】你有没有做过这类脚本或者对接翻译平台？做了一定要讲

### Q3：语言包会不会拖慢首屏？

- 所有语言全打进 bundle 是常见错误——用户只需要一种
- **按需加载**：`vue-i18n` 支持异步加载 locale message，
  只加载当前语言
- 微前端下语言状态由主应用持有（见 [微前端](微前端-qiankun与多框架共存.md)）

## 二、ratePlan 与 channel（简历自己标了"难"，必被问）

### Q4：ratePlan 是什么？难在哪？

**先讲清业务再讲技术**：

- ratePlan（价格方案）= 房型 + 价格规则的组合。
  同一个房型可以有多个 ratePlan：含早餐的、不可退的、连住 3 晚优惠的……
- **难点在于价格是"日历维度"的**——
  同一个 ratePlan 在不同日期价格不同（周末、节假日、旺季）
- 你简历里的四项正好对应四类复杂度：
  - **多人价**——1 人住和 2 人住价格不同
  - **ratePlan 整合**——多个方案的合并展示
  - **批量改价**——运营要一次改一个月/一个季度
  - **衍生价格**——基础价 ± 规则推导出的价格（这是最难的）

### Q5：ratePlan 日历（标了"难"）技术上难在哪？

**答题骨架**：

1. **数据量大**——房型 × ratePlan × 天数，
   一个酒店 20 个房型 × 5 个方案 × 365 天 = 3.65 万个单元格
2. **渲染性能**——全量渲染必卡
   → 虚拟滚动（横向按日期、纵向按房型都要虚拟化，是**二维虚拟滚动**）
   → 或者限制可见范围（一次只展示一个月）
3. **编辑交互复杂**——单个改、拖拽批量选、按规则批量改
4. **联动**——衍生价格意味着改了基础价，一片衍生价都要跟着变，
   前端要实时算出预览
5. **保存**——3 万个单元格不能全量提交，要做**脏数据 diff**，只提交改动的

【需确认】你实际做了虚拟滚动吗？还是分页/按月加载？
**这题答案的技术含量差别很大，务必如实。**

### Q6：channel 渠道对接难在哪？

- **渠道**指 Booking.com、Airbnb、携程这类 OTA 平台
- **难点**：
  - **房态房价同步**——本地改了价要推给所有渠道，
    渠道那边有订单要同步回来。这是典型的**分布式数据一致性**问题
  - **超售（overbooking）**——两个渠道同时卖掉最后一间房
  - 各渠道的 API、字段、规则都不一样，要做**适配层**
- **前端侧**（你负责的部分）：渠道授权流程、渠道配置映射
  （本地房型 ↔ 渠道房型的对应关系）、同步状态的展示和错误处理

**答题要点**：前端在这里的价值是**把复杂的映射关系做得让运营不出错**——
配错一个映射，可能导致卖错房价。
所以校验、预览、二次确认比界面好看重要得多。

## 三、这段经历的其他可挖点

### Q7：Vue2 和 Vue3 你都用过，怎么看它们的差异？

**别背 API 差异表，讲你实际感受到的：**

- **响应式**：`Object.defineProperty` → `Proxy`。
  Vue2 无法检测新增属性（要 `$set`）、数组索引赋值，Vue3 没这个问题
- **Composition API 的真正价值不是"更像 React"，是逻辑复用**——
  Vue2 的 mixin 有命名冲突和来源不清的问题，
  组合式函数（`useXxx`）解决了这个
- **TS 支持**——Vue2 的 Options API 类型推导很别扭，Vue3 好很多
- **你的实际场景**：老项目在 Vue2 上迁不动，
  所以是靠微前端让新模块用 Vue3（见微前端篇）

### Q8：「CDN 维护」「SEO（gtag 埋点）」这些做了什么？

【需确认，简历只列了名字】

- CDN：静态资源分发、缓存策略（hash 文件名 + 长缓存，
  index.html 不缓存）、跨域配置（呼应 Sentry 篇的 `Script error.`）
- gtag 埋点：事件设计、和 SEO 的关系其实不大——
  **注意别把埋点和 SEO 混为一谈，面试官会觉得你概念不清**
