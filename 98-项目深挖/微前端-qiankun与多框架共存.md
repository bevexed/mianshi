## 一、动机（必问，且是筛人题）

### Q1：为什么要用微前端？

**⚠️ 最差的答法是「为了技术栈无关」——这是宣传语，不是理由。**

**真实且有力的答法（你的场景恰好是最正当的两个）**：

1. **存量老项目迁移不动**——选购下单前台是纯 Angular，
   完全重写成本高、风险大、业务不会给这个时间。
   微前端让**新功能用新技术写，老代码原地不动**，是一种渐进式迁移策略
2. **团队/发布解耦**——不同业务域由不同人维护，独立发布，
   不用因为改一个模块全量回归

**必须补的一句**：

> 微前端的正当理由基本只有「组织和存量」，不是技术先进性。
> 如果是一个从零开始的新项目、一个团队维护，用微前端纯属自找麻烦。

### Q10：px2rem 和 rem 换算问题是什么？

- px2rem 是构建时把 px 转成 rem 的插件，配合根字号动态设置做移动端适配
- **典型坑**：
  - 第三方 UI 库的样式也被转了，导致组件尺寸错乱 → 需要配 `exclude`
  - 1px 边框被转成很小的 rem 值，渲染成 0 → 需要配置最小转换阈值
  - 两个应用共存时，**根字号是全局的**，一个应用改了 `html { font-size }`
    会影响另一个应用 → 这大概率就是你踩的坑

## 四、PMS：Vue2 / Vue3 共存

### Q11：Vue2 和 Vue3 子应用共存有什么问题？

- 两个版本的 Vue 同时存在，**bundle 体积翻倍**
- Vue2 用 `Object.defineProperty` 做响应式，Vue3 用 `Proxy`——
  数据不能直接共享，跨应用传对象会丢响应性
- element-ui（Vue2）和 element-plus（Vue3）**类名前缀都是 `el-`**，
  样式冲突非常严重 → 必须改前缀或严格隔离
- 【需确认】你实际是怎么处理 element-ui / element-plus 类名冲突的？

### Q12：i18n 在微前端下怎么统一？

（这条呼应你 PMS 的 i18n 经历，见 [PMS 酒店管理系统](PMS酒店管理系统-国际化.md)）

- 语言状态应该由**主应用持有**，通过 props 或全局 state 下发给子应用
- 每个子应用维护自己的语言包（避免主应用变成翻译文件的垃圾场），
  但共享公共词条
- 切换语言时要通知所有已挂载的子应用
