> 代码核对范围：`inewgrand-gch-app`、`inewgrand-mini-app`，截至 2026-09-10。

## 2. 60 秒项目介绍

> 这个项目有两个移动客户端：App 使用 Expo SDK 57、React Native 0.86、React 19 和 Expo Router；小程序使用原生框架、TypeScript 和 Sass。两端面对的是同一套工程行业业务，但不能简单复制代码，因为路由、网络流、文件选择、键盘、弹层和生命周期能力都不同。
>
> 业务上，我们把用户会话和当前租户作为全局上下文。用户既可以进入个人工作台，也可以切换到企业主体；资质日报、认证状态、消息和 AI 会话都必须跟当前主体一致。工程上，两端都建立了统一 HTTP 层、登录态恢复、Token 失效处理、路由门禁、消息未读状态和错误监控。
>
> 最复杂的一条链路是 AI 智能体。App 用可读取响应体的 `fetch` 消费 SSE，小程序用 `wx.request` 的 `enableChunked` 和 `onChunkReceived` 获取分块。两端都要处理 UTF-8 字符跨 chunk、SSE 事件跨 chunk、服务端会话 ID 接管、回答停止、Markdown 展示和用户向上阅读时不被自动滚动抢位置。这个项目让我真正理解了：跨端一致性不是共享 UI，而是共享业务不变量、分别适配平台能力。

## 3. 为什么做两个客户端，而不是只做一套跨端代码

### Q1：App 和小程序分别是什么技术栈？

| 维度       | App                                               | 微信小程序                                   |
| ---------- | ------------------------------------------------- | -------------------------------------------- |
| UI 运行时  | React Native 0.86、React 19                       | 原生 WXML/WXSS 组件模型                      |
| 工程框架   | Expo SDK 57、Expo Router                          | 原生小程序 + TypeScript + Sass               |
| 网络请求   | `expo/fetch`、`ReadableStream`、`AbortController` | `wx.request`、`RequestTask`、`enableChunked` |
| 列表       | `FlatList`                                        | `scroll-view`                                |
| 文件与图片 | Expo ImagePicker、原生 Activity 生命周期          | `wx.chooseMedia`、`wx.uploadFile`            |
| 安全存储   | `expo-secure-store`                               | 小程序本地会话封装                           |
| 弹层       | Bottom Sheet、React Native 组件                   | 页面内弹层、公共导航和原生弹窗               |
| 质量门禁   | TypeScript、ESLint、Jest/组件测试                 | TypeScript、ESLint、Vitest、Prettier         |

### Q2：为什么不追求 UI 代码完全复用？

**推荐回答：**

> 两端应该复用的是业务语义和接口契约，不是强行复用每一行 UI。比如“切换主体后旧租户页面不能继续留在返回栈”“生成成功必须收到业务结束事件”“用户向上阅读时不能强制贴底”，这些不变量两端一致；但 App 用 Expo Router、FlatList 和 AbortController，小程序用页面栈、scroll-view 和 RequestTask，适配方式必须不同。强行套一层跨端抽象，反而可能把平台能力压成最低公分母。

### Q3：跨端迁移怎么避免“看起来一样，行为不一样”？

不要只对截图，要按四层核对：

1. **接口层**：路径、参数、响应包裹、业务码、分页游标。
2. **领域层**：状态枚举、权限条件、个人/企业主体差异。
3. **交互层**：loading、empty、error、键盘、滚动、弹层、返回行为。
4. **渲染层**：最终绑定的字段、文案、图标、数量和条件分支。

项目里的典型例子是消息标签、未读数量和资质注册类别：中间模型“差不多”不够，必须检查最终页面实际渲染了什么。

### 两个“小改动”怎么讲出分析过程

**市场活动轮播露出上一张边缘：** 外层容器有左右 padding，却用外层 `onLayout` 得到的宽度作为每一页宽度，导致 slide 比 ScrollView 的真实可视区更宽。修复不是随手加负 margin，而是把尺寸测量移到真正负责分页的 ScrollView，并给 slide 建立明确裁剪边界。可以借此说明：分页宽度必须来自实际滚动 viewport，不能从“看起来差不多”的祖先容器推导。

**活动分页字段有时是字符串：** 后端会把 Long 序列化成字符串，小程序在响应 parser 边界兼容有限数字和数字字符串，再统一输出 number；非法值仍然报响应格式错误。不要把下游类型直接放宽成 `number | string`，否则兼容分支会扩散到每个页面。

**认证和资质申请自动回填：** 统一社会信用代码、联系电话这类字段要先定义来源优先级：已有详情优先，其次使用当前租户或当前用户资料，最后才为空；默认值只在初始化阶段写入，不能在异步资料返回后覆盖用户已经输入的内容。这类需求本质上仍是“谁是当前状态的权威来源”。

## 5. 登录、会话和权限

### Q4：登录态是怎么维护的？

App 的可讲主线：

1. 登录成功后保存 Access Token、Refresh Token、有效期、用户和租户信息。
2. Token 对和设备标识放在安全存储中，不进入 URL、普通日志或崩溃上下文。
3. 应用启动时恢复会话，受保护路由只在会话有效时开放。
4. Access Token 临近过期主动轮换；遇到 401 时，并发请求共享同一个刷新任务。
5. 刷新成功后只对允许重放的请求重试一次；刷新失败则清空会话并返回登录页。
6. 退出时尽量通知服务端撤销设备会话，但无论接口成功与否都清理本地 Token。

### Q5：为什么 401 不能让每个请求各自刷新一次？

> 页面并发加载时，多个请求可能同时收到 401。如果各自刷新，会产生刷新风暴，Refresh Token 轮换时还可能让后一个请求使用已经失效的旧 Token。更稳妥的做法是维护一个共享中的 refresh Promise，所有失败请求等待同一次刷新。刷新成功后再按请求语义决定是否重放，失败则统一退出。

### Q6：所有请求都能在刷新后自动重放吗？

不能。GET 通常可以限制为最多重试一次；创建、提交、删除、发送 AI 问题等有副作用的 POST，如果服务端已经执行但响应丢失，盲目重放可能造成重复数据或重复消耗。

回答时补一句：

> 是否可重放不是看 HTTP 方法名字，而是看业务是否幂等、是否有幂等键，以及客户端能不能确认服务端尚未执行。

### Q7：SM2 加密是不是就可以不用 HTTPS？

不可以。客户端公钥加密可以减少密码以明文形态出现在某些调试链路中的风险，但它不能提供完整的服务端身份校验、传输完整性和防重放能力。HTTPS 仍然是底线，服务端也必须做密码哈希、限流和异常登录防护。

## 6. 多租户状态为什么难

### Q8：个人版和企业版切换，难点在哪里？

它不是改一个 `tenantId`，而是切换完整业务上下文：

```text
当前用户
  └─ 当前主体（个人 / 企业）
       ├─ Token / 会话资料
       ├─ 页面权限与认证状态
       ├─ 资质运维数据
       ├─ 消息可见范围
       ├─ AI 会话范围
       └─ 后续导航与返回栈
```

需要处理：

- 企业可能是已加入、待接受邀请、未认证或不可切换状态。
- 个人主体不能因为缺少企业成员字段而被误判为不可选。
- 普通切换要回首页并替换旧路由，避免 Back 返回旧租户页面。
- “去企业认证”是带业务意图的例外，要保留认证入口，不能被统一首页逻辑抹掉。
- 切换过程需要防重复点击，成功后重新加载当前主体相关数据。

### Q9：为什么切换后用 replace/reLaunch，而不是普通 push？

> 因为旧页面已经绑定旧租户数据。普通 push 会把旧页面保留在栈里，用户按返回键可能重新看到旧主体内容，甚至继续发起操作。App 使用 `router.replace('/')`，小程序使用 `reLaunch('/pages/home/home')`，本质上是在主体切换后建立新的导航边界。

### Q10：前端做了租户隔离，服务端还需要校验吗？

必须。前端只能控制展示和交互，不能作为权限边界。服务端应从可信会话解析当前用户和租户，再做资源级授权；不能相信客户端传来的用户身份、权限或任意 tenantId。

## 7. 消息中心：小功能里的状态一致性

### Q11：未读数为什么不能直接用消息分页接口的 total？

列表 `total` 表示筛选条件下的记录总量，不等于未读数量；两个端展示的消息范围还可能不同。项目后来统一使用独立的未读数接口，并传入移动端可见范围 `visibleClient=2`。

这件事能提炼成三个原则：

1. 数量语义要由专用契约定义，不能拿“看起来像”的字段代替。
2. 列表范围和角标范围必须一致。
3. App、小程序都要检查最终 service 调用和最终渲染绑定，不能只改共享类型。

### Q12：多个页面都有消息入口，怎么避免未读状态各管一份？

> 把未读状态放在共享 store/service 中，页面只订阅和触发刷新；弹层负责分页、已读和加载状态。否则首页读了一份、个人中心又读一份，关闭弹层后的角标很容易不同步。

### Q13：小程序弹层为什么要隔离异步写回？

典型竞态是：弹层 A 发起加载，用户快速关闭并重新打开或切换上下文，旧请求最后返回，把新一轮状态覆盖了。处理方式是给每轮加载建立 controller 或 generation，只允许当前实例、当前轮次写回。

这和 AI 会话切换时阻止旧流写入新会话，本质上是同一个问题：**异步结果必须验证它还属于当前上下文。**

## 8. 资质运维：怎么把复杂业务讲出技术含量

### Q14：资质运维模块有哪些复杂点？

- 个人版与企业版工作台的入口和文案不同。
- 企业是否认证、功能是否开通、用户是否有权限，会组合出多种门禁状态。
- 日报包含智能总结、资质到期、人员到期、安全许可证和达标分析。
- 弹层里有筛选、横向列表、申请表单和进一步解决方案入口。
- 同一套业务要在 App 和原生小程序保持字段和交互语义一致。

### Q15：举一个“字段映射看似简单，实际容易错”的例子

达标分析里同时存在：

- `registrationCategory`：注册类别，例如一级注册建造师。
- `registrationSpecialty`：注册专业。
- 等级文本：可能包含甲（I）级、甲（II）级这类括号结构。

规则不是粗暴去重：同一类别出现多个等级时可以合并等级，但单条数据必须保留原等级，不同类别或专业也不能被误合并。

**面试表达：**

> 我不会先写一个正则“把重复前缀删掉”，而是先明确数据语法：什么字段代表类别、什么字段代表专业、什么情况下才允许合并。然后用单类别单等级、同类别多等级、不同类别和带全角括号的等级做边界用例。这个问题本质上是领域规则建模，不是字符串技巧。

### Q16：为什么“未认证企业”仍可能显示企业版工作台？

`subjectType` 表示当前主体类型，认证状态表示这个企业走到了哪一步，两者不是同一个维度。把“企业版”错误绑定到“已认证”，会让未认证企业显示成个人版，后续认证入口和文案都错位。

### Q17：弹层层级为什么不能只靠不断加 z-index？

项目里需要同时考虑提示层、底部导航、业务弹层和顶部公共导航。更稳妥的语义层级是：

```text
页面内容 < prompt < footer-nav < modal < header-nav
```

顶部导航仍需可操作时，打开租户或消息入口前还要主动关闭页面内其他弹层。只堆 `z-index` 会留下多个仍在响应触摸和异步写回的隐藏弹层。

## 9. 原生移动端问题怎么讲

### Q18：Android 图片选择后页面为什么可能“丢状态”？

系统图片选择器可能让 Activity 被回收或重建。用户回到 App 时，React 组件不一定还保持原来的抽屉、表单草稿和“正在选择头像/营业执照”状态。

项目里的处理思路：

1. 对头像和营业执照维护独立的操作标识。
2. 在进入系统选择器前保存需要恢复的 UI 和草稿状态。
3. App 恢复后串行消费对应结果，不能让旧回调清除新一轮选择标识。
4. 对取消、失败、页面卸载和连续选择分别清理。

**亮点不是“会用 ImagePicker”，而是理解跨进程原生 UI 会改变应用生命周期。**

### Q19：上传图片要处理哪些边界？

- 相册/相机权限与拒绝后的反馈。
- MIME、扩展名、尺寸和服务端大小限制。
- 高分辨率图片压缩时的内存峰值。
- 本地预览、上传中、失败重试和更换图片。
- App 的 FormData 与小程序 `wx.uploadFile` 契约差异。
- 不能把 Token、文件路径或内部错误完整写进日志。

### Q20：移动端键盘适配为什么经常“修一次坏一次”？

因为布局可能同时受到系统 `adjustResize`、安全区、固定底栏、页面滚动和组件自动避让影响。项目里分别处理了 Android 登录页、AI 输入区、中文组合输入、placeholder 宽度和小程序键盘高度变化。

推荐回答：

> 键盘问题不能只加一个固定 bottom。我要先确认是谁在移动布局：系统窗口、框架 KeyboardAvoidingView，还是业务自己设置的 padding；只保留一个主要事实源，再用真实键盘高度和安全区计算。中文输入还要避免受控输入在 composition 期间反复回写造成文字重叠。

## 10. 构建、监控和交付

### Q21：Sentry 接入除了填 DSN 还有什么？

- 按开发、测试、生产区分环境和 release。
- Source Map 与构建产物版本匹配，否则堆栈无法还原。
- 过滤 Token、验证码、手机号等敏感上下文。
- 小程序在用户同意隐私协议前不主动发送事件。
- 小程序后台需要配置合法 HTTPS 域名。
- App 的 Metro/Expo Plugin 与小程序 SDK 接入方式不同。

### Q22：双端构建脚本最值得讲什么？

不是“把命令串起来”，而是：

- 明确 development、test、production 的 API 和构建 profile 映射。
- 构建命令不读取开发机私有 IP。
- 复用项目本地工具和 lockfile，减少环境漂移。
- 对网络上传做有限重试，不无限循环掩盖真实失败。
- 临时调整缓存或配置后按原始字节恢复，避免污染工作区。
- 签名证书和 Provisioning Profile 属于共享资产，自动化不能擅自吊销或覆盖。

### Q23：小程序包体怎么优化？

先找主包大头，再压缩背景图和 SVG、启用上传压缩、移除无用资源；依赖要评估是否必须进入主包。不能只看开发者工具“能编译”，还要真机检查资源路径、npm 构建和分包边界。

## 11. AI 智能体：项目里最值得主动引导的主线

### Q24：AI 智能体完整能力有哪些？

- 服务端 bootstrap 与能力开关。
- 推荐问题和首次空态。
- 新建、切换、搜索、分页和删除历史会话。
- 文本提问、图片选择/上传和能力禁用提示。
- SSE 流式回答、Markdown 子集和知识来源展示。
- 本地临时会话 ID 接管服务端 ID。
- 停止生成、失败重试、断流内容保留和历史恢复。
- 个人/企业主体隔离。
- 自动跟随最新消息，但尊重用户向上阅读。

### Q25：一句话讲清流式渲染怎么做

> 我把它拆成五层：平台流式请求负责拿 chunk，增量解码器处理 UTF-8 和 SSE 边界，事件归约器维护会话与消息状态，20ms 打字器控制显示节奏，最后由滚动跟随和失败恢复保证长回答的阅读体验。网络流和 UI 动画是两件事，不能把每个 chunk 直接当成一个可渲染字符。

详细追问见：[AI 对话流式渲染](../11-AI工程/AI对话流式渲染.md)。

### Q26：App 和小程序的流式实现最大差异是什么？

> App 可以通过 `fetch` 读取 `response.body.getReader()`，用 `TextDecoder(..., { stream: true })` 保留跨 chunk 的 UTF-8 尾字节；小程序要使用 `wx.request({ enableChunked: true })` 和 `RequestTask.onChunkReceived`，并自己缓存最多三个未完成的 UTF-8 尾字节。上层 SSE 事件和会话状态规则一致，但底层 transport adapter 不同。

### Q27：断流后为什么不能简单把 partial text 清掉？

用户可能已经等了几十秒，清空会造成信息和信任同时丢失。项目里的策略是保留已生成内容并标记可重试；App 如果已经拿到远程 `messageId`，还会回查历史，判断服务端是否其实已经完成，只是 SSE 尾包在移动网络中丢失。

## 12. 三个可用的 STAR 案例

### 案例一：流式回答“已经生成，却被前端判失败”

**S**：移动网络波动时，服务端可能已完成回答，但客户端没有收到最后的 `message_end`，页面显示中断。

**T**：既不能把 TCP 正常关闭误判为生成成功，也不能丢掉服务端已经生成的完整答案。

**A**：

1. 继续要求 `message_end` 作为业务完成标志。
2. 在流中记录 `conversationId` 和远程 `messageId`。
3. 断流时按会话回查历史，并用远程消息 ID 找到已落库回答。
4. 找到完整回答就恢复为成功；回查失败则保留 partial text，进入可重试状态。

**R**：同时覆盖了“尾包丢失但服务端成功”和“服务端确实中断”两种情况，避免用一个粗暴重试掩盖状态不确定性。

### 案例二：切换租户后返回旧页面

**S**：用户从资质日报切换企业，普通 push 会保留旧租户页面；按返回键可能重新看到旧数据。

**T**：主体切换后建立新的页面和数据边界，同时保留“前往认证”这类显式业务意图。

**A**：App 普通切换统一 `replace('/')`，小程序统一 `reLaunch` 首页；认证入口通过独立参数继续跳个人中心认证流程。

**R**：普通切换不会回到旧主体页面，业务例外也没有被统一规则破坏。

### 案例三：Android 连续选择图片状态串线

**S**：用户选择头像或营业执照时 Activity 可能重建，快速连续操作还会让旧恢复回调清掉新状态。

**T**：恢复正确的抽屉和草稿，并隔离不同图片操作及不同轮次。

**A**：为两类操作设置独立标识，保存恢复快照，串行消费恢复结果，并让旧回调校验当前轮次后再清理。

**R**：覆盖 Activity 重建、取消、失败和连续选择，而不是只修一次“回到页面看不到图”的表象。

## 13. 高频追问速答

### Q28：SSE 和 WebSocket 怎么选？

AI 回答主要是服务端单向增量输出，SSE 语义更简单，也容易经过普通 HTTP 基础设施；如果需要高频双向协作、音视频或实时共同编辑，再考虑 WebSocket。这个项目还需要 POST JSON、Bearer Token 和移动端平台适配，所以没有直接依赖浏览器原生 EventSource。

### Q29：为什么 AI 会话要按租户隔离？

同一个用户在个人主体和不同企业下看到的知识、权限和历史可能不同。客户端切换租户后要重载 bootstrap 与历史，服务端更必须基于当前可信租户做授权，不能只依赖客户端把列表清空。

### Q30：为什么要支持停止生成？

停止不是只把按钮变回“发送”：客户端要停止 UI 写回并 abort 网络连接；拿到服务端 taskId 后还要调用停止任务接口，减少服务端继续推理造成的资源浪费。

### Q31：为什么 Markdown 只支持子集？

移动端答案主要需要标题、列表、引用和加粗。自定义受控子集更容易保证布局、性能和安全；小程序不能直接信任模型返回 HTML，必须先转义，再生成受控节点。

### Q32：怎么测试这种跨端项目？

分三层：

1. 纯函数：字段解析、状态转换、权限条件、SSE 分块、Markdown 转换。
2. 组件/页面：弹层、键盘、滚动、禁用态、最终字段绑定。
3. 真机链路：登录、主体切换、图片选择恢复、长回答、弱网中断、安装包和小程序预览。

单测通过不能替代 Developer Tools、Android/iOS 真机和真实测试环境验收。
