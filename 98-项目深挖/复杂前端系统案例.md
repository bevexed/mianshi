# 复杂前端系统案例

复杂前端系统的难点通常不是页面数量，而是业务状态、权限、协作边界和长期演进。下面是一套通用分析框架。

## 领域与页面边界

- 按业务能力划分模块，不直接按菜单或组件目录等同领域边界。
- 服务器状态、URL 状态、表单草稿和纯 UI 状态分别管理。
- 跨模块共享的数据要有所有者、schema 和失效策略；避免随意暴露全局 store。
- 列表、详情、编辑和审批状态用显式状态机描述非法转换。

## 权限模型

前端权限用于导航和体验，服务端权限才是安全边界。

```text
身份认证 → 租户/组织范围 → 角色/策略 → 对象级权限 → 字段与操作权限
```

- 路由守卫不能代替接口授权。
- 菜单、按钮和 API 应来自同一权限语义，避免三套配置漂移。
- 权限变化后缓存需要失效；切换租户时清理请求和持久状态。
- 审计记录保留“谁在何时对哪个对象做了什么”，而不是只记页面访问。

## 复杂表单

- schema 描述字段、校验和条件关系，但不要把所有业务逻辑塞入不可调试的配置 DSL。
- 同步校验解决格式，异步校验处理唯一性或服务端规则；提交时服务端仍需全量校验。
- 草稿保存包含 schema 版本和冲突策略。
- 多人编辑用版本号/ETag 做乐观并发控制，不应静默覆盖他人修改。
- 大表单按步骤或区域延迟渲染，同时保留错误定位和键盘可访问性。

## 数据请求与错误

- Query key 包含影响结果的全部身份、租户和筛选条件。
- 取消过期请求，防止旧响应覆盖新页面。
- 将无权限、资源不存在、校验冲突、暂时失败和未知错误分开呈现。
- 写操作使用幂等键或版本条件；乐观更新必须能回滚并处理服务端最终结果。

## 性能与可观测性

先按真实用户数据定位：路由加载、接口、渲染、长任务还是内存。常见手段包括代码分割、虚拟列表、减少无效渲染和服务端分页，但每项都需同口径验证。

监控至少关联版本、路由、用户匿名标识、trace ID 和关键业务结果。敏感字段默认不采集，source map 和回放数据限制访问与保留期。

## 演进策略

- 用适配层包住旧 API 和组件，逐模块替换，避免长期双写业务逻辑。
- 共享组件先稳定契约和所有权，再抽包；“出现两次就抽象”通常过早。
- 微前端只在独立交付或存量治理收益明确时使用。
- 为弃用 API、feature flag 和临时兼容层设置移除条件。

## 验证清单

- 权限矩阵和对象级越权测试；
- 旧数据、空数据、冲突更新和离线恢复；
- 核心流程端到端测试与发布冒烟；
- p75 性能、错误率和内存的上线前后对比；
- 回滚后旧前端与新接口是否仍兼容。
