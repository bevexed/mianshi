# 可靠任务系统案例

本案例适用于报表、媒体处理、通知、数据同步和采集等后台任务。重点是交付语义和故障恢复，不限定具体队列产品。

## 系统边界

```text
业务请求 → 数据库事务/Outbox → 派发器 → 队列
                                      ↓
结果/状态 ← 业务存储 ← 幂等 Worker ← 重试与死信
```

先定义任务状态和业务结果的真相来源。队列状态适合调度，业务数据库适合对外查询；两者需要明确的同步和补偿方式。

## 一致性

“先写数据库再入队”会在进程崩溃时丢任务，“先入队再写数据库”会出现找不到业务记录。常见方案是事务 Outbox：在同一数据库事务中写业务记录和待发布事件，由独立派发器可靠入队并标记已发送。

这仍可能重复发布，所以 Worker 必须幂等。Exactly-once 往往只能在受限边界内实现，端到端系统更应按重复与重放设计。

## 幂等与并发

- 稳定业务键 + 数据库唯一约束守住最终结果。
- 状态更新带期望版本或合法前置状态，避免乱序覆盖。
- 外部服务使用幂等键；无此能力时保存调用记录并设计人工对账。
- 锁只保护临界区，必须有租约、所有者校验和超时；不要把长网络调用包进数据库锁。

## 重试与死信

- 区分暂时错误、限流、永久业务错误和程序缺陷。
- 暂时错误使用有上限的指数退避与抖动；总体重试预算防止下游恢复时形成流量洪峰。
- 永久错误进入 failed/dead-letter，保留脱敏上下文和可审计的人工重放入口。
- 重放前确认代码版本和输入 schema，避免用新逻辑误处理旧消息。

## 容量与背压

用到达率、平均处理时长、并发度和下游容量估算积压。监控队列长度之外，还要看最老任务年龄、端到端完成时间和各失败分类。

- 下游变慢时降低消费并发或暂停非关键任务。
- 为租户/任务类型设置公平性，避免大客户耗尽全部 Worker。
- CPU 密集任务与 I/O 任务分队列和资源池。
- 设置负载上限、过期策略和降级，而不是无限接收任务。

## 发布与恢复

- 新旧 Worker 在滚动发布期间要兼容消息 schema。
- 优雅停机停止领取新任务，并为在途任务设置可取消边界。
- 定期演练 Worker 崩溃、Redis/消息系统不可用、下游 429、数据库超时和重复消息。
- 对账任务寻找“业务状态长时间未完成”“outbox 未发布”和“队列完成但结果缺失”等不变量破坏。

## 结果验证

至少记录任务成功率、端到端 p95、重试率、永久失败率、积压年龄、重复抑制次数和恢复时间。吞吐提升如果以更多重复写、下游错误或 Redis 内存为代价，不是有效优化。
