# 经历表达与职业规划

职业类问题没有通用“高分答案”。可信表达来自一致的事实、清楚的选择标准和对未来岗位的匹配判断。

## 经历介绍

用一条主线连接经历，而不是从第一份工作逐年报流水账：

```text
当前定位 → 两三个关键能力与证据 → 最近的成长变化 → 为什么匹配目标岗位
```

每个案例只保留与岗位相关的背景、个人行动和可验证结果。不要把团队全部产出归为个人，也不要用无法解释的数据美化影响。

## 离职与空档

- 说明客观事实和决定标准，不评价具体个人。
- 把重点放在希望承担的职责、工作方式和成长方向。
- 短期经历如实写清合同关系、职责和结束原因；避免为了“看起来稳定”篡改日期。
- 空档期说明实际活动和产出，没有产出也不必虚构长期规划。

可以使用的结构：

```text
事实：当时发生了什么
判断：哪些条件与长期目标不匹配
行动：如何处理交接或调整
未来：目标岗位需要满足什么，以及自己能贡献什么
```

## 职业规划

职业规划不需要预测五年后的职位名称，重点是方向、能力缺口和下一步：

- 希望解决哪类问题、服务哪类用户或系统；
- 想走资深个人贡献者、技术负责人还是管理方向，当前倾向和依据是什么；
- 下一阶段需要补哪些能力，如何通过项目和反馈验证；
- 什么工作环境能支持这些目标，自己愿意承担哪些代价。

允许方向随事实更新。比“固定三年当架构师”更可信的是说明决策标准和最近一年的可执行计划。

## 管理与协作题

### 任务分配

结合业务优先级、风险、人员熟悉度和成长机会分配。关键任务设置 owner 和备份，公开依赖和完成标准，不用平均分工作量代替负责。

### 技术分歧

先对齐目标和约束，列备选方案，用小实验、数据或可逆性降低争论成本。负责人最终决策时记录理由和复盘条件，不把职位当论据。

### Code Review

自动化检查格式和基础错误，评审重点放在行为、边界、可维护性和风险。评论具体到影响和建议，重要设计在编码前沟通，避免 PR 末尾才推翻方案。

### 绩效与反馈

及时、具体地反馈观察到的行为和影响，听取上下文，共同约定下一步。不要把第一次出现的问题积累到正式绩效周期才提出。

## 自检

- 时间、职责和结果能否与简历及背调信息一致？
- 每个“主导/优化/搭建”能否说清亲自做的动作？
- 结果数据是否有基线、口径和来源？
- 是否泄露客户、同事、薪资、源代码或公司内部敏感信息？
- 目标岗位不带人或技术栈不同，自己的核心价值是否仍成立？
