## 四种规范

| 规范         | 语法                         | 环境                | 加载               |
| ------------ | ---------------------------- | ------------------- | ------------------ |
| **CommonJS** | `require` / `module.exports` | Node                | **运行时同步**     |
| **ESM**      | `import` / `export`          | 浏览器 + Node       | **编译时静态分析** |
| **AMD**      | `define` / `require`         | 浏览器（RequireJS） | 异步               |
| **UMD**      | 兼容写法                     | 通用                | 运行时判断环境     |

AMD 和 UMD 现在基本只在老库的产物里见到，了解即可。

## CommonJS vs ESM（核心考点）

### 1. 加载时机

- **CJS 是运行时加载**——`require()` 是一个函数调用，
  可以写在 if 里、可以拼接路径
  ```js
  const m = require(condition ? './a' : './b'); // ✅ 合法
  ```
- **ESM 是编译时静态分析**——
  `import` 声明会被提升，路径必须是字符串字面量
  ```js
  import m from condition ? './a' : './b'        // ❌ 语法错误
  const m = await import(path)                    // ✅ 动态导入
  ```

**这是 Tree Shaking 只能基于 ESM 的根本原因**——
只有静态结构才能在打包时确定哪些导出没被使用。

### 2. 导出对象和 live binding

**这是最容易考的细节：**

```js
// CJS：module.exports 是缓存的普通对象；解构会取得当时的属性值
// a.js
let count = 1;
setTimeout(() => count++, 100);
module.exports = { count };

// b.js
const moduleA = require('./a');
const { count } = moduleA;
setTimeout(() => console.log(count), 200); // 1（解构出的局部值不更新）
setTimeout(() => console.log(moduleA.count), 200); // 仍是 1，因为导出对象属性没有被更新
```

```js
// ESM：导出的是绑定（live binding）
// a.js
export let count = 1;
setTimeout(() => count++, 100);

// b.js
import { count } from './a';
setTimeout(() => console.log(count), 200); // 2（引用原始绑定）
```

**ESM 的导入是只读绑定**——不能给 import 进来的变量赋值。

不能简单说“CommonJS 永远导出值拷贝”：如果导出的是对象，所有调用方拿到的是
同一个缓存对象引用，后续修改它的属性可以被看到；上例看不到更新，是因为模块只修改了
局部变量 `count`，没有同步修改 `module.exports.count`。

### 3. 循环依赖的表现

- **CJS**：拿到的是**部分完成的 exports 对象**（可能是空的）
- **ESM**：因为有提升和 live binding，函数声明能正常工作，
  但访问未初始化的变量会 TDZ 报错

### 4. this 的指向

- CJS 模块顶层 `this` === `module.exports`
- ESM 模块顶层 `this` === `undefined`

### 5. 顶层 await

- CJS：❌ 不支持
- ESM：✅ 支持（ES2022）

## Node 里怎么区分

```json
// package.json
{ "type": "module" }    // .js 按 ESM 解析
{ "type": "commonjs" }  // .js 按 CJS 解析（默认）
```

- `.mjs` → 强制 ESM
- `.cjs` → 强制 CJS

### 互相引用的限制

|           | 能否引用     | 说明                                                                             |
| --------- | ------------ | -------------------------------------------------------------------------------- |
| ESM → CJS | ✅           | 默认导入最可移植；具名导入取决于运行时静态分析能力                               |
| CJS → ESM | 优先动态导入 | `await import('x')` 最可移植；新版 Node 对部分同步 ESM 提供有限 `require()` 支持 |

**这就是"ESM/CJS 双模态地狱"的来源**——
库作者要同时发布两套产物。

## exports 字段

现代包用 `exports` 声明入口，同时支持两种规范：

```json
{
	"exports": {
		".": {
			"types": "./dist/index.d.ts",
			"import": "./dist/index.mjs",
			"require": "./dist/index.cjs"
		}
	}
}
```

**注意**：`exports` 一旦声明，**就封闭了包的内部路径**——
使用方不能再 `import 'pkg/src/internal'`，除非显式暴露。
这是好事（明确的公共 API 边界），但升级依赖时可能踩到。

## 常见追问

**Q：为什么 `import lodash from 'lodash'` 经常难以 tree shake？**
→ lodash 主包主要以 CommonJS 入口发布，静态分析和副作用判断比 ESM 困难。
用 `lodash-es` 或 `import debounce from 'lodash/debounce'`。

**Q：动态 `import()` 返回什么？**
→ 一个 Promise，resolve 后是模块的 namespace 对象
（默认导出在 `.default` 上）。
