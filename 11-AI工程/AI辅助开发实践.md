# AI 辅助开发实践

AI 编码工具的价值不只在生成代码，更在于缩短理解、验证和重复修改的反馈周期。工程目标应是提高可验证的交付效率，而不是最大化生成量。

## 适合与不适合直接委托的工作

适合：

- 定位相关文件、解释陌生代码和生成修改草案；
- 机械迁移、样板代码、测试用例和文档同步；
- 基于日志和可复现步骤提出诊断假设；
- 在明确 schema 下转换或汇总数据。

需要更严格人工控制：

- 鉴权、支付、隐私、并发一致性和数据迁移；
- 缺少测试或无法回滚的核心逻辑；
- 需求本身含糊、跨团队责任未明确的改动；
- 许可证、合规或生产权限敏感的工作。

## Agent 的基本闭环

```text
目标 → 获取上下文 → 制订步骤 → 调用工具 → 读取结果
  ↑                                      ↓
  └──────── 修正假设 / 继续 / 停止 ←──────┘
```

一个可控 Agent 至少需要：工具权限边界、任务状态、失败处理、终止条件和验证标准。能循环调用工具不代表能安全自主完成任务；Host 仍需约束危险操作并提供确认机制。

## 上下文工程

1. 提供与任务相关的代码、接口、规范和失败输出，而不是无差别塞入整个仓库。
2. 把不可违反的约束写成可检查规则，例如类型检查、lint、测试和目录边界。
3. 对易变知识使用检索或工具实时读取，并保留来源与版本。
4. 长任务维护简短的决策记录，压缩过期探索过程。
5. 限制秘密、个人数据和生产信息进入第三方模型上下文。

## 指令与结构化输出

- 明确目标、范围、完成标准和禁止事项。
- 需要机器消费时使用 schema 或工具参数，而不是只给一段格式描述。
- 示例用于澄清边界，不应与规则互相冲突。
- 对不确定信息要求标注假设和证据，允许回答“资料不足”。
- 指令修改要通过固定任务集评测，避免只凭一次体验判断。

## 团队接入方式

| 层次       | 重点                                       |
| ---------- | ------------------------------------------ |
| 个人辅助   | 代码解释、补全、测试和小范围重构           |
| 仓库上下文 | 架构约束、组件规范、命令和代码所有权       |
| 流程集成   | PR 摘要、静态检查、测试建议、变更风险提示  |
| 平台治理   | 模型与数据策略、权限、审计、成本和质量评测 |

AI 生成代码与人工代码使用同一质量门槛：作者必须理解变更，reviewer 检查行为和风险，CI 验证可自动化约束。不能把“由 AI 生成”当成降低责任的理由。

## 常见失败模式

- 引用不存在或已过时的 API；
- 只满足正常路径，遗漏空值、权限、并发和回滚；
- 为迎合指令修改无关代码，扩大 diff；
- 测试验证了实现细节，却没有验证需求行为；
- 长任务中忘记早期约束或重复劳动；
- 把工具返回的恶意文本当成高优先级指令。

对应措施是缩小变更、提供真实输出、分阶段验收、执行独立测试，并对外部内容和工具结果保持不信任。

## 评估收益

不要只记录“生成了多少行”。更有意义的指标包括：

- 从需求到可评审变更的周期；
- review 返工次数和缺陷逃逸率；
- 测试覆盖的关键行为数量；
- Agent 任务成功率、人工接管率、延迟和成本；
- 开发者能否解释并维护最终代码。

用同类任务做前后对比，并观察质量是否下降。速度提升但返工和线上缺陷增加，不是有效收益。
