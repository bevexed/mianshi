# AI 辅助开发实践

AI 编码工具的价值不只在生成代码，更在于缩短理解、验证和重复修改的反馈周期。工程目标应是提高可验证的交付效率，而不是最大化生成量。

## 适合与不适合直接委托的工作

适合：

- 定位相关文件、解释陌生代码和生成修改草案；
- 机械迁移、样板代码、测试用例和文档同步；
- 基于日志和可复现步骤提出诊断假设；
- 在明确 schema 下转换或汇总数据。

需要更严格人工控制：

- 鉴权、支付、隐私、并发一致性和数据迁移；
- 缺少测试或无法回滚的核心逻辑；
- 需求本身含糊、跨团队责任未明确的改动；
- 许可证、合规或生产权限敏感的工作。

### 按风险决定 AI 的自主程度

| 风险 | 任务示例 | AI 自主程度 |
| ---- | -------- | ----------- |
| 低 | 样板代码、文档同步、局部字段修改 | 可生成初稿，人工审查并运行基础检查 |
| 中 | 跨层 CRUD、状态流转、树结构、缓存 | 先方案和测试清单，再分片实施 |
| 高 | 鉴权、支付、租户、迁移、并发一致性 | 只辅助分析，关键决策和发布由人完成 |

风险分级用于决定协作方式，而不是给高风险改动贴上“不能做”的标签。风险越高，越要缩小工具权限、补全证据与回滚方案，并把需求解释、决策、审批和发布留给人。

## 从需求到交付的个人闭环

下面的顺序适用于不同语言和工具；每一步都要留下下一步可检查的输入，而不是把一次生成当成完成。

1. **任务风险分级**：识别数据、权限、兼容、并发、迁移和回滚风险，确定 AI 只能生成草案、能否执行本地命令，以及哪些动作必须人工确认。
2. **读取仓库规则**：先读 README、目录说明、贡献规范、构建命令和局部规则，确认分层、代码风格、测试约定与禁止改动的范围。
3. **检索相似实现**：用已稳定的模块、接口和测试作为候选模式，核对哪些约定可复用；相似不等于相同，不能据此推断当前业务规则。
4. **明确业务不变量**：把权限、状态、唯一性、删除语义、事务、租户、兼容性等写成可检查条件；缺少证据的规则标记为待确认，而不由 AI 以常见做法补全。
5. **方案与影响面**：先列改动文件、数据流、依赖、风险、验证和回滚点，确认接口、数据库、缓存、前后端或外部服务可能受影响的边界。
6. **垂直切片实现**：每次只完成一个能走通的最小路径，例如模型、业务逻辑、接口和相应测试；保持小 diff、可回滚，逐阶段验收后再扩大范围。
7. **分层验证**：按变更风险组合运行测试、类型检查、编译、联调，并进行人工 diff 审查；任何一种检查通过都不代表其余检查已被替代。
8. **复盘与沉淀**：记录实际失败、遗漏约束、有效验证和可复用规则，把已确认的边界转成回归测试、文档或任务模板。

### 分层验证分别验证什么

| 检查 | 主要能发现什么 | 不能替代什么 |
| ---- | -------------- | ------------ |
| 测试 | 需求定义的可观察行为、边界条件、已知历史缺陷和回归问题 | 不能证明所有类型、模块装配、真实环境与改动范围都正确 |
| 类型检查 | 字段、接口、调用签名和可空性等静态约束不一致 | 不能理解权限、业务语义、运行时配置或数据事实 |
| 编译 | 模块依赖、语法、生成代码或构建配置导致的集成问题 | 不能证明业务规则、真实 SQL、请求链路或用户可见行为正确 |
| 联调 | 请求/响应契约、序列化、鉴权、真实依赖、数据与环境配置之间的断点 | 不能替代对全部分支的自动回归，也不能替代人工的范围判断 |
| 人工 diff 审查 | 改动是否在范围内、是否夹带无关重构、是否符合现有模式，以及 AI 是否遗漏未写在代码里的业务约束 | 不能替代可重复执行的测试和构建证据 |

测试场景先从需求和历史缺陷推导，再让 AI 协助补充或实现测试草案。若先让 AI 阅读实现后生成“必过”测试，测试往往只是在复述当前实现，难以证明需求真的被满足。

## Agent 的基本闭环

```text
目标 → 获取上下文 → 制订步骤 → 调用工具 → 读取结果
  ↑                                      ↓
  └──────── 修正假设 / 继续 / 停止 ←──────┘
```

一个可控 Agent 至少需要：工具权限边界、任务状态、失败处理、终止条件和验证标准。能循环调用工具不代表能安全自主完成任务；Host 仍需约束危险操作并提供确认机制。

## 上下文工程

1. 提供与任务相关的代码、接口、规范和失败输出，而不是无差别塞入整个仓库。
2. 把不可违反的约束写成可检查规则，例如类型检查、lint、测试和目录边界。
3. 对易变知识使用检索或工具实时读取，并保留来源与版本。
4. 长任务维护简短的决策记录，压缩过期探索过程。
5. 限制秘密、个人数据和生产信息进入第三方模型上下文。

## 指令与结构化输出

- 明确目标、范围、完成标准和禁止事项。
- 需要机器消费时使用 schema 或工具参数，而不是只给一段格式描述。
- 示例用于澄清边界，不应与规则互相冲突。
- 对不确定信息要求标注假设和证据，允许回答“资料不足”。
- 指令修改要通过固定任务集评测，避免只凭一次体验判断。

## 团队接入方式

| 层次       | 重点                                       |
| ---------- | ------------------------------------------ |
| 个人辅助   | 代码解释、补全、测试和小范围重构           |
| 仓库上下文 | 架构约束、组件规范、命令和代码所有权       |
| 流程集成   | PR 摘要、静态检查、测试建议、变更风险提示  |
| 平台治理   | 模型与数据策略、权限、审计、成本和质量评测 |

AI 生成代码与人工代码使用同一质量门槛：作者必须理解变更，reviewer 检查行为和风险，CI 验证可自动化约束。不能把“由 AI 生成”当成降低责任的理由。

## 常见失败模式

- 引用不存在或已过时的 API；
- 只满足正常路径，遗漏空值、权限、并发和回滚；
- 为迎合指令修改无关代码，扩大 diff；
- 测试验证了实现细节，却没有验证需求行为；
- 长任务中忘记早期约束或重复劳动；
- 把工具返回的恶意文本当成高优先级指令。

对应措施是缩小变更、提供真实输出、分阶段验收、执行独立测试，并对外部内容和工具结果保持不信任。

## 真实心得与反模式

- AI 最擅长缩短定位信息、梳理调用链和形成候选实现的时间；最容易遗漏的是未写进代码的隐含业务约束、历史数据语义和责任边界。
- 高质量输入的核心是范围、不变量、证据和完成标准，而不是华丽提示词。没有这些输入时，工具的流畅输出仍只是待验证的假设。
- 一次生成大量代码会放大遗漏、审查和回滚成本；小 diff、可回滚和逐阶段验收更可靠。
- 不把测试、类型检查、编译、联调或人工 diff 审查中的任一项，当作其他层的替代品；根据失败模式补齐相应证据。
- 最终责任属于提交、评审和发布代码的人。AI 可以提出方案、草案和诊断假设，但不能接管需求解释、风险接受、合并和发布决定。

## 评估收益

不要只记录“生成了多少行”。更有意义的指标包括：

- 从需求到可评审变更的周期；
- review 返工次数和缺陷逃逸率；
- 测试覆盖的关键行为数量；
- Agent 任务成功率、人工接管率、延迟和成本；
- 开发者能否解释并维护最终代码。

用同类任务做前后对比，并观察质量是否下降。速度提升但返工和线上缺陷增加，不是有效收益。
