# AI 辅助开发实践

> 这块题在 2025-2026 年几乎必问，尤其你简历上有 MCP。
> **面试官真正想知道的是：你是把 AI 当玩具，还是当工程手段。**

## AI 怎么提升开发效率（最常见的开场题）

**❌ 平庸答法**：「用 Cursor 写代码很快」

**✅ 分层答法**：

| 层次 | 做什么 | 效果 |
|---|---|---|
| **个人使用** | 补全、写样板代码、改 bug、写测试 | 快，但天花板明显 |
| **上下文工程** | 给 AI 提供项目规范、组件库、架构约定 | **质量跃升**——AI 产出符合团队规范 |
| **流程集成** | code review 辅助、PR 描述生成、CI 里跑 | 团队级收益 |

**你的差异化就在第二层**——大多数人停在第一层。

> 我做 MCP 服务的时候意识到，
> 现在拉开差距的不是「会不会用 AI 写代码」，
> 而是「能不能把 AI 变成团队基建的一部分」——
> 上下文怎么给、产出怎么校验、怎么和现有工程流程结合。

## Agent 是什么

**能自主规划并调用工具完成多步任务的 AI 系统。**

和单次问答的区别：
```
问答：  输入 → 模型 → 输出
Agent： 输入 → 模型规划 → 调用工具 → 看结果 → 再规划 → ... → 输出
```

**关键组成**：
- **工具调用（Tool Use / Function Calling）**——模型能调外部能力
- **循环（Loop）**——根据工具返回结果决定下一步
- **上下文管理**——长任务中如何保留必要信息
- **终止条件**——什么时候算完成

**MCP 就是给 Agent 提供工具的标准化方式**——
这是两个概念的连接点，能说清很加分。

## Prompt 怎么设计

**别背"角色扮演/给例子"这种老生常谈，讲工程化的部分：**

1. **明确输出格式**——要 JSON 就给 schema，
   现在更好的做法是用**结构化输出/工具调用**约束，而不是祈祷模型听话
2. **给约束而不是给鼓励**——
   「不要虚构不存在的组件」比「请认真回答」有效
3. **提供上下文而不是要求记忆**——
   与其描述规范，不如把规范文档检索出来放进去（这就是 RAG）
4. **少样本示例（few-shot）**——对格式要求高的任务效果显著
5. **可迭代**——prompt 要能测。改了之后怎么知道变好了？
   → 需要 evals

## 团队怎么用 AI（管理向，你是负责人）

**这题很可能被问，因为你带 4 人团队。**

> 我们团队用 AI 主要在三个地方：
>
> 一是日常编码，这个各人自己用，我不做强制。
>
> 二是**上下文规范化**——我做了 UI 规范的 MCP 服务，
> 让 AI 生成组件代码时能查到我们自己的设计系统，
> 而不是凭空造一个 div 加样式。这是团队级的收益。
>
> 三是**卡口**——AI 生成的代码同样要过 ESLint、类型检查和 review。
> 我不认为 AI 产出可以豁免这些。
>
> 【需确认】我比较警惕的是**大段 AI 生成的代码没人真正读过**就合进去，
> 所以 review 时我会问一句"这段你自己讲得清吗"。

**最后那句非常加分**——显示你意识到了 AI 的风险而不只是好处。

## AI 编码工具的对比（可能被问用过哪些）

按你的实际情况答，别硬吹。常见的：
- **Cursor / Windsurf**——IDE 集成，补全和多文件编辑
- **Claude Code / Codex CLI**——终端 Agent，适合大改动和自动化
- **GitHub Copilot**——补全为主，生态最广

**回答要点**：说清**你用它做什么**比说用过哪个重要。
> 我主要用它做两类事：
> 一是重复性改造（比如把一批组件从 class 改成 hooks）；
> 二是陌生领域的探路（做 NestJS 服务时它帮我快速理解 BullMQ 的 API）。
> 核心业务逻辑我仍然自己写，因为出问题时要能改。

## AI 的局限（必须能说）

- **会自信地编造**——不存在的 API、不存在的配置项
- **不知道你的私有上下文**——这正是 MCP/RAG 要解决的
- **长任务会偏离**——需要人拆解和验收
- **代码能跑 ≠ 代码对**——边界条件、并发、安全往往考虑不到

**能坦率说局限的人，比一味吹 AI 的人可信得多。**
