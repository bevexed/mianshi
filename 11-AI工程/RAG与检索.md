# RAG 与检索

## RAG 是什么

**Retrieval-Augmented Generation（检索增强生成）**——
在让模型回答之前，先从外部知识库检索相关内容，
把检索结果塞进上下文再生成。

### 为什么需要 RAG（而不是全塞进 prompt）

1. **上下文窗口装不下**——完整文档体量太大，既超限又贵
2. **塞进去也会被稀释**——大量无关内容会降低模型对关键信息的注意力，
   给 100 个组件的文档不如**精准给出当前需要的那 3 个**
3. **知识会变**——硬编码在 prompt 里的内容会过期，
   RAG 读的是**当前**的数据
4. 需要的是「**按需检索**」而不是「一次性灌输」

> **给 AI 提供什么上下文，比怎么问 AI 更能决定产出质量。**

---

## Embedding 是什么

把文本转成**高维向量**，语义相近的文本在向量空间中距离也近。

- 检索时把 query 也转成向量，找距离最近的 K 个文档块
- 常用距离度量：余弦相似度
- **中文场景的坑**：很多默认 embedding 模型（如 `all-MiniLM-L6-v2`）
  是英文为主的，**中文效果会明显打折**，
  需要换中文/多语言模型（bge-m3、text-embedding-3 等）

---

## 为什么要混合检索（向量 + 关键词）

**这题是 RAG 的深度分水岭。**

| | 擅长 | 失效场景 |
|---|---|---|
| **向量检索** | 语义相似，「怎么做一个下拉选择」能匹配到 Select 组件 | **精确名词**——查 `NgTable` 这种专有组件名时，相似度未必排第一 |
| **关键词检索**（BM25/MiniSearch） | 精确匹配组件名、prop 名、错误码 | 语义泛化能力为零，换个说法就查不到 |

**UI 规范这类场景两种查询都很常见**——
既有"我要做个带搜索的下拉"（语义），
也有"NgSelect 的 mode 属性有哪些值"（精确），所以必须混合。

### 结果融合

- **RRF（Reciprocal Rank Fusion）**——
  按各路结果的排名倒数加权合并，不需要归一化分数，最常用
- 或者加权打分后去重

## Chunking（切分）

**RAG 的效果七成取决于切分。**

### 原则

- **不能按固定字符数暴力切**——
  会把一个组件的说明和它的 props 表格切散
- **按语义结构切**：
  Markdown 按**标题层级**切（用 remark 解析出 AST，按 heading 分块），
  保证一个 chunk 是语义完整的一节
- **保留上下文**：
  组件的 props 表格单独成块时，
  **要带上组件名作为前缀**，否则脱离上下文后检索不到
- **overlap**：相邻 chunk 留一点重叠，避免边界信息丢失

### metadata 过滤

给 chunk 加 metadata（组件名、分类、文档来源），
检索时可以先按 metadata 过滤再算相似度——
这比纯向量检索精准得多。

## evals：怎么评估检索质量

**很多做 RAG 的人根本不做评测，做了就是差异化。**

### 为什么要做

RAG 系统的调参（chunk 大小、top-k、混合权重）
如果靠人工抽查，改一个参数不知道是变好还是变坏，**纯凭感觉**。
必须有**可重复的评测集**。

### 怎么做

构造一批「查询 → 期望命中的文档」用例，
跑检索后看期望文档有没有进 top-k。

**指标**：
- **Recall@k**——期望结果出现在前 k 个的比例
- **MRR**（Mean Reciprocal Rank）——期望结果排名倒数的均值
- **NDCG**——考虑排序位置的加权

### 分两层评

> **RAG 的评测要分检索层和生成层。**
> 我这个场景重点评的是检索层，因为生成是交给 AI 编码工具的，我控制不了；
> **我能控制的是给它的上下文准不准。**

**这句话显示你想清楚了系统边界。**

---

## 索引怎么更新

- **全量重建**——简单，适合数据量小、更新不频繁
- **增量更新**——按文档 hash 判断变更，只重新 embed 变化的部分
- **触发时机**：CI 里组件库发版时触发，或定时任务

**如果只做了手动重建，诚实说**：
> 目前是手动触发重建，量不大还能接受。
> 如果要推广到更多团队，这是首先要补的。
