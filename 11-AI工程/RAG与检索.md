# RAG 与检索

RAG（Retrieval-Augmented Generation，检索增强生成）在生成前检索外部资料，把相关证据加入上下文。它适合知识经常变化、需要来源依据或资料超出上下文容量的任务，但会新增索引、召回、权限和评测链路。

## 基本流程

```text
资料采集 → 清洗与切分 → 建立索引
                           ↓
问题 → 查询改写/过滤 → 召回 → 重排 → 上下文组装 → 生成 → 引用与校验
```

RAG 不能自动保证事实正确。检索可能漏掉证据，文档本身也可能过期或相互矛盾；生成阶段仍要约束回答只依据可用证据，并在证据不足时明确拒答或降级。

## 稀疏、稠密与混合检索

| 方式                   | 优势                         | 常见短板                               |
| ---------------------- | ---------------------------- | -------------------------------------- |
| 关键词/BM25 等稀疏检索 | 精确名称、编号、错误码、术语 | 对同义改写和语义表达不敏感             |
| 向量/稠密检索          | 语义近似、自然语言改写       | 可能错过精确标识，受模型与语料语言影响 |
| 混合检索               | 兼顾两类信号                 | 需要融合、调参和更复杂的评测           |

是否混合取决于查询分布。专有名词多的技术文档通常受益明显；结构化过滤已经很强的小数据集未必需要两套索引。

多路结果可使用 RRF（按排名融合）或经过校准的加权分数合并，再由 reranker 精排。RRF 的优势是不要求不同检索器分数同尺度，并不代表它总是最佳默认值。

## Embedding 与向量索引

Embedding 把文本映射为向量，检索时比较查询与文档向量的相似度。选型时要测试：

- 实际语种、领域术语和代码混合文本；
- 维度、吞吐、成本和数据驻留要求；
- 模型升级后是否需要重建索引；
- 余弦、点积或欧氏距离是否与模型建议一致。

不要仅凭公开榜单决定模型。用自己的查询—相关文档数据集比较召回质量，索引中记录模型版本，避免不同向量空间混用。

## Chunking

切分目标是让每个 chunk 既包含完整语义，又足够聚焦。常见策略：

- Markdown 按标题和段落结构切，表格、代码和说明尽量保持在一起。
- 为片段补充文档标题、章节路径、版本、权限等 metadata。
- 超长章节再按 token 上限细分；overlap 只在跨边界信息确有价值时使用。
- 对 API 文档、FAQ、工单等不同资料采用不同切分器。

固定字符切分适合做基线，并非一律错误；结构切分也需要用数据证明收益。过多 overlap 会增加索引体积和重复上下文。

## 权限与时效

- 检索前按用户或租户权限过滤，不能“先召回敏感文档、再让模型别说”。
- 索引记录来源、更新时间、版本和失效状态。
- 删除或降权过期内容，保证源删除后索引也能同步删除。
- 对需要强时效的资料设置更新延迟目标，并监控索引滞后。

## 评测

将系统分层，才能定位问题：

| 层次   | 示例指标/检查                            |
| ------ | ---------------------------------------- |
| 检索   | Recall@k、MRR、NDCG、过滤正确率          |
| 上下文 | 证据覆盖率、重复率、token 成本           |
| 生成   | 忠实度、答案相关性、引用正确性、拒答质量 |
| 线上   | 任务成功率、延迟、成本、用户纠错率       |

评测集应覆盖精确术语、同义改写、多跳问题、无答案问题、权限边界和过期文档。参数调整前后使用同一版本数据集对比，同时保留人工误差分析；单一平均分可能掩盖关键场景退化。

## 索引更新

- 小规模资料可全量重建，流程简单且容易验证。
- 大规模资料按内容 hash 增量更新，并对删除、重命名和权限变化单独处理。
- 蓝绿索引或版本别名可以在重建后原子切换，避免用户读到半成品。
- 定期做源数据与索引的对账，不能只依赖“更新任务成功”日志。
