# MCP（Model Context Protocol）

## MCP 是什么，解决了什么问题

- **MCP 是 Anthropic 提出的开放协议**，
  用来标准化「AI 应用」和「外部上下文/工具」之间的连接
- **解决的是 M×N 问题**：
  过去每个 AI 客户端要对接每个数据源都得写一套适配，
  N 个工具 × M 个客户端 = M×N 份集成代码；
  有了 MCP，工具只实现一次 Server，
  所有支持 MCP 的客户端都能用——**变成 M+N**

常被类比为「**AI 应用的 USB-C 接口**」。

---

## 三种原语：Tools / Resources / Prompts

**这题能筛掉 90% 只是听说过 MCP 的人。**

| 原语 | 谁来触发 | 类比 | 典型用途 |
|---|---|---|---|
| **Tools** | **模型**决定调用 | POST 接口 / 函数调用 | 查询、执行操作——有副作用或需要模型判断时机 |
| **Resources** | **应用/用户**选择 | GET 接口 / 文件 | 把某份文档作为上下文附加进去 |
| **Prompts** | **用户**主动触发 | 快捷命令 / 模板 | 预设好的工作流 |

**核心区别是「谁决定用它」**——
Tools 是模型自主决策，Resources 是应用侧挑选，Prompts 是用户显式调用。

## 传输层

| 方式 | 场景 |
|---|---|
| **stdio** | 本地进程，客户端直接启动 Server 子进程通信。最简单，适合本地工具 |
| **Streamable HTTP**（较新）<br>早期是 HTTP + SSE | 远程服务，适合**团队共享部署** |

**选型理由要能讲**：
> 我们做的是给团队用的服务，规范文档在服务端统一维护和更新，
> 不需要每个同事本地跑一份、也不用各自同步文档，
> 所以用 HTTP 方式。

## 工具描述（description）怎么写

**这是 MCP 实践里最容易被忽略、但最影响效果的一环。**

- 模型是**靠 tool 的 name 和 description 决定要不要调用、怎么传参**的
- 描述写得含糊，模型就不调用或者传错参数
- 所以**工具描述本质上是写给模型看的 prompt**，
  不是写给人看的 API 文档

**实践**：描述里要写清楚「**什么时候该用这个工具**」，
而不只是「这个工具做什么」。

```
❌ "查询 UI 规范"
✅ "在编写或修改任何 UI 组件代码之前调用，用于查询公司设计系统中
    对应组件的名称、props 和使用规范。当用户要求实现表单、列表、
    弹窗等界面元素时应优先调用。"
```

## 怎么保证 AI 一定会调用它

**诚实答**：保证不了。MCP 只提供能力，调不调是模型决定的。

**提升调用率的手段**：
1. 工具描述写清楚触发时机
2. 在项目的规则文件（`CLAUDE.md` / `.cursorrules` / `AGENTS.md`）里
   明确要求「写组件前先查规范」
3. **除了 query 还提供 validate 工具**——
   事后校验能兜住事前没查的情况

---

## 安全考量（可能被追问）

MCP Server 暴露的是**可被模型自主调用的能力**，所以：
- 有副作用的操作要谨慎暴露（删除、发送、支付）
- Server 侧要做鉴权和入参校验，
  **不能假设调用方是可信的**
- 返回内容会进入模型上下文，注意不要泄露敏感数据

**这个思路和 Server Actions 的安全考量是一样的**——
凡是能被外部触发的端点，都要自己验。
