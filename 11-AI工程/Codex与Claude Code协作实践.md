# Codex 与 Claude Code 协作实践

> 【真实使用】本文只总结实际使用 Codex、Claude Code 的经验。

## 我的核心结论

我把 Codex、Claude Code 当作同一套工程流程中的协作工具：它们帮助我检索代码、解释调用链、整理候选方案和生成局部实现或测试草案；需求语义、风险判断、代码审查、验证和最终交付责任仍由我承担。

这套做法来自一次进入既有 Spring Boot 多模块工程的实践。面对菜单权限维护、应用市场分类路径和行业文件管理等需求，我不从“让工具一次写完功能”开始，而是先让它基于 README、相似模块和调用链还原工程约束，再把任务拆成可验证的小步骤。这样即使我面对的是陌生的 Java 工程，仍能说明请求如何经过 Controller、Service、Repository/DAO、Mapper、VO、Convert 到 SQL，以及权限、事务和异常分别在哪里生效。

我不会把工具生成的内容当成正确答案。不能解释的改动不提交；没有证据的业务规则不由工具补全；没有统计口径时，也不把主观感受包装成效率数字。

## 场景一：理解陌生代码库

开始编码前，我先限定阅读范围：需求涉及的接口和模型、一到两个相似实现、README 或模块规范，以及脱敏后的错误输出。随后让 Codex 或 Claude Code 协助回答：功能应放在哪个模块和包、现有接口返回与异常结构是什么、数据如何从请求流向落库、哪些文件可以改、哪些公共约定不能动。

例如菜单权限维护不是普通 CRUD。先追踪菜单、角色菜单关系和权限缓存的调用链，才知道新增、编辑、删除会牵连权限域、父子节点、角色关系、缓存和逻辑删除；再由我确认不改表结构、不清洗历史数据、前端路由仍以代码为准等边界。工具擅长快速定位和归纳，但“这个相似模式能否套用到当前业务”必须由我判断。

## 场景二：先做方案和风险清单

我要求先输出方案、影响文件和待确认项，不直接开始修改。方案把自然语言需求变成可审查条件：权限标识是否唯一、父子节点是否允许、状态能否切换、删除是否有引用、关联更新是否需要事务、历史逻辑删除记录是否仍占用唯一键，以及已有接口和数据是否兼容。

应用市场分类路径是一个典型例子。需求不是“多返回一个字段”这么简单，而是从叶子分类向上回溯父节点，反转为完整名称路径，并确保 Service 组装后的字段能穿过 Convert 到响应模型。先列清数据流与风险后，再决定批量取分类 Map、避免逐条查询，并把路径构造和字段传递作为两层验证目标。

如果方案存在未知信息，我会要求明确标成假设，并回到代码、需求方或团队规范确认；不会让 Codex 或 Claude Code 依据常见做法自行决定权限、租户或数据迁移规则。

## 场景三：小步实现和审查 diff

实现按垂直切片推进，而不是让工具修改整个仓库：请求/响应模型、数据访问、Service 业务约束、Controller 接口与权限、数据库脚本、目标测试和编译。每完成一层，我都逐文件看 diff：改动是否仍在任务范围、是否遵循现有分层、是否夹带无关格式化或重构、异常与事务是否符合项目模式。

菜单权限案例中，这个过程暴露过两个必须修正的问题：自定义菜单 ID 在 Convert 中没有保留，导致保存时仍走自动编号；自动编号只看未删除记录，但逻辑删除的历史 ID 仍会占用主键，可能造成冲突。前者通过补齐转换链路修复，后者改为在编号规则中考虑逻辑删除记录，并用回归测试固定。这说明“能编译”不等于实现已覆盖真实数据约束。

我的提交前标准是最小 diff 且有可检查证据：关键业务约束有对应代码或测试，目标测试与相关模块编译完成，数据库脚本可审查，必要时再做接口联调。是否合并、发布或回滚由人决定。

## 场景四：生成测试草案但由行为定义测试

Codex、Claude Code 可以把已明确的约束转换成 JUnit 5 和 Mockito 测试草案，但测试场景必须先由需求和历史问题定义，而不是先看实现再生成一组必然通过的断言。

我关注外部可观察行为：返回结果、业务异常、哪些 DAO 调用或不应调用、事务内的关联更新，以及权限缓存是否失效。对 Service，用 Mockito 隔离 DAO 来验证分支和协作；对 Convert 这类纯转换逻辑，则使用真实实现，避免 Mock 把字段遗漏隐藏起来。然后再通过编译和联调补足单测看不到的模块依赖、Spring 装配、真实 SQL、序列化和权限拦截问题。

因此测试的顺序是：业务不变量 → Given/When/Then 场景 → 预期结果 → 实现 → 回归。工具可以提议遗漏的边界，但我会检查这些测试在错误实现下是否真的会失败，并避免把私有方法调用次数等实现细节写死。

## 场景五：根据真实失败输出继续诊断

当测试、编译或联调失败时，我提供的是可复现步骤、最小相关日志和失败输出，而不是一句“修一下”。工具据此帮助我定位关联文件、列出假设和修复候选；我再核对调用链与业务不变量，决定是否修改。

例如逻辑删除主键冲突的排查，不能只看 ORM 查询结果“查不到”，还要确认数据库主键约束仍然存在、编号生成查询的过滤条件是什么、根节点与子节点的规则是否一致。修复后重新运行相关测试、检查 diff，并确认错误信息能让使用者理解“已删除记录仍占用 ID”。真实失败输出把诊断落到证据上，也能避免把工具的推测直接当结论。

## 长任务如何控制上下文

长任务中，我会把上下文维持在“当前切片所需”的尺度：保留任务目标、允许与禁止修改的范围、已确认的不变量、当前文件清单、验证命令及其真实输出；已排除的探索过程只留下简短结论。切换到下一切片时，重新读取相关模块和相似实现，而不是依赖对话记忆替代源码。

每轮输出都要求区分事实、假设、影响范围和下一步验证。这样出现上下文压缩、任务中断或需要人工接手时，仍能从记录恢复：已改了什么、为什么改、尚未证实什么、如何复现和回滚。工具读到的上下文越少而准确，敏感数据暴露面和无关改动风险也越小。

## 我不会交给 AI 自主完成的工作

以下工作可以让 AI 协助阅读、列风险或生成测试建议，但不能自主决定和执行：

- 生产数据库迁移、数据修复和生产 SQL；
- 支付金额、资金状态、登录鉴权和跨租户访问；
- 密钥、证书、生产环境配置，以及含客户隐私的完整日志；
- 不可回滚、缺少测试的核心链路；
- 需求责任边界未确认的跨团队变更；
- Git push、合并、部署和发布。

数据进入上下文前，我只提供完成任务所需的代码；生产数据、密钥、Token、Cookie、AK/SK、数据库密码和私钥不进入对话，客户日志先脱敏。仓库忽略本地工具文件只能减少误提交，不能证明模型侧绝不保留数据；工具使用许可、账号类型和数据保留政策必须以公司制度为准。

## 可复用任务模板

```text
目标：可验收的业务结果。
范围：允许修改和禁止修改的目录、文件、接口。
现有模式：README、相似模块、异常与返回结构。
业务不变量：权限、租户、状态、唯一性、事务、删除、兼容。
风险：敏感数据、历史数据、并发、缓存、迁移和回滚。
验证：测试、类型检查、编译、联调和人工检查。
输出：先列方案与影响范围；假设必须显式标注；保持最小 diff。
```

使用时我会再补上当前需求的具体禁止项和完成标准。例如菜单权限任务会明确：不改表结构、不清洗历史数据；删除前检查子节点和系统权限引用；角色关系变化后清缓存；逻辑删除记录仍占用主键；先给出测试场景与文件清单，再输出改动。模板的目的不是把工程判断交给工具，而是让判断前置、让结果可验证。

## 复盘心得

这次实践让我更重视“理解—约束—小步—验证”的闭环。Codex、Claude Code 提升了我检索陌生工程、解释局部代码和形成候选实现的速度，但它们不了解未写在代码中的团队约定与业务历史。真正降低返工风险的，是先写清不变量、控制变更范围、逐文件审查、把真实问题沉淀为回归测试。

我也会保留诚实边界：不能据此宣称所有 Java 代码都由我独立设计，不能在没有报告时宣称测试覆盖率，不能说所有检查已进入 CI 强制卡口，不能声称没有线上故障或 AI 上下文绝不留存。对未核实的制度、鉴权链路和运行记录，应明确说“需要确认”。

## 面试表达

> 我实际使用 Codex 和 Claude Code 协作进入一个既有的 Spring Boot 多模块工程。它们主要帮我检索代码、解释调用链、整理方案和生成局部实现、JUnit 5/Mockito 测试草案；我先确认 README 和相似模块的工程约束，再把权限、租户、事务、逻辑删除和兼容写成可检查的不变量。
>
> 实现时我按模型、数据访问、Service、Controller、SQL 和验证分层小步推进，逐文件看 diff。菜单权限改造里，我就通过这个流程发现并修复了 Convert 丢自定义 ID、逻辑删除记录仍占用主键这两类问题，再把它们固化为回归测试。最后还要运行目标测试、相关模块编译和必要的接口联调。
>
> 所以我不会把 AI 当成可自主交付的主体：生产数据、密钥、生产库、发布和高风险业务决策不交给它。工具提高的是形成可评审候选方案的效率，最终能否解释、验证、合并和承担责任仍在我。
