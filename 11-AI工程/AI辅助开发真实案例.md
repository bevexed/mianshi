# AI 辅助开发真实案例

这些案例用于面试口述，统一按照“结论 → 背景约束 → AI → 人工 → 修正 → 边界”展开。这里的 AI 协作仅指 Codex、Claude Code；候选代码、检索结果和测试草案都必须经过人工理解与验证。

## 一、进入 Spring Boot 3 多模块工程

### 30 秒回答

【真实项目】进入 Spring Boot 3 多模块工程后，我让 Codex、Claude Code 梳理 README 和调用链；我确认约束、分切片修改并验证。结论：AI 给候选实现，交付责任由我承担。

### 背景与约束

- 工程按 `common`、`infras`、`service`、`app`、`openapi` 拆分，已有分层、统一异常、鉴权、事务、逻辑删除和权限缓存约定。
- 我不是传统 Java 后端，目标是在既有规范内完成菜单权限、应用市场等功能，不能为了赶进度改变公共结构或扩散改动范围。
- 不能把密钥、生产数据、客户日志交给 AI，也不让 AI 连接生产库、执行部署或发布。

### AI 做了什么

- 检索 README、相似模块和调用链，整理现有工程规则与各层职责。
- 为一个小的垂直切片生成 VO、数据访问、Service、Controller 或测试的候选初稿，并列出可能的边界。
- 协助解释编译或测试失败输出，供我定位下一步检查点。

### 我做了什么

- 决定任务风险等级、改动范围、权限与事务边界，并把需求约束列为可审查条件。
- 每次只推进“请求/响应模型 → 数据访问 → Service → Controller → SQL → 验证”的一个切片，逐文件查看 diff。
- 用 JUnit 5/Mockito 验证业务分支；对 Convert 直接使用真实实现；再执行目标测试、Maven 编译和接口联调。

### 问题与修正

首次接入并非直接出错在语法，而是风险在于“语法正确但不属于这个工程”。因此把先读工程、找相似实现、明确约束作为编码前置条件；发现无法解释的变更就不把它视为可交付代码。后续菜单的 Convert 丢字段、逻辑删除占位等问题也证明，仅能编译不足以覆盖历史数据和真实业务规则。

### 心得与边界

AI 负责阅读、检索、解释和生成候选实现；我负责需求语义、数据与权限边界、测试标准、是否合并以及发布回滚决定。目标测试和编译是我执行的验证动作；当前是否存在 CI 强制卡口仍需核对，不能按推测表述。

## 二、Convert 丢失自定义菜单 ID

### 30 秒回答

【真实项目】菜单新增首次允许自定义 ID，但 Convert 丢失字段，最后仍走自动生成。AI 帮我追调用链；我补齐转换并加回归测试。结论：编译通过不等于字段在各层保留，验收由我负责。

### 背景与约束

- 菜单权限原先依赖 Excel 和 SQL 维护，历史数据存在重复主键、空名称等不一致；改为后台 UI 维护时不能扩大角色权限，也不能破坏路由和授权逻辑。
- 前端传入自定义 ID 是明确业务输入，不能在转换层静默丢失，更不能用自动生成掩盖该问题。

### AI 做了什么

- 快速梳理 MenuEntity、MenuService、角色菜单关系、缓存清理的调用链。
- 根据已有分层提供候选实现，并在问题出现后协助检索自定义 ID 的完整数据流。

### 我做了什么

- 确认不改表结构、不清洗历史数据，数据库仍是菜单数据的唯一来源。
- 从请求模型、Convert、Service 到落库逐层审查字段去向，判断自定义 ID 应被保留而不是自动改写。
- 审查接口鉴权、事务和测试场景，最终补齐转换逻辑及回归测试。

### 问题与修正

第一次候选实现允许了输入字段，却遗漏了 Convert 的字段映射，导致自定义 ID 没有进入后续处理。修正不是只在最后一层“补一个值”，而是补齐该转换逻辑，并用真实 Convert 的测试防止以后再次漏字段。

### 心得与边界

这个缺陷说明 AI 生成的候选代码、甚至通过编译的分层实现，仍可能在字段穿透处偏离需求。测试要覆盖外部可观察的业务行为，而不是只断言某个内部实现细节；最终映射语义和验收由人工确认。

### 60～90 秒展开

我会先讲清楚这不是“AI 写错了一行代码”这么简单。菜单权限本身是高风险业务，新增菜单既关联数据，也关联角色授权和缓存等后续逻辑。前端已经提交自定义 ID，编译器只能检查类型是否匹配，不能知道这个字段是否在 Convert 中被遗漏，更不能知道“最后自动生成了一个 ID”是否违反需求。我的做法是从请求、Convert、Service 一直追到落库，确认字段链路；发现丢失后补齐转换，再把真实 Convert 放进回归测试。这样以后即使重构转换层，测试也能在字段消失时失败。AI 可以缩短查调用链的时间，但“要保留什么、为什么保留、怎样才算验证过”由我负责。

## 三、逻辑删除记录导致主键冲突风险

### 30 秒回答

【真实项目】自动生成菜单 ID 首次忽略逻辑删除记录，但旧 ID 仍占主键。AI 帮我追数据流；我改为检查删除记录，并加回归测试。结论：“查不到”不等于不存在，数据库约束由我确认。

### 背景与约束

- 菜单表使用逻辑删除，历史记录对普通查询隐藏，但其主键仍被数据库占用。
- 自动编号要同时兼顾根节点、子节点的编号规则，以及用户输入的自定义 ID；不能通过清理历史数据来规避风险。

### AI 做了什么

- 在修复阶段检索逻辑删除、自定义 ID 和编号生成的完整数据流。
- 生成候选的测试场景和代码修改草案，供人工审查。

### 我做了什么

- 以数据库主键约束为准，而非以 ORM 默认查询结果为准，确认风险原因和修复口径。
- 决定编号区间查询显式包含逻辑删除记录，同时让用户自定义 ID 按同一口径检查。
- 为根节点、子节点与自定义 ID 补充回归测试，并检查错误提示能说明“已删除菜单仍占用 ID”。

### 问题与修正

首次按“未删除记录的最大 ID”生成编号，看上去能正常查询和编译，却漏掉历史逻辑删除记录。修正后，编号区间查询包含逻辑删除记录；自定义 ID 也会检查被删除记录是否已占用，避免新记录触发主键冲突。

### 心得与边界

编译通过解决的是类型和模块问题，不能覆盖历史数据、数据库唯一约束和业务编号规则。这里的回归测试能固定已识别的边界，不能据此宣称所有菜单场景都已被穷尽；数据迁移或既有记录的处理范围仍要按需求单独评审。

### 60～90 秒展开

这个案例我会用“ORM 视角和数据库事实不一致”来解释。最初逻辑只从未删除记录里找最大 ID，代码能编译，普通查询也看起来正确；但逻辑删除不是物理删除，旧记录还占着主键。于是当自动生成结果恰好复用旧 ID，才会在插入时暴露冲突。这不是单纯把查询条件改一下，而是要统一自动生成和前端自定义 ID 的占用口径。我让 AI 帮我把调用链和候选测试列出来，自己确认数据库约束和编号规则，再把查询改成包含逻辑删除记录，并分别覆盖根节点、子节点、自定义 ID。这个过程说明“通过编译”从来不等于“覆盖历史数据”；真正的验证要针对失败模式写回归场景。

## 四、分类路径的 Service 与 Convert 双层验证

### 30 秒回答

【真实项目】商品只带叶子分类 ID，前端需要完整路径。AI 帮我定位转换链；我批量取分类，并分测 Service 路径和 Convert 字段。结论：数据经过两层，只测一层不够，测试边界由我定。

### 背景与约束

- 需求不仅是增加字段，还要让已发布接口商品从叶子分类 ID 得到完整名称路径。
- 需要避免对每件商品逐级查询数据库；响应还会经过 Convert 的精简转换，路径算对也可能在后续丢失。

### AI 做了什么

- 查找相似的 Service、响应模型和 Convert 代码，解释分类路径的数据流。
- 生成候选的映射与测试草案，帮助列出路径构造和字段穿透两个检查点。

### 我做了什么

- 决定批量获取分类 Map，从叶子向父节点回溯、反转得到正向路径，同时返回名称数组和斜杠拼接字符串。
- 把验证拆为两层：Service 测试检查完整路径；真实 Convert 测试检查 `categoryNameList` 在精简响应中不丢失。
- 审查数据流和测试失败含义，确保测试对错误实现会失败，而非只迎合当前代码。

### 问题与修正

风险不是只有“路径算错”，还包括“路径算对但转换丢字段”。因此没有用一条大而全的测试覆盖所有层，而是让 Service 和 Convert 各自承担可定位的回归责任：前者发现父级回溯或顺序问题，后者发现字段映射遗漏。

### 心得与边界

Mockito 隔离 DAO 适合验证 Service 分支，但不能替代真实 Convert、编译或接口联调；反过来，编译也不能替代业务行为测试。这里的两层测试是针对这条数据流的防线，不代表未列出的响应链路已得到同等验证。

## 五、ng-design-mcp：把规范变成 AI 可用上下文

### 30 秒回答

【真实项目】我把 UI 规范和组件文档做成 MCP 服务，供 AI 查询校验；检索结合 ChromaDB、MiniSearch 和 evals。结论：上下文应可检索、可验证；模型是否调用工具不能保证。

### 背景与约束

- 常见现象是 AI 生成表单时自行写 `input` 和样式，而没有使用内部封装组件；目标是让它先获得规范、组件名和 props 上下文。
- 仓库只有 6 次提交，跨度为 2026-05-06 到 05-22（16 天）；其中我的提交为初始化框架、多源内容解析与多工具支持、UI 规范查询与验证工具、CLAUDE.md 项目向导。应按这一体量讲述，不能扩写成大规模长期项目。
- 不把返工率、组件复用率等效果数据说成既成事实；来源明确标注为【需本人确认】。

### AI 做了什么

- MCP 服务向 AI 客户端提供查询与校验能力，使模型在需要时能够取得相关规范上下文。
- 向量检索处理语义相近的需求，关键词检索处理组件名、prop 名、错误码等精确名词；两类结果互补。

### 我做了什么

- 把 Markdown UI 规范与组件类型定义接入索引：用 unified/remark 按标题层级处理文档，使用 react-docgen-typescript 提取组件类型信息。
- 选择混合检索：ChromaDB 服务语义检索，MiniSearch 覆盖精确匹配；保留 `evals/queries.json` 作为可重复检索验证的证据。
- 明确把问题限定在“提供上下文与校验能力”，而不承诺模型一定调用工具或一定生成符合规范的代码。

### 问题与修正

首次问题不是缺少更多 prompt，而是静态塞入完整规范会超出或稀释上下文，并且文档更新后容易过期。修正思路是按需检索当前文档与类型定义：语义需求走向量检索，精确组件/prop 查询由关键词检索补足。对检索效果，不能只靠人工抽查，需用“查询 → 期望文档”的 evals 用例验证期望结果是否进入 top-k。

### 心得与边界

MCP 只提供能力，模型是否调用由模型决定；工具描述与项目规则可以提高被调用的机会，但不能作保证。以下实现细节仍是【需本人确认】：具体 tool 的名称、入参和出参；结果融合是否使用 RRF 或其他加权方式；chunk metadata；索引是手动还是自动重建；实际 evals 用例数与指标；中文 embedding 模型及其效果。因此不能把这些细节、任何效果指标或部署规模当作确定事实。

### 60～90 秒展开

我会先承认它是一个 16 天、6 次提交的小项目，再说明它解决的工程问题。内部规范和组件库文档很大，全部放进 prompt 成本高、相关内容会被稀释，文档更新后还会过期；所以我做了 MCP 服务，让编码工具按需查询当前文档和类型。检索上，像“做一个带搜索的下拉”这类语义需求适合 ChromaDB，而 `NgTable`、prop 名和错误码这类精确名词需要 MiniSearch 补齐；文档按标题切分，组件类型单独组织，以便把语义完整的片段交给模型。`evals/queries.json` 证明项目有检索评测用例，但具体指标、用例数、重建流程和工具签名都还要本人核对。我不会承诺模型必然调用 MCP，也不会把没有统计的返工或复用效果说成结果；这段经历的价值是把 AI 上下文当作可检索、可验证的工程问题来处理。
