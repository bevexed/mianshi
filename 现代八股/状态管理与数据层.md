# 状态管理与数据层（Zustand / Redux / Mobx / react-query）

> 简历第 25 行写了「熟练使用 Zustand、Redux、Mobx、Vuex/Pinia，
> 以及 react-query」——**列了这么多，必然被追问「为什么最后用 Zustand」**。
> 这类题考的不是 API，是**你有没有一套判断标准**。

---

## 一、最核心的一题

### Q1：Server State 和 Client State 有什么区别？

**这是整块的地基，答清楚了后面所有题都好答。**

| | Client State | Server State |
|---|---|---|
| 归属 | 前端**拥有**它 | 前端只是**缓存**了远端的一份副本 |
| 例子 | 弹窗开关、表单草稿、当前选中的 tab、主题 | 用户列表、订单详情、商品数据 |
| 是否会过期 | 不会 | **会**——别人改了，你手里的就是旧的 |
| 是否需要同步 | 不需要 | 需要重新请求、后台刷新、失效 |
| 是否异步 | 通常同步 | 异步，有 loading / error 状态 |
| 归谁管 | Zustand / useState / Context | **react-query / SWR** |

**一句话结论**：
> 把服务端数据塞进 Redux/Zustand，就等于要自己实现缓存、失效、
> 重试、去重、竞态处理——那是在重写一遍 react-query。

**这也是过去几年前端状态管理最大的认知变化**：
以前 Redux 里 70% 的代码是在管接口数据，
现在这部分被 react-query 拿走了，剩下的真正的客户端状态很少，
所以 Zustand 这种轻量方案就够用了。

**能讲出这段演进，比会用十个库更有说服力。**

## 二、库的选型

### Q2：为什么后来用 Zustand？Redux 最大的问题是什么？

**Redux（即使用 RTK）的问题**：
- **样板代码多**——即使 RTK 简化了，仍然要 slice、reducer、
  store 配置、Provider
- **心智负担**——action/reducer/dispatch 这套间接层，
  在小项目里带来的规范收益不如它的成本
- **性能**——`useSelector` 需要手动做 selector 优化，
  否则容易全量重渲染
- **最根本的**：Redux 的设计初衷是解决大型应用的**可预测状态流转**
  （时间旅行、中间件、严格的单向数据流）。
  一旦服务端状态被 react-query 拿走，剩下的客户端状态往往简单到
  用不上这套重型机制

**Zustand 的优势**：
- API 极简，一个 `create` 就完事，**不需要 Provider**
- 天然支持 **selector 细粒度订阅**：`useStore(s => s.count)`，
  只有 count 变才重渲染
- 体积小（~1KB）
- 可以在 React 外部读写 store（`store.getState()`），
  在工具函数、拦截器里很方便

**但要能说出 Zustand 的代价**（不然像背通稿）：
- 缺少 Redux DevTools 那种成熟的调试体验（虽然有中间件）
- 没有强约束，团队大了容易写得很随意——
  **这点对你尤其重要，你带团队，可以讲你怎么约束的**

### Q3：Mobx 呢？

- 响应式 / 可变数据模型，用 Proxy 追踪依赖，自动精确更新
- **优点**：写起来最像"普通 JS"，不需要手动优化重渲染
- **缺点**：可变数据 + 隐式依赖追踪，debug 时数据从哪变的不直观；
  和 React 的不可变心智模型有冲突；社区热度下降
- **诚实答法**：我用过但不是现在的首选，
  它在「大量细粒度更新的复杂表单/表格」这类场景仍有优势

### Q4：Context 能替代状态管理库吗？

**不能，要说清楚两个原因：**
1. **无法细粒度订阅**——Context value 变化时，
   **所有消费该 Context 的组件都会重渲染**，
   哪怕它只用了 value 里的一个字段
2. **拆分导致 Provider 嵌套地狱**——为了缓解第 1 点要拆成多个 Context，
   然后就是十几层 Provider

**Context 的正确定位**：**依赖注入**，不是状态管理。
适合传很少变化的东西——主题、语言、当前用户、配置。

### Q5：Zustand 在 Next.js（SSR）里有什么坑？

**这题和你的 Next.js 项目直接相关，很可能被连着问：**

模块级单例 store 在服务端是**跨请求共享**的——
Node 进程常驻，A 用户的数据会串到 B 用户。

**正确做法**：每个请求创建新的 store 实例，用 Provider 传下去；
客户端则复用同一个实例。

```js
// 服务端每次新建，客户端复用
let clientStore
const getStore = () => {
  if (typeof window === 'undefined') return createStore()  // 服务端：每次新建
  return (clientStore ??= createStore())                    // 客户端：单例
}
```

## 三、react-query（深圳高频）

### Q6：staleTime 和 gcTime 的区别？

- **staleTime**：数据多久后被标记为「陈旧」。**未过期时，组件重新挂载不会重新请求**
- **gcTime**（旧名 cacheTime，默认 5 分钟）：数据**没有任何组件在用之后**，
  多久从缓存中被回收
- 关系：staleTime 决定**要不要重新请求**，gcTime 决定**缓存留多久**

**最容易被问倒的点**：默认 `staleTime: 0`，
意味着数据一拿到就是 stale 的，任何重新挂载/窗口聚焦都会触发后台重新请求。
很多人以为"用了 react-query 就有缓存了"，其实默认行为是
**先展示缓存、同时后台刷新**（stale-while-revalidate）。

### Q7：缓存什么时候失效？

三种途径：
1. **时间**——超过 staleTime 自动变 stale
2. **触发条件**——`refetchOnMount` / `refetchOnWindowFocus` /
   `refetchOnReconnect`（默认都开）
3. **手动**——`queryClient.invalidateQueries({ queryKey })`，
   典型场景是 mutation 成功后让相关列表失效

### Q8：queryKey 怎么设计？

**这题能看出是不是真用过：**
- **queryKey 就是缓存的唯一标识 + 依赖数组**——
  key 里的任何值变化都会触发重新请求，这是它的核心机制
- **必须把所有影响结果的参数放进 key**：
  ```js
  useQuery({ queryKey: ['orders', { page, status, keyword }], ... })
  ```
  漏了 page，翻页就不会重新请求
- **层级化设计便于批量失效**：
  `['orders']` → `['orders', 'list', filters]` → `['orders', 'detail', id]`
  这样 `invalidateQueries({ queryKey: ['orders'] })` 能一次失效所有订单相关缓存
- 大项目建议用 **query key factory**（集中定义 key 的工厂函数），
  避免各处手写字符串拼错

### Q9：prefetch 是什么？什么时候用？

- `queryClient.prefetchQuery()` 提前把数据放进缓存，
  等用户真正进入页面时直接命中
- 典型场景：**hover 列表项时预取详情**、
  翻页时预取下一页、SSR 时服务端预取

### Q10：react-query 在 SSR 里怎么 hydrate？

```
服务端：
  const qc = new QueryClient()
  await qc.prefetchQuery({ queryKey, queryFn })
  const state = dehydrate(qc)          // 把缓存序列化

客户端：
  <HydrationBoundary state={state}>    // 把序列化的缓存注入
```

要点：
- **QueryClient 必须每个请求新建**（和 Zustand 一样的跨请求污染问题）
- 客户端拿到 dehydrate 的数据后，**不会立刻重新请求**（因为已在缓存里），
  但如果 staleTime 是 0，聚焦/挂载时仍会后台刷新——
  SSR 场景通常要设一个合理的 staleTime

### Q11：mutation 之后怎么更新列表？

三种策略，**要能说出取舍**：
1. **invalidate**（最常用）——让缓存失效，重新请求。简单可靠，但多一次请求
2. **setQueryData 手动更新**——直接改缓存，无需请求。快，
   但要自己保证和服务端一致
3. **乐观更新**（`onMutate` + `onError` 回滚）——先改 UI 再发请求，
   体验最好，但要处理失败回滚

**答题加分**：说清什么时候用哪个——
点赞/收藏这种高频轻量操作用乐观更新；
订单提交这种重要操作用 invalidate，宁可慢也要拿服务端的真实结果。

## 四、结合你的项目

### Q12：你的项目里 Zustand 和 react-query 怎么分工的？

**准备一个具体例子**（官网选购链路，见
[Next.js 篇](../简历深挖/产业互联网平台官网-NextJS.md)）：

> 产品套餐、版本列表这些是从后端来的，走 react-query，
> 我不需要关心什么时候刷新。
>
> 用户当前选了哪个版本、选了多少年限、加购了哪些项——
> 这些是纯客户端状态，而且要跨页面保持（购买页选完跳到配置页），
> 放 Zustand。
>
> 价格是**算出来的**，两边都不存——
> 因为一旦存了，套餐变了、年限变了都要记得同步，
> 迟早会漏掉一条路径。

**最后那句「能算就别存」是通用原则，会被记住。**
