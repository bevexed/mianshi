## 一、HTTP 版本演进

### Q1：HTTP/1.1、HTTP/2、HTTP/3 的核心区别？

| | HTTP/1.1 | HTTP/2 | HTTP/3 |
|---|---|---|---|
| 传输层 | TCP | TCP | **QUIC（基于 UDP）** |
| 并发 | 一个连接一次一个请求，靠开 6 个连接凑并发 | **多路复用**：一个连接跑多个流 | 多路复用 |
| 队头阻塞 | **应用层**有 | 应用层解决了，**TCP 层仍有** | **彻底解决** |
| 头部 | 明文，重复发送 | **HPACK 压缩** | **QPACK 压缩** |
| 服务端推送 | 无 | 有（已基本废弃） | 无 |
| 握手 | TCP 3 次 + TLS | 同左 | **0-RTT / 1-RTT**（合并传输层和 TLS 握手）|

### Q2：什么是队头阻塞？为什么 HTTP/2 没彻底解决？

**这题是理解 HTTP/3 存在意义的关键，必须答清楚：**

- **HTTP/1.1 的队头阻塞在应用层**：一个 TCP 连接上，
  请求必须按顺序响应，前面的慢就堵住后面的
- **HTTP/2 用多路复用解决了应用层**：多个流可以交错传输
- **但 TCP 本身要求字节流有序**——如果某个 TCP 包丢了，
  **整个连接上所有流都要等它重传**，哪怕其他流的数据已经到了。
  这就是 **TCP 层的队头阻塞**
- **HTTP/3 换成 QUIC（基于 UDP）**，
  各个流独立管理，**一个流丢包不影响其他流**

**补一句**：正因为 HTTP/2 是单连接多路复用，
**弱网丢包时 HTTP/2 反而可能比 HTTP/1.1 慢**——
这个反直觉的点能答出来很加分。

### Q3：有了 HTTP/2，前端的哪些优化手段过时了？

- **雪碧图（CSS Sprites）**——为了减少请求数，现在请求数不是瓶颈了
- **域名分片**——为了突破 6 个连接限制，现在反而有害
  （多个域名意味着多次握手，且削弱多路复用）
- **合并 JS/CSS 文件**——不必激进合并了，
  但**仍要按变更频率分组做缓存优化**（见 [工程化篇](工程化与构建.md) Q6）

## 二、TCP / HTTPS

### Q4：TCP 三次握手，为什么是三次不是两次？

```
客户端 → SYN(seq=x)           → 服务端
客户端 ← SYN+ACK(seq=y,ack=x+1) ← 服务端
客户端 → ACK(ack=y+1)          → 服务端
```

**为什么必须三次**：
- 目的是**双方都确认对方的收发能力都正常**
- 两次的话，服务端无法确认「客户端能收到我的包」
- **更实际的原因**：防止**已失效的连接请求**突然到达服务端。
  如果只有两次，一个滞留在网络中的旧 SYN 到达后服务端就建立连接并等待，
  白白占用资源

**四次挥手为什么比握手多一次**：
关闭时被动方收到 FIN 后可能还有数据要发，
所以 ACK 和 FIN 分开发（握手时 SYN 和 ACK 可以合并）。

### Q5：HTTPS 的握手过程？

```
1. 客户端 Hello：支持的 TLS 版本、加密套件、随机数
2. 服务端 Hello：选定的套件、随机数、证书（含公钥）
3. 客户端验证证书链 → 用公钥加密 pre-master secret 发过去
4. 双方用三个随机数算出对称密钥
5. 之后用对称加密通信
```

**核心考点**：
- **为什么要非对称 + 对称混合？**
  非对称加密安全但慢，对称加密快但密钥无法安全传输。
  所以**用非对称加密来安全地交换对称密钥**，之后用对称加密传数据
- **证书解决什么问题？** 防中间人攻击——
  证明"这个公钥确实属于这个域名"，由 CA 背书
- **TLS 1.3 的改进**：握手从 2-RTT 降到 1-RTT，
  支持 0-RTT 会话恢复，砍掉了不安全的旧算法

## 三、认证：Cookie / Session / JWT

### Q6：Cookie、Session、Token(JWT) 的区别？

| | Session（服务端存储） | JWT（无状态） |
|---|---|---|
| 状态存哪 | 服务端（内存/Redis） | **令牌本身**（客户端持有） |
| 服务端负担 | 要存储和查找 | 无需存储，验签即可 |
| 水平扩展 | 需共享存储（Redis） | 天然支持 |
| **能否主动失效** | ✅ 删掉即可 | ❌ **签发后到期前一直有效** |
| 体积 | Cookie 里只有一个 id | 每次请求都带完整 payload |
| 跨域/跨端 | Cookie 受同源和 SameSite 限制 | 放 header，灵活 |

### Q7：JWT 的结构？有什么坑？

```
header.payload.signature
{alg,typ}.{业务数据,exp}.HMAC或RSA签名
```

**坑（面试重点）**：
1. **payload 只是 base64 编码，不是加密**——
   任何人都能解开看内容，**绝不能放敏感信息**
2. **无法主动注销**——用户改密码/被封禁后，
   已签发的 token 到期前仍然有效
   → 解法：短 access token（15 分钟）+ refresh token，
   或维护一个黑名单（但这就退化成有状态了）
3. **`alg: none` 攻击**——早期实现如果信任 header 里的算法声明，
   攻击者把 alg 改成 none 就能绕过验签。**服务端必须硬编码算法**
4. **续期策略**——refresh token 怎么存、怎么防止被盗用

### Q8：token 存 localStorage 还是 cookie？

**经典题，必须答出权衡而不是给一个答案：**

| | localStorage | httpOnly Cookie |
|---|---|---|
| XSS | ❌ JS 可读，脚本注入就能偷走 | ✅ JS 读不到 |
| CSRF | ✅ 不会自动携带 | ❌ 会自动携带，需要额外防护 |
| 跨域 | 手动加 header，灵活 | 受 SameSite/域名限制 |
| SSR | ❌ 服务端读不到 | ✅ **服务端能直接读**|

**结论**：
> **httpOnly + Secure + SameSite=Lax 的 cookie 是更安全的默认选择**，
> CSRF 用 SameSite + CSRF token 防。
> 而且在 Next.js 这种 SSR 场景下，cookie 还有一个额外好处——
> 服务端能直接读到登录态，避免了「服务端不知道登录状态、
> 客户端知道」导致的水合不匹配
> （见 [Next.js 篇](../简历深挖/产业互联网平台官网-NextJS.md) Q3）。

**XSS 面前没有绝对安全的存储**——如果被 XSS 了，
httpOnly cookie 虽然读不到，攻击者仍可以直接用你的身份发请求。
所以**根本解法是防住 XSS**（CSP、输出转义、避免 `dangerouslySetInnerHTML`）。

## 四、浏览器存储

### Q9：各种存储方案怎么选？

| | 容量 | 生命周期 | 是否随请求发送 | 同步/异步 |
|---|---|---|---|---|
| **Cookie** | ~4KB | 可设过期 | ✅ 每次都带 | 同步 |
| **localStorage** | ~5-10MB | 永久 | ❌ | **同步（会阻塞主线程）** |
| **sessionStorage** | ~5-10MB | 标签页关闭即失效 | ❌ | 同步 |
| **IndexedDB** | 大（通常几百 MB 起） | 永久 | ❌ | **异步** |
| **Cache Storage** | 大 | 永久 | ❌ | 异步 |

**选择原则**：
- 少量配置、需要同步读 → localStorage
- 结构化大数据、离线数据、需要索引查询 → IndexedDB
- 服务端也要读 → Cookie
- 静态资源离线 → Cache Storage + Service Worker

**加分点**：`localStorage` 是**同步 API**，
存取大对象（尤其配合 `JSON.parse`）会阻塞主线程，
影响 INP。频繁读写的大数据应该用 IndexedDB。

### Q10：IndexedDB 什么时候用？

- 离线应用、大量结构化数据、需要按索引查询
- 缺点：API 很难用（基于事件的事务模型）→
  实践中用 `idb` / `dexie` 这类封装库
- 【需确认】你项目里用过吗？没用过就诚实说了解但没实践，
  别硬编——这题深挖起来细节很多

## 五、跨标签页通信（补充现有文档）

仓库已有 [浏览器内多个标签页之间相互通信.md](../浏览器/浏览器内多个标签页之间相互通信.md)，
补充一个现在更推荐的方案：

- **BroadcastChannel**（推荐）——同源标签页间的广播，API 简单
  ```js
  const ch = new BroadcastChannel('app')
  ch.postMessage({ type: 'logout' })
  ch.onmessage = e => { ... }
  ```
- **storage 事件**——监听 localStorage 变化（老方案，
  注意**不会在触发变化的那个页面里触发**）
- **SharedWorker**——多标签共享一个 worker 实例
- **典型场景**：一个标签页退出登录，其他标签页同步登出
