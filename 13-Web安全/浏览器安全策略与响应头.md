# 浏览器安全策略与响应头

安全响应头把服务端的信任策略告诉浏览器，用于限制脚本、嵌入、传输、能力和信息泄露。它们是纵深防御：不能替代服务端授权、参数化查询、输出编码或安全的业务设计。

## 常用策略

| 控制                                      | 主要作用                                                     |
| ----------------------------------------- | ------------------------------------------------------------ |
| `Content-Security-Policy`                 | 限制脚本、样式、图片、连接、frame 等资源及嵌入关系           |
| `Strict-Transport-Security`               | 浏览器记住站点只使用 HTTPS，降低后续降级访问                 |
| `X-Content-Type-Options: nosniff`         | 阻止部分 MIME 猜测，配合正确 `Content-Type`                  |
| CSP `frame-ancestors` / `X-Frame-Options` | 限制谁能嵌入页面，防点击劫持                                 |
| `Referrer-Policy`                         | 控制导航和子资源请求携带多少 Referer 信息                    |
| `Permissions-Policy`                      | 限制摄像头、麦克风、定位等浏览器能力                         |
| COOP/COEP/CORP                            | 加强跨源文档/资源隔离；启用跨源隔离能力时需配套              |
| Cookie 属性                               | 限制 Cookie 的脚本可读性、传输、站点和作用域                 |

具体策略必须按应用资源和兼容性生成，不能机械复制一组 header 就宣称“已安全”。

## CSP 落地

```http
Reporting-Endpoints: csp-endpoint="https://reports.example.com/csp"
Content-Security-Policy-Report-Only: default-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none'; script-src 'nonce-{每次响应随机值}' 'strict-dynamic'; report-to csp-endpoint
```

1. 先盘点第一方、第三方脚本、样式、图片、字体、worker、frame 和网络连接。
2. 用 `Report-Only` 配合 `Reporting-Endpoints`/`report-to` 收集真实违例，修复内联代码和动态执行，而不是不断放宽策略；需要兼容旧浏览器时再评估 `report-uri`。
3. 服务端为每个 HTML 响应生成高熵 nonce，只授予可信脚本；不能复用固定 nonce。
4. 明确设置 `object-src`、`base-uri`、`frame-ancestors`，避免只关注 `script-src`。
5. 执行态策略稳定后再启用阻断，并持续监控新依赖和路由。

`unsafe-inline`、`unsafe-eval`、过宽域名和允许用户托管内容的 CDN 都会削弱 CSP。CSP 报告可能包含 URL 和页面信息，需要采样、限流与脱敏。

`Report-Only` 只观测、不阻断，包括其中的 `frame-ancestors` 也不会提供实际的点击劫持防护；生产必须另有已执行的 CSP/X-Frame-Options，或在验证后切换为执行态策略。

## HTTPS 与 HSTS

全站使用 HTTPS，HTTP 只做无内容的跳转。除浏览器预置的 preload 规则外，HSTS 通常要先在安全连接中收到才会生效；可逐步提高 `max-age`：

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

启用 `includeSubDomains` 或提交 preload 前，必须确认所有子域长期支持 HTTPS、证书续期和故障恢复；错误配置可能让大量站点不可访问。HSTS 不会修复 XSS、越权或服务端注入。

TLS、证书和 HTTPS 建连过程见 [TCP 与 HTTPS](../04-浏览器与网络/TCP与HTTPS.md)。

## 点击劫持与嵌入

- 优先使用 CSP `frame-ancestors 'none'` 或明确允许来源；需要兼容旧客户端时再配合 `X-Frame-Options: DENY` 或 `X-Frame-Options: SAMEORIGIN`。
- 业务确需被第三方 iframe 嵌入时，按合作方精确授权，并用 iframe `sandbox`、消息 origin 校验和最小能力设计。
- JavaScript “frame busting” 容易被绕过，不应作为唯一防线。
- 敏感操作仍要重新认证/确认，降低点击劫持和会话滥用影响。

## CORS 不是认证

CORS 决定浏览器是否允许某个 origin 的脚本读取响应，不限制非浏览器客户端，也不代表调用者拥有业务权限。

- 对允许源做精确匹配；不要把请求头原样反射，尤其是宽泛子域正则。
- 携带凭据时不能返回 `Access-Control-Allow-Origin: *`，并要设置正确的 `Vary: Origin`。
- 只开放需要的方法、header 和暴露 header；预检结果缓存要考虑策略更新。
- WebSocket 不走 CORS 预检，但浏览器会发送 `Origin`，服务端要验证并对每条消息授权。

完整协议见 [跨域与 CORS](../04-浏览器与网络/跨域.md) 和 [WebSocket](../04-浏览器与网络/websocket.md)。

## Cookie、缓存与信息泄露

- 会话 Cookie 通常设置 `Secure; HttpOnly; SameSite=Lax/Strict`，并缩小 `Domain`/`Path`；跨站需求单独评审。
- 敏感响应根据业务使用 `Cache-Control: no-store` 或私有缓存策略；共享缓存 key 必须包含授权差异，不能仅靠前端隐藏。
- Referrer 策略避免把敏感路径/查询泄露给外站；敏感值本身就不应放 URL。
- 正确设置 `Content-Type` 和 `nosniff`，用户上传内容使用隔离域名或下载响应。
- 按源码敏感度和排障需求决定生产 Source Map 是否公开；不公开只能减少信息暴露，不是安全边界。上传监控平台时限制访问，构建产物和源码本身都不能包含密钥或不必要的个人信息。

Cookie 和浏览器存储的生命周期、作用域与性能边界见 [浏览器存储](../04-浏览器与网络/浏览器存储.md)。

## 第三方脚本与跨窗口通信

- 第三方脚本在页面 origin 下通常拥有接近第一方脚本的能力；减少数量、固定版本、评审数据收集范围。
- 静态跨源资源可在适用时使用 Subresource Integrity（SRI）并配合正确 CORS；动态脚本和频繁变更资源要设计更新流程。
- `postMessage` 发送时指定精确 `targetOrigin`，接收时校验 `event.origin`、必要时校验 `source`，并验证消息 schema。
- 外链新窗口使用 `noopener` 等隔离，防止不可信页面控制 opener。
- COOP/COEP/CORP 能建立更强隔离，但会影响 iframe、第三方资源和弹窗流程，应先用报告和集成测试评估。

## 验证清单

1. 从浏览器实际响应检查 header，覆盖 HTML、API、错误页、下载和 CDN 缓存命中。
2. CSP 从报告模式逐路由收紧，验证 SSR/CSR、worker、第三方登录和支付流程。
3. 测试不受信任 origin 的 CORS 预检、带凭据请求、WebSocket 和 `postMessage`。
4. 验证 iframe 嵌入、MIME、Referrer、Cookie 和缓存行为，而不是只检查配置文件。
5. 对 header 变更做自动化回归，避免代理/CDN 覆盖、重复或在错误状态码中遗漏。
