# Web 安全高频面试题

面向中高级前端、Node.js 与全栈面试，包含 28 道核心口述题和 3 道附加场景题。回答时先给结论，再说明漏洞成立条件、根因防护、纵深防御和边界；不要把安全题答成没有优先级的工具清单。

## 通用口述模板

一道漏洞题可以按 30 秒主干回答：

```text
它是什么、成立条件是什么
  → 不可信数据或身份在哪个边界失控
  → 优先修根因，再补纵深防御
  → 说明方案不能解决什么
  → 给一个验证方法或项目场景
```

如果面试官继续追问，再展开 source → transform → sink、浏览器/服务端职责、失败策略和自动化回归。

## 一、浏览器与前端最高频

### 1. 什么是 XSS？有哪些类型？怎么防？

**结论：XSS 是不可信数据被浏览器当成 HTML、JavaScript、CSS 或可执行 URL 解释。常见分为存储型、反射型和 DOM 型。**

防护顺序：优先用安全 DOM API 和框架文本插值；按 HTML/属性/URL/JS 等输出上下文编码；富文本用允许列表 sanitizer；最后用 CSP、Trusted Types、HttpOnly Cookie 等限制影响。关键词过滤和 WAF 不能代替根因修复。

**常见追问：** HttpOnly 只能减少 Cookie 被直接读取，XSS 仍可能以用户身份发请求；CSP 是纵深防御，不替代输出编码。

### 2. React/Vue 默认转义后，为什么还会有 XSS？

**结论：框架通常只保证普通文本插值按文本渲染，不保证所有逃生口和第三方数据流安全。**

风险点包括 React `dangerouslySetInnerHTML`、Vue `v-html`、手工 DOM 操作、富文本/Markdown 渲染器、动态 URL、服务端手拼 HTML、模板编译和第三方脚本。面试中要说明“默认安全路径”和“绕过默认路径的危险 sink”。

**常见追问：** 净化后的 HTML 若再次拼接或交给其他解释器，仍可能重新产生风险。

### 3. CSP 能防 XSS 吗？nonce/hash 怎么用？

**结论：CSP 能限制脚本来源和执行方式，显著降低部分 XSS 的利用面，但不是 XSS 的根治方案。**

生产常用随机且每响应不同的 nonce，或对固定内联脚本使用 hash；逐步移除 `unsafe-inline`、`unsafe-eval` 和宽泛来源。先用 Report-Only + 上报端点观察，再切换执行态策略。

**常见追问：** nonce 不能固定或由前端生成；只写 `default-src 'self'` 也不代表策略完整；Report-Only 只报告、不阻断。

### 4. XSS 和 CSRF 有什么区别与联系？

**结论：XSS 是目标站执行了攻击者可控脚本；CSRF 是浏览器带着环境凭据替攻击者发起非预期请求。**

XSS 的核心边界是输出到执行上下文，CSRF 的核心条件是 Cookie 等凭据自动携带且服务端无法证明请求来自受信任交互。XSS 往往能读取 CSRF token 或在同源上下文直接发请求，因此可能绕过 CSRF 防护。

### 5. CSRF 的成立条件和防护方案是什么？

**结论：典型 CSRF 需要自动携带的身份凭据、可被跨站触发的有副作用请求，以及缺失的来源/token/用户确认校验。**

防护组合：GET/HEAD 不做状态变更；Cookie 设置合适的 SameSite；写请求校验框架提供的 CSRF token；校验 Origin，必要时 Referer 兜底；现代浏览器可叠加 Fetch Metadata；改密、转账、提权等操作重新认证或确认。

**常见追问：** SameSite 是纵深防御，不应在有不可信兄弟子域、兼容旧客户端或跨站业务时单独承担全部防护。

### 6. CORS、简单请求和预检怎么工作？为什么它不是鉴权或通用 CSRF 防线？

**结论：CORS 主要决定浏览器是否允许某个 origin 的脚本读取响应，不普遍阻止跨站发送请求，也不限制非浏览器客户端。**

- 满足 CORS safelist 的方法、header 和 `Content-Type` 可直接发送，浏览器再根据响应头决定脚本能否读取；表单、导航、图片等也可能跨站发出请求。
- 超出 safelist 时，浏览器先发 `OPTIONS` 预检，询问服务端是否允许该 origin、方法和 header；只有预检通过才发送实际请求。
- Postman、curl 和服务间调用不受浏览器同源策略约束，不能靠 CORS 限制它们。

服务端仍必须独立做认证、对象授权和 CSRF 设计。预检只是浏览器执行的跨源能力协商，不是身份认证；凭据模式还要求精确允许 origin 和 `Access-Control-Allow-Credentials: true`，不能用 `Access-Control-Allow-Origin: *`。动态返回允许源时要精确匹配并设置 `Vary: Origin`。

### 7. 同源（origin）和同站（site）有什么区别？

**结论：origin 比较 scheme、host、port；schemeful site 主要看 scheme 与可注册域，因此兄弟子域可能 same-site 但一定不是 same-origin。**

同源策略约束 DOM、脚本读取和 Web Storage 等；Cookie Domain、SameSite 使用另一套作用域语义。不能把“跨域”“跨站”“Cookie 可携带”混成同一个概念。

### 8. token 放 localStorage 还是 HttpOnly Cookie？

**结论：不存在脱离威胁模型的绝对答案；浏览器会话通常优先考虑 Secure + HttpOnly + 合适 SameSite 的 Cookie，但必须处理 CSRF。**

localStorage 里的 token 不会自动随请求携带，经典 CSRF 面较小，但 XSS 可直接读取并导出；HttpOnly Cookie 不能被脚本直接读取，却会自动携带，且 XSS 仍能代发请求。两者都不能代替 XSS 防护、短期令牌、撤销和最小权限。

使用 Cookie 时还要设置 `Secure`、`HttpOnly`、合适的 `SameSite`，并尽量收窄 `Domain` 和 `Path`；条件允许时使用要求 `Secure`、`Path=/` 且不含 `Domain` 的 `__Host-` 前缀。`Path` 不是授权边界。

### 9. 什么是点击劫持？怎么防？

**结论：点击劫持是攻击页面用透明或误导性的 iframe 覆盖目标页面，诱导用户点击真实敏感控件。**

优先使用 CSP `frame-ancestors` 限制嵌入方，兼容旧客户端时配合 `X-Frame-Options: DENY` 或 `SAMEORIGIN`；高风险操作再做确认或重新认证。JavaScript frame busting 不能作为唯一防线。

### 10. `postMessage` 有哪些安全注意点？

**结论：发送方指定精确 `targetOrigin`，接收方校验 `event.origin`、必要时校验 `event.source`，并对消息做 schema 校验。**

不要因消息来自 iframe/父窗口就默认可信，也不要使用 `*` 发送敏感数据。收到的消息仍是不可信输入，不能直接进入 `innerHTML`、跳转、请求或权限操作。

### 11. 什么是原型污染？前端如何防？

**结论：原型污染是攻击者通过可控 key/path 修改对象原型上的属性，使后续对象继承恶意状态，并可能继续触发越权、XSS 或服务端危险 sink。**

防护：请求体做 schema 和未知字段校验；递归拒绝 `__proto__`、`constructor`、`prototype` 等危险路径；避免不安全深合并；字典场景优先 Map/Set 或无原型对象；读取安全关键字段时检查自有属性；及时升级受影响依赖。

**常见追问：** 只禁用 `__proto__` 不够，`constructor.prototype` 仍可能形成路径；冻结内建原型是有兼容成本的纵深措施。

## 二、认证、授权与接口安全

### 12. 认证和授权有什么区别？

**结论：认证确认主体是谁，授权判断这个主体此刻能否对这个资源执行这个动作。登录成功不代表可以访问任意资源。**

前端路由守卫和隐藏按钮只改善体验，真正的功能级、对象级、属性级和租户级授权必须在服务端靠近敏感操作处执行，并默认拒绝。

### 13. 什么是 IDOR/BOLA？不可猜 UUID 能解决吗？

**结论：IDOR/BOLA 是服务端收到对象标识后没有校验当前主体是否有权访问该对象。UUID 只降低枚举概率，不是授权。**

查询时把 user/tenant/权限范围放入条件，列表、导出、批量操作、文件下载、WebSocket 订阅和缓存命中都要做对象授权。测试要覆盖跨用户、跨租户和不同对象状态。

### 14. Session 和 JWT 怎么选？

**结论：Session 把会话状态放服务端，容易单点撤销；JWT 常把声明和有效期放令牌中，便于跨服务本地验签，但撤销和权限变更更复杂。**

选择看调用方、跨服务边界、撤销时效和运维能力，不是“JWT 一定更先进”。JWT 也可能搭配服务端状态；Session 也能通过共享存储水平扩展。

**常见追问：** Session 登录成功、权限提升和其他身份边界变化后应轮换会话标识，设置空闲与绝对过期，并在退出、改密或封禁时撤销；JWT 则要说明短有效期、刷新轮换和撤销策略。

### 15. 服务端验证 JWT 要检查什么？

**结论：至少固定允许算法并验签，同时验证 issuer、audience、过期时间、not-before 和令牌用途；不能只把 payload 解码出来。**

访问令牌应短期有效，刷新令牌轮换并检测重用；改密、封禁、提权变化等场景需要撤销或版本策略。常见签名 JWT 只保证完整性、不提供机密性，不能放秘密。

### 16. OAuth 2.0、OIDC、PKCE 分别解决什么？

**结论：OAuth 2.0 解决委托授权，OIDC 在其上增加身份层；PKCE 把授权码与客户端临时生成的 verifier 绑定，降低授权码被截获后兑换的风险。**

浏览器和其他 public client 通常使用授权码流程 + PKCE，不再选择会在前端直接返回令牌的 Implicit Flow。还要精确匹配 redirect URI；`state` 关联发起与回调并防登录请求串线/CSRF，OIDC `nonce` 绑定认证请求与 ID Token。access token 用于调用资源 API，ID Token 用于向客户端表达认证结果，不能互换；public client 也不能安全保存固定 client secret。

### 17. 密码、MFA 和找回流程如何设计？

**结论：密码使用成熟库的专用密码哈希；登录和找回防枚举、多维限速；高风险账号/操作使用 MFA，恢复链路不能比正常登录更弱。**

改密、换绑和权限提升后轮换或撤销相关会话；验证码短期、限制次数、一次性消费且不写日志。简单锁死账号可能被反向用于拒绝服务。

### 18. SQL 注入的根因是什么？参数化为什么有效？

**结论：根因是把不可信数据拼进 SQL 结构；参数化让查询结构与数据值分离，使输入不会改变语法。**

表名、列名、排序方向等动态标识符通常不能按普通值参数化，应从服务端允许列表映射。ORM 里的 raw query、字符串条件仍可能注入；数据库账号还要最小权限。

### 19. NoSQL、命令和模板注入怎么统一回答？

**结论：它们本质上都是不可信数据进入解释器并改变了程序结构，防护核心是结构与数据分离。**

NoSQL 不直接接收客户端查询对象；按 schema 提取标量并拒绝未知操作符。命令执行优先改用库/API，必须启动进程时固定程序、数组传参、关闭 shell、限制资源和权限。模板固定源码，只把输入当数据。

### 20. 什么是 SSRF？为什么只校验 URL 前缀不够？

**结论：SSRF 是攻击者影响服务端出站请求，使其访问非预期的内网、云元数据、本机或外部目标。URL 字符串校验覆盖不了解析差异、DNS 重绑定和重定向。**

业务允许时不接收完整 URL，改用资源 ID/固定目标；否则限制 scheme/host/port，解析并检查全部 A/AAAA 地址，并确保实际连接使用已校验地址或由强制出站代理执行同等策略，不能校验后再做一次不受控 DNS 解析。每次重定向都重新校验，再用 egress proxy、防火墙和低权限服务做网络层隔离。

### 21. 文件上传要防什么？

**结论：要同时防执行、解析器漏洞、XSS、路径穿越、压缩炸弹、存储耗尽和越权读取。**

认证授权和限额；扩展名允许列表 + MIME + 文件签名；服务端重命名；隔离、低权限处理；限制解压后的数量/大小/深度；存到 webroot 外或私有对象存储；下载时重新做对象授权并设置安全响应头。

### 22. 路径穿越、开放重定向和 XXE 分别怎么防？

**结论：三者都应尽量把攻击者可控字符串替换成服务端 ID/允许列表，再在真实解释边界做校验。**

路径使用服务端映射并确认规范化结果位于基目录内，处理符号链接和解压条目；重定向目标使用路由名或允许列表；XML 不需要外部实体时关闭 DTD、外部实体和网络访问。

### 23. WebSocket 有哪些安全点？

**结论：建立连接时认证并校验 Origin，连接后对每条消息做 schema、对象授权、大小/频率限制，断线和令牌过期策略也要明确。**

WebSocket 不走 CORS 预检；Origin 校验主要约束浏览器发起方，不是认证。仅握手时登录成功不代表之后所有 topic、房间和对象都可访问；退出、封禁或会话过期后要终止或降权连接。浏览器端不要把长期 token 放 URL，必要时使用短期一次性 ticket；服务端还要处理背压并记录连接、鉴权失败和高风险消息审计事件。

### 24. 业务安全为什么不能只靠前端校验和限流？

**结论：价格、权限、库存、状态转换和幂等是服务端业务不变量；前端字段、按钮状态和请求顺序都不可信。**

服务端重算关键数据，状态机校验允许转换，用唯一约束/版本/幂等键防重放和并发，多维限流只负责容量与滥用成本。验证码也不是身份认证或业务授权的替代品。

## 三、安全工程与系统题

### 25. HTTPS 解决什么，不能解决什么？

**结论：HTTPS 提供传输机密性、完整性和服务端身份验证，但不修复 XSS、CSRF、注入、越权和恶意业务输入。**

还要正确验证证书、管理 TLS 配置和重放风险；HSTS 可减少后续降级访问，但首次访问与 preload、子域兼容和证书运维要说明边界。

### 26. 常见安全响应头怎么答？

**结论：按风险说明用途，不要背成“复制一组 header 就安全”。**

- CSP：限制资源和脚本执行；
- HSTS：要求后续只用 HTTPS；
- `X-Content-Type-Options: nosniff`：限制 MIME 猜测；
- `frame-ancestors`/X-Frame-Options：防点击劫持；
- Referrer-Policy：控制 Referer 泄露；
- Permissions-Policy：限制摄像头、定位等能力；
- COOP/COEP/CORP：加强跨源隔离，但可能影响第三方集成。

### 27. 前端可见配置、第三方脚本和依赖供应链有哪些风险？

**结论：打包进客户端的环境变量、API Key 和 Source Map 都应按可公开信息处理；第三方脚本通常运行在页面 origin 下，依赖则贯穿安装、构建和发布链路。**

真正的秘密留在服务端或受控密钥系统。减少依赖和第三方脚本；锁定版本、冻结安装并使用可信 registry；评审安装脚本、维护者变化和传递依赖；CI 使用短期最小权限身份；构建一次晋级不可变制品；适用的静态跨源资源使用 SRI。

**常见追问：** lockfile 保证解析结果更可复现，不证明依赖可信；SCA 主要发现已知组件漏洞，SBOM 主要提供组件清单，三者都不能替代来源、发布权限和制品完整性控制。

### 28. 安全测试和日志如何形成闭环？

**结论：权限与业务不变量靠负向单元/集成测试，危险数据流靠 SAST，已知组件问题靠 SCA，运行配置和路由靠 DAST/IaC 检查，再用人工评审补业务语义。**

日志记录服务端确认的主体、动作、资源、结果和策略原因，但不记录密码、token、验证码和完整敏感请求体。告警要可处置，并关联账号、设备、租户、资源和时间窗口。

## 四、附加场景追问题

### 29. 设计一个安全的富文本/Markdown 展示功能

**结论：把富文本当作不可信主动内容，而不是普通字符串。**

服务端和/或客户端使用维护良好的允许列表 sanitizer，限制标签、属性和 URL 协议；图片/附件走独立上传与授权；渲染后不再危险拼接；CSP/Trusted Types 做纵深防御；测试存储型、DOM 型和不同渲染入口。

### 30. 设计“输入 URL，服务端生成预览”的功能

**结论：这是典型 SSRF 场景，优先限制业务目标并隔离出站能力。**

只允许 HTTP(S) 和必要端口；统一解析 URL，检查全部 A/AAAA，阻断本机、内网、链路本地和元数据目标；让实际连接使用已校验地址或统一经过强制出站代理，避免校验与连接之间再次解析；默认不跟随重定向或逐跳复检；限制超时、大小和内容类型；使用隔离 worker，并不把原始响应直接返回页面。

### 31. 线上发现高危漏洞后怎么处理？

**结论：先分级，在不延误紧急止损的前提下同步保全易失证据，然后迭代做遏制与范围确认，再根除、受控恢复和持续监控。**

可先关闭入口、限权、撤销密钥或隔离网络；修复后增加原路径和相邻路径回归，并确认是否已被利用。法务、隐私、业务和沟通按触发条件并行介入，通知不能固定等技术恢复后才决定。
