# 注入攻击与输入处理

注入发生在不可信数据被拼进 SQL、命令、模板、表达式或其他解释器语句后，数据改变了原本的程序结构。根本防线不是“过滤几个字符”，而是让**代码结构与数据参数始终分离**。

## 统一分析模型

```text
Source：URL / JSON / Header / 文件 / 消息 / 数据库旧值
  → Transform：解析、拼接、解码、类型转换、模板渲染
  → Sink：SQL / NoSQL 查询 / Shell / 模板 / LDAP / XPath / 日志解释器
```

数据库里的旧数据、内部服务返回值和管理员输入也可能最初来自攻击者，不能因“来自内部”就跳过安全处理。

## 常见注入类型

| 类型       | 危险做法                               | 首选防护                                      |
| ---------- | -------------------------------------- | --------------------------------------------- |
| SQL 注入   | 字符串拼接查询和值                     | 预编译/参数化查询，动态标识符使用允许列表     |
| NoSQL 注入 | 把客户端 JSON 对象直接作为查询条件     | Schema 校验、只取预期标量、拒绝未知操作符     |
| 命令注入   | 拼字符串交给 shell                     | 不调用 shell；固定程序 + 独立参数 + 最小权限  |
| 模板注入   | 让用户输入成为服务端模板源码或表达式   | 固定模板，只把输入当数据；必要时隔离沙箱      |
| Header/日志注入 | 未限制换行和结构化字段，后续被重新解释 | 使用框架 API、结构化日志、限制控制字符        |
| 原型污染        | 可控 key/path 被不安全地写入对象原型   | Schema、危险 key 拒绝、安全字典与依赖升级     |

## SQL 与 NoSQL

```js
// 数据库驱动按占位符传参；具体占位符语法以所用驱动为准。
const result = await db.query(
  "SELECT id, name FROM users WHERE tenant_id = ? AND id = ?",
  [tenantIdFromSession, userId],
);
```

- 参数化保护的是**值**。表名、列名、排序方向等标识符通常不能作为普通参数，应从服务端允许列表映射。
- ORM/查询构造器不自动保证所有 API 安全；raw query、字符串条件和动态表达式仍需评审。
- 不把整个请求体交给数据库查询或更新。先按 schema 解析，再显式构造字段，避免 NoSQL 操作符注入和批量赋值。
- 数据库账号按服务拆分读写范围；即使发生注入，也不应拥有建库、文件系统或全库管理权限。
- 错误响应不返回 SQL、表名、驱动堆栈或连接信息；服务端日志也要脱敏。

## OS 命令与进程调用

优先调用库或系统 API，而不是启动命令行。必须执行外部程序时：

1. 程序路径固定，不让用户选择可执行文件；
2. 参数以数组独立传递，关闭 `shell`，不拼接管道、重定向和子命令；
3. 参数按业务允许列表校验，并限制长度、数量和文件范围；
4. 使用低权限账号、只读文件系统、容器/沙箱和出站网络限制；
5. 设置超时、输出上限和并发配额，防止资源耗尽；
6. 不把密钥或敏感环境变量无差别继承给子进程。

转义 shell 元字符只是高脆弱度的末级方案：不同 shell、操作系统、编码和嵌套上下文规则不同。

## 模板、表达式与反序列化

- 模板由开发者固定，用户只提供经过类型校验的数据；“允许用户自定义模板”应被当作执行不可信代码的高风险能力设计。
- 关闭不需要的动态表达式、反射、任意属性访问和文件/网络能力。
- 不反序列化不可信数据为可执行对象图；使用简单数据格式、schema 校验和允许类型集合。
- 签名只能证明数据未被篡改，不能让危险反序列化逻辑本身变安全。

## JavaScript 原型污染

原型污染通常发生在递归合并、路径赋值或查询参数解析时，攻击者通过 `__proto__`、`constructor.prototype` 等路径修改共享原型。后续普通对象可能继承被污染属性，并进一步触发权限绕过、配置篡改、XSS 或服务端危险 sink。

1. 请求体和配置输入按 schema 解析，拒绝未知字段，并递归拦截危险 key/path。
2. 避免把不可信对象交给通用深合并或动态路径赋值；升级已知受影响的解析/合并库。
3. 字典场景优先使用 `Map`/`Set` 或 `Object.create(null)`，避免无意继承 `Object.prototype`。
4. 安全关键判断使用明确默认值并检查自有属性，例如 `Object.hasOwn()`；不能依赖“属性平时不存在”。
5. Node.js 的 `--disable-proto`、冻结内建原型等只能减少部分攻击面，还要考虑 `constructor.prototype` 和兼容成本。

## 输入校验、规范化与输出处理

1. 在接收边界完成类型、范围、长度、枚举和结构校验，拒绝未知字段。
2. 对协议、域名、文件扩展名、排序字段、状态转换等有限集合使用允许列表。
3. 只规范化一次并使用解析后的规范值做校验；警惕双重 URL/Unicode 解码造成检查和使用不一致。
4. 输入校验不能替代参数化或输出编码，编码也不能替代业务权限与状态校验。
5. 客户端校验用于体验，服务端必须独立重复关键规则。

## 防护误区

- 只屏蔽引号、空格或关键字会误伤合法输入，也挡不住编码和语法变体。
- WAF 可以临时降低已知攻击流量，但不能理解所有业务上下文或修复代码结构。
- “只允许管理员调用”不能降低后台和供应链输入的安全要求。
- 存储过程只有在内部不拼动态语句时才提供参数化收益。

## 验证清单

- 搜索字符串 SQL、raw query、`exec`/shell、动态模板和反序列化入口。
- 对类型错配、嵌套对象、未知字段、超长值、编码差异和并发请求做负向测试。
- 验证数据库/系统账号的实际权限，而不是只审查应用代码。
- 将参数化、schema、权限和错误脱敏纳入回归；WAF 命中不应是唯一成功判据。
