# 认证、授权与会话安全

认证回答“你是谁”，授权回答“这个主体此刻能否对这个资源执行这个动作”。前端隐藏菜单、使用不可猜 ID 或完成登录，都不能替代服务端对每次敏感访问的授权判断。

## 认证链路

登录安全要覆盖注册、登录、MFA、找回密码、换绑、退出和管理员恢复，而不是只加一个密码框。

- 密码使用成熟库的专用密码哈希算法和当前推荐参数；每个密码有独立 salt，服务端 pepper 如使用应放在密钥系统中。
- 登录、找回和注册返回尽量一致，减少账号枚举；同时保留服务端可关联的审计信号。
- 按账号、IP、设备、租户和全局容量多维限速，采用渐进延迟/挑战，避免简单锁死账号被用于拒绝服务。
- 高风险账号和操作支持抗钓鱼 MFA；恢复流程的强度不能低于正常认证，否则恢复入口会成为绕过路径。
- 改密、换绑、提权和支付前验证当前会话新鲜度，必要时重新认证。

## 授权模型与越权

| 层级       | 典型失败                                             |
| ---------- | ---------------------------------------------------- |
| 功能级     | 普通用户直接调用管理员接口                           |
| 对象级     | 修改订单 ID 后读取或操作他人对象（IDOR/BOLA）        |
| 属性级     | 客户端提交 `role`、`ownerId`、`price` 等受保护字段   |
| 租户级     | 查询漏掉租户条件，缓存 key 或消息消费跨租户          |
| 流程级     | 绕过前置步骤、重放旧状态或利用并发打破业务不变量     |

授权应默认拒绝，并基于服务端确认的 `subject + action + resource + context` 判断。RBAC 适合粗粒度职责，ABAC/策略规则适合资源归属、租户、时间和状态等条件；模型名称不重要，策略完整且可测试才重要。

```js
// 把租户和资源范围放进查询，而不是查询后只在前端隐藏结果。
const order = await orders.findOne({
  id: request.params.id,
  tenantId: auth.tenantId,
  ownerId: auth.userId,
});
```

- 列表、导出、搜索、批量操作、WebSocket 订阅和后台任务同样需要授权。
- 服务端从认证上下文取得用户/租户/角色；不要信任请求体中的所有权字段。
- 使用 DTO/允许字段映射防批量赋值，敏感字段由业务规则计算。
- 缓存 key、对象存储路径、队列消息和日志查询都要包含正确隔离维度。
- 404 或 403 的对外选择可按信息泄露策略决定，但内部要保留准确审计原因。

## Session 安全

- 登录和权限提升后轮换 session ID，防会话固定；ID 使用安全随机数，不承载可预测业务信息。
- Cookie 使用 `Secure`、`HttpOnly`、合适的 `SameSite`、最小 `Path/Domain`，并设置空闲与绝对过期。
- 服务端保存撤销/版本状态；退出、改密、风险事件和账号禁用后使相关会话失效。
- 不把 session ID 放 URL，避免进入历史、Referer、日志和分析系统。
- 分布式会话要定义并发登录、撤销传播和故障时的失败策略。

Cookie 自动携带带来 CSRF 面，详见 [CSRF 与跨站请求防护](CSRF与跨站请求防护.md)。

Session、JWT、OAuth/OIDC 的基础区别见 [认证方案对比](../04-浏览器与网络/认证方案对比.md)；本篇只聚焦其安全边界。

## JWT 与访问令牌

JWT 是令牌格式，不自动解决身份、撤销或权限更新：

1. 固定允许的签名算法并验证签名，不能相信 token 自报算法；
2. 验证 `iss`、`aud`、`exp`、`nbf` 等与当前服务匹配的 claims；
3. 访问令牌短期有效，刷新令牌轮换并检测重用；高风险场景保留撤销能力；
4. 常见的签名 JWT 只保证完整性、不提供机密性，claims 对客户端可见；不放密码、密钥和不必要的个人信息；
5. 权限变化不能只等旧 token 自然过期，需版本、撤销或短 TTL 等策略；
6. 不同用途/受众使用不同 key 或严格隔离，防止把一种 token 当另一种 token 接受。

## OAuth/OIDC 常见边界

- OAuth 处理授权委托，OIDC 在其上提供身份层；不要把 access token 当作随意格式的登录凭证。
- 授权码流程使用精确 redirect URI、`state` 和 PKCE；nonce/issuer/audience 等按协议和客户端类型验证。
- 不在 URL、日志或前端分析事件中暴露长期令牌；第三方 SDK 只获得最小 scope。
- “使用知名身份供应商”不能替代本系统的账号绑定、租户映射和对象授权。

## 验证清单

1. 建立角色/属性 × 动作 × 资源状态的权限矩阵，并生成允许与拒绝用例。
2. 对每个 ID、批量 ID、导出、搜索和实时通道做跨用户/跨租户测试。
3. 测试登录前后/提权后 session 轮换、退出撤销、并发设备和超时边界。
4. 测试 token 的错误算法、错误 issuer/audience、过期、未来生效和密钥轮换。
5. 检查找回、换绑、邀请、客服代操作和服务账号是否形成更弱旁路。
