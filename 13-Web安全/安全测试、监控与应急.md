# 安全测试、监控与应急

安全控制只有经过负向测试、生产观测和事件演练才算闭环。扫描器擅长发现模式，却很难理解租户隔离、价格重算、审批顺序等业务不变量，因此自动化工具和人工评审要分工组合。

## 安全开发闭环

```text
需求滥用故事
  → 威胁建模与权限矩阵
  → 安全编码和代码评审
  → 自动化/人工测试
  → 部署策略验证
  → 监控告警与事件响应
  → 根因修复和回归
```

越靠前修复成本通常越低，但生产检测仍不可缺少：配置漂移、被盗账号、供应链事件和未知攻击不会在提交阶段全部暴露。

## 测试层次

| 方法                 | 擅长发现                                         | 主要盲区                                   |
| -------------------- | ------------------------------------------------ | ------------------------------------------ |
| 单元/集成安全测试    | 授权、状态机、输入边界、验签、失败策略           | 环境配置和真实代理链                       |
| SAST/lint            | 危险 API、数据流、硬编码密钥、常见编码模式       | 业务语义、运行配置、误报                   |
| SCA                  | 把依赖/镜像组件与已知漏洞、策略规则关联          | 未知恶意更新、实际可达性和业务影响         |
| SBOM                 | 提供组件与版本清单，支持追踪和事件排查           | 本身不判断漏洞、可达性或配置是否安全       |
| DAST/API 扫描        | 运行中路由、header、部分注入和配置问题           | 需特定身份/状态的流程、源码中的隐藏路径    |
| IaC/配置检查         | 公开存储、网络/IAM、安全头和危险默认值           | 运行时漂移与应用层权限                     |
| 人工代码/设计评审    | 信任边界、业务滥用、组合攻击和例外               | 覆盖率依赖经验，需要可重复检查表           |
| 渗透测试/演练        | 控制组合和真实攻击路径                           | 时间点抽样，不能替代持续治理               |

## 应优先自动化的回归

### 权限矩阵

为 `角色/属性 × 动作 × 资源归属/状态` 同时生成允许和拒绝用例，重点覆盖：

- 跨用户、跨租户、已删除/冻结对象、批量 ID 和分页/导出；
- 普通接口、管理接口、WebSocket、文件下载、队列任务和缓存命中；
- 登录前后、提权前后、令牌过期/撤销和角色即时变更；
- 正常流程之外的跳步、重放、并发和乱序。

### 输入与输出边界

- schema 未知字段、错误类型、最大/最小值、嵌套深度和超长数据；
- SQL/命令/模板参数化路径和动态标识符允许列表；
- HTML/属性/URL 等不同输出上下文，富文本净化和 CSP；
- URL 抓取、重定向、文件类型、归档展开和资源上限；
- 错误页、降级分支、超时和部分失败不能绕过关键控制。

## 安全日志

日志应回答“谁在何时、从何处、对什么资源做了什么、策略为何允许/拒绝、结果是什么”，并能用 request/trace ID 关联代理、应用和下游服务。

建议记录：

- 登录/MFA/恢复成功与失败、会话创建/撤销、令牌异常；
- 授权拒绝、管理操作、角色/策略/密钥/配置变化；
- 输入校验高风险失败、异常出站请求、上传扫描和完整性校验失败；
- 限流、WAF/CSP 等纵深控制信号，以及告警处置结果。

不要记录密码、session/refresh token、完整密钥、验证码、支付数据或不必要的请求体。对日志字段去除控制字符并结构化写入，防日志注入；限制读取权限、保留期和跨租户查询。

## 告警设计

- 以可处置的行为序列和业务影响告警，不只依赖单次字符串命中。
- 同时观察基线偏离、失败率、成功后的异常行为和控制被关闭/放宽。
- 账号、IP、设备、租户、资源和时间窗口多维关联，避免共享 IP 误伤。
- 每个高优告警有负责人、处置步骤、证据位置和升级路径；定期验证通知真的可达。
- 对告警做采样和聚合但保留关键审计，避免攻击者用噪声压垮值班。

## 漏洞处置

1. 复现前先保护敏感数据和环境，避免在生产扩大影响。
2. 按暴露面、可利用条件、权限、数据和业务影响定级，不只看通用 CVSS。
3. 能立即降低风险时先收紧权限、关闭入口、撤销密钥或隔离网络，再修根因。
4. 修复危险数据流/授权/设计，并为原路径和相邻路径增加回归。
5. 查询日志、制品、账号和数据判断是否已被利用；“漏洞已修”不等于“未发生事件”。
6. 记录时间线、根因、控制为何未发现、长期行动项和负责人；验证行动项真正关闭。

## 事件响应最小流程

```text
发现与分级
  → 紧急止损与易失证据保全并行权衡
  → 遏制影响 ↔ 确认范围（持续迭代）
  → 根除根因与受控恢复
  → 持续监控复发
  → 复盘和长期改进
```

隔离、撤销、重启等止损动作可能破坏内存、连接和短保留日志等易失证据；团队应在不延误人身、资金或大范围数据风险止损的前提下，尽早或同步保全证据，并记录取舍。证据采集要有时间同步、访问控制和保全记录。

法务、隐私、业务和沟通团队应在各自触发条件出现时并行介入，用户、监管、客户或供应商通知按组织预案、合同和适用规则的时限处理，不能固定等到技术恢复或只由临时技术判断决定。

## 衡量闭环

- 高风险资产和接口是否有负责人、威胁模型和权限回归？
- 从引入漏洞到发现、从发现到控制、从控制到根因修复分别多久？
- 高风险依赖/密钥/配置例外是否有明确到期时间？
- 告警有多少可处置、多少误报，演练是否发现证据或权限缺口？
- 同类漏洞是否重复出现；若重复，需修规则、组件或流程，而不是只修单点。
