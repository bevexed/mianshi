# AI 辅助开发面试材料设计

## 目标

在 `11-AI工程` 中补充一组可长期维护、直接服务面试的 AI 辅助开发材料，把候选人真实使用 Codex、Claude Code 的经历整理成可复述、可追问、可验证的工程经验，同时补齐对行业代表性 AI 开发工具的选型认知。

材料不能把“会使用 AI”简化成生成代码，也不能把未实际使用的工具包装成个人经历。核心定位是：候选人能够借助 AI 扩展交付边界，同时通过上下文约束、最小改动、测试、编译、联调和人工审查对最终结果负责。

## 当前基础

`11-AI工程` 已有以下通用专题：

- `AI辅助开发实践.md`：Agent 闭环、上下文工程、团队接入和收益评估；
- `MCP协议.md`：协议、原语、传输、工具设计和安全；
- `RAG与检索.md`：检索、切分、索引、权限和评测。

`98-项目深挖` 已有两个可作为事实来源的个人案例：

- `产业互联网平台Java后端-AI协作与稳定性.md`；
- `ng-design-mcp.md`。

新增材料复用并链接这些事实源，不在多个文档中复制完整项目长文。

## 事实标签与表达边界

材料统一使用以下标签：

| 标签                         | 使用条件                                           |
| ---------------------------- | -------------------------------------------------- |
| `【真实使用】`               | 候选人实际使用过 Codex 或 Claude Code              |
| `【真实项目】`               | 有现有项目文档、代码或 Git 记录可以支撑             |
| `【行业认知，未实际使用】`   | 只了解定位或能力，不能使用第一人称经验表述         |
| `【需本人确认】`             | 缺少当前证据的数量、指标、组织制度、执行结果或细节 |

Codex、Claude Code 可以写个人流程和经验，但不凭空编造两者的速度、模型质量、使用次数或固定分工。Cursor、GitHub Copilot、Windsurf、Cline、Roo Code、Aider 等行业工具只进入生态与选型文档，并显式标明未实际使用。

不宣称固定效率提升百分比、测试覆盖率、零线上事故、完整 CI 卡口或公司允许的数据策略，除非现有证据能够直接支持。

## 各文档设计

### 1. AI 辅助开发实践

保留现有通用原理，增加面向个人交付的内容：

- 按低、中、高风险决定 AI 自主程度；
- 从需求到交付的完整闭环；
- 仓库规则、相似实现和真实失败输出如何构成上下文；
- 方案先行、垂直切片、最小 diff 和阶段验收；
- 测试、类型检查、编译、联调和人工审查各自解决什么问题；
- 数据、权限、提示注入和危险写操作的边界；
- 对 AI 辅助开发的真实心得与反模式。

这篇回答“你的 AI 开发方法论是什么”，不展开单个工具的功能百科。

### 2. Codex 与 Claude Code 协作实践

只写候选人实际使用的两个工具，围绕任务而不是品牌优劣组织：

- 代码库理解、调用链追踪和陌生技术栈学习；
- 方案评审、风险清单和任务拆分；
- 局部实现、机械修改、测试草案和文档同步；
- 读取命令输出后继续诊断的 Agent 闭环；
- 长任务的上下文压缩、决策记录和停止条件；
- 常用任务模板、审查清单和不委托事项；
- 两个工具共用的质量门槛，以及无法由证据支持的差异不做结论。

这篇回答“你具体怎么用 Codex 和 Claude Code”，所有第一人称案例都要能回到事实源。

### 3. AI 辅助开发真实案例

使用统一结构整理案例：

```text
结论 → 项目背景与约束 → AI 做了什么 → 我做了什么
     → 首次方案的问题 → 如何验证和修正 → 取舍与边界
```

计划覆盖：

1. 借助 AI 进入 Spring Boot 3 多模块工程，先还原分层和调用链；
2. 菜单权限功能中发现 Convert 丢失自定义 ID；
3. 逻辑删除记录仍占主键导致自动生成 ID 可能冲突；
4. 分类路径同时验证 Service 组装和 Convert 字段穿透；
5. `ng-design-mcp` 将组件规范转成可检索、可校验的 AI 上下文能力。

每个案例提供 30 秒结论和 60～90 秒展开，并链接到 `98-项目深挖` 的完整材料。案例不新增无法核验的结果数字。

### 4. AI 开发工具生态与选型

按交互形态而不是排行榜组织：

- IDE/编辑器内联补全与对话；
- 终端或本地仓库 Agent；
- 可执行多步骤任务的异步/云端 Agent；
- 开源、自托管或可替换模型的工具；
- 团队级上下文、MCP、规则文件、评审和治理能力。

至少覆盖 Cursor、GitHub Copilot、Windsurf、Cline/Roo Code、Aider 等代表性工具。实现时使用当前官方资料核对仍在提供的功能、支持环境和权限模型，记录核对日期；不根据品牌宣传直接判断代码质量，不制作未经数据支持的市场排名。

选型维度包括：任务形态、上下文范围、可控性、工具调用、模型选择、数据策略、权限、成本、团队治理和可验证性。Codex、Claude Code 标为真实使用，其他工具标为行业认知。

### 5. AI 辅助开发面试题

按面试追问链组织，不写成零散题库：

1. 为什么使用 AI，具体提高了哪个环节；
2. 如何证明自己理解 AI 生成的代码；
3. 如何提供上下文并减少幻觉；
4. 如何保护源码、密钥、客户数据和生产权限；
5. 测试由 AI 生成是否可靠；
6. AI 首次实现出错的真实案例；
7. 如何评估收益而不编造效率数字；
8. 哪些任务不会交给 AI 自主完成；
9. Codex 与 Claude Code 如何使用；
10. 如何评价 Cursor、Copilot 等未实际使用的工具；
11. AI 出问题时责任归属和回滚方式；
12. 如何把个人使用升级为团队工程能力。

重点问题同时提供 30 秒短答、追问要点和容易翻车的错误说法。答案采用“结论 → 真实项目证据 → 取舍/边界”。

## 内容生成流程

1. 从现有项目深挖文档提取可核验事实和待确认项；
2. 从 Codex、Claude Code 的真实项目流程抽取共用方法；
3. 浏览代表性行业工具的当前官方资料，核对能力和版本边界；
4. 先完成四篇新文档，再扩充通用实践并更新目录；
5. 对照事实标签扫描第一人称表述，防止把行业认知写成个人经验；
6. 进行结构、链接、语义和 diff 验证。

## 失败处理与维护边界

- 官方资料与旧知识冲突时，以当前官方资料为准，并标注核对日期；
- 工具能力无法确认时不猜测，删除该结论或改为 `【需本人确认】`；
- 个人项目材料相互冲突时，以代码、Git 和已有事实源为准；
- 内容过长时优先保留可口述答案、真实案例和边界，删除重复教程；
- 不修改或清理当前工作区已有的无关改动；
- 本次不提交、不推送，也不创建 PR。

## 验证与完成标准

- 两个现有文件按设计更新，四个新文件全部存在；
- `11-AI工程/目录.md` 可以进入所有新增专题，新增文档中的项目链接均可解析；
- Codex、Claude Code 之外的工具没有第一人称使用表述，并带有 `【行业认知，未实际使用】` 边界；
- 五个计划案例均包含结论、证据、AI/人工分工、修正和边界；
- 面试题覆盖数据安全、幻觉、测试、收益、责任和高风险任务；
- 代码围栏与 `<details>` 标签成对，无尾随空格和意外占位符；
- 对范围内文件执行链接检查、结构检查、语义清单和 `git diff --check`；
- 最终说明实际检查结果，并明确没有提交或推送。
