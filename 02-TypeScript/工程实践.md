# TypeScript 工程实践

> 你的定位是**前端负责人**，这块被问的概率比类型体操还高——
> 因为它考的是你怎么在团队里落地。

## 项目里 TS 该配多严格

- **`strict: true` 是底线**（包含 `strictNullChecks`、`noImplicitAny`、
  `strictFunctionTypes` 等）
- **额外推荐**：
  - `noUncheckedIndexedAccess`——数组索引访问返回 `T | undefined`，
    能挡掉很多运行时错误（`arr[0].name` 直接报错）
  - `exactOptionalPropertyTypes`——区分"没有这个属性"和"属性是 undefined"
  - `noImplicitOverride`、`noFallthroughCasesInSwitch`

### 老项目怎么迁移

**不要一次开全**，否则几千个报错没人愿意动：

1. `allowJs: true`，js 和 ts 共存
2. 先开 `noImplicitAny`，再开 `strictNullChecks`（这个最痛）
3. 逐文件迁移，用 **`// @ts-expect-error`** 标记待处理项

**为什么用 `@ts-expect-error` 而不是 `@ts-ignore`**：
前者在**错误消失后会自己报错**提醒你删掉，
后者会永远烂在代码里——三年后没人知道这行还需不需要。

【需确认】你团队的 tsconfig 实际怎么配的？**这题你作为负责人被问的概率很高。**

## 接口返回的数据类型怎么保证和后端一致

**手写类型的问题**：后端改了字段前端不知道，类型是**"假的安全"**——
编译通过但运行时 undefined。

**方案**：
1. **从 OpenAPI/Swagger 自动生成**类型
   （你们用 Apifox，可以导出 OpenAPI 再生成）
2. **运行时校验**（zod / io-ts）——类型 + 运行时双保险，
   zod 可以从 schema 反推类型，**一份定义两处用**：
   ```ts
   const UserSchema = z.object({ id: z.number(), name: z.string() })
   type User = z.infer<typeof UserSchema>        // 类型
   const user = UserSchema.parse(await res.json()) // 运行时校验
   ```

**核心认知**：
> TS 的类型在运行时是不存在的，所以**系统边界处必须有运行时校验**。
> 接口响应、`localStorage` 读取、URL 参数、第三方 SDK 回调——
> 这些地方的类型断言都是在骗自己。

这句话能体现你想清楚了 TS 的能力边界。

## 泛型什么时候是过度设计

> 泛型的价值是**建立输入和输出之间的类型关联**。
> 如果一个泛型参数只出现一次，它多半是多余的——
> `function f<T>(x: T): void` 和 `function f(x: unknown): void` 没区别。
>
> 我 review 时看到三层以上嵌套的条件类型会问一句：
> 这个复杂度是必要的，还是我们在炫技？**类型是给人读的**，
> 看不懂的类型比 any 更糟，因为它还额外消耗了编译时间。

**这段话对「带团队」的定位特别加分。**

## 团队里常见的 TS 反模式

| 反模式 | 问题 | 改法 |
|---|---|---|
| 到处 `as any` | 关闭检查，等于没用 TS | 用 `unknown` + 类型守卫 |
| `as` 断言当类型转换用 | 断言不做检查，运行时照样炸 | 用类型守卫或运行时校验 |
| 接口类型手写且散落各处 | 后端一改就全线不一致 | 自动生成 + 单一来源 |
| 用 `enum` | 生成运行时代码、`const enum` 有编译问题 | 用 `as const` 对象 + `typeof x[number]` |
| 类型定义堆在一个 `types.ts` | 越滚越大没人敢删 | 就近定义，跨模块的才提取 |
