# 队列与任务编排（BullMQ）

任务队列适合把耗时工作移出请求链路，并提供重试、延时、限流和并发控制。引入队列也会带来重复执行、状态一致性、积压和运维成本，不应把“异步化”理解为自动可靠。

## 任务队列与消息系统

| 维度     | 任务队列（如 BullMQ）                  | 消息/流系统（如 RabbitMQ、Kafka）  |
| -------- | -------------------------------------- | ---------------------------------- |
| 核心目标 | 安排并执行后台作业                     | 在生产者与消费者间传递事件或数据流 |
| 常见能力 | 重试、延时、优先级、任务进度、父子任务 | 路由、订阅、分区、消费组、事件保留 |
| 常见场景 | 邮件、报表、媒体处理、采集             | 跨服务事件、日志流、数据管道       |

这不是严格的产品边界，实际系统能力有重叠。选择时还要比较吞吐、顺序、保留策略、运维基础和故障语义。

## BullMQ 核心对象

```text
Queue        生产者，添加与管理 job
Worker       消费者，执行处理函数
QueueEvents  监听跨 Worker 的队列事件
FlowProducer 创建有依赖关系的任务流
```

典型状态流转：

```text
waiting / delayed → active → completed
                         └→ failed → waiting（满足重试条件）
```

## 交付语义与幂等

Worker 崩溃、锁丢失或网络故障可能让同一个业务动作再次执行。BullMQ 的作业处理在最坏情况下可能出现重复，因此消费端应按可重放设计。

常见防线：

1. 用稳定的业务标识生成 `jobId`，减少同一作业的重复入队；已移除的历史 job 不再参与去重。
2. 在数据库用唯一约束守住最终边界，而不只做“先查再写”。
3. 使用 upsert、状态机或幂等记录，让重复执行得到相同结果。
4. 调用不受自己控制的外部系统时，传递对方支持的幂等键，并保存调用结果。

队列去重不能代替业务幂等：作业完成后被清理、人工重放或不同 jobId 都可能绕过去重。

## 失败与重试

| 类型                     | 推荐处理                           |
| ------------------------ | ---------------------------------- |
| 网络瞬断、暂时性 5xx     | 有上限的指数退避，并加入抖动       |
| 429                      | 尊重服务端重试时间，并配合全局限流 |
| 参数或业务规则错误       | 直接失败，不自动重试               |
| 程序缺陷、数据格式不兼容 | 失败、告警并保留诊断上下文         |

```ts
import { UnrecoverableError, Worker } from 'bullmq';

const worker = new Worker('orders', async (job) => {
	const result = await processOrder(job.data);

	if (result.kind === 'invalid-input') {
		// 抛出不可恢复错误会进入 failed，但不会消耗剩余自动重试次数。
		throw new UnrecoverableError(result.message);
	}

	if (result.kind === 'temporary-failure') {
		throw new Error(result.message);
	}
});
```

不能用 `return` 表示不可恢复失败，因为正常返回会把 job 标记为 `completed`。自动重试应设置 `attempts` 和 backoff；还要限制总时长，避免重试风暴。

## stalled job

Worker 处理 job 时持有并定期续期锁。如果进程退出、事件循环被 CPU 任务长时间阻塞或连接异常导致锁无法续期，job 会被判定为 stalled：它会回到 waiting 供其他 Worker 处理；超过 `maxStalledCount` 后进入 failed。

- BullMQ 2.0 起不再需要 `QueueScheduler` 来处理 stalled job；旧教程中的强制要求已经过时。
- CPU 密集处理宜使用沙箱进程、Worker Threads 或外部计算服务。
- stalled 恢复只能处理已成功入队的 job；“数据库状态已写但入队失败”需要 outbox、补偿扫描等一致性方案。

## 优雅停机

```ts
let closing = false;

async function shutdown() {
	if (closing) return;
	closing = true;

	await worker.close();
	await app.close();
}

process.once('SIGTERM', shutdown);
process.once('SIGINT', shutdown);
```

`worker.close()` 会停止领取新任务并等待在途任务结束，但它自身没有超时。部署平台的终止宽限期、任务超时和 stalled 恢复应配套设计；处理函数也应支持取消或在安全检查点退出。

## 数据保留与观测

```ts
const queue = new Queue('orders', {
	defaultJobOptions: {
		removeOnComplete: { count: 1000 },
		removeOnFail: { age: 7 * 24 * 3600, count: 5000 }
	}
});
```

保留数量只是示例，应按审计需求、故障排查周期和 Redis 容量设定。至少监控：等待/延时/活动/失败数量、最老 job 年龄、处理延迟、重试次数、stalled 数、Redis 内存与连接错误。

## 并发度

并发度由完整链路的瓶颈决定：外部服务限流、数据库连接池、CPU、网络、内存和单任务耗时都要考虑。应从保守值开始压测，根据吞吐、尾延迟和错误率调整；增加并发不一定增加有效吞吐。
