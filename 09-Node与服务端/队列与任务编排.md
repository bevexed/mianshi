# 队列与任务编排：BullMQ、RabbitMQ 与 Kafka

任务队列适合把耗时工作移出请求链路，并提供重试、延时、限流和并发控制。引入队列也会带来重复执行、状态一致性、积压和运维成本，不应把“异步化”理解为自动可靠。

## 先判断：任务、消息还是事件流

一句话区分：

- BullMQ：**有一项后台任务需要某个 Worker 完成**。
- RabbitMQ：**有一条业务消息需要按路由规则交给一个或多个队列**。
- Kafka：**有一段可保留、可回放的事件日志，多个消费组按自己的进度读取**。

这不是严格的产品边界：RabbitMQ 也能承载任务，Kafka 也能实现消息处理，BullMQ 也能发布队列事件。选型看的是哪种抽象最贴近主要矛盾，而不是产品能否勉强实现。

| 维度         | BullMQ                                         | RabbitMQ                                                     | Kafka                                                        |
| ------------ | ---------------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 定位         | 基于 Redis 的任务队列                          | 消息代理，擅长业务消息路由                                   | 分布式事件流与持久化日志                                     |
| 核心抽象     | Queue、Job、Worker、Flow                       | Producer、Exchange、Binding、Queue、Consumer                 | Topic、Partition、Record、Consumer Group、Offset             |
| 消费方式     | 同一队列的 Worker 竞争领取 job                 | Exchange 先路由到队列；同一队列的消费者通常竞争消费          | 不同消费组独立读取；传统消费组内一个分区同时只交给一个消费者 |
| 消费后数据   | job 按保留配置留在 Redis 或被清理              | 消息确认后通常从队列移除                                     | 消费不删除记录；按时间、容量或日志压缩策略保留               |
| 顺序边界     | 优先级、延时、重试和并发都会影响完成顺序       | 可讨论单队列投递顺序，但并发处理与重新投递会影响业务完成顺序 | 只保证分区内顺序；全局顺序通常意味着单分区和吞吐下降         |
| 突出能力     | 重试、延时、优先级、进度、并发、限流、任务依赖 | 灵活路由、确认、拒绝/重入队、TTL、死信、队列模型             | 高吞吐、分区扩展、事件保留、回放、多消费组、流处理生态       |
| 典型场景     | 邮件、报表、媒体处理、定时任务、采集           | 订单事件、通知、跨服务解耦、需要复杂路由的业务消息           | 埋点、日志、CDC、实时计算、数据管道、需要回放的领域事件      |
| 主要运维依赖 | Redis 的可用性、内存、持久化和淘汰策略         | Broker 集群、队列类型、磁盘、连接和拓扑治理                  | Broker、分区、副本、磁盘容量、消费延迟和再均衡               |

不要只背“吞吐量排名”。消息大小、确认策略、副本数、持久化、批处理、网络和硬件都会改变结果；面试中应先讲语义与场景，再谈压测数据。

## RabbitMQ：路由业务消息

典型链路：

```text
Producer → Exchange ──Binding / Routing Key──→ Queue → Consumer
                └────────────────────────────→ Queue → Consumer
```

Producer 通常把消息发布到 Exchange，而不是直接指定消费者。Exchange 根据绑定关系把消息路由到零个、一个或多个队列：

| Exchange 类型 | 路由规则                             | 常见用途                 |
| ------------- | ------------------------------------ | ------------------------ |
| Direct        | Binding Key 与 Routing Key 精确匹配  | 按明确业务类型分发       |
| Topic         | 按 `.` 分段并用 `*`、`#` 做模式匹配  | 领域事件分类订阅         |
| Fanout        | 忽略 Routing Key，复制到所有绑定目标 | 广播通知                 |
| Headers       | 根据消息 Headers 匹配                | 路由条件不适合字符串表达 |

### ACK、Confirm 与可靠性

Publisher Confirm 和 Consumer ACK 解决的是两段不同链路：

```text
Producer ──Publisher Confirm──→ RabbitMQ ──Consumer ACK──→ Consumer
```

- **Publisher Confirm**：Broker 确认已经接管发布的消息；它不代表消费者已经处理成功。
- **Consumer ACK**：消费者在业务处理完成后确认，Broker 才能删除该投递；消费者断开且未 ACK 时，消息可以重新投递。
- **持久化不只设一个开关**：通常要组合 durable queue、persistent message、合适的复制队列类型与 Publisher Confirm。
- **仍需消费幂等**：业务完成后、ACK 发出前进程崩溃，会造成消息重新投递。

消费失败时要区分：

- 暂时性故障：`nack/reject` 后重新入队，但必须限制次数，避免高速死循环。
- 永久性故障：拒绝且不重新入队，可通过 Dead Letter Exchange 路由到隔离队列。
- 消息过期、队列超长等情况也可触发 dead-letter。死信是重新发布和路由机制，不等于自动修复失败消息。

延迟消息常见做法是 TTL + Dead Letter Exchange，或使用延迟消息插件；需要考虑队头阻塞、插件运维和精度，而不是简单认为 RabbitMQ 原生就有通用定时任务能力。

## Kafka：保留并回放事件流

典型结构：

```text
Producer → Topic
             ├── Partition 0: offset 0, 1, 2...
             ├── Partition 1: offset 0, 1, 2...
             └── Partition 2: offset 0, 1, 2...
                         ↓
              Consumer Group A / B
```

- Producer 决定记录进入哪个 Partition；常用业务 key 让同一实体的事件稳定进入同一分区。
- Consumer 主动向分区 Leader 发起 fetch，并携带读取位置。
- Offset 表示消费组在某个分区的进度。提交 Offset 不等于业务副作用已经可靠完成，提交时机决定可能丢处理还是重复处理。
- 在传统 Consumer Group 中，一个分区同一时刻只分配给组内一个 Consumer；因此组内有效并行度通常受分区数限制。
- 不同 Consumer Group 维护各自的 Offset，可以独立消费同一批事件，也可以回退 Offset 后重新处理。

Kafka 的记录不会因为某个消费者读过就立即删除，但也不是“永远不删”：Topic 可以按时间或容量删除旧日志，也可以按 key 做 Log Compaction，保留每个 key 的较新状态。

### 为什么吞吐高

回答时不必只背“顺序写”三个字，应组合说明：

1. 日志以分段追加为主，适合顺序磁盘 I/O。
2. Producer 和 Consumer 都支持批量传输，摊薄网络与系统调用成本。
3. Partition 把存储和消费并行度分散到多个 Broker / Consumer。
4. 消费进度压缩为每个分区的 Offset，不需要为每条消息维护复杂的已消费状态。

代价是 Partition 数量、key 设计、热点、再均衡、消费延迟、副本和保留容量都需要治理；Kafka 不是所有异步任务的默认答案。

## 可靠性不是“用了 MQ 就有”

三者都不能替业务自动实现端到端 exactly-once。至少要分别检查：

1. **生产端**：业务数据已提交但消息没发出怎么办？可用 Transactional Outbox、补偿扫描等方案。
2. **中间件**：是否持久化、复制并获得发布确认？Redis 淘汰、RabbitMQ 队列类型、Kafka 副本与 ACK 配置都会影响边界。
3. **消费端**：业务写成功但确认/Offset 提交失败怎么办？按至少一次交付设计幂等。
4. **失败治理**：限制重试次数，隔离不可恢复消息，保留诊断上下文，并提供人工重放入口。
5. **积压治理**：监控最老消息年龄、消费延迟、失败率和下游容量，而不只看队列长度。

## 如何选型

先按下面的顺序提问：

1. 这是“必须完成的一项工作”，还是“发生过的一件事”？
2. 是否需要 Exchange 级别的精确路由、广播或多队列拓扑？
3. 是否需要保留历史、多个消费组独立处理、回退进度和重新计算？
4. 延时、重试、进度、优先级、任务依赖是否是一等需求？
5. 团队已经可靠运维 Redis、RabbitMQ 或 Kafka 中的哪一种？
6. 实际吞吐、消息大小、顺序范围、可接受丢失窗口和恢复目标是什么？

对应结论：

- 后台任务 + Node/NestJS + 已有 Redis，且重试、延时、限流、进度最重要：优先评估 BullMQ。
- 跨服务业务消息，需要灵活路由、ACK、TTL、死信和相对低延迟：优先评估 RabbitMQ。
- 海量事件、日志/CDC、实时计算、多消费组、长期保留与回放：优先评估 Kafka。
- 业务规模小、可靠性要求有限时，数据库任务表 + 有界轮询也可能比新增中间件更合适，但锁、抢占、重试与清理都要自行实现。

## 面试经验边界

没有在线上使用过 RabbitMQ 和 Kafka，不要说“用过一点”。可以明确区分实战与认知：

> BullMQ 是我在采集项目中实际使用的，我能结合任务拆分、并发限流、幂等、重试、stalled job 和优雅停机说明。
> RabbitMQ 和 Kafka 没有在线上项目落地过，但我系统了解过它们的定位和核心机制：
> RabbitMQ 重点是 Exchange、Routing Key、ACK、Publisher Confirm、TTL 和死信；
> Kafka 重点是 Topic、Partition、Consumer Group、Offset、分区内顺序、保留与回放。
> 如果项目需要，我会先根据可靠性和容量目标做最小验证，而不是把“了解”包装成生产经验。

如果被问“为什么项目不用 RabbitMQ / Kafka”，回答选型约束，不要贬低没用过的技术：

> 这个项目的主要问题是采集任务的延时、重试、并发限制、任务进度和逐级派生。
> 项目已经使用 Redis，BullMQ 与 NestJS/Node 技术栈结合直接，能以较低运维成本覆盖这些任务语义。
> RabbitMQ 更适合需要 Exchange 路由和跨服务消息解耦的场景；Kafka 更适合需要分区扩展、事件保留、回放和多消费组的数据流。
> 当前项目没有这些核心需求，所以没有额外引入它们。

### 常见表述陷阱

- “ACK 以后就绝不重复”：错误。业务完成到 ACK/Offset 提交之间仍有故障窗口。
- “BullMQ 的 `jobId` 保证业务幂等”：错误。job 被清理或换 ID 后仍可再次执行。
- “Kafka 从来不删除消息”：错误。它按 Topic 的 retention / compaction 策略保留。
- “Kafka 保证消息全局有序”：错误。默认只保证 Partition 内顺序。
- “同组 Consumer 越多吞吐越高”：不一定。传统 Consumer Group 的有效并行度受 Partition 数和下游容量限制。
- “死信队列就是失败任务终点”：不完整。还需要告警、原因分类、修复和受控重放。

## BullMQ 核心对象

```text
Queue        生产者，添加与管理 job
Worker       消费者，执行处理函数
QueueEvents  监听跨 Worker 的队列事件
FlowProducer 创建有依赖关系的任务流
```

典型状态流转：

```text
waiting / prioritized / delayed / waiting-children
                         ↓
                       active → completed
                         └────→ failed → waiting（满足重试条件）
```

`stalled` 不是可查询的持久状态，而是 job 因锁续期失败从 active 被移回 waiting（或超过次数后进入 failed）时发出的事件。

### 常用能力与边界

| 需求     | BullMQ 能力                              | 需要额外考虑                                          |
| -------- | ---------------------------------------- | ----------------------------------------------------- |
| 延时     | job 的 `delay`                           | 是“不早于某时可领取”，队列积压时不保证准点开始        |
| 自动重试 | `attempts` + fixed / exponential backoff | 只重试暂时性错误，并设置抖动和总上限                  |
| 周期任务 | Job Scheduler                            | BullMQ 5.16 起替代旧 Repeatable Job API；忙时可能延后 |
| 优先级   | `priority`                               | 优先级会改变 FIFO，不能同时宣称严格顺序               |
| 单机并发 | Worker 的 `concurrency`                  | I/O 密集和 CPU 密集任务要采用不同并发模型             |
| 速率限制 | Worker limiter / 全局限流能力            | 限流保护的是完整下游，不只保护 Worker CPU             |
| 父子任务 | `FlowProducer`                           | 适合已知依赖图；运行时逐级派生不一定适合 Flow         |
| 减少重复 | 稳定 `jobId` 或 deduplication            | 只减少重复入队，不能代替消费侧业务幂等                |
| 历史清理 | `removeOnComplete` / `removeOnFail`      | 去重窗口、审计周期与 Redis 容量之间需要权衡           |

多个 Worker 监听同一 Queue 时，可以通过 Redis 中的原子领取与锁机制横向扩容；同一个 job 正常情况下只会同时交给一个 Worker。但 Worker 崩溃或锁续期失败后 job 会被重新领取，所以整体仍应按至少一次处理设计。

BullMQ Core 通常把最终失败的 job 保留在 failed 集合中，并不等同于 RabbitMQ 的 Dead Letter Exchange。若业务需要独立死信队列，可以在失败事件或人工处置流程中，把诊断信息和原始业务标识受控地写入另一条队列；必须防止“转移死信也失败”或死信无限循环。

Redis 故障也不能靠 BullMQ 自动消失：

- Producer 可能无法入队，必须把失败返回给调用方，或用 Outbox / 补偿任务恢复。
- Worker 可能无法续锁或更新状态，恢复后 job 可能再次执行。
- 生产环境要评估 Redis 持久化、高可用、容量与 `maxmemory-policy`，并监控连接错误和内存水位。
- 不要让无限离线命令缓存把故障期间的请求全部堆在应用内存里；连接超时和降级策略要有上限。

## 交付语义与幂等

Worker 崩溃、锁丢失或网络故障可能让同一个业务动作再次执行。BullMQ 的作业处理在最坏情况下可能出现重复，因此消费端应按可重放设计。

常见防线：

1. 用稳定的业务标识生成 `jobId`，减少同一作业的重复入队；已移除的历史 job 不再参与去重。
2. 在数据库用唯一约束守住最终边界，而不只做“先查再写”。
3. 使用 upsert、状态机或幂等记录，让重复执行得到相同结果。
4. 调用不受自己控制的外部系统时，传递对方支持的幂等键，并保存调用结果。

队列去重不能代替业务幂等：作业完成后被清理、人工重放或不同 jobId 都可能绕过去重。

## 失败与重试

| 类型                     | 推荐处理                           |
| ------------------------ | ---------------------------------- |
| 网络瞬断、暂时性 5xx     | 有上限的指数退避，并加入抖动       |
| 429                      | 尊重服务端重试时间，并配合全局限流 |
| 参数或业务规则错误       | 直接失败，不自动重试               |
| 程序缺陷、数据格式不兼容 | 失败、告警并保留诊断上下文         |

```ts
import { UnrecoverableError, Worker } from 'bullmq';

const worker = new Worker('orders', async (job) => {
	const result = await processOrder(job.data);

	if (result.kind === 'invalid-input') {
		// 抛出不可恢复错误会进入 failed，但不会消耗剩余自动重试次数。
		throw new UnrecoverableError(result.message);
	}

	if (result.kind === 'temporary-failure') {
		throw new Error(result.message);
	}
});
```

不能用 `return` 表示不可恢复失败，因为正常返回会把 job 标记为 `completed`。自动重试应设置 `attempts` 和 backoff；还要限制总时长，避免重试风暴。

## stalled job

Worker 处理 job 时持有并定期续期锁。如果进程退出、事件循环被 CPU 任务长时间阻塞或连接异常导致锁无法续期，job 会被判定为 stalled：它会回到 waiting 供其他 Worker 处理；超过 `maxStalledCount` 后进入 failed。

- BullMQ 2.0 起不再需要 `QueueScheduler` 来处理 stalled job；旧教程中的强制要求已经过时。
- CPU 密集处理宜使用沙箱进程、Worker Threads 或外部计算服务。
- stalled 恢复只能处理已成功入队的 job；“数据库状态已写但入队失败”需要 outbox、补偿扫描等一致性方案。

## 优雅停机

```ts
let closing = false;

async function shutdown() {
	if (closing) return;
	closing = true;

	await worker.close();
	await app.close();
}

process.once('SIGTERM', shutdown);
process.once('SIGINT', shutdown);
```

`worker.close()` 会停止领取新任务并等待在途任务结束，但它自身没有超时。部署平台的终止宽限期、任务超时和 stalled 恢复应配套设计；处理函数也应支持取消或在安全检查点退出。

## 数据保留与观测

```ts
const queue = new Queue('orders', {
	defaultJobOptions: {
		removeOnComplete: { count: 1000 },
		removeOnFail: { age: 7 * 24 * 3600, count: 5000 }
	}
});
```

保留数量只是示例，应按审计需求、故障排查周期和 Redis 容量设定。至少监控：等待/延时/活动/失败数量、最老 job 年龄、处理延迟、重试次数、stalled 数、Redis 内存与连接错误。

## 并发度

并发度由完整链路的瓶颈决定：外部服务限流、数据库连接池、CPU、网络、内存和单任务耗时都要考虑。应从保守值开始压测，根据吞吐、尾延迟和错误率调整；增加并发不一定增加有效吞吐。
