# 队列与任务编排（BullMQ）

> 实战细节见
> [13-项目深挖/住建部企业资质采集服务.md](../13-项目深挖/住建部企业资质采集服务.md)

## 为什么需要队列

1. **削峰**——突发流量不直接打到下游
2. **异步化**——耗时操作不阻塞请求响应
3. **重试与断点续跑**——失败的任务可以单独重试，
   不影响整体
4. **限流**——控制对下游/第三方的调用速率
5. **解耦**——生产者和消费者可以独立部署和扩容

---

## 消息队列 vs 任务队列

**这个区分很重要，选型题的关键：**

| | 任务队列（BullMQ / Celery） | 消息队列（Kafka / RabbitMQ） |
|---|---|---|
| 语义 | **执行一个任务** | **传递一条消息** |
| 内置能力 | 重试、延时、优先级、进度、定时 | 路由、持久化、分区、消费组 |
| 典型场景 | 后台作业、爬虫、发邮件 | 事件流、日志、跨服务通信 |
| 吞吐 | 中 | 极高（Kafka） |

**选 BullMQ 的理由**：
> 项目已有 Redis；Node 生态一等公民，NestJS 有官方集成；
> 重试、指数退避、延时任务、并发控制开箱即用。
> 我需要的是**任务队列**语义，不是消息流。

---

## BullMQ 的核心概念

```
Queue     → 生产者，往队列里加 job
Worker    → 消费者，处理 job
QueueEvents → 监听全局事件
FlowProducer → 父子任务编排
```

**任务状态流转**：
```
waiting → active → completed
                 ↘ failed → (重试) → waiting
        delayed ↗
```

## 幂等怎么保证

**这是队列系统最核心的问题，必答。**

> 消息队列基本都是 **at-least-once** 语义——
> 网络抖动、Worker 崩溃都可能导致同一个任务执行两次。
> **所以消费端必须幂等，这不是可选项。**

**三道防线**：

1. **业务唯一键**——由业务字段拼出确定性 key
2. **数据库唯一索引** + `INSERT IGNORE` / `ON DUPLICATE KEY UPDATE`
3. **BullMQ 的 jobId 去重**——相同 jobId 的任务会被自动去重
4. **消费侧 upsert**——即使真执行两次，结果也一致

**强调「幂等不是靠一个机制，是派生侧 + 队列侧 + 消费侧三道」**，
这句话很能体现设计水平。

## 失败重试策略

**关键在于区分错误类型**——一律重试是新手做法：

| 错误类型 | 处理 |
|---|---|
| 网络超时、5xx | 重试，**指数退避** |
| 限流 429 | 重试，但要退避更久 |
| 参数错误 4xx | **不重试**，直接标记失败 |
| 业务上不存在 | **不重试**，终态 |
| 解析异常（代码问题） | **不重试**，告警——重试解决不了 bug |

```ts
// 代码里用不同异常类型区分
class RetryableError extends Error {}
class FatalError extends Error {}

// Worker 里
try { ... }
catch (e) {
  if (e instanceof FatalError) return    // 不抛 = 标记完成
  throw e                                 // 抛出 = 触发 BullMQ 重试
}
```

## 孤儿任务 / stalled job

**定义**：任务已被 Worker 领走（状态 active），
但 Worker 进程崩了 / Pod 被驱逐，
任务既没成功也没失败，**永远卡在 active**。

**BullMQ 的机制**：
Worker 定期**续租（renew lock）**，
`stalledInterval` 内没续上就判定 stalled，
自动搬回 wait 队列重试，
超过 `maxStalledCount` 才标记失败。

**额外的兜底**：
定时扫描业务表，捞出「状态是 running 且 updated_at 超过阈值」的记录重新派生——
因为 BullMQ 的机制覆盖不了「业务表写了但入队失败」的情况。

## 优雅停机（K8s 场景必问）

Pod 缩容/滚动更新时，正在跑的任务怎么办？

```ts
process.on('SIGTERM', async () => {
  await worker.close()   // 停止领新任务，等待在途任务完成
  await app.close()
})
```

配合 K8s 的 `terminationGracePeriodSeconds`，
给足够时间让在途任务跑完。
真的没跑完的，靠 stalled 机制回收。

## Redis 内存别爆

BullMQ 的 job 数据存在 Redis 里，跑久了会积累：

```ts
new Queue('q', {
  defaultJobOptions: {
    removeOnComplete: { count: 1000 },   // 只保留最近 1000 条成功记录
    removeOnFail: { count: 5000 },
  }
})
```

**这题是验真题**——真跑过生产的人一定配过这个。

## 并发度怎么定

- **不是看本机 CPU**，看**下游能承受多少**
- 调外部 API → 受对方限流约束
- 写数据库 → 受连接池大小约束
- 采集类 → 受目标站风控约束（**这是你的场景**）

**方法论**：从低并发起步，观察成功率/错误率曲线，找拐点。
