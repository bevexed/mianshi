# NestJS 请求生命周期

NestJS 把一次请求拆成多个可组合的扩展点。面试和排障时，既要记住整体顺序，也要知道全局、控制器和路由级组件的局部顺序，以及异常发生后会跳过哪些阶段。

## 一次 HTTP 请求的主链路

```text
客户端请求
  → Middleware
  → Guard
  → Interceptor（进入）
  → Pipe
  → Controller / Service
  → Interceptor（返回）
  → 响应
```

如果链路中抛出未处理异常，会进入 Exception Filter。Interceptor 的返回阶段基于 RxJS 流执行，因此顺序与进入阶段相反。

更精确地看：

1. Middleware：全局中间件先执行，再按模块绑定顺序执行。
2. Guard：全局 → Controller → Route。
3. Interceptor 进入：全局 → Controller → Route。
4. Pipe：全局 → Controller → Route → 参数级。
5. Controller 调用应用服务完成业务处理。
6. Interceptor 返回：Route → Controller → 全局。
7. 未捕获异常由 Filter 按 Route → Controller → 全局查找。

Filter 与普通调用栈不同：一旦某层 Filter 捕获并响应，不会继续向外执行其他 Filter。

## 五类扩展点的职责

| 机制             | 最适合处理                               | 不宜承担                           |
| ---------------- | ---------------------------------------- | ---------------------------------- |
| Middleware       | 通用预处理、请求 ID、兼容现有中间件      | 依赖 handler 元数据的授权          |
| Guard            | 认证、角色/权限判断、决定能否继续        | 修改业务返回值或实现领域规则       |
| Interceptor      | 调用前后逻辑、耗时、超时、缓存、响应映射 | 代替应用服务或吞掉所有异常         |
| Pipe             | 单个参数的运行时校验和转换               | 全局错误兜底或数据库查询编排       |
| Exception Filter | 把未处理异常映射成稳定的 transport 响应  | 把未知错误伪装成成功或省略诊断信息 |

选择扩展点时可以问：它发生在 handler 前、调用前后，还是只在失败路径？它是否需要读取 `ExecutionContext` 中的路由元数据？答案通常比“我熟悉哪个装饰器”更可靠。

## Middleware：通用请求预处理

Middleware 在 Guard 之前执行，适合生成请求 ID、记录原始入口信息或复用 Express/Fastify 生态能力。

```ts
@Injectable()
export class RequestIdMiddleware implements NestMiddleware {
	use(req: Request, res: Response, next: NextFunction) {
		const requestId = req.header('x-request-id') ?? randomUUID();
		req.requestId = requestId;
		res.setHeader('x-request-id', requestId);
		next();
	}
}
```

它不天然知道将要执行哪个 handler，也不适合依赖 `@Roles()` 等路由元数据。需要 handler 元数据时使用 Guard 或 Interceptor。

## Guard：是否允许进入

Guard 返回布尔值或异步结果，决定请求是否继续。它能读取 `ExecutionContext` 和 Reflector，因此适合认证与授权。

```ts
@Injectable()
export class RolesGuard implements CanActivate {
	constructor(private readonly reflector: Reflector) {}

	canActivate(context: ExecutionContext): boolean {
		const roles = this.reflector.getAllAndOverride<string[]>('roles', [
			context.getHandler(),
			context.getClass()
		]);

		if (!roles) return true;

		const request = context.switchToHttp().getRequest();
		return roles.some((role) => request.user?.roles?.includes(role));
	}
}
```

Guard 只回答“能否访问”。复杂业务资格判断如果依赖订单状态、额度或库存，通常应由应用服务表达，再把结果映射为明确异常。

## Interceptor：包裹一次调用

Interceptor 在 handler 前后都能工作，适合统一耗时、超时、缓存或响应映射。

```ts
@Injectable()
export class TimingInterceptor implements NestInterceptor {
	intercept(context: ExecutionContext, next: CallHandler) {
		const startedAt = performance.now();

		return next.handle().pipe(
			finalize(() => {
				const durationMs = performance.now() - startedAt;
				// 实际项目中应写入结构化 Logger，并带上路由和请求上下文。
				console.log({ durationMs });
			})
		);
	}
}
```

多个 Interceptor 像洋葱模型：

```text
Global.before
  Controller.before
    Route.before
      Handler
    Route.after
  Controller.after
Global.after
```

如果在 Interceptor 中直接返回另一个 Observable 而不调用 `next.handle()`，handler 不会执行。这可以实现缓存短路，但必须保证权限、审计和缓存键边界正确。

## Pipe：校验与转换参数

Pipe 在 handler 调用前处理参数。TypeScript 类型只存在于编译阶段，不能代替运行时校验。

```ts
app.useGlobalPipes(
	new ValidationPipe({
		whitelist: true,
		forbidNonWhitelisted: true,
		transform: true
	})
);
```

```ts
@Get(':id')
findOne(@Param('id', ParseUUIDPipe) id: string) {
  return this.orderService.findById(id);
}
```

`whitelist` 可以移除 DTO 中没有装饰器声明的字段，`forbidNonWhitelisted` 则直接拒绝多余字段。是否开启转换和隐式转换要结合接口契约测试，避免字符串、数字、布尔值被意外转换。

## Exception Filter：稳定失败响应

Filter 负责把未处理异常映射成 HTTP、RPC 或 WebSocket 响应。应用服务可以抛出业务异常，边界层再决定 transport 状态码和响应结构。

```ts
@Catch(DomainError)
export class DomainExceptionFilter implements ExceptionFilter {
	catch(error: DomainError, host: ArgumentsHost) {
		const http = host.switchToHttp();
		const response = http.getResponse<Response>();

		response.status(422).json({
			code: error.code,
			message: error.message
		});
	}
}
```

不要把未知异常统一转换成 200，也不要只返回“系统错误”后丢掉内部异常栈。对外响应应避免泄漏敏感细节，对内日志仍要保留 request ID、异常类型、stack 和关键业务键。

## 常见场景怎样放

| 需求                   | 首选位置                | 原因                                 |
| ---------------------- | ----------------------- | ------------------------------------ |
| 生成 request ID        | Middleware 或日志适配器 | 尽早建立上下文，覆盖后续链路         |
| JWT 认证与角色授权     | Guard                   | 需要决定能否执行，并可读取路由元数据 |
| DTO 校验和参数转换     | Pipe                    | 面向 handler 参数的运行时边界        |
| 统一耗时、超时与响应壳 | Interceptor             | 需要包裹 handler 的进入和返回        |
| 领域异常映射为 HTTP    | Exception Filter        | 只处理失败路径和 transport 映射      |
| 订单提交事务           | 应用服务                | 属于业务用例，不是横切请求机制       |

## 三个容易答错的边界

1. Interceptor 能捕获和映射异常，但全局异常响应规范更适合 Filter；不要让每个 Interceptor 各自定义错误结构。
2. Guard 可以查询依赖以完成授权，但不应顺便修改订单、扣库存或提交事务。
3. HTTP 生命周期不覆盖定时任务、队列消费者和消息事件；这些入口需要各自的上下文、校验、异常与日志策略。

## 40 秒面试回答

> NestJS 的典型请求顺序是 Middleware、Guard、Interceptor 进入、Pipe、Controller/Service、Interceptor 返回，未处理异常进入 Filter。Guard 判断能否访问，Pipe 做参数转换和校验，Interceptor 包裹调用处理日志、超时或响应映射，Filter 负责异常到 transport 响应的映射。全局、Controller、Route 级组件通常由外到内进入，Interceptor 返回时反向执行；Filter 从最接近路由的位置开始匹配。实际设计还要注意 HTTP 链路不覆盖任务和消息消费者。

## 复习检查

- 能不看文档写出主链路，并说明异常分支。
- 能解释 Interceptor 的进入和返回顺序为何相反。
- 能区分 Middleware 与 Guard 是否能使用 handler 元数据。
- 知道 TypeScript 类型不能替代 ValidationPipe 的运行时校验。
- 能把认证、参数校验、统一耗时、异常映射和业务事务放到正确边界。
- 知道 Filter 捕获异常后不会继续向外层层冒泡执行。
