# NestJS 模块与依赖注入

NestJS 用模块描述封装边界，用 Provider 描述可注入能力，再由 IoC 容器根据 token 构建依赖图。学习这一章时，重点不是背 `@Module` 和 `@Injectable`，而是理解“谁能看见谁、容器凭什么找到实现、配置在什么时候确定”。

## 模块元数据与封装边界

```ts
@Module({
	imports: [PaymentModule],
	controllers: [OrderController],
	providers: [OrderService],
	exports: [OrderService]
})
export class OrderModule {}
```

| 元数据        | 作用                                         |
| ------------- | -------------------------------------------- |
| `imports`     | 引入其他模块导出的 Provider，建立模块间依赖  |
| `controllers` | 注册当前模块负责的请求入口                   |
| `providers`   | 注册由当前模块容器管理的 Provider            |
| `exports`     | 暴露 Provider 或导入的模块，形成对外公共接口 |

Provider 默认只在声明它的模块上下文内可见。其他模块要使用它，需要满足：

1. 声明模块将 Provider 放入 `exports`。
2. 使用方模块将声明模块放入 `imports`。

不要为了“少写一个 imports”就把大量模块设为全局模块。显式依赖更容易阅读、测试和拆分。

## 依赖注入与 Provider token

`providers: [OrderService]` 是类 Provider 的简写，等价于：

```ts
{
  provide: OrderService,
  useClass: OrderService
}
```

容器真正查找的是 token。token 可以是类、字符串或 `Symbol`。TypeScript 接口在编译后会被擦除，不能直接作为运行时 token；需要配合 `@Inject()` 使用字符串或 `Symbol`。

```ts
export const API_BASE_URL = Symbol('API_BASE_URL');
export const PAYMENT_PORT = Symbol('PAYMENT_PORT');
export const CACHE = Symbol('CACHE');

@Injectable()
export class SharedCache {}

@Injectable()
export class ApiClient {
	constructor(readonly baseUrl: string) {}
}

const providers: Provider[] = [
	OrderService,
	{
		provide: API_BASE_URL,
		useValue: 'https://api.example.com'
	},
	{
		provide: PAYMENT_PORT,
		useClass: StripePaymentAdapter
	},
	SharedCache,
	{
		provide: CACHE,
		useExisting: SharedCache
	},
	{
		provide: ApiClient,
		inject: [API_BASE_URL],
		useFactory: (baseUrl: string) => new ApiClient(baseUrl)
	}
];
```

| 写法          | 适用场景                                 |
| ------------- | ---------------------------------------- |
| `useValue`    | 常量、配置对象或测试替身                 |
| `useClass`    | 根据 token 选择一个具体类实现            |
| `useFactory`  | 需要根据其他依赖或运行配置创建实例       |
| `useExisting` | 为同一个实例提供别名，不会再创建一份实例 |

```ts
export interface PaymentPort {
	pay(orderId: string): Promise<void>;
}

@Injectable()
export class OrderService {
	constructor(
		@Inject(PAYMENT_PORT)
		private readonly paymentPort: PaymentPort
	) {}
}
```

这里依赖的是业务端口而不是具体支付 SDK。测试时可以用相同 token 替换 Provider，而不必修改业务服务。

## 静态模块与动态模块

静态模块的元数据在代码声明时已经确定，导入方式也固定：

```ts
@Module({
	providers: [ClientService],
	exports: [ClientService]
})
export class ClientModule {}

@Module({
	imports: [ClientModule]
})
export class OrderModule {}
```

动态模块允许调用方传入配置，由模块方法返回 `DynamicModule`：

```ts
export const CLIENT_OPTIONS = Symbol('CLIENT_OPTIONS');

export interface ClientModuleOptions {
	baseUrl: string;
	timeout: number;
}

@Module({})
export class ClientModule {
	static register(options: ClientModuleOptions): DynamicModule {
		return {
			module: ClientModule,
			providers: [
				{
					provide: CLIENT_OPTIONS,
					useValue: options
				},
				ClientService
			],
			exports: [ClientService]
		};
	}
}
```

调用方通过方法生成本次导入所需的模块元数据：

```ts
@Module({
	imports: [
		ClientModule.register({
			baseUrl: 'https://api.example.com',
			timeout: 3_000
		})
	]
})
export class OrderModule {}
```

动态模块返回的元数据会扩展 `@Module()` 中已有的静态元数据，不是把它完全替换掉。返回对象必须包含 `module` 属性，`providers`、`imports`、`exports` 和 `global` 等字段按需要提供。

| 维度     | 静态模块                  | 动态模块                                     |
| -------- | ------------------------- | -------------------------------------------- |
| 配置来源 | 在模块声明中固定          | 由调用方在导入时传入                         |
| 导入形式 | `imports: [ClientModule]` | `imports: [ClientModule.register(options)]`  |
| 典型用途 | 固定 Provider 集合        | 可配置 SDK、数据库、缓存、日志等基础设施模块 |
| 多次导入 | 通常配置相同              | 可以按导入位置生成不同配置                   |

动态模块描述的是“模块元数据如何生成”，不等于懒加载。Nest 仍会在应用启动构建模块图时解析它，除非另外使用 `LazyModuleLoader` 等懒加载机制。

## register、forRoot、forFeature 和异步配置

这些方法名是社区约定，不是语法关键字：

| 命名                             | 常见语义                                             |
| -------------------------------- | ---------------------------------------------------- |
| `register`                       | 为当前调用方创建一份模块配置                         |
| `forRoot`                        | 在应用根部设置共享或全局基础配置                     |
| `forFeature`                     | 在功能模块中注册局部模型、Repository 或扩展 Provider |
| `registerAsync` / `forRootAsync` | 配置工厂需要注入 ConfigService、SecretClient 等依赖  |

```ts
@Module({
	imports: [
		ClientModule.forRootAsync({
			imports: [ConfigModule],
			inject: [ConfigService],
			useFactory: async (config: ConfigService) => ({
				baseUrl: config.getOrThrow<string>('CLIENT_BASE_URL'),
				timeout: config.get<number>('CLIENT_TIMEOUT', 3_000)
			})
		})
	]
})
export class AppModule {}
```

`Async` 表示配置可以通过依赖注入和异步工厂获得，不表示模块会等到第一次请求才加载。配置失败通常应让应用启动失败，避免带着不完整配置继续提供服务。

Nest 还提供 `ConfigurableModuleBuilder` 来减少可配置模块的样板代码：

```ts
export interface ClientModuleOptions {
	baseUrl: string;
	timeout: number;
}

export const { ConfigurableModuleClass, MODULE_OPTIONS_TOKEN } =
	new ConfigurableModuleBuilder<ClientModuleOptions>().setClassMethodName('forRoot').build();

@Module({
	providers: [ClientService],
	exports: [ClientService]
})
export class ClientModule extends ConfigurableModuleClass {}
```

## 共享、全局、动态与懒加载不是同一维度

| 概念       | 回答的问题                                     |
| ---------- | ---------------------------------------------- |
| 共享模块   | 多个模块能否通过 imports/exports 复用 Provider |
| 全局模块   | 是否省略各处显式 imports                       |
| 动态模块   | 导入时如何根据参数生成模块元数据               |
| 懒加载模块 | 是否延后到运行阶段再加载模块                   |

一个动态模块可以是全局模块，也可以不是；一个静态模块同样可以被多个模块共享。不要因为名称相似就把这些概念合并。

## Provider 作用域

| 作用域            | 生命周期                     | 常见用途                       |
| ----------------- | ---------------------------- | ------------------------------ |
| `Scope.DEFAULT`   | 默认单例，应用生命周期内复用 | 无请求状态的服务、客户端和缓存 |
| `Scope.REQUEST`   | 每个请求创建一份             | 必须绑定请求的上下文对象       |
| `Scope.TRANSIENT` | 每个注入位置获得独立实例     | 需要消费者隔离的轻量对象       |

请求作用域会沿依赖链向上传播：单例 Controller 如果依赖请求作用域 Provider，也会变成请求作用域。大量使用会增加实例创建和垃圾回收开销。只需要 request ID、租户或用户上下文时，可以评估 `AsyncLocalStorage`，不必让整条依赖链都变成请求作用域。

## 循环引用

要先区分三类问题：

1. 文件导入循环：A 文件 import B，B 又 import A。
2. 模块循环：`OrdersModule` imports `PaymentsModule`，后者又 imports 前者。
3. Provider 循环：`OrderService` 注入 `PaymentService`，后者又注入前者。

遇到 `Nest can't resolve dependencies` 或 `imports` 中出现 `undefined` 时，先检查：

- 导入路径和 token 是否正确；
- Provider 所属模块是否将它放入 `exports`；
- 使用方是否在 `imports` 中引入了正确模块；
- 内部 `index.ts` 桶文件是否形成隐式文件循环。

缺少 `exports` 不等于必须增加反向模块依赖。

`forwardRef()` 能延迟 token 解析，但不会自动修复职责混乱。更优先的做法是重画依赖方向：

```text
OrderService <── CheckoutService ──> PaymentService
```

把跨模块编排提取到更上层的 `CheckoutService`，让订单与支付不再互相调用。也可以提取双方都依赖的领域服务、端口或事件。

不要为了消除循环，把双方的大量业务代码塞进巨大的 `CommonModule`。如果反向调用只是通知任务完成、状态变化或触发后续异步处理，可以发布事件；需要立即取得返回值的请求-响应调用仍应保留显式依赖，不要为了消环强行事件化。

确实无法立即消除时，可以临时使用：

```ts
@Module({
	imports: [forwardRef(() => PaymentsModule)]
})
export class OrdersModule {}

@Module({
	imports: [forwardRef(() => OrdersModule)]
})
export class PaymentsModule {}

@Injectable()
export class OrderService {
	constructor(
		@Inject(forwardRef(() => PaymentService))
		private readonly paymentService: PaymentService
	) {}
}

@Injectable()
export class PaymentService {
	constructor(
		@Inject(forwardRef(() => OrderService))
		private readonly orderService: OrderService
	) {}
}
```

Provider 循环的实例化顺序是不确定的，不要在构造函数中依赖对方已经完成初始化。`ModuleRef` 可以在生命周期钩子中按 token 获取 Provider，但它隐藏了静态依赖，也应只用于框架集成、插件或迁移边界。

## 40 秒面试回答

### 静态与动态模块的口述版本

> 静态模块的 providers、imports 和 exports 在声明时固定；动态模块通过 register、forRoot 或异步工厂返回 DynamicModule，让调用方在导入时提供配置。动态模块解决可配置元数据生成，不等于懒加载。register、forRoot、forFeature 是语义约定，分别常用于局部配置、根配置和功能级注册。

### 循环依赖

> 我会先区分文件、模块和 Provider 三类循环，再检查职责和依赖方向。优先提取上层编排服务、共同依赖或端口来消环。forwardRef 只是延迟解析，适合过渡；ModuleRef 更动态但隐藏依赖。保留循环时还要避免在构造阶段依赖不确定的实例化顺序。

## 复习检查

- 能根据 imports、providers 和 exports 判断 Provider 可见性。
- 能解释类、字符串和 Symbol token 的区别，以及接口为何不能直接注入。
- 能为 useValue、useClass、useFactory 和 useExisting 各举一个场景。
- 能说明静态模块、动态模块、全局模块和懒加载模块不是同一概念。
- 能解释 register、forRoot、forFeature 与异步配置的语义。
- 能说明请求作用域传播的性能影响。
- 遇到循环引用时，先分析边界而不是直接添加 forwardRef。
