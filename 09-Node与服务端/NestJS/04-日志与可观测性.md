# NestJS 日志与可观测性

日志不是把字符串打印到控制台，而是为一次请求、后台任务或领域事件留下可检索的结构化证据。NestJS 提供统一日志抽象；Pino 和 Winston 负责具体记录与输出；采集器、日志平台、指标和链路追踪共同构成生产可观测性。

## 先分清三层职责

1. **Nest 日志抽象**：`LoggerService` 统一框架启动日志和业务日志的调用方式。
2. **结构化与上下文**：记录 `requestId`、`traceId`、路由、状态码、耗时和业务键，并让同一执行上下文内的日志可关联。
3. **输出与采集**：将 JSON 写到 stdout 或指定目标，再由容器运行时、Agent 或日志平台采集、索引、保留和告警。

HTTP Interceptor 只覆盖进入 Nest handler 的 HTTP 调用，不会自动覆盖应用启动、定时任务、队列 Worker、领域事件和微服务消息处理。因此“写了日志 Interceptor”不等于完成日志体系。

## Nest 内置 Logger 与自定义 Logger

Nest 内置 `Logger` 适合开发期输出和简单服务，支持 `fatal`、`error`、`warn`、`log`、`debug`、`verbose` 等级和 context：

```ts
@Injectable()
export class OrderService {
	private readonly logger = new Logger(OrderService.name);

	submit(orderId: string) {
		this.logger.log('order submitted: ' + orderId);
	}
}
```

生产环境需要结构化字段、统一脱敏或外部日志库时，可以实现 `LoggerService`，也可以使用 Pino/Winston 的 Nest 适配模块。

```ts
const app = await NestFactory.create(AppModule, {
	bufferLogs: true
});

app.useLogger(app.get(MyLogger));
await app.listen(3000);
```

`bufferLogs` 用于暂存自定义 Logger 创建完成前的启动日志，不是业务日志的磁盘队列，也不能在进程崩溃或远程 transport 故障时保证不丢日志。

## 一条可用的结构化日志

```json
{
	"level": "info",
	"time": "2026-08-21T10:00:00.000Z",
	"service": "order-api",
	"env": "production",
	"version": "a1b2c3d",
	"context": "OrderService",
	"event": "order.submitted",
	"requestId": "req-123",
	"traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
	"orderId": "order-456",
	"durationMs": 42,
	"message": "order submitted"
}
```

可查询字段应放在对象中，`message` 保留简短的人类可读说明。字段名称、类型和含义需要稳定；如果今天记录 `cost` 表示毫秒，明天又表示金额，查询与告警都会失真。

## Pino：低开销 JSON 与请求上下文

`nestjs-pino` 集成 `pino-http`，可以自动记录请求/响应，并通过 `AsyncLocalStorage` 让同一请求中的业务日志关联请求上下文。

```ts
// app.module.ts
@Module({
	imports: [
		LoggerModule.forRoot({
			pinoHttp: {
				level: process.env.NODE_ENV === 'production' ? 'info' : 'debug',
				redact: {
					paths: ['req.headers.authorization', 'req.headers.cookie', 'req.body.password'],
					censor: '[REDACTED]'
				},
				transport: process.env.NODE_ENV !== 'production' ? { target: 'pino-pretty' } : undefined
			}
		})
	]
})
export class AppModule {}

// main.ts
const app = await NestFactory.create(AppModule, { bufferLogs: true });
app.useLogger(app.get(Logger)); // Logger 从 nestjs-pino 导入
await app.listen(3000);
```

`pino-pretty` 需要单独安装，适合本地阅读；生产环境通常保留机器可解析的 JSON，把美化、索引和保留交给进程外采集链路。

```ts
@Injectable()
export class OrderService {
	constructor(
		@InjectPinoLogger(OrderService.name)
		private readonly logger: PinoLogger
	) {}

	submit(orderId: string) {
		this.logger.info({ event: 'order.submitted', orderId }, 'order submitted');
	}

	onError(orderId: string, err: Error) {
		this.logger.error({ err, event: 'order.submit_failed', orderId }, 'order submit failed');
	}
}
```

Pino 对 `Error` 有专门的序列化处理；不要只记录 `err.message` 而丢失类型和 stack。自定义序列化器时需要测试异常字段和脱敏规则仍然生效。

## Winston：Format 与 Transport 组合

Winston 将日志格式与输出目标拆成可组合的 format/transport，`nest-winston` 可将其适配为 Nest `LoggerService`。

```ts
// app.module.ts
@Module({
	imports: [
		WinstonModule.forRoot({
			level: 'info',
			format: winston.format.combine(
				winston.format.timestamp(),
				winston.format.errors({ stack: true }),
				winston.format.json()
			),
			transports: [new winston.transports.Console()]
		})
	]
})
export class AppModule {}

// main.ts
const app = await NestFactory.create(AppModule, { bufferLogs: true });
app.useLogger(app.get(WINSTON_MODULE_NEST_PROVIDER));
await app.listen(3000);
```

Winston 可以为不同 transport 配置不同级别和格式，例如 Console、File、HTTP 或社区 transport。容器环境通常优先输出 JSON 到 stdout，由采集器负责轮转与转发。应用进程直接写多个文件或远程 transport，会把外部延迟、重试、缓冲和背压带入请求进程，必须明确：

- 远程目标不可用时是阻塞、丢弃还是本地缓冲；
- 队列上限和溢出策略是什么；
- 进程退出前等待多久；
- 同一日志是否会被重复采集。

## Pino 与 Winston 怎么选

| 维度          | Pino / `nestjs-pino`                          | Winston / `nest-winston`                         |
| ------------- | --------------------------------------------- | ------------------------------------------------ |
| 主要取向      | 低开销结构化 JSON，减少请求路径上的格式化工作 | 灵活组合 format 和多种 transport                 |
| HTTP 请求日志 | `pino-http` 自动记录，可通过 ALS 关联上下文   | 通常另行组合 Middleware/Interceptor 与上下文传递 |
| 输出策略      | 倾向保持应用输出简单，在进程外美化和采集      | 按目标分级、分格式和 transport 生态更突出        |
| 常见场景      | API、高请求量服务、希望自动关联请求日志       | 复杂输出目标、特殊格式或团队已有 Winston 体系    |

两者都能输出 JSON，也都能接入日志平台。不能只背“Pino 更快”或“Winston 功能更多”；应使用真实字段数量、异常比例、请求日志量、transport 和部署方式压测，并考虑团队已有运维链路。

## 请求 ID 与 Trace Context

`requestId` 用于关联一个服务接收到的一次请求。服务可以接受可信网关传入的值，否则自行生成并写回响应头。

`traceId` 属于分布式追踪上下文，用于关联跨服务、消息和异步边界的一整条调用链。它应遵循所采用的追踪标准传播，不能简单把任意请求头当作可信 trace context。

两者可以相同但语义不同。常见实践是日志同时记录 `requestId`、`traceId` 和 `spanId`，让使用者能从日志跳到 trace，也能按单次入口请求检索。

后台任务和消息消费者没有 HTTP request，需要在各自入口创建日志上下文：

```ts
async process(job: Job<OrderPayload>) {
  this.logger.info(
    {
      event: 'order_job.started',
      jobId: job.id,
      orderId: job.data.orderId,
      traceId: job.data.traceId
    },
    'order job started'
  );
}
```

跨队列传播 trace context 前要定义序列化格式、信任边界和缺失时的降级行为。

## 生产日志的关键约束

- **字段稳定**：统一 `service`、`env`、`version`、`context`、`event`、`requestId`、`traceId`、`durationMs` 和关键业务键。
- **异常可诊断**：记录异常类型、message、stack、操作名称和必要业务键，不只写“执行失败”。
- **默认脱敏**：禁止记录密码、Token、Cookie、验证码、密钥、完整证件号和不必要的请求体；对脱敏路径写自动化测试。
- **容量可控**：健康检查、高频成功请求和可预期 4xx 可按路由降级、采样或关闭自动记录；错误、慢请求和关键审计事件需要保留。
- **审计独立建模**：安全审计需要不可抵赖、访问控制和专门保留策略时，不应只依赖普通应用日志。
- **时间一致**：统一时间格式和时区，记录机器时间同步状态，避免跨实例排序失真。
- **退出策略明确**：优雅停机时确认缓冲日志如何刷新，但不要无限等待不可用的远程目标。

## 日志、指标与追踪的边界

| 信号 | 擅长回答                                     | 示例                                |
| ---- | -------------------------------------------- | ----------------------------------- |
| 日志 | 某个具体事件发生了什么，携带了哪些诊断上下文 | 某订单失败时的异常栈和业务键        |
| 指标 | 系统整体是否异常，变化趋势和分位数如何       | 请求量、错误率、P95 延迟、队列积压  |
| 追踪 | 跨组件调用时间花在哪里，因果链如何传播       | 网关 → 订单服务 → 支付服务 → 数据库 |

不要用每秒扫描海量日志代替稳定指标，也不要期待 trace 保存每个业务细节。告警通常先由指标触发，再通过 trace 定位慢节点，最后用结构化日志查看具体事件。

## 常见故障与排查

| 现象                     | 优先检查                                                     |
| ------------------------ | ------------------------------------------------------------ |
| 启动日志丢失             | 是否使用 `bufferLogs`，自定义 Logger 是否成功替换            |
| Service 日志缺 requestId | 是否脱离 ALS 上下文、使用错误 Logger、异步边界是否重建上下文 |
| 错误日志没有 stack       | 是否只记录 message，Error serializer/format 是否正确         |
| 日志量突然暴涨           | 自动请求日志、重试循环、健康检查和 debug 级别                |
| 容器磁盘被写满           | 是否在容器内写文件、轮转与采集失败、stdout 驱动配置          |
| API 延迟随日志平台抖动   | 是否同步写远程 transport，缓冲和背压策略是否合理             |

## 40 秒面试回答

> Nest 的 LoggerService 是调用抽象，完整日志体系还包括结构化字段、执行上下文和采集链路。API 服务如果重视低开销 JSON 和自动请求关联，我倾向 nestjs-pino；如果需要复杂 format、多 transport 或已有 Winston 体系，会选择 nest-winston。生产中统一 requestId、traceId、event、业务键、耗时和异常栈，默认脱敏 Token、Cookie 与隐私字段，用级别、采样和保留期控制成本。日志负责事件细节，指标负责趋势和告警，trace 负责跨服务因果链，最终选型要用真实负载验证。

## 复习检查

- 能区分 Nest Logger 抽象、结构化上下文和日志采集三层。
- 能写出 Pino 与 Winston 的最小 Nest 接入方式。
- 能根据请求关联、format/transport 和运维体系比较二者。
- 能解释 requestId 与 traceId 的语义区别。
- 知道 HTTP Interceptor 不覆盖任务、队列和应用启动。
- 能列出敏感字段、容量控制、远程背压和异常栈要求。
- 能说明日志、指标与分布式追踪各自适合回答什么问题。
