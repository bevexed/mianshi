# NestJS 框架定位与项目结构

## NestJS 解决什么问题

NestJS 是一个面向 Node.js 服务端应用的组织层。它以 TypeScript 和装饰器描述模块、Provider 与请求处理组件，再由 IoC 容器创建依赖图。框架的核心价值不是“装饰器更少写代码”，而是为中大型 TypeScript 服务提供明确的封装边界、依赖方向和横切扩展点。

它较适合：

- 需要持续扩展、多人协作和长期维护的 API/BFF 或后台服务；
- 需要统一鉴权、校验、异常、日志、配置和测试方式的团队；
- 需要将 HTTP、定时任务、队列 Worker 或消息 transport 组织在一套依赖注入体系中的应用。

NestJS 不会自动解决职责混乱、数据一致性、慢 SQL、事件循环阻塞或分布式故障。框架只提供组织机制，模块边界和失败策略仍需要开发者设计。

## 应用图与根模块

Nest 从根模块开始构建模块图，再根据每个模块的元数据解析 Controller 和 Provider。

```ts
@Module({
	imports: [OrderModule, PaymentModule],
	providers: [AppService],
	controllers: [AppController]
})
export class AppModule {}
```

```text
AppModule
  ├── OrderModule
  │     ├── OrderController
  │     └── OrderService
  └── PaymentModule
        └── PaymentService
```

这里要分清两张图：

- TypeScript/JavaScript `import` 建立的是文件与模块加载关系。
- Nest `@Module({ imports: [...] })` 建立的是运行时模块和 Provider 可见性图。

两者都可能循环，但错误表现和修复方式不完全一样。详见[模块与依赖注入](02-模块与依赖注入.md)。

## Controller、Provider 与 Module 如何协作

```ts
@Injectable()
export class OrderService {
	findById(id: string) {
		return { id };
	}
}

@Controller('orders')
export class OrderController {
	constructor(private readonly orderService: OrderService) {}

	@Get(':id')
	findOne(@Param('id') id: string) {
		return this.orderService.findById(id);
	}
}

@Module({
	controllers: [OrderController],
	providers: [OrderService],
	exports: [OrderService]
})
export class OrderModule {}
```

- Controller 处理 transport/HTTP 边界：接受输入、调用应用服务、返回结果。
- Provider 承担可被容器管理和注入的能力，例如应用服务、Repository、客户端适配器和策略。
- Module 声明这些组件的封装和可见性，`exports` 是对其他模块的公共接口。

领域规则不应全部堆在 Controller 里；但也不要把每个两行函数都拆成 Service。拆分依据是职责、变化原因和可测试边界，而不是类的数量。

## Express 与 Fastify 适配器

Nest 默认使用 Express，也可以通过 `FastifyAdapter` 切换到 Fastify。

| 维度         | Express                          | Fastify                                            |
| ------------ | -------------------------------- | -------------------------------------------------- |
| 生态与熟悉度 | 中间件生态广，团队往往更熟悉     | 插件和 hook 模型更强调封装                         |
| 校验与序列化 | 通常另行组合工具                 | 强调 schema 驱动的校验与序列化                     |
| 性能         | 取决于真实路由、中间件与负载     | 在部分负载下可能具有更高吞吐，仍需实测             |
| 迁移成本     | 许多 Node 库直接假设 Express API | 需要核对库是否依赖 Express 的 request/response API |

不能把 TypeScript 类型当成运行时校验。无论使用哪个适配器，都要对外部输入做显式校验，并用接近生产的路由、序列化、日志、数据库和 TLS 配置压测；空框架 QPS 不代表业务吞吐。

## 什么情况不适合 NestJS

- 短小的一次性脚本或只有少量路由的内部工具，框架约束可能大于收益。
- CPU 密集任务不应长时间占用主事件循环；可使用 Worker Threads、独立进程或专用计算服务。
- 如果团队的语言、运维、事务和生态约束明显更适合其他技术栈，不应只因为前后端都能写 TypeScript 就强行选 NestJS。

选型至少要比较团队经验、一致性要求、负载特征、依赖生态、监控部署以及长期所有权成本。NestJS、Spring、Express 或 Fastify 都没有脱离场景的绝对优劣。

## 40 秒面试回答

> NestJS 是 Node.js 上的应用组织层，核心是模块、依赖注入和统一的请求处理扩展点。它适合需要明确边界、多人协作和长期维护的 TypeScript 服务。Controller 处理 transport 边界，Provider 承担可注入能力，Module 组织封装和可见性。它可以使用 Express 或 Fastify，选择要结合生态兼容性和真实负载压测。框架不会自动解决领域边界、数据一致性和 Node 事件循环阻塞，这些仍需要工程设计和验证。

## 复习检查

- 能区分文件 import 图与 Nest 运行时应用图。
- 能说清 Controller、Provider 和 Module 的职责边界。
- 知道 Express/Fastify 是 HTTP 适配器选择，不会改变模块与 DI 的核心模型。
- 能给出一个不应选 NestJS 或不应在主线程直接执行的反例。
- 会用真实约束和测量说明技术选型，不背“某框架一定更快”。
