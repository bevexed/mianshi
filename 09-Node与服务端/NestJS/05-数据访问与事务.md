# NestJS 数据访问与事务

NestJS 负责组织依赖和应用边界，不替数据库设计、ORM 查询计划或事务一致性做决定。数据访问层的核心问题是：业务服务依赖什么抽象、查询是否可预测、同一用例的写操作是否共享事务上下文，以及外部副作用如何与数据库状态协调。

## NestJS 不绑定 ORM

NestJS 可以集成 TypeORM、Prisma、Sequelize、MikroORM、Mongoose，也可以直接使用数据库驱动。框架只要求把客户端、Repository 或适配器注册为 Provider。

选型要结合：

- 数据模型是关系、文档还是键值；
- 团队是否需要 Unit of Work、实体关系和迁移工具；
- 查询复杂度、批量写入、类型安全与调试 SQL 的能力；
- 连接池、事务、读写分离和监控支持；
- 现有代码、团队经验和长期迁移成本。

不要因为 NestJS 官方示例展示某个 ORM，就把它当成框架强制要求。

## Repository 边界与依赖注入

应用服务可以依赖面向用例的 Repository 端口，而不是在 Controller 中直接拼查询。

```ts
export const ORDER_REPOSITORY = Symbol('ORDER_REPOSITORY');

export interface OrderRepository {
	findById(id: string): Promise<Order | null>;
	save(order: Order): Promise<void>;
}

@Injectable()
export class SubmitOrderService {
	constructor(
		@Inject(ORDER_REPOSITORY)
		private readonly orders: OrderRepository
	) {}

	async execute(orderId: string) {
		const order = await this.orders.findById(orderId);
		if (!order) throw new OrderNotFoundError(orderId);

		order.submit();
		await this.orders.save(order);
	}
}
```

基础设施模块绑定具体实现：

```ts
@Module({
	providers: [
		TypeOrmOrderRepository,
		{
			provide: ORDER_REPOSITORY,
			useExisting: TypeOrmOrderRepository
		}
	],
	exports: [ORDER_REPOSITORY]
})
export class OrderPersistenceModule {}
```

Repository 不必机械地为每张表生成一套 CRUD。边界应围绕聚合或用例，既隐藏 ORM 细节，又保留调用方真正需要的查询能力。过度通用的 `BaseRepository<T>` 往往会泄漏分页、关联、事务和性能差异。

## 连接归还、释放与关闭

先判断“连接是谁取得、由谁管理”，不要看到数据库连接就统一调用 `release()`：

| 使用方式                                         | 谁管理连接              | 调用方需要做什么                              |
| ------------------------------------------------ | ----------------------- | --------------------------------------------- |
| TypeORM Repository 普通查询                      | ORM 与连接池            | 等待查询完成，不手动释放连接                  |
| 普通 EntityManager 查询                          | ORM 与连接池            | 不手动释放连接                                |
| `DataSource.transaction()` 回调                  | TypeORM 事务管理        | 使用回调传入的 manager，让回调正常结束或抛错  |
| 手动创建 `QueryRunner`                           | 当前调用方              | commit/rollback 后在 `finally` 中 `release()` |
| 驱动层 `pool.getConnection()` / `pool.connect()` | 当前调用方              | 按驱动约定在 `finally` 中归还连接             |
| 应用级 `DataSource` / 连接池                     | 创建它的模块或 Provider | 长期复用，在应用终止阶段统一关闭              |

### release 不等于关闭物理连接

连接池模式下，`release()` 通常表示把借出的连接归还池中，供后续请求复用：

```text
请求
  → 从连接池借一个 connection
  → 执行 SQL
  → release()
  → connection 回到连接池
```

它不等于每次查询后都断开数据库 TCP 连接。真正关闭整个 TypeORM `DataSource` 及其连接池使用 `dataSource.destroy()`，通常只发生在脚本执行结束、测试清理或应用正常终止阶段。

如果 `TypeOrmModule` 已经负责创建和关闭 `DataSource`，业务 Service 不要再重复调用 `destroy()`。只有自己创建并拥有 DataSource 的 Provider，才应在对应的应用关闭钩子中关闭它。

### 正常停机与异常断开

| 场景                              | 应用侧行为                                           | 数据库侧结果                                         |
| --------------------------------- | ---------------------------------------------------- | ---------------------------------------------------- |
| 显式 `app.close()`                | Nest 执行关闭钩子，资源拥有者主动关闭连接池          | 数据库及时结束连接                                   |
| `SIGTERM` 且已启用 shutdown hooks | Nest 进入终止生命周期并等待异步钩子                  | 在终止宽限期内正常断开                               |
| 进程崩溃、`SIGKILL` 或机器断电    | JavaScript 清理代码没有执行机会，OS 回收本地进程资源 | 数据库之后通过 socket 状态、keepalive 或超时确认断连 |
| 网络分区                          | 客户端和数据库可能暂时都无法确认对方状态             | 连接和锁可能保留到探测或超时生效                     |

会话被数据库确认断开后，未提交事务通常会回滚；具体检测时机和超时行为取决于数据库、驱动、操作系统及网络配置。因此异常断开不能依赖应用的 `finally` 或生命周期钩子，也不能假设数据库会瞬间发现断电。

真正容易耗尽连接池的情况通常是“进程仍然存活，但手动借出的连接没有归还”：

```text
连接池上限 10
  → 10 个 QueryRunner 各占一个连接且没有 release
  → 第 11 个请求等待
  → 获取连接超时或服务持续堆积
```

除了代码中成对释放，还要监控连接池已用/空闲/等待数量、获取连接耗时、长事务和数据库会话数。

## TypeORM 常见风险

### N+1 查询

先查一批订单，再逐条加载客户或明细，会让查询次数随数据量增长。应检查生成 SQL 和数据库指标，根据场景选择：

- 使用 join 一次获取有限关联；
- 收集 ID 后批量查询并在内存中映射；
- GraphQL 场景使用 DataLoader 合并同一批次的读取；
- 对大集合分页，避免一次加载整个对象图。

不能看到关联就无条件 eager join。多组一对多关系同时 join 可能产生笛卡尔膨胀，必须对真实数据量执行 `EXPLAIN` 并测量。

#### 场景追问：查询一百家企业及证书，如何消除 N+1？

**面试官：** 一次查一百家企业，再循环查每家证书，会有多少 SQL？JOIN、relations、批量 IN 查询怎么选？

**口语参考答案：**

> 这个简化场景是一条企业查询加一百条证书查询，共一百零一条。可以用关联 JOIN 获取有限数据，也可以先分页查企业，再一次按企业 ID 批量查证书并分组，把这里的查询降到两次。但企业很多、证书很多时，JOIN 或批量加载仍会返回大量行，列表可能只需要证书数量，明细应按需分页。TypeORM 的 relations 还受 relationLoadStrategy 等配置影响，不能只看 API 就断言 SQL 次数，要看真实日志和执行计划。

**追问与易错点：** JOIN 后 SQL 行数与实体数不同，ORM 分页、计数还可能执行额外 SQL。优化目标包括数据库往返、结果字节和映射内存，不是强求一条 SQL。

### 批量写入

实体级 `save()` 方便触发实体生命周期逻辑，但大批量写入时可能产生额外查询、逐条钩子和较高内存开销。需要根据语义选择分批、`insert()`、`upsert()`、QueryBuilder 或数据库原生批量能力，并验证：

- 唯一约束和冲突策略；
- 实体 hook/subscriber 是否仍执行；
- 单批大小、锁时间和失败回滚范围；
- 返回值是否满足业务需要。

### Schema 变更

生产环境不应依赖 `synchronize: true` 自动修改表结构。使用可审计的 migration，并在发布前检查：

1. 前向与回滚步骤是否明确；
2. 老代码和新代码是否能跨发布窗口兼容；
3. 大表 DDL 是否锁表或触发长时间回填；
4. 索引创建、默认值和非空约束是否分阶段进行；
5. 迁移是否在正确环境只执行一次。

## 十万条数据筛选与流式导出

大数据导出的核心不是把 Node.js 堆内存调大，而是让整条链路都有界：

```text
数据库 WHERE 筛选
  → 稳定排序下的游标分批
  → 每批转换为 CSV
  → 遵守背压写入 HTTP Response
  → 客户端断开时停止后续查询
```

不要先加载全量实体，再在内存中筛选和生成大 Buffer：

```ts
const users = await this.userRepository.find();
const selected = users.filter(matchesExportCondition);
const file = await buildWorkbookBuffer(selected);

res.send(file);
```

这种写法可能同时保留全量实体、筛选数组、文件库中间对象和最终 Buffer；记录数只是一个维度，字段数、长文本、关联对象和 XLSX 样式都会放大内存。

### 筛选要下推到数据库

前端传入的状态、时间范围、租户和关键字等条件，应在 DTO 校验和权限检查后组成参数化 SQL。查询只选导出需要的列，不要加载无关实体和关联。

```ts
async findExportBatch(
	dto: ExportUsersDto,
	lastId: number,
	upperBoundId: number,
	limit: number
) {
	const qb = this.userRepository
		.createQueryBuilder('user')
		.select('user.id', 'id')
		.addSelect('user.name', 'name')
		.addSelect('user.email', 'email')
		.where('user.id > :lastId', { lastId })
		.andWhere('user.id <= :upperBoundId', { upperBoundId })
		.orderBy('user.id', 'ASC')
		.take(limit);

	if (dto.status !== undefined) {
		qb.andWhere('user.status = :status', { status: dto.status });
	}

	if (dto.startTime) {
		qb.andWhere('user.createdAt >= :startTime', {
			startTime: dto.startTime
		});
	}

	if (dto.keyword) {
		qb.andWhere('user.name LIKE :keyword', {
			keyword: `%${dto.keyword}%`
		});
	}

	return qb.getRawMany<UserExportRow>();
}
```

查询导出上界的 `findExportUpperBound()` 必须复用同一组租户、权限和业务筛选条件，不能只取全表最大 ID。参数化能防 SQL 注入，但不代表查询就高效。经常组合筛选时，要用真实 SQL 和数据分布检查 `EXPLAIN`；`LIKE '%关键词%'` 通常无法有效利用普通 B-Tree 索引，可能需要全文索引、搜索引擎或改变检索语义。

### 分批优先使用稳定游标

高页码 `OFFSET` 需要数据库跳过越来越多的记录，并可能在并发写入下出现重复或遗漏。导出更适合 keyset pagination：

- 使用稳定、唯一且带索引的排序键，如递增 `id`。
- 每批保存最后一条的游标，下一批使用 `id > lastId`。
- 若按 `createdAt` 排序，时间可能重复，应使用 `(createdAt, id)` 组合游标和同序索引。
- 批次大小用压测确定；过小会增加往返，过大会提高查询、转换和写入峰值。

也可使用 TypeORM QueryBuilder 的 `.stream()` 读取驱动返回的原始行，但需要自己完成实体转换、错误传播、背压和断开清理，并核对当前数据库驱动的流式能力。分批 keyset 查询更容易跨驱动理解和调试。

### NestJS 中写入 CSV 并处理背压

CSV 生成和传输应边查边写。`response.write()` 返回 `false` 表示数据已在用户态缓冲区排队，生产者要等待 `drain`，否则慢客户端会让内存继续增长。

```ts
type UserExportRow = {
	id: number;
	name: string;
	email: string;
};

function csvTextCell(value: unknown) {
	let text = value === null || value === undefined ? '' : String(value);

	// 面向表格软件的文本列需要防公式注入；机器再导入场景要单独约定。
	if (/^[=+\-@]/.test(text)) {
		text = `\t${text}`;
	}

	return `"${text.replace(/"/g, '""')}"`;
}

function toCsvLine(row: UserExportRow) {
	return [String(row.id), csvTextCell(row.name), csvTextCell(row.email)].join(',');
}

function writeWithBackpressure(res: Response, chunk: string) {
	if (res.destroyed) return Promise.resolve(false);
	if (res.write(chunk)) return Promise.resolve(true);

	return new Promise<boolean>((resolve, reject) => {
		const cleanup = () => {
			res.off('drain', onDrain);
			res.off('close', onClose);
			res.off('error', onError);
		};
		const onDrain = () => {
			cleanup();
			resolve(true);
		};
		const onClose = () => {
			cleanup();
			resolve(false);
		};
		const onError = (error: Error) => {
			cleanup();
			reject(error);
		};

		res.once('drain', onDrain);
		res.once('close', onClose);
		res.once('error', onError);
	});
}

@Get('users/export')
async exportUsers(
	@Query() dto: ExportUsersDto,
	@Res() res: Response
): Promise<void> {
	const batchSize = 1000;
	let lastId = 0;
	let clientClosed = false;

	res.once('close', () => {
		clientClosed = !res.writableEnded;
	});

	// DTO、权限、筛选上界和首批查询都在发送响应头前完成。
	const upperBoundId = await this.users.findExportUpperBound(dto);
	let rows =
		upperBoundId === null
			? []
			: await this.users.findExportBatch(
					dto,
					lastId,
					upperBoundId,
					batchSize
			  );

	if (clientClosed) return;

	res.setHeader('Content-Type', 'text/csv; charset=utf-8');
	res.setHeader('Content-Disposition', 'attachment; filename="users.csv"');

	try {
		// BOM 用于降低常见表格软件打开中文 CSV 时的编码问题。
		if (!(await writeWithBackpressure(res, '\uFEFFid,name,email\r\n'))) {
			return;
		}

		while (rows.length > 0 && !clientClosed) {
			const csvChunk = `${rows.map(toCsvLine).join('\r\n')}\r\n`;
			if (!(await writeWithBackpressure(res, csvChunk))) return;

			lastId = rows[rows.length - 1].id;
			rows = await this.users.findExportBatch(
				dto,
				lastId,
				upperBoundId!,
				batchSize
			);
		}

		if (!clientClosed) res.end();
	} catch (error) {
		this.logger.error('users export failed', { error, lastId });

		if (!res.headersSent) throw error;

		// 首个 chunk 发出后已无法再改成 JSON 错误响应，只能终止传输并记录进度。
		if (!res.destroyed) {
			res.destroy(error instanceof Error ? error : undefined);
		}
	}
}
```

这个示例的内存主要与单批行数、当前 CSV chunk 和 Response 内部缓冲区相关，而不随导出总行数线性增长。实际项目还应对导出并发数、查询时间、生成字节数、中断数和失败位置做限制与监控。

### 数据一致性、失败与格式选型

- 导出开始时固定 `upperBoundId`，可以防止后续新增的更大 ID 进入本次文件，但不能防止旧数据在导出中被更新或删除。
- 如果业务必须得到同一时点的严格快照，需要结合数据库隔离级别和版本能力，评估长事务对 MVCC、连接池和存储的成本；更稳妥的方案常是异步任务物化快照。
- 在首个 chunk 发出前完成 DTO、权限和可预见的查询检查。响应开始后发生错误，不能再切换为带新状态码的 JSON，应终止流、记录 traceId/游标与失败原因。
- CSV 最适合大数据量、表格型数据和低内存生成。CSV 公式注入没有同时适用所有表格软件和下游导入程序的通用清洗策略，必须先明确文件消费方式。如果必须支持多 Sheet、样式、公式或图表，选择 XLSX 流式写入器，不要先构造全量 Workbook 再转 Buffer。
- NestJS `StreamableFile` 适合返回已封装为 `Readable` 的内容，并保留框架的后置 Interceptor 链路；直接使用 `@Res()` 时，当前处理器要对响应头、结束、背压和中途错误负责。
- 没有“10 万条一定同步”或“一定异步”的固定阈值。当预计时间超过网关超时、需要重试/审计/进度、会占用稀缺连接，或多个用户可并发导出时，应改为“提交任务 → 队列生成 → 对象存储 → 有期限下载”。

## 场景题：大数据筛选与导出

### 场景 1：10 万条中按复杂条件筛选后导出，怎样避免 OOM？

**回答要点：**

1. DTO 校验和权限检查后，把租户、状态、时间等条件下推到 SQL，不先查全量再 `filter()`。
2. 只 `select` 需要的列，为常用筛选与排序检查索引和查询计划。
3. 按稳定唯一键做 keyset 分批，不使用越来越大的 offset。
4. 优先 CSV，每批转一个小 chunk 并写入 Response，不生成全量 Buffer。
5. 处理 `write()` 背压、客户端断开和并发导出上限。

### 场景 2：筛选后只有 2 万条，为什么还是很慢？

**回答要点：** 不只看返回行数，还要看数据库为找到这 2 万条扫描了多少数据。核对组合索引顺序、选择性、排序是否用索引、模糊匹配、关联膨胀、回表和查询计划；同时区分 SQL 慢、CSV 转换慢还是网络传输慢。

### 场景 3：导出过程中又有新增和更新，结果以哪个时点为准？

**回答要点：** 先定义业务一致性。固定最大 ID 只能排除后续新增，不能固定旧记录的更新。若接受“导出期间逐渐读到”，可记录截止条件并明示口径；若要严格快照，需评估一致性快照事务或异步物化方案的成本。

### 场景 4：前端下载很慢或用户取消了，后端怎么停下？

**回答要点：** `response.write()` 返回 `false` 时等待 `drain`，不继续生产。监听请求中止或 Response `close`，终止后续批次，并按驱动能力取消当前查询或销毁数据库流。如果手动占用 QueryRunner/游标，必须在 `finally` 中归还资源。

### 场景 5：文件下载一半时数据库报错，能否返回统一 JSON 错误？

**回答要点：** 不能。首个 chunk 发出后响应头和状态码已确定，只能中断连接，让客户端把文件视为失败或不完整，同时记录 traceId、已导出行数和最后游标。需要可靠重试和可查询错误时，应使用异步导出任务。

### 场景 6：产品要求必须导出 XLSX，还要样式和多 Sheet，怎么办？

**回答要点：** 使用 XLSX 库的 streaming writer，逐行写入并及时提交已完成行，避免在内存中保留整个 Workbook。先评估合并单元格、图片、图表、公式和共享样式对流式模式的限制；文件生成时间长时改为异步任务，生成完成后再下载。

### 场景 7：只做了逗号和双引号转义，CSV 就安全了吗？

**回答要点：** 不是。语法转义只保证 CSV 结构，不会自动阻止表格软件把 `=`、`+`、`-`、`@` 开头的不可信文本当作公式。应区分数值列与文本列，为面向人工打开的 CSV 定义公式注入防护策略，并与需要保留原值的机器导入格式分开。

### 场景 8：什么时候应该改成异步导出？

**回答要点：** 不只按行数判断。要综合文件字节、查询与生成时间、网关超时、并发导出数、重试与审计需求。典型链路是接口创建任务并返回 taskId，Worker 分批生成后上传对象存储，前端查询进度并获取短期下载凭证；还要限流、幂等、清理过期文件，并避免在日志中记录下载凭证。

## 事务边界

事务应围绕一个需要原子提交的业务用例，而不是围绕 Controller 或单个 Repository 方法随意切分。

```ts
await this.dataSource.transaction(async (manager) => {
	const orders = manager.getRepository(OrderEntity);
	const outbox = manager.getRepository(OutboxEventEntity);

	const order = await orders.findOneByOrFail({ id: orderId });
	order.status = 'SUBMITTED';

	await orders.save(order);
	await outbox.insert({
		aggregateId: order.id,
		type: 'order.submitted',
		payload: { orderId: order.id }
	});
});
```

事务回调内的所有数据库操作必须使用传入的 `manager`。如果某个 Repository 偷偷使用全局 `DataSource` 或注入的默认 Repository，它的写入可能落在事务之外。

需要手动控制连接、隔离级别或分段操作时，可以使用 `QueryRunner`：

```ts
const queryRunner = this.dataSource.createQueryRunner();
await queryRunner.connect();
await queryRunner.startTransaction();

try {
	await queryRunner.manager.save(order);
	await queryRunner.commitTransaction();
} catch (error) {
	await queryRunner.rollbackTransaction();
	throw error;
} finally {
	await queryRunner.release();
}
```

`release()` 必须放在 `finally` 中，把独占连接归还连接池，避免异常路径泄漏；释放后的 QueryRunner 也不能继续执行查询。

### 场景追问：如何保证企业和证书两次写入要么都成功，要么都失败？

**面试官：** 企业写入成功，证书写入失败，TypeORM 应该如何处理？整个采集流程都要放进事务吗？

**口语参考答案：**

> 如果这两步在业务上必须原子提交，我会使用数据库事务。TypeORM 的 DataSource.transaction 会提供事务专用 manager，所有查询都通过这个 manager 执行，成功则提交，异常向外传播则回滚。不能一部分使用事务 manager，另一部分使用外部默认 Repository。耗时的抓取和外部接口调用放在事务之外，采集按阶段保存状态和恢复点，避免用长事务覆盖整个流程。

```ts
await dataSource.transaction(async (manager) => {
	const enterprise = await manager.save(Enterprise, enterpriseInput);
	await manager.save(Certificate, {
		...certificateInput,
		enterpriseId: enterprise.id
	});
});
```

**追问与易错点：** 示例假设实体和输入已定义、输入已校验。吞掉异常可能导致回调正常提交；数据库回滚无法撤回已经执行的外部副作用。手动 QueryRunner 要在 `finally` 中 `release()`。

## 事务与外部副作用

不要在数据库事务中执行慢 HTTP 请求、发送邮件或等待消息代理确认。外部调用延长锁持有时间，而且数据库回滚不能撤回已经完成的第三方副作用。

常见处理方式：

- 先完成外部调用再写库：需要处理外部成功、数据库失败的补偿。
- 先提交数据库再发消息：需要处理提交成功、发送失败的重试。
- Transactional Outbox：业务状态和待发送事件写入同一数据库事务，再由独立发布器可靠投递。

Outbox 仍需要幂等消费者、重试、积压监控和清理策略，并不自动提供“恰好一次”。

## 常见误区

| 误区                            | 风险与修正                                                 |
| ------------------------------- | ---------------------------------------------------------- |
| Controller 直接操作 ORM         | transport 与持久化耦合；把用例和事务边界放到应用服务       |
| Repository 方法各自开启事务     | 一个用例被切成多个提交点；由上层统一事务上下文             |
| 事务内仍调用全局 Repository     | 查询可能不属于当前事务；显式传播 manager/事务上下文        |
| 所有关联都设为 eager            | 隐藏额外 SQL 或结果膨胀；按用例加载并检查查询计划          |
| 用 `synchronize` 管生产表结构   | 变更不可审计且可能破坏数据；使用版本化 migration           |
| 长事务中等待远程服务            | 锁时间和失败面扩大；缩短事务并设计补偿或 Outbox            |
| 捕获异常后不再抛出              | 事务回调可能正常提交；回滚后应保留失败语义                 |
| 把 ORM 类型安全等同于数据库约束 | 并发仍可突破应用检查；关键唯一性和完整性要由数据库约束守住 |

## 40 秒面试回答

> NestJS 不绑定 ORM，我会把数据库客户端或 Repository 作为 Provider 注入，让应用服务拥有用例和事务边界。Repository 普通查询由 ORM 和连接池管理，不手动释放；手动创建的 QueryRunner 要在 finally 中归还连接，应用级 DataSource 只在拥有者的终止生命周期统一关闭。事务内所有查询必须使用同一个 manager，也不会在事务里等待慢网络请求。跨数据库与消息的一致性再结合幂等、补偿或 Transactional Outbox 设计。

**十万条数据筛选与导出：**

> 我不会把 10 万条先查到 Node.js 再筛选或生成大 Buffer。筛选条件要下推到 SQL，只查需要的列，通过带索引的稳定游标分批读取，边转 CSV 边写入 Response。`write()` 返回 false 就等待 `drain`，客户端断开就停止后续查询。同时要先定义导出的数据快照口径、CSV 公式注入策略和并发限制；超过请求时间或需要可重试审计时，改为队列异步生成文件。

## 复习检查

- 能解释 NestJS 与具体 ORM 的关系。
- 能说明为什么 Repository 边界不等于为每张表生成通用 CRUD。
- 能区分普通 Repository 查询、手动 QueryRunner 和应用级 DataSource 的资源所有权。
- 能解释 release 是归还池中连接，destroy 才是关闭整个 DataSource。
- 能发现 N+1、过度 eager join 和大批量 save 的风险。
- 知道大数据筛选要下推到 SQL，而不是在 Node.js 中全量 `filter()`。
- 能比较 offset、keyset 分批和数据库流的适用边界。
- 能解释 `response.write()` 背压、`drain` 和客户端断开清理。
- 知道分批导出不自动等于同一时点的数据快照。
- 知道 CSV 语法转义不等于防止公式注入。
- 能根据文件格式、时间、并发、重试和审计要求选择同步或异步导出。
- 知道生产使用 migration，而不是 `synchronize: true`。
- 能保证事务内所有查询使用同一个事务管理器。
- 知道 QueryRunner 必须释放连接，异常不能被静默吞掉。
- 知道优雅停机可以执行关闭钩子，SIGKILL、崩溃或断电不能依赖这些钩子。
- 能说明为什么远程调用不应放在数据库长事务中。
- 能解释 Outbox 解决什么窗口，以及它为什么仍需要幂等和重试。
