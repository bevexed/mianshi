## 一、P0：前端基础与公开面经

### 01. 闭包会导致内存泄漏吗

来源：S1。考点：作用域与引用生命周期。

> 闭包让函数在外层调用结束后仍能访问其词法环境。闭包本身是正常能力；当监听器、定时器或缓存长期引用这个函数，又保留了不再需要的大对象或 DOM，才会形成意外内存保留。我会先复现页面进入退出后的内存增长，比较 Heap Snapshot，看 Retainer Path，再针对引用来源清理。

追问：

- 有循环引用就泄漏吗？不一定，现代追踪式 GC 可以回收不可达的引用环。
- 组件卸载要清什么？事件、计时器、订阅、Observer、Worker，以及不再使用的缓存。
- 怎么验证修好？重复相同操作，观察回收后基线与脱离 DOM 数量，而非只看某一时刻内存。

易错：不要把所有闭包或所有内存上涨都叫泄漏；缓存和 GC 周期也会造成波动。

项目证据：选真实的流式回调或页面订阅清理问题，说明引用从哪来、在哪里解除。

### 02. CSS 为什么从右向左匹配

来源：S1。考点：选择器匹配，不是字符串解析方向。

> 对 `.panel .item.active`，常见匹配方式先找符合最右侧条件的候选元素，再验证祖先是否有 `.panel`，可以减少无效搜索。工程上会优先保持选择器简单、范围清晰；真正慢时通过样式重算和选择器统计定位，不只凭选择器长度猜。

追问：

- 后代选择器为什么可能更贵？要沿祖先链验证，成本也受候选元素数量、DOM 结构和更新范围影响。
- scoped 或 CSS Modules 解决什么？主要是样式组织与作用域，不等于自动提升所有选择器性能。
- 重排和重绘谁更慢？看具体布局范围和绘制成本，不能仅凭 CSS 属性名下绝对结论。

易错：把“匹配通常从右向左”说成所有 CSS 解析、所有选择器和所有引擎都遵循同一实现。

### 03. Vue 插槽的本质与作用域是什么

来源：S1。考点：内容提供者、渲染出口和作用域。

> 父组件决定插槽内容，子组件决定放在哪。以 Vue 3 为例，插槽可以理解为父组件传给子组件的 VNode 生成函数，子组件在出口调用它。插槽模板默认读取父作用域；子组件通过 slot props 传出行数据等内容，父组件再决定怎么渲染。

追问：

- 表格为什么用作用域插槽？表格掌握行数据和布局，调用方负责单元格展示。
- 为什么不把所有东西做成 props？内容结构复杂时，插槽比大量配置或布尔 props 更易组合。
- Vue 2 和 Vue 3 一样吗？概念相近，普通/作用域插槽的运行时形态存在版本差异，要说明所讲版本。

易错：认为父模板可以直接访问子组件全部内部状态。

### 04. nextTick 怎么实现，为什么不能只包一层 Promise

来源：S1。考点：响应式更新调度与 DOM Patch 的先后关系。

> 响应式状态修改后，组件更新任务先进入调度队列，同一轮更新可以去重。nextTick 需要等待当前这批更新完成，再执行回调；Vue 3 可以从 currentFlushPromise 理解这层关联。单独 Promise.resolve().then(callback) 只能说明进入了微任务，无法说明前面一定有 DOM 更新任务。

下面是教学用调度器，`queueJob` 模拟框架提交 DOM 更新；不是 Vue 完整源码：

```js
const resolvedPromise = Promise.resolve();
const jobs = [];
const queued = new Set();
let currentFlushPromise = null;

function queueJob(job) {
	if (!queued.has(job)) {
		queued.add(job);
		jobs.push(job);
	}
	if (!currentFlushPromise) {
		currentFlushPromise = resolvedPromise.then(flushJobs);
	}
}

function flushJobs() {
	try {
		for (let index = 0; index < jobs.length; index++) {
			try {
				jobs[index]();
			} catch (error) {
				console.error(error);
			}
		}
	} finally {
		jobs.length = 0;
		queued.clear();
		currentFlushPromise = null;
	}
}

function nextTick(callback) {
	const promise = currentFlushPromise || resolvedPromise;
	return callback ? promise.then(callback) : promise;
}
```

手写验收：重复提交同一 job 只执行一次；执行期间新加入的不同 job 能处理；某个 job 抛错不会阻断后续 job；支持 `await nextTick()`。

追问：

- 为什么不能修改状态前就 await？那时可能根本没有待刷新任务，不能等待尚未安排的更新。
- nextTick 后浏览器一定绘制了吗？只保证相应 DOM 更新完成，不保证屏幕已绘制。
- Vue 完整调度还缺什么？父子组件顺序、pre/post 队列、递归更新限制、组件错误处理等。

易错：把教学队列说成 Vue 源码等价实现。真实项目直接使用框架提供的 API。

核对：[Vue nextTick 文档](https://vuejs.org/api/general.html)、[Vue 调度器源码](https://raw.githubusercontent.com/vuejs/core/main/packages/runtime-core/src/scheduler.ts)。

### 05. 事件循环和浏览器渲染是什么关系

来源：S1，合并“事件循环”和“DOM 渲染属于哪类任务”两题。

> JavaScript 先执行当前任务，随后在微任务检查点清空队列，浏览器在合适的渲染机会更新画面。Promise 回调和 queueMicrotask 是微任务，计时器和消息回调属于任务。渲染不能直接归为某个普通宏任务或微任务，也不保证每执行一个任务就绘制一次。

输出顺序练习：

```js
console.log('A');
setTimeout(() => console.log('B'), 0);
Promise.resolve().then(() => {
	console.log('C');
	queueMicrotask(() => console.log('D'));
});
console.log('E');
// A E C D B
```

追问：

- 微任务里继续产生微任务？本次检查点还会处理，持续产生可能推迟渲染和 I/O。
- rAF 在哪？回调通常在渲染更新中、绘制前执行，不是“已经绘制完成”的通知。
- Promise 能把 CPU 计算搬走吗？不能，then 回调仍占用 JavaScript 执行线程。

易错：递归 Promise 分片不等于把执行机会交回浏览器；重计算应考虑任务切片或 Worker。

### 06. Webpack 流程是什么，Vite 为什么快

来源：S1 + JD。

> Webpack 从配置和入口构建模块依赖图，Loader 转换资源，Plugin 通过生命周期参与编译、优化和产物输出，再按入口和动态导入组织 Chunk。Vite 开发阶段利用按需转换、模块图和更小的 HMR 失效范围减少等待；生产阶段仍要做打包与优化。

追问：

- Loader 和 Plugin 区别？前者主要转换单个模块内容，后者参与整体生命周期。
- Tree shaking 为什么可能失败？模块形态、side effects、转译和导出使用方式都会影响。
- 构建慢先查什么？依赖规模、转换与类型检查、插件耗时、缓存命中和产物分析。

版本边界：旧版 Vite 常见 esbuild/Rollup 组合；当前工具链已演进到 Rolldown/Oxc。讲自己的项目时先说实际版本，不能把旧实现说成永远固定。

易错：把“Vite 快”解释成完全不构建、不打包或没有依赖预处理。

核对：[Vite 官方说明](https://vite.dev/guide/why.html)。

### 07. HTTPS 页面可以采集吗，TLS 保护什么

来源：S1。考点：传输加密与访问权限的区别。

> 可以通过正常 HTTPS 客户端访问已授权的内容。TLS 保护传输机密性、完整性和身份认证，客户端完成连接后仍会获得 HTTP 响应。是否能获取目标数据还取决于登录态、接口权限、动态渲染和频控。

追问：

- 为何既用非对称机制又用对称加密？握手通过证书认证和密钥交换建立共享秘密，后续应用数据用对称算法高效保护。
- TLS 1.2 与 1.3 一样吗？握手和算法选择有差异，回答时明确版本，不死背一份通用消息顺序。
- 采集服务真正难在哪？按实际项目讲会话生命周期、受控并发、业务成功校验、重试与恢复。

易错：HTTPS 加密不等于响应不能读取；访问成功也不等于业务数据正确。

### 08. 只有某个地区白屏，前五分钟做什么

来源：S1。考点：定位能力与止损顺序。

> 先确认影响的地区、运营商、版本和比例，再找同版本正常样本。检查 HTML 能否返回、入口 JS/CSS 是否成功、API 是否异常，以及是否出现启动时运行错误。先隔离出网络资源问题还是应用问题，再决定切 CDN、回滚或关闭地区相关开关。

追问：

- 连 Sentry 都没有？可能入口脚本未加载，或监控域名本身受影响，需查 CDN 日志、资源错误和地区探针。
- 首屏只有旧用户失败？检查 HTML/Chunk 版本不一致、缓存、Service Worker 与旧资源保留策略。
- 资源都成功？看语法兼容、第三方脚本、语言包、日期解析、时区和地区数据。

易错：本机换代理能打开，不能证明所有目标用户恢复。先用真实地区证据，不一开始堆十个无先后顺序的名词。

项目证据：准备一个真实线上故障，讲清日志、版本和请求链路怎么对齐。

### 09. HTTP/1.1、HTTP/2、HTTP/3 怎么比较

来源：S2；A2 仅作补充线索。

> 三者沿用 HTTP 语义，主要区别在传输组织。HTTP/1.1 常通过多个连接提高并行度；HTTP/2 用二进制帧和流在一个 TCP 连接上多路复用并压缩头部；HTTP/3 基于 QUIC，让不同流的丢包恢复减少相互阻塞。HTTP/2 仍有 TCP 层队头阻塞。

追问：

- HTTP/2 后还做域名分片吗？多域名会增加 DNS/TLS 等成本，不能照搬旧优化，应按真实连接与资源情况测量。
- HTTP/3 消灭全部阻塞吗？没有，同一流内顺序、拥塞和应用依赖仍存在。
- keep-alive、HTTP 缓存和 WebSocket 是一回事吗？分别涉及连接复用、响应复用和双向消息协议。

易错：把 HTTP/2 多路复用说成丢包后其他流完全不受影响。

## 二、P0：框架、SSR 与 Node.js 主线

### 10. Vue 3 响应式到 DOM 更新怎么走

来源：JD。

> 读取响应式对象时，Proxy 拦截 getter 并关联当前 effect；写入时触发依赖对应的 effect。组件更新 effect 通常交给调度器去重批处理，再执行 render 和 Patch。ref 通过 value 的访问和更新收集、触发依赖；DOM 并不会在每次赋值时立即同步刷新。

追问：

- 解构 reactive 为什么可能丢响应式？普通值被取出后不再经过原对象的代理；可按场景使用 toRef/toRefs。
- computed 和 watch？computed 派生缓存值；watch 用于变化后的副作用，watchEffect 自动收集同步执行阶段读取的依赖。
- watch flush 时机？默认 pre、post、sync 要按组件 DOM 更新边界解释，不把所有 watcher 都说成 DOM 更新后执行。

易错：Proxy 解决了部分检测限制，但不代表解构、异步依赖收集和调度时机都自动正确。

### 11. React Hooks、陈旧闭包和请求竞态怎么处理

来源：S2 + JD。

> 每次 render 都有自己的状态快照，回调会捕获那次 render 的值。Hooks 调用顺序要稳定，Effect 用来同步外部系统。依赖完整、函数式更新和 ref 分别适合不同问题；异步请求还要取消旧请求或用请求序号忽略旧结果，避免旧数据覆盖新页面。

追问：

- 连续三次 setCount(count + 1)？通常都使用同一快照；需要累加时用函数式更新。
- 为什么开发环境 Effect 可能执行两遍？Strict Mode 检查 setup/cleanup 的对称性，不能靠永久开关掩盖泄漏。
- useMemo/useCallback 一定优化吗？只有依赖比较、子组件 memo 或计算成本确实值得时才有收益。

易错：把不完整依赖统一改成空数组，或把所有派生状态都放 Effect。

核对：[React Effect 文档](https://react.dev/learn/synchronizing-with-effects)。

### 12. SSR、RSC、Client Component 怎么区分

来源：JD + 项目追问。

> SSR 关注请求时生成 HTML；RSC 关注组件在服务端执行并产出可组合结果，减少客户端需要运行的组件代码。App Router 里，Server Component 可以获取服务端数据，交互区域放 Client Component。Client Component 在首次加载时也可能参与服务端 HTML 预渲染，再到客户端水合，所以 use client 不等于纯 CSR。

追问：

- 服务端组件能用 useState、事件和 window 吗？不能按浏览器组件方式使用，应把交互边界拆出去。
- use client 会影响什么？它建立客户端模块边界，其导入依赖需适合浏览器；服务端渲染结果可通过 children 等方式组合传入。
- SSR/SSG/ISR 怎么选？根据新鲜度、个性化与成本选择；RSC 与这些策略不是互斥分类。

易错：把 RSC 当 SSR 的新名字，或认为页面变成 Client Component 就完全失去服务端 HTML。

核对：[Next.js Server 与 Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components)。

### 13. 登录态水合不一致、缓存串用户怎么避免

来源：JD + 项目追问。

> 水合要求服务端 HTML 和客户端首次渲染结果一致。服务端可读取的会话统一在服务端判断；只能从浏览器存储恢复的状态，先用一致占位再挂载更新。用户资产和订单数据明确使用请求级上下文和私有缓存策略，不能让共享 HTML、数据缓存或 CDN 复用给其他用户。

追问：

- 已加 no-store 就万事大吉？还要排查 CDN、反向代理、应用缓存键和请求之间共享的全局变量。
- 时间、随机数、HTML 嵌套也会出错吗？会，不能只排查登录态。
- 缓存默认行为怎么回答？先确认 Next.js 版本、路由模式及配置；不背“fetch 永远默认缓存”。

易错：suppressHydrationWarning 不是修复数据不一致；禁用 SSR 也不应成为默认答案。

项目证据：讲一个首屏状态来源及修正点，不宣称实际完成过自己未做的缓存治理。

### 14. Node.js 为什么能并发，什么时候会卡死

来源：JD + 项目追问。

> 默认一个 JavaScript 执行线程，网络 I/O 借助操作系统，部分文件、DNS 和加密工作可由 libuv 线程池承担。I/O 等待期间可以服务其他请求，但大 JSON 处理、同步 API 和 CPU 循环会阻塞主线程。async/await 只改变编排方式，不会自动把计算搬到线程池。

追问：

- CPU 高怎么看？看 CPU profile、事件循环延迟、GC 和热点调用；必要时使用 Worker Threads 或独立计算服务。
- setImmediate 和 setTimeout 谁先？顶层不应保证固定顺序，I/O 回调内通常可解释为 check 与 timers 阶段差异。
- nextTick 呢？它不是 libuv 的一个阶段；CJS/ESM 和调用位置会影响与 Promise 的观察顺序。滥用会饿死 I/O。

版本边界：Node.js 20 对应的 libuv 定时器调度发生过变化，具体输出题要说明运行版本与模块类型。

核对：[Node.js 事件循环](https://nodejs.org/learn/asynchronous-work/event-loop-timers-and-nexttick)。

### 15. Koa 洋葱模型和全局错误处理怎么解释

来源：JD。这是当前生产栈迁移到 Koa 最值得补的一题。

> 中间件先执行 await next 之前的逻辑，再进入下游，等下游完成后反向执行后半段，所以日志、计时和异常处理可以包住整个请求。全局 try/catch 放在外层，鉴权、校验、路由放内层。漏写 await 会破坏等待和异常边界。

手写简化 compose：

```js
function compose(middlewares) {
	return function run(ctx) {
		let index = -1;
		function dispatch(i) {
			if (i <= index) {
				return Promise.reject(new Error('next() called multiple times'));
			}
			index = i;
			const middleware = middlewares[i];
			if (!middleware) return Promise.resolve();
			try {
				return Promise.resolve(middleware(ctx, () => dispatch(i + 1)));
			} catch (error) {
				return Promise.reject(error);
			}
		}
		return dispatch(0);
	};
}
```

手写验收：两层的顺序为外前、内前、内后、外后；同步抛错与异步拒绝可被外层接住；同一 next 重复调用会拒绝。

追问：Koa 与 NestJS 的层次差异是什么？前者主要提供 ctx 和中间件组合，后者提供依赖注入、模块、Guard/Pipe/Interceptor 等工程结构。不要说两者只是名称不同。

核对：[Koa 官方文档](https://koajs.com/)。

### 16. BFF 怎么设计超时、聚合、鉴权与网关边界

来源：JD。

> BFF 面向具体客户端整合领域服务、裁剪页面数据；网关负责更通用的入口路由和流量治理。BFF 按页面设置总时限，把账户、行情等调用并行组织，非关键数据允许部分降级，关键权限和交易校验失败就明确失败。统一 Trace ID、错误模型和依赖耗时，凭据只在可信边界内转发。

追问：

- 某个上游一直慢？设总 deadline 与单依赖预算、并发限制、熔断和可接受的缓存。
- 请求取消意味着下游业务停止吗？不保证，需下游支持取消或根据业务状态补偿。
- 什么请求能重试？先看幂等语义、错误类型和剩余预算，用退避限制重试放大。

易错：仅用 Promise.race 返回超时并不会终止底层请求；核心交易规则仍由领域服务最终执行。

### 17. Session、JWT、Cookie、XSS、CSRF 怎么连起来

来源：JD；A2 仅补充题目线索。

> Session 通常在服务端保存状态，客户端带会话 ID；JWT 是一种令牌格式，签名载荷默认不保密。Cookie 是承载和自动发送凭据的机制，JWT 也可以放 Cookie，两者不是互斥选项。选择时要考虑 XSS 读取、CSRF、撤销、刷新和多端管理。

追问：

- HttpOnly 能解决 XSS 吗？限制脚本读取 Cookie，但 XSS 仍可能以用户身份发请求。
- SameSite 能取代全部 CSRF 防护吗？要看站点和业务，敏感请求仍需考虑来源校验与 Token。
- WebSocket 怎么鉴权？校验会话、Origin、订阅权限；浏览器 WebSocket 构造器不能随意加 Authorization 头，别把长期 Token 放 URL。

易错：前端验签或把按钮隐藏不能代替服务端权限；不可信 HTML、日志和第三方脚本是独立风险面。

### 18. 实时行情如何做到不漏数据、不把页面刷卡

来源：JD + 场景题。

> 先确认协议。可以先订阅并缓存增量，再取带基准序列号 S 的快照；装载快照后丢掉不高于 S 的事件，按协议规则继续应用后续增量。重连时使用最后确认位置补发，不能补发就重新同步。展示层按标的合并最新值并定时批量提交，盘口增量和订单事件则先正确归约，不能直接丢中间变化。

追问：

- WebSocket 会把一条连接的数据随机乱序吗？底层 TCP 保序；业务缺口更多来自上游、多流合并、重连和异步处理。
- 一定检查 seq+1 吗？先确认序列号是全局、频道还是标的级，过滤后的全局序号可能本来就不连续。
- 一次 rAF 能解决所有卡顿吗？不能，解析、消息进入速率和绘制成本仍可能超预算；还需细粒度订阅、虚拟化、背压和降频。

易错：HTTP 快照回来才开始订阅，会在两者之间产生漏数窗口。

完整方案见[实时行情与金融场景](04-实时行情与金融场景.md)。

### 19. 下单超时和重复请求如何保证幂等

来源：S4 + JD 场景。

> 超时说明结果未知。为一次业务意图生成稳定幂等键，重试沿用同一个键；服务端用用户范围、业务键、请求参数摘要及唯一约束关联记录和最终订单。处理中返回可查询状态，已完成返回同一结果，不同参数复用同键应拒绝。订单状态通过事务和条件更新合法推进。

追问：

- 查不到订单就能换新键再下吗？不能，可能是读延迟或原请求仍在处理。查权威状态，或在协议允许时以原键安全重试。
- 按钮禁用够不够？只改善体验，无法应对重试、多个客户端和进程重启。
- Redis 键过期呢？最终约束不能只靠短 TTL；外部交易通道也需对应客户端订单号或幂等协议。

易错：前端生成随机新 ID 再重试，反而失去同一次业务意图的去重依据。

### 20. 受控并发、任务队列与背压怎么设计

来源：JD + Node.js 项目。

> Promise.all 只聚合结果，不限制任务启动。我会给 I/O 调用设置并发上限、连接池与超时，持久任务交给队列，并通过业务键和事实状态处理重复、重试和进程崩溃。队列积压时看等待时间和下游容量，必要时对生产端限流，不能只加 Worker。

手写一个汇总成功和失败的请求池：

```js
async function runPool(tasks, limit) {
	if (!Number.isInteger(limit) || limit < 1) {
		throw new RangeError('limit must be a positive integer');
	}
	const results = new Array(tasks.length);
	let cursor = 0;

	async function worker() {
		while (cursor < tasks.length) {
			const index = cursor++;
			try {
				const value = await tasks[index]();
				results[index] = { status: 'fulfilled', value };
			} catch (reason) {
				results[index] = { status: 'rejected', reason };
			}
		}
	}

	await Promise.all(Array.from({ length: Math.min(limit, tasks.length) }, () => worker()));
	return results;
}
```

手写验收：空数组返回空数组；同步抛错和异步失败都保留；结果按输入顺序；实际并发不超过 limit。

追问：

- 传 Promise 数组为何不对？请求可能在进入池之前已经启动，应传任务函数。
- 想快速失败？定义停止派发和取消在途请求的语义；Promise.all 拒绝本身不会自动取消请求。
- 任务永远不结束？需要外层超时和 AbortSignal；这个示例不自带持久化、取消和分布式能力。

## 三、P1：有针对性地补足

### 21. 联合索引和慢 SQL 怎么回答

来源：S3/S4。

> (a,b,c) 按列顺序组织，a、a+b、a+b+c 可形成前导定位。a+c 通常仍能先用 a 缩小范围，不能说整个索引失效；b+c 是否走扫描或 Skip Scan 取决于查询和优化器。慢 SQL 先定位真实语句、参数与等待，再看 EXPLAIN 或安全环境中的 EXPLAIN ANALYZE，核对索引、实际行数、回表和排序。

追问：SQL 条件书写顺序不决定最左匹配；范围后面的列也可能用于索引条件过滤或覆盖；深分页可改稳定组合游标，但要讲一致性和排序约束。

易错：EXPLAIN ANALYZE 会实际执行语句，生产排查需评估负载；不要背“a+c 全部失效”或“索引越多越快”。

核对：[MySQL 多列索引](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html)。

### 22. Redis 分布式锁超时，续期够不够

来源：S3/S4。

> 获取时原子写唯一 owner 与租约，释放时原子校验 owner。续期降低正常超时概率，但进程长暂停、网络隔离仍可能导致旧持有者在失锁后继续写。重要资源需要数据库版本/条件写，或由下游校验单调 fencing token，拒绝过期持有者的操作。

追问：锁过期、业务完成、网络返回是三个事件；Redis 释放 Lua 能防误删，不能自动防止旧请求继续访问业务资源。

易错：把自动续期说成绝对互斥保证；fencing token 必须由被保护的资源执行校验。

### 23. H5 渲染、SEO 和首屏性能怎么一起回答

来源：S2。

> 页面从导航、缓存与连接进入响应处理，再解析 HTML、加载样式和脚本，完成布局、绘制和合成。优化先拆 TTFB、LCP 资源发现与下载、主线程工作和渲染。公开内容重视状态码、标题、Canonical、结构化数据和可抓取 HTML，交互体验再看 INP、长任务与 CLS。

追问：LCP 不等于 JS 总体积；图片、字体和服务端时间也可能主导。SSR 输出快但水合很重仍可能交互慢；Client Component 首屏也可能有服务端 HTML。

易错：只给 Lighthouse 总分或承诺未经测量的提升比例。给同条件前后数据和回归范围。

### 24. qiankun、iframe、服务端微服务怎么比较

来源：S2。

> 先划清比较层次：qiankun 组织前端子应用加载和生命周期，iframe 提供独立浏览上下文，Seneca 属于 Node.js 服务端微服务工具，不能当作同层替代品。是否引入微前端，要看多团队独立交付、遗留迁移的收益能否覆盖隔离、依赖和排障成本。

追问：iframe 通过 postMessage 通信要校验来源和消息 Schema；前端 JS 沙箱通常不等于浏览器级安全边界；模块联邦解决模块共享与加载，不自动提供完整业务隔离。

易错：因为原面经把不同工具放一起问，就跟着比较谁“性能更好”而不澄清目标。

### 25. H5 与 App Bridge、快速加载怎么设计

来源：S2。

> Bridge 用版本化协议暴露受控能力，调用携带 requestId，管理回调、超时、取消和页面销毁；原生主动通知走明确事件。性能先测 WebView 初始化、资源和接口，再选择预热、预取、缓存或离线包，离线包要有完整性校验、版本兼容和原子回退。

追问：能力不存在如何降级；异步响应回来时页面已切换如何避免写错实例；原生端必须再次鉴权和校验参数。

易错：把任意 URL、文件访问和脚本执行开放给 H5；用隐藏长期存活 WebView 导致状态和内存泄漏。

### 26. 组件体系、工程效率与 CI/CD 怎么体现资深度

来源：JD。

> 先统一基础样式和稳定组件 API，再沉淀重复业务模式。组件设计关注组合、受控状态、可访问性和兼容；工程上把类型、Lint、必要测试、产物与发布检查放进流水线。是否提高效率，用交付周期、返工、缺陷和接入成本等实际证据评价。

追问：Breaking Change 如何升级；大组件很多布尔 props 如何拆；发布失败如何回滚；某条检查为什么值得保留。

易错：只罗列工具名；搭了组件库却不能举出复用调用和迁移案例。

### 27. 低代码动态渲染最难的约束是什么

来源：JD 加分项。

> 把版本化 Schema、组件注册表、数据源和事件能力分开。数据先校验，再映射白名单组件；权限仍由服务端执行。表达式只开放必要语法与函数，配置发布要有兼容、灰度、回滚和观测。

追问：旧客户端遇到新组件怎么办；配置出错能否整体回退；如何限制表达式耗时、越权访问和数据泄露。

易错：new Function、同源 iframe 或简单对象白名单都不能自动构成安全沙箱；优先使用受限表达式解释器和能力隔离。

### 28. 国际化、RTL 与金融数字怎么处理

来源：JD 加分项 + 海外项目。

> 文案使用翻译键，日期、数字和货币按 locale 展示，业务时间用市场时区和交易日历。RTL 使用 dir 与逻辑属性，按语义决定图标是否镜像，股票代码和数字需控制双向文本。金额和价格从数据契约明确精度，不能随意用浮点数作为最终业务计价。

追问：美股夏令时、半日市；图表时间轴不能因为 RTL 就无脑翻转；富文本翻译需按输入边界处理。

易错：把语言等同于时区，或把 toFixed 当成精确计算方案。

### 29. AI Coding 与 SDD 怎么证明是自己的能力

来源：S4。

> 先确认 SDD 是否指 Spec-Driven Development。我的实践是把需求、现有实现、限制和验收标准讲清，按小步产出代码。我检查业务边界和异常，再运行适当验证并审查 diff。AI 参与检索或草稿可以如实说，关键决策、验证和责任要能由自己解释。

追问：举出一次拒绝 AI 建议的真实原因；如何防止过度重构；如何证明项目真的完成到某一步。

易错：使用过 AI 不等于做过 RAG；未落地的建议不能说成生产经验。

### 30. 严重线上事故与个人失误怎么讲

来源：S4 + 项目追问。

> 先确认影响和沟通负责人，用回滚、限流、开关或隔离止损，并保留可用日志、Trace 和时间线。定位后验证修复，灰度观察，再补触发条件、根因和预防。讲自己的案例时，要明确当时负责哪一步和采取了什么动作。

追问：无法回滚怎么办；怎样区分源站、网关和客户端故障；没有监控为什么没发现；恢复的证据是什么。

易错：只有“加日志、修 Bug、发版本”，没有影响范围、证据和验证。不要为了显得资深编造严重事故。

## 四、最后十分钟只看这些边界

1. 闭包与循环引用都不自动等于泄漏。
2. nextTick 等调度队列的 DOM 更新，不保证浏览器已绘制。
3. Promise 不搬走 CPU 工作，Promise.all 不限流。
4. use client 不等于完全不做服务端 HTML。
5. Session/JWT 是会话方案与令牌格式，Cookie 是携带机制。
6. 快照和订阅之间必须有序列或恢复协议消除漏数窗口。
7. TCP 保序与业务序列校验是两个层面。
8. 超时结果未知，重试沿用业务意图对应的幂等键。
9. (a,b,c) 下 a+c 不能简单判为整个索引失效。
10. 方案是否有效，要能指向真实代码、日志、测试或指标。
