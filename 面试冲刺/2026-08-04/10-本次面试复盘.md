## 四、四道题的下次答案

### 1. NestJS 循环引用

#### 40 秒版本

> 我会先区分模块互相 `imports`、Provider 互相注入，以及 `index.ts` 桶文件造成的 TypeScript 文件循环。首选不是直接加 `forwardRef()`，而是重新整理职责和依赖方向：公共能力抽成独立模块，跨多个服务的流程放到编排层；如果只是状态通知，可以用事件消除反向调用。确实拆不开时，模块两侧用 `forwardRef()`，Provider 循环注入再配合 `@Inject(forwardRef(...))`，特殊动态依赖才考虑 `ModuleRef`。这些 API 解决的是容器加载问题，不等于消除了架构耦合。

#### 容易说错的地方

- 不是把两个模块的业务都塞进巨大的 `CommonModule`。
- 需要立即返回结果的同步调用，不要强行改成事件。
- 遇到依赖解析错误，先检查导入路径、`exports` 和 `imports`，不要先制造双向依赖。
- 内部文件通过 `index.ts` 反向导入，可能制造隐式文件循环。

延伸阅读：[NestJS 核心概念](../../09-Node与服务端/NestJS核心概念.md#循环引用)

### 2. Redis 使用场景

#### 60 秒版本

> 我通常从四类需求判断是否用 Redis。第一类是可重建的热点数据缓存，用低延迟换数据库压力；第二类是验证码、会话和任务进度这类带 TTL 的临时状态；第三类是计数、限流、去重和锁这类需要原子操作或多实例共享的协调；第四类是 BullMQ 这样的任务队列。判断时还要问数据丢失后能否恢复、是否需要复杂查询、内存成本是否值得。订单、支付、正式业务数据不能只放 Redis，最终真相仍应由数据库和业务约束守住。

#### 本人项目证据

> 采集服务里实际用 BullMQ 与 Redis 做任务派发和延迟调度，MySQL 的任务表保存长期业务事实。共享出口轮换还使用 Redis TTL 和 Lua compare-and-delete 处理竞态；抓取到的企业、资质和人员数据仍落 MySQL。这样 Redis 负责低延迟调度与协调，数据库负责最终事实。

边界：不要把 Redis 快速去重说成永久幂等。严格结果仍需要数据库唯一约束、合法状态转换和幂等写入。

延伸阅读：[Redis 数据结构与使用场景](../../15-数据库/Redis数据结构与场景.md#什么时候使用-redis)

### 3. Webpack 构建慢

#### 60 秒版本

> 我不会先上 `thread-loader`，而是先固定环境和缓存条件，把 install、类型检查、Loader 转换、压缩、Source Map、插件和上传耗时拆开，用 Webpack stats 或 profiler 找主要瓶颈。常见第一步是启用并持久化文件系统缓存，同时把 lockfile、构建配置、Node 版本和环境纳入缓存失效条件；然后用 `include` 缩小 Loader 范围，区分开发与生产配置，拆开转译和类型检查，再检查压缩、Source Map、Sentry 上传等插件。只有 profile 证明转换是 CPU 瓶颈后，才评估 SWC 或多线程，并分别比较冷构建和热构建。
