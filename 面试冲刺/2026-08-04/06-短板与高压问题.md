## MongoDB 没有深度生产经验

> MongoDB 没有在正式项目中深度使用过，我目前实际使用更多的是 MySQL 和 Redis。我的理解是 MongoDB 的文档模型适合结构演进较快、天然聚合读取、嵌套关系明显的数据；MySQL 更适合强事务、复杂关系和约束清晰的核心业务。选型时我会先看一致性、访问模式、索引和数据生命周期，而不是因为 schema 灵活就默认选择 MongoDB。

可能追问：MongoDB 适合存聊天记录吗？

> 可以，但不是必然。会话与消息是自然聚合，但消息可能无限增长，不适合把整个会话永远塞进一个文档。可以会话一张集合、消息独立集合，通过 conversationId 和时间索引查询；如果系统已经围绕 MySQL 建设，关系库也完全能胜任。选型要结合查询、事务、团队和运维能力。

## Express / Koa 不是主生产栈

> 我的生产项目主要使用 NestJS，适配器使用过 Fastify。对于路由、中间件、异常处理、请求上下文和 Node.js 异步机制是熟悉的，只是没有用 Koa 独立维护过大型生产项目。NestJS 把这些机制组织成 Module、Provider、Guard、Pipe、Interceptor 和 Filter；如果需要进入 Express/Koa 项目，我会先从中间件链、错误边界和项目约定入手。

不要说“会 NestJS 就等于精通 Express/Koa”。

### 设计一个 AI 助手时的主线

```text
用户请求
  → 鉴权 / 限流 / 参数校验
  → 会话与消息持久化
  → 上下文选择与裁剪
  → 模型网关（超时、取消、重试、降级）
  → SSE 流式返回
  → 前端增量渲染、停止生成、重连提示
  → 成本、错误、延迟与安全审计
```

关键边界：生成中断不等于服务端一定立即停止计费；重试必须判断是否会生成重复消息；模型输出在浏览器渲染时仍属于不可信输入。
