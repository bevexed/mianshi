# 核心技术速答

练法：先只看问题，口述 20–40 秒，再看参考。面试中先给这一层，面试官追问后再展开。

## 1. Vue 2 和 Vue 3 的核心差异

> Vue 3 的响应式从 `Object.defineProperty` 转到 Proxy，能直接覆盖属性新增删除、数组索引和更多集合类型；架构上引入 Composition API，更适合按业务关注点组织复杂逻辑，并改善逻辑复用和 TypeScript 推导。Vue 3 还重写了虚拟 DOM 编译优化和 Tree Shaking。迁移时真正需要关注的是生态/API 变化、全局能力和响应式语义，不是简单说“Vue 3 更快”。

可能追问：

1. Proxy 为什么不能完全兼容旧浏览器？它无法像普通 API 一样完整 polyfill。
2. Composition API 是否替代 Options API？不是，复杂逻辑组织和复用时更有优势。
3. Vue 3 为什么仍有 `ref`？基础值无法直接被 Proxy，且 ref 能提供统一的可追踪容器。

## 2. `ref`、`reactive`、`computed`、`watch`

> `ref` 适合基础值或需要整体替换的引用，脚本中通过 `.value` 访问；`reactive` 适合对象代理，但直接解构会丢失响应式，需要 `toRefs`。`computed` 表达可缓存的派生状态，能计算就不要额外存；`watch` 用于状态变化后的副作用，比如请求、持久化或与外部系统同步。不要用 watch 维护本可计算出的第二份状态。

可能追问：

1. `watch` 与 `watchEffect`：前者显式指定依赖并拿新旧值，后者立即执行并自动收集同步阶段依赖。
2. 深度监听成本：会遍历嵌套结构，应缩小数据源或监听具体字段。
3. `nextTick`：等待 Vue 将当前批次状态变化刷新到 DOM 后再执行。

## 3. Vue 组件通信与状态边界

> 父子数据用 props 向下、emit 向上；跨层但范围局部的依赖可用 provide/inject；跨页面或长期共享状态再考虑 Pinia。是否进入全局 store 的判断不是“多个组件都用”，而是它是否跨越组件生命周期、是否需要统一变更规则。服务端数据还要交给请求缓存层，避免把接口数据全部复制进 store。

可能追问：

1. 为什么不使用事件总线？依赖隐式、难追踪、清理不当易泄漏。
2. `key` 的作用：标识同层节点身份，帮助 diff 复用或重建正确实例。
3. Pinia 与 Vuex：Pinia API 更轻、TypeScript 推导更自然，仍要避免 store 无限膨胀。

## 4. Vue 页面性能怎么排查？

> 先用真实指标和 Performance/Vue DevTools 确认瓶颈属于网络、渲染还是运行时。组件层面减少无意义的响应式范围和重复渲染，长列表虚拟化，稳定 props，重计算用 computed；资源层面做路由分包、图片与字体优化；最后用相同设备和数据复测。不要把所有函数都缓存或所有组件都拆成异步组件。

可能追问：

1. `v-if` 与 `v-show`：前者有挂载销毁成本，后者有初始渲染成本；按切换频率选。
2. 大表格：虚拟滚动、分页、局部订阅、避免深度响应式大对象。
3. 如何验证：看 INP/LCP/长任务、组件更新时间和用户真实数据。

## 5. TypeScript 在工程中的价值

> TypeScript 的价值不是消灭所有 bug，而是把接口契约和状态分支前移到编译期，并改善重构和协作。我会开启严格模式，用 `unknown` 处理未验证外部输入，使用判别联合表达有限状态，用泛型保留调用关系；运行时数据仍需 schema 或 DTO 校验，因为类型会在编译后消失。

可能追问：

1. `any` 与 `unknown`：前者放弃检查，后者使用前必须缩小类型。
2. `interface` 与 `type`：对象扩展可偏 interface，联合/映射/条件类型需要 type；一致性比口诀重要。
3. 类型守卫：`typeof`、`in`、判别字段或自定义谓词，外部输入最终仍需要运行时校验。

## 6. NestJS 的核心结构与请求生命周期

> Module 组织边界，Controller 处理协议输入输出，Provider 承载可注入业务能力，依赖注入降低创建与替换成本。典型请求先经过 Middleware，再到 Guard；Interceptor 包裹调用，Pipe 在进入控制器前做转换和校验；Controller/Service 执行业务，返回值再经过 Interceptor，异常由 Filter 统一映射。鉴权放 Guard，DTO 校验放 Pipe，日志和耗时适合 Interceptor。

可能追问：

1. 为什么不把业务都写 Controller？协议层与业务耦合，难复用和测试。
2. Provider scope：默认单例；request scope 会增加实例化和上下文传播成本。
3. Middleware 与 Guard：前者偏通用请求预处理，后者理解执行上下文并决定是否放行。

## 7. Node.js 适合什么，不适合什么？

> Node.js 单线程执行 JavaScript、用事件循环和底层线程池处理大量异步 I/O，所以适合高并发 I/O 和 BFF/业务 API。CPU 密集计算会阻塞事件循环，应拆 Worker Thread、子进程或独立服务。判断性能不能只说“异步很快”，要看事件循环延迟、长任务、内存和下游容量。

可能追问：

1. Promise 回调属于微任务，会在当前阶段结束后优先清空，过多微任务也可能拖延 I/O。
2. 哪些操作会占线程池：部分文件、DNS、加密等；网络 I/O 通常由系统事件机制处理。
3. 怎么发现阻塞：事件循环延迟、CPU profile、火焰图和慢请求关联。

## 8. BullMQ 如何做到可靠？

> 队列不会自动带来 exactly-once。需要稳定业务键、数据库唯一约束和幂等 Worker 承受重复；按错误类型设置有上限的重试与退避；数据库任务状态支持补偿和对账；Worker 处理优雅停机与 stalled job；监控积压年龄、失败分类、重试率和 Redis 内存。队列负责调度，业务结果仍由业务存储守住。

可能追问：

1. 先写库还是先入队：两者都有失败窗口，事务 Outbox 更严格，简单场景可先写库再补偿入队。
2. 为什么不能无限重试：会放大下游故障并制造重试风暴。
3. 如何防重复消费：唯一键、合法状态转换、幂等外部调用和结果 upsert。

## 9. MySQL 索引怎么回答

> 索引是用额外空间和写入成本换查询效率。联合索引顺序应结合等值、范围、排序和覆盖需求设计，不只背最左前缀。排查慢 SQL 先看实际查询和数据分布，再用 `EXPLAIN` 观察访问类型、估算行数、使用索引和额外操作；索引存在不等于一定会用，也不等于查询一定快。

可能追问：

1. 覆盖索引：所需列都可从索引获得，减少回表；宽索引也有写入和缓存成本。
2. 范围条件：通常会影响其后列继续用于索引定位，但是否可用于过滤/排序要看版本和执行计划。
3. 索引失效：函数或隐式转换、前导模糊、选择性差等，最终以执行计划和数据验证。

## 10. 事务与并发控制

> 事务提供原子性、一致性、隔离性和持久性，但隔离级别越高并发代价通常越大。业务中先缩小事务范围，保持访问顺序稳定，再根据冲突概率选择悲观锁或乐观锁。乐观锁通过版本条件更新并检查影响行数，适合冲突较低、可重试场景；涉及外部网络调用时不要长时间持有数据库事务。

可能追问：

1. InnoDB 默认隔离通常是可重复读，但以实际配置为准。
2. 幻读与 next-key lock：当前读和索引范围会影响锁行为，不能只背定义。
3. 死锁：保持加锁顺序、缩短事务、建立合适索引，并对死锁失败做有限重试。

## 11. Redis 缓存与分布式锁

> 缓存先定义数据真相来源和可接受不一致窗口。常见 cache-aside 是读未命中查库回填，写时先更新数据库再失效缓存，但仍要处理并发窗口。穿透用校验/空值或布隆过滤器，击穿用互斥重建、逻辑过期或热点预热，雪崩用过期抖动、限流降级和多层保护。锁必须有唯一所有者、原子加锁、TTL 和校验释放，不能只 `SETNX` 后无条件删除。

可能追问：

1. 锁过期但任务未结束：需要续租或 fencing token，单纯延长 TTL 仍要处理暂停和失联。
2. 为什么删缓存而不是更新：失效逻辑通常更简单，但高一致性场景需结合消息或版本。
3. Redis 挂了怎么办：区分缓存和关键协调；缓存可降级，关键锁失效不能默认继续写。

## 12. MongoDB 与 MySQL 怎么选

> MongoDB 适合文档聚合边界清晰、结构演进频繁、读写经常以整个文档为单位的场景；MySQL 适合关系约束、复杂联表、强事务和成熟报表。MongoDB 也支持事务和索引，MySQL 也能存 JSON，所以不能用“一个无 schema、一个有 schema”简单判断。应从访问模式、原子边界、索引、增长方式和团队运维能力选择。

可能追问：

1. 文档会无限增长怎么办：拆分子集合，避免无界数组。
2. MongoDB 是否无需建模：不是，数据共置和引用关系更依赖访问模式建模。
3. 聊天消息：会话与消息通常分开，按会话 ID 与时间建立查询索引。

## 13. 设计一个 AI 聊天产品

> 我会把系统拆成会话持久化、上下文构建、模型网关和流式交付。请求先鉴权、限流和校验，再从历史消息中按 token 预算选择上下文；模型网关负责超时、取消、重试、模型差异和降级；通过 SSE 向前端增量返回，前端支持停止生成、错误提示和安全渲染。最后记录模型、延迟、token、成本、错误分类和安全审计。

可能追问：

1. 为什么用 SSE：服务端到浏览器单向流足够，基于 HTTP、实现与代理兼容通常更简单；双向实时协作再考虑 WebSocket。
2. 断线怎么办：事件 ID、可恢复缓冲或按最终消息状态重新拉取；不能假设断线即停止模型生成。
3. 如何防 XSS：模型输出视为不可信，Markdown 解析后做白名单净化，代码块与链接协议也要限制。

## 14. Web 安全主线

> 我先看身份、输入、输出和资源授权。所有外部输入都做服务端校验和参数化查询；输出根据上下文编码，富文本做白名单净化；认证后每次访问仍要基于当前用户与目标资源关系授权，避免 IDOR/越权；Cookie 会话设置 HttpOnly、Secure、SameSite，并结合 CSRF 防护；同时做好限流、敏感字段、文件上传和日志脱敏。

可能追问：

1. XSS 与 CSRF：XSS 是脚本在受信任页面执行，CSRF 是借用户身份发请求；根因与防护不同。
2. CORS 能防 CSRF 吗：不能等同；简单请求可能仍会发出，CORS 主要约束浏览器读取响应。
3. 前端隐藏按钮能防越权吗：不能，服务端必须按身份和资源再次鉴权。

## 15. C 端性能优化

> 我会先用真实用户数据和实验室工具定位 LCP、INP、CLS 以及资源瀑布，再针对最大瓶颈处理。LCP 常见方向是首屏资源优先级、图片、字体和服务端响应；INP 看长任务、过度渲染和事件处理；CLS 为媒体预留空间。优化后在相同设备、网络和数据口径下复测，不用“感觉更快”代替证据。

可能追问：

1. bundle 变小为什么不一定更快：请求数量、执行成本、缓存和关键路径同样重要。
2. 图片优化：正确尺寸、现代格式、响应式、懒加载；LCP 图不能盲目懒加载。
3. 前端监控：性能、错误、请求、版本与用户路径关联，注意采样和隐私。

## 16. 线上接口突然变慢怎么排查

> 先确认影响范围、开始时间和近期变更，再拆浏览器网络、网关、应用、数据库和下游。用 request ID 串联日志与追踪，比较各阶段耗时；同时检查错误率、资源、连接池、慢 SQL 和队列积压。先止损，例如回滚、降级、限流或扩容，再定位根因。前端可做超时、取消、骨架和局部降级，但不能用无限重试掩盖服务端问题。

可能追问：

1. 为什么不能先扩容：数据库/下游已饱和时会放大压力。
2. 为什么重试要有抖动：避免所有客户端同时再次请求。
3. 如何验证修复：同口径指标恢复、错误分类消失，并补监控和复盘。

## 最后 5 分钟只背这 8 句

1. 能计算出的状态不再存第二份。
2. TypeScript 类型不替代运行时校验。
3. NestJS 的 Guard 管放行，Pipe 管输入，Interceptor 包裹调用，Filter 管异常。
4. 队列可能重复，最终结果必须幂等。
5. 数据库任务记录是业务事实，队列状态负责调度。
6. 前端价格只做展示，交易结果以后端为准。
7. AI 输出与用户输入一样都不可信。
8. 性能和故障处理都要先量化证据，再改，再复测。
