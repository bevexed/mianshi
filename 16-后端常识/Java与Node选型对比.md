# Java 与 Node.js 选型

语言运行时不是业务架构的替代品。选型应从团队能力、现有平台、依赖生态、延迟/吞吐目标、故障模型和长期维护成本出发。

## 并发模型

### Node.js

- JavaScript 回调默认在事件循环线程执行，非阻塞 I/O 由运行时和操作系统协调。
- I/O 回调中长时间同步计算会阻塞同进程请求。
- CPU 工作可用 Worker Threads、子进程或独立服务；多副本用于并行和故障隔离。

### Java

- 传统服务常用有界线程池处理请求；线程、队列、连接池和下游容量需要一起调优。
- 虚拟线程可以降低大量阻塞式 I/O 任务的线程成本，但不会让 CPU、数据库连接或下游服务容量变无限。
- 也可以使用响应式/事件驱动模型，不应把 Java 永久等同于“一请求一平台线程”。

两者都能处理 I/O 和 CPU 工作，差异主要在默认模型、生态、团队经验和可观测/运维方式，不是“Node 只能 I/O、Java 只能计算”。

## 评估维度

| 维度         | 要问的问题                                               |
| ------------ | -------------------------------------------------------- |
| 团队与所有权 | 谁开发、值班和升级？人员流动后谁能维护？                 |
| 生态         | 协议、驱动、框架和公司平台是否成熟？                     |
| 性能         | p95/p99、吞吐、CPU、内存和启动目标是什么？有真实基准吗？ |
| 一致性       | 事务边界、消息和外部系统如何恢复？                       |
| 安全合规     | 依赖治理、数据驻留、补丁和审计能力如何？                 |
| 部署         | 镜像、伸缩、优雅停机、探针和可观测性是否标准化？         |
| 生命周期     | 预计维护多久，升级节奏和迁移成本是什么？                 |

## 常见适配倾向

Node.js 常见于 BFF、SSR、实时连接、自动化工具和 TypeScript 团队拥有的服务。Java/Spring 常见于已有 Java 平台、复杂企业业务和需要成熟 JVM 生态的系统。这些是组织与生态倾向，不是能力限制。

例如 BFF 如果只是聚合少量接口，Node.js 可让前端团队共享类型和工具链；如果公司已有统一 Java 网关、监控和运维平台，另建 Node 服务的长期成本可能高于语言便利。

## 基准与容量

- 使用真实路由、序列化、日志、认证、数据库和 TLS 配置压测，空框架 QPS 不能代表业务。
- 分别测正常、尾延迟、突发流量和依赖变慢。
- 限制连接池、队列和并发，观察背压而不是只追求最大吞吐。
- 记录 CPU profile、事件循环延迟/线程池饱和、GC、内存和下游指标。

## 稳定性共同要求

- 明确启动、就绪和存活语义；
- 收到终止信号后停止接新流量并有界等待在途工作；
- 未处理的致命错误记录必要上下文后让进程退出，由编排系统重启；
- 设置请求/任务超时、取消、重试预算和幂等；
- 固定依赖版本、持续更新安全补丁并演练回滚。
