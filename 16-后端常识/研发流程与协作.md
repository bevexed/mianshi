# 研发流程与前后端协作

协作的目标是尽早暴露不确定性，用明确契约和自动反馈减少串行等待。

## 需求到上线

| 阶段      | 关键产出                                     |
| --------- | -------------------------------------------- |
| 需求澄清  | 用户目标、范围、异常流程、成功指标、不做什么 |
| 技术设计  | 边界、数据流、备选方案、风险、迁移与回退     |
| 契约评审  | API/schema、权限、错误、幂等、版本和 mock    |
| 实现      | 小批次集成、测试、观测和文档同步             |
| 联调/验收 | 真实边界、失败注入、兼容和端到端流程         |
| 发布      | 不可变制品、灰度、观察指标和回退             |
| 复盘      | 结果、偏差、债务和有 owner 的后续动作        |

流程按风险裁剪；小改动不需要冗长文档，高风险数据迁移不能只靠口头约定。

## 契约优先

1. 前后端共同列出页面/调用链需要的操作和数据，不由任一方单独猜。
2. 用 OpenAPI 等机器可读 schema 定义请求、响应、错误和示例。
3. 评审命名、金额/时间、大整数、枚举、分页、权限和幂等。
4. 契约稳定后生成 mock 和类型并行开发。
5. 任何变更先更新契约并做兼容性检查，避免文档在实现后补写。

Mock 只能证明客户端符合预期契约，不能替代真实序列化、网关、权限和数据库集成测试。消费者驱动契约测试适合关键跨团队 API。

## 减少阻塞

- 客户端请求集中在适配层，业务组件不依赖后端临时字段。
- 先实现可验证的窄切片，尽早打通一条真实链路，而不是最后集中联调。
- 后端不可用时使用契约 mock；契约不清楚时不能用假数据掩盖决策缺失。
- 每个跨团队依赖明确 owner、截止时间、降级和升级路径。

“防御性渲染”不等于用可选链吞掉所有数据错误。关键响应应在边界校验并明确降级，schema 违约要监控。

## 技术分歧

```text
共同目标 → 已知约束 → 可选方案 → 数据/实验 → 决策 owner → 复审条件
```

- 将安全、正确性和偏好分开；安全边界不能用“先这样”带过。
- 用请求瀑布、执行计划、故障样本等证据替代角色权威。
- 小而可逆的决策快速试验，大而不可逆的决策增加评审和记录。
- 未采用自己的方案时，在最终方案内降低风险并支持团队决策；同时保留复审触发条件。

## 流程自动化

- 格式、lint、类型、测试和构建放入 CI，不能只依赖本地 hook。
- code review 关注行为、边界和维护性，重大设计在编码前评审。
- 发布观察技术指标和业务成功率，异常自动停止放量。
- 事故行动项转化为门禁、测试、监控或演练，并跟踪是否完成。

自动化也有维护成本。门禁太慢、误报高或无人负责会被绕过，应监控耗时和失败原因并持续精简。

## 迭代方式

Scrum、Kanban 和版本列车都是工具。无论采用哪种方式，都要限制在制品、公开阻塞、缩短反馈周期并在回顾中改进系统。站会用于协调与暴露风险，不应成为逐人向负责人汇报。
