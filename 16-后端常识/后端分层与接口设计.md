# 后端分层与接口设计

分层的目标是让业务规则、传输协议和数据访问可以独立理解和测试。目录名称和 DTO/VO/Entity 术语因团队而异，重要的是边界一致。

## 常见分层

```text
Transport / Controller：解析协议、认证上下文、输入输出映射
Application Service：用例编排、事务边界、权限与幂等协调
Domain：业务不变量、状态转换和值对象
Infrastructure：数据库、消息、缓存和第三方适配器
```

简单 CRUD 不必强行复制完整 DDD 目录；复杂业务也不应把所有逻辑堆在 Controller 或 ORM Entity 中。按变化来源和测试边界决定层数。

## 请求、响应与持久化模型

不直接暴露数据库 Entity：

- 避免密码 hash、内部标记和租户字段泄露；
- 防止数据库迁移直接破坏公开 API；
- 请求与响应往往需要组合、裁剪和不同校验；
- 防止客户端批量赋值不应修改的字段。

输入模型采用 allowlist 映射，服务端从认证上下文取得用户/租户，不能信任客户端传来的所有权字段。

## HTTP 资源设计

```text
GET    /orders             列表
GET    /orders/{id}        详情
POST   /orders             创建或提交非幂等命令
PUT    /orders/{id}        按契约替换资源，HTTP 语义要求幂等
PATCH  /orders/{id}        部分修改，幂等性取决于 patch 格式与操作
DELETE /orders/{id}        删除资源，重复请求应得到等效状态
```

业务动作可建模为子资源或命令端点，例如 `POST /orders/{id}/cancellations`。一致、可发现且有文档的契约比生硬避免所有动词更重要。

## 状态码与错误

- 2xx 表示请求按 HTTP 语义成功；创建常用 201，异步接受可用 202。
- 400 语法/通用请求问题，401 未认证，403 已认证但无权，404 不存在或按安全策略隐藏，409 状态冲突，422 可用于语义校验，429 限流，5xx 服务端故障。
- 错误体提供稳定错误类型/code、可展示消息、字段错误和 trace ID；不要返回内部堆栈。

全部返回 200 会削弱 CDN、网关、监控和通用客户端的语义。业务细分 code 可以与正确的 HTTP 状态码并存，不必强制所有成功响应套 `{code,message,data}`。

## 分页与并发控制

- offset 适合小数据和跳页，cursor/keyset 适合稳定顺序和深分页。
- 排序必须有唯一 tie-breaker，cursor 绑定筛选条件并防篡改。
- 更新可使用 ETag/`If-Match` 或业务 version 防止丢失更新；冲突返回 409/412 等明确结果。

## 幂等

HTTP 方法的规范语义与业务实现要区分：PUT、DELETE 应幂等，POST 默认不保证。支付、下单等需要安全重试的 POST 可接受 `Idempotency-Key`：

- key 绑定调用者、目标操作和请求摘要；
- 原子记录处理中/成功/失败状态；
- 相同 key 不同请求体应拒绝；
- 定义保存期限和并发请求行为；
- 最终仍由唯一约束和状态机守住业务不变量。

前端禁用按钮只能改善体验，不能作为服务端幂等保证。

## 安全

- 每次访问按当前身份做对象级授权，列表查询也要带租户/范围过滤。
- 价格、折扣和权限由服务端计算/验证，客户端字段均视为不可信。
- 参数化 SQL；动态标识符使用 allowlist。
- 浏览器 cookie 会话考虑 CSRF；令牌 API 校验签发者、受众、有效期和权限。
- 对外 webhook 验证签名、时间窗口、防重放和密钥轮换。
- 限流是多维容量和滥用防线，不应只按 IP。

## 演进

- 先增加兼容字段/行为，再迁移消费者，最后清理旧契约。
- 字段新增通常可兼容，但新增枚举值、改变 NULL 语义和排序也会破坏客户端。
- OpenAPI/JSON Schema 作为契约来源，CI 检查破坏性变化并生成类型时仍需 review。
- 版本化只解决标识，不自动解决维护和数据迁移。
