# 跨域与 CORS

## 什么是同源

URL 的**协议、主机、端口**都相同才是同源。同源策略主要限制脚本读取其他源的
DOM 和响应数据；它并不阻止所有跨源请求，`<img>`、`<script>`、表单等仍可能发送请求，
这也是 CSRF 能发生的原因之一。

## 首选方案：服务端配置 CORS

浏览器发送请求，服务端用响应头声明允许哪些源读取响应：

```http
Access-Control-Allow-Origin: https://app.example.com
Vary: Origin
```

### 简单请求与预检

满足限定方法、头部和 Content-Type 的请求可能直接发送；其他请求先发 `OPTIONS` 预检：

```http
Access-Control-Request-Method: PUT
Access-Control-Request-Headers: authorization, content-type
```

服务端需要返回允许的方法和头部。预检成功只代表浏览器允许发送正式请求，
不代表业务鉴权已经通过。

### 携带 Cookie

```js
fetch('https://api.example.com/user', {
	credentials: 'include'
});
```

服务端还要返回 `Access-Control-Allow-Credentials: true`，并把
`Access-Control-Allow-Origin` 写成明确来源，不能使用 `*`。Cookie 自身的
SameSite、Secure、Domain 等属性也必须允许该场景。

## 反向代理

开发服务器或 Nginx 可以让浏览器请求同源地址，再由服务端转发到真实 API。
代理改变的是浏览器看到的请求源；服务到服务通信本来就不受浏览器同源策略限制。
开发代理配置不会自动成为生产配置。

## iframe / 窗口通信

跨源窗口不能直接读对方 DOM，但可以使用 `postMessage`：

```js
otherWindow.postMessage({ type: 'ready' }, 'https://trusted.example.com');

window.addEventListener('message', (event) => {
	if (event.origin !== 'https://trusted.example.com') return;
	if (event.data?.type === 'ready') handleReady();
});
```

发送时使用精确 `targetOrigin`，接收时同时校验 `origin` 和消息结构。

## 旧方案边界

- JSONP 利用 `<script>` 可跨源加载，只支持 GET，且会执行对方返回的脚本；只用于遗留接口。
- `document.domain` 已废弃，并会破坏现代跨源隔离能力。
- `location.hash`、`window.name` 等 iframe 中转方案维护和安全成本高，不用于新项目。
- WebSocket 不由 CORS 机制控制，但浏览器会发送 `Origin`，服务端仍必须校验允许来源。

归档清单见 [旧版跨域方案](../99-归档/旧版跨域方案清单.md)。
