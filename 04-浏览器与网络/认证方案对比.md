# 认证方案：Cookie / Session / JWT

## Session 和 JWT 的区别

|                  | Session（服务端存储）         | JWT（无状态）                                         |
| ---------------- | ----------------------------- | ----------------------------------------------------- |
| 状态存哪         | 服务端（内存/Redis）          | **令牌本身**（客户端持有）                            |
| 服务端负担       | 要存储和查找                  | 无需存储，验签即可                                    |
| 水平扩展         | 需共享存储或会话粘滞          | 自包含 access token 易于跨实例验签                    |
| **能否主动失效** | ✅ 删除会话即可               | 纯无状态验签不能逐个撤销；可加 denylist/token version |
| 体积             | Cookie 里只有一个 id          | 每次请求都带完整 payload                              |
| 跨域/跨端        | Cookie 受同源和 SameSite 限制 | 放 header，灵活                                       |

## JWT 的结构与坑

```
header.payload.signature
{alg,typ}.{业务数据,exp}.HMAC或RSA签名
```

### 坑（面试重点）

**1. payload 只是 base64 编码，不是加密**
任何人都能解开看内容，**绝不能放敏感信息**（密码、身份证、完整手机号）。

**2. 纯无状态 JWT 难以立即注销**
用户改密码/被封禁后，已签发的 token 到期前仍然有效。

- 解法 A：**短 access token（15 分钟）+ refresh token**
- 解法 B：维护 denylist、用户 token version 或轮换签名密钥；这会引入服务端状态或扩大失效范围

**3. `alg: none` 攻击**
早期实现如果信任 header 里的算法声明，
攻击者把 `alg` 改成 `none` 就能绕过验签。
服务端库必须配置允许算法和正确密钥，不能无条件信任 header 声明。

**4. 续期策略**
refresh token 存哪、怎么防止被盗用、
并发请求同时发现 token 过期时怎么避免刷新多次（要做请求队列）。

## token 存 localStorage 还是 cookie

**经典题，必须答出权衡而不是给一个答案。**

|      | localStorage                 | httpOnly Cookie             |
| ---- | ---------------------------- | --------------------------- |
| XSS  | ❌ JS 可读，脚本注入就能偷走 | ✅ JS 读不到                |
| CSRF | ✅ 不会自动携带              | ❌ 会自动携带，需要额外防护 |
| 跨域 | 手动加 header，灵活          | 受 SameSite/域名限制        |
| SSR  | ❌ 服务端读不到              | ✅ **服务端能直接读**       |

### 结论

> **httpOnly + Secure + SameSite=Lax 的 cookie 是更安全的默认选择**，
> CSRF 用 SameSite + CSRF token 防。
>
> 而且在 Next.js 这种 SSR 场景下，cookie 还有一个额外好处——
> 服务端能直接读到登录态，避免了「服务端不知道登录状态、客户端知道」
> 导致的水合不匹配。

> 关联：[05-React 生态/Next.js/RSC 与水合.md](../05-React生态/Next.js/RSC与水合.md)、
> [XSS 与前端注入](../13-Web安全/XSS与前端注入.md)、
> [CSRF 与跨站请求防护](../13-Web安全/CSRF与跨站请求防护.md)

### 但要补一句

**XSS 面前没有绝对安全的存储**——
如果被 XSS 了，httpOnly cookie 虽然读不到，
攻击者仍可能在页面上下文中直接以当前身份发请求。
所以**根本解法是防住 XSS**（CSP、输出转义、避免 `dangerouslySetInnerHTML`）。

## OAuth 2.0 / OpenID Connect

- **授权码模式**：前端拿 code → 后端用 code + 客户端凭据换 token；
  浏览器/移动端等 public client 使用 PKCE，不能安全保存固定 client secret
- **为什么要 code 这一步**，不直接返回 token？
  → 因为 token 走前端 URL 会被浏览器历史、Referer、日志记录下来；
  code 是一次性的、短时效的，并绑定 redirect URI；机密客户端还用 secret 认证自己，
  public client 则用 PKCE 的 code verifier 防止授权码被截获后直接兑换

OAuth 2.0 主要解决委托授权；登录身份层通常使用 OpenID Connect。实现时必须按具体提供方文档验证 PKCE、redirect URI、state/nonce、token 受众和刷新令牌轮换。
