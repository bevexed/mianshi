# TCP 与 HTTPS

## TCP 三次握手

```
客户端 → SYN(seq=x)              → 服务端
客户端 ← SYN+ACK(seq=y,ack=x+1)  ← 服务端
客户端 → ACK(ack=y+1)            → 服务端
```

### 为什么必须是三次，不能是两次

- 目的是**双方都确认对方的收发能力都正常**
- 两次的话，服务端无法确认「客户端能收到我的包」
- **更实际的原因**：防止**已失效的连接请求**突然到达服务端。
  如果只有两次，一个滞留在网络中的旧 SYN 到达后，
  服务端就会建立连接并等待，白白占用资源

### 四次挥手为什么比握手多一次

```
主动方 → FIN     → 被动方
主动方 ← ACK     ← 被动方     （此时被动方可能还有数据要发）
主动方 ← FIN     ← 被动方
主动方 → ACK     → 被动方     （等 2MSL 后关闭）
```

关闭时被动方收到 FIN 后**可能还有数据要发**，
所以 ACK 和 FIN 要分开发；
而握手时 SYN 和 ACK 可以合并成一个包。

**为什么要等 2MSL**：确保最后一个 ACK 能到达对方
（如果丢了，对方会重发 FIN，这边还能再回一次）。

## HTTPS 握手过程

```
TLS 1.3 简化流程：
1. ClientHello：支持的版本/套件、随机数、(EC)DHE key share
2. ServerHello：选择参数并返回自己的 key share
3. 服务端发送证书、对握手摘要的签名和 Finished
4. 客户端验证证书链、域名和签名，发送 Finished
5. 双方从 (EC)DHE 共享秘密和握手摘要派生对称会话密钥
```

“客户端生成 pre-master secret，再用证书 RSA 公钥加密”主要是旧版 TLS 的 RSA
密钥交换流程；TLS 1.3 已移除 RSA 密钥交换，证书公钥主要用于认证签名。

### 核心考点

**为什么要非对称 + 对称混合？**
非对称密码用于认证和密钥协商，对称加密用于高效保护后续数据。
现代 TLS 通常通过临时 (EC)DHE 协商共享秘密，并用证书签名防止中间人替换握手参数，
不是简单地“用公钥加密后传一个对称密钥”。

**证书解决什么问题？**
防中间人攻击——证明"这个公钥确实属于这个域名"，由 CA 背书。
浏览器内置根证书，逐级验证证书链。

**TLS 1.3 的改进**：

- 握手从 2-RTT 降到 **1-RTT**
- 支持 **0-RTT** 会话恢复（但有重放攻击风险，只用于幂等请求）
- 砍掉了 RSA 密钥交换、SHA-1、RC4 等不安全的旧算法

## 前端能感知到的部分

- **证书过期/域名不匹配** → 浏览器拦截，用户看到警告页
- **混合内容（Mixed Content）** → HTTPS 页面里引 HTTP 资源会被阻止
- **HSTS** → 服务端声明"以后只能用 HTTPS 访问我"，
  浏览器会自动把 http 请求改成 https
- **握手耗时** → 影响 TTFB，可以用 `preconnect` 提前完成握手：
  ```html
  <link rel="preconnect" href="https://cdn.example.com" />
  ```
