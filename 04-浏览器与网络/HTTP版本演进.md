# HTTP 版本演进

> 原 `http对比.md` 侧重 HTTP/1.0 vs 1.1，本篇补 HTTP/2 与 HTTP/3。

## 三个版本的核心区别

|            | HTTP/1.1                                   | HTTP/2                             | HTTP/3                                         |
| ---------- | ------------------------------------------ | ---------------------------------- | ---------------------------------------------- |
| 传输层     | TCP                                        | TCP                                | **QUIC（基于 UDP）**                           |
| 并发       | 浏览器通常开多个连接；单连接很少使用流水线 | **多路复用**：一个连接跑多个流     | 多路复用                                       |
| 队头阻塞   | **应用层**有                               | 应用层解决，**TCP 层仍有跨流阻塞** | 移除 TCP 造成的跨流队头阻塞                    |
| 头部       | 明文，重复发送                             | **HPACK 压缩**                     | **QPACK 压缩**                                 |
| 服务端推送 | 无                                         | 协议支持，主流浏览器已很少启用     | 协议支持，但客户端可禁用                       |
| 握手       | TCP；HTTPS 再做 TLS                        | 同左                               | 首次通常 1-RTT；恢复连接可 0-RTT（有重放风险） |

## 什么是队头阻塞？为什么 HTTP/2 没彻底解决

**这题是理解 HTTP/3 存在意义的关键，必须答清楚。**

- **HTTP/1.1 的队头阻塞在应用层**：一个 TCP 连接上，
  请求必须按顺序响应，前面的慢就堵住后面的
- **HTTP/2 用多路复用解决了应用层**：多个流可以交错传输
- **但 TCP 本身要求字节流有序**——如果某个 TCP 包丢了，
  **整个连接上所有流都要等它重传**，哪怕其他流的数据已经到了。
  这就是 **TCP 层的队头阻塞**
- **HTTP/3 换成 QUIC（基于 UDP）**，各个流独立排序，
  一个流缺失数据不会阻塞其他流继续交付；受拥塞控制和共享网络路径影响，
  不能理解成“丢包对其他流完全没有任何性能影响”

### 一个反直觉的加分点

正因为 HTTP/2 通常在单个 TCP 连接上复用，丢包会阻塞该连接的所有流；
在特定弱网和连接配置下，它可能比多 TCP 连接的 HTTP/1.1 更受单次丢包影响。
这不是普遍的“HTTP/2 更慢”结论，还要考虑握手、拥塞控制和连接复用收益。

## 有了 HTTP/2，哪些前端优化过时了

- **只为减少请求数而制作的大雪碧图**——收益下降；小图标仍可因缓存、设计资产等原因使用
- **域名分片**——为了突破 6 个连接限制，现在**反而有害**
  （多个域名意味着多次 DNS + 握手，且削弱多路复用）
- **激进合并 JS/CSS**——不必了，
  但**仍要按变更频率分组做缓存优化**

## HPACK / QPACK 头部压缩

- HTTP/1.1 每个请求都要重发一遍 `Cookie`、`User-Agent`、`Accept`，
  几百字节 × N 个请求
- **HPACK**：维护一份静态表（常见头部）+ 动态表（本连接出现过的），
  重复的头部只发一个索引号
- **QPACK** 是 HTTP/3 版本——因为 QUIC 的流是乱序的，
  HPACK 的动态表依赖顺序会出问题，QPACK 解决了这个
