# 浏览器存储方案对比

> 原 `cookie和storage.md` 已并入本篇。
> 认证场景下 token 存哪里，见 [认证方案对比.md](认证方案对比.md)

## 全景对比

|                    | 容量                                    | 生命周期            | 随请求发送                   | 同步/异步                                 | 跨域                         |
| ------------------ | --------------------------------------- | ------------------- | ---------------------------- | ----------------------------------------- | ---------------------------- |
| **Cookie**         | 单条及总量都有较小限制（常见约 4KB/条） | session 或显式过期  | ✅ 匹配域名/路径等条件时携带 | `document.cookie` 同步；Cookie Store 异步 | 受 Domain/Path/SameSite 限制 |
| **localStorage**   | 配额因浏览器而异（常见数 MB）           | 持久，除非清理/回收 | ❌                           | **同步（阻塞主线程）**                    | 同源隔离                     |
| **sessionStorage** | 配额因浏览器而异                        | 页面会话结束时清理  | ❌                           | 同步                                      | 同源 + 顶级浏览上下文        |
| **IndexedDB**      | 由站点存储配额和磁盘策略决定            | 持久或被回收        | ❌                           | **异步**                                  | 同源                         |
| **Cache Storage**  | 由站点存储配额决定                      | 持久或被回收        | ❌                           | 异步                                      | 同源                         |

---

## 怎么选

- **少量配置、需要同步读** → localStorage
- **只在当前标签页有效**（如多开互不干扰的表单草稿）→ sessionStorage
- **结构化大数据、离线数据、需要索引查询** → IndexedDB
- **服务端也要读** → Cookie
- **Request/Response 离线缓存** → Cache Storage，常与 Service Worker 配合

容量不是跨浏览器保证；隐私模式、磁盘压力和用户清理都可能让持久数据不可用，
重要数据必须以服务端为准并处理配额错误。

### 一个容易被忽略的性能点

`localStorage` 是**同步 API**，存取大对象（尤其配合 `JSON.parse`）
**会阻塞主线程**，直接影响 INP 指标。
频繁读写的大数据应该用 IndexedDB。

## Cookie 的关键属性

```
Set-Cookie: token=abc;
  Domain=.example.com;   // 作用域名（含子域）
  Path=/;
  Expires=...  / Max-Age=3600;
  HttpOnly;              // JS 读不到，防 XSS 窃取
  Secure;                // 只在 HTTPS 下发送
  SameSite=Lax           // 防 CSRF
```

**SameSite 三个值**：

- `Strict`——完全不跨站发送，体验差（从外链点进来是未登录态）
- `Lax`（现代浏览器默认）——顶层导航的 GET 请求会带，
  其余跨站请求不带
- `None`——跨站也带，但**必须同时设 `Secure`**

## IndexedDB

- 适合：离线应用、大量结构化数据、需要按索引查询
- 缺点：**API 很难用**（基于事件的事务模型）→
  实践中用 `idb` / `dexie` 这类封装库

```js
// 用 idb 封装后
const db = await openDB('mydb', 1, {
	upgrade(db) {
		db.createObjectStore('users', { keyPath: 'id' });
	}
});
await db.put('users', { id: 1, name: 'a' });
```

生产使用还要处理事务自动提交时机、版本升级被其他标签页阻塞、配额错误和 schema 迁移；封装库不会消除这些平台语义。
