# MySQL 事务与锁

以下默认讨论 InnoDB。事务正确性来自数据库机制、约束和应用状态设计共同作用，不能只靠选择一个隔离级别。

## ACID

| 属性   | 含义                                                     |
| ------ | -------------------------------------------------------- |
| 原子性 | 一个事务内的修改整体提交或整体回滚                       |
| 一致性 | 事务把数据库从一个满足约束的状态带到另一个满足约束的状态 |
| 隔离性 | 并发事务观察和影响彼此的程度受控                         |
| 持久性 | 已确认提交的结果在约定故障模型下可恢复                   |

undo、redo、锁和 MVCC 是重要实现机制，但业务不变量还需要唯一约束、外键/检查约束和应用逻辑表达。

## 隔离级别

| 级别             | 典型现象                                        |
| ---------------- | ----------------------------------------------- |
| Read Uncommitted | 可读到未提交修改                                |
| Read Committed   | 每个一致性读建立新快照，同一行可能两次结果不同  |
| Repeatable Read  | 同一事务的一致性读通常复用快照；InnoDB 默认级别 |
| Serializable     | 普通读的并发限制更强，吞吐和阻塞成本更高        |

InnoDB 的一致性读、锁定读和 DML 行为不同：普通 `SELECT` 主要使用 MVCC 快照，`SELECT ... FOR UPDATE/FOR SHARE` 读取当前版本并加锁。Repeatable Read 下一致性读通常不会看到新插入的“幻行”，但当前读、后续写入和范围锁的语义不能用一句“彻底解决幻读”概括。

事务应显式理解当前数据库版本、隔离级别和语句类型，不能把不同数据库的教科书表格直接当成实现保证。

## MVCC 与锁定读

MVCC 保存多个行版本，并通过 read view 判断当前事务可见版本，使多数一致性读不必阻塞写入。它不是“事务开始必定拍快照”：在 InnoDB Repeatable Read 中，快照通常由第一次一致性读建立；显式一致性快照事务另有控制。

```sql
SELECT * FROM accounts WHERE id = 1;           -- 一致性读
SELECT * FROM accounts WHERE id = 1 FOR SHARE; -- 共享锁定读
SELECT * FROM accounts WHERE id = 1 FOR UPDATE;-- 排他锁定读
```

锁定读必须在事务中使用，并尽快提交/回滚。

## InnoDB 锁范围

InnoDB 具有记录锁、间隙锁、next-key lock、意向锁等。DML 找不到合适索引时可能扫描并锁住大量索引记录或范围，造成接近“整表不可更新”的效果，但这不是传统意义上的行锁升级为表锁；InnoDB 不因锁数量自动做这种锁升级。

锁范围受索引、条件、隔离级别、唯一查找和执行计划影响。用 `performance_schema.data_locks`、`data_lock_waits` 和事务信息确认实际阻塞，而不是仅看 SQL 文本猜测。

## 并发更新

库存扣减可以把条件和更新合为一条原子 SQL：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

影响行数为 1 表示成功，0 表示无库存或记录不存在。涉及多表规则时，可使用锁定读或版本号，但仍要定义重试和失败返回。

乐观版本更新：

```sql
UPDATE orders
SET status = ?, version = version + 1
WHERE id = ? AND version = ? AND status = ?;
```

版本冲突不应无限重试；返回冲突、重新读取或进入人工处理取决于业务语义。

## 死锁与锁等待

数据库可以检测部分死锁并回滚一个事务。应用必须把死锁当成可预期的并发结果：

- 所有路径按一致顺序访问资源；
- 缩短事务，外部 HTTP、消息和人工等待放在事务外；
- 用合适索引缩小扫描和锁范围；
- 对安全可重试事务设置有限次数退避；
- 保存死锁图和涉及 SQL，不能只在客户端捕获错误后重试。

长锁等待不一定形成死锁，也需要监控和超时。

## 数据库与外部系统

本地事务不能自动覆盖消息系统或第三方 API。常见做法包括事务 Outbox、幂等消费者、补偿和对账。不要在数据库提交成功后假定“随后发消息一定成功”，也不要在持锁期间调用不稳定的外部服务。

框架事务还要注意：

- 所有查询是否真正使用同一个事务连接/manager；
- 异常是否被吞掉或被转换为不会回滚的类型；
- Spring 代理模式下自调用是否绕过 `@Transactional`；
- 异步任务是否跨线程/进程而失去原事务上下文。
