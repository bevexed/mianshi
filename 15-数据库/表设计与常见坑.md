# 表设计与常见坑

表设计先表达业务不变量、生命周期和查询方式，再选择类型与索引。下面以 MySQL/InnoDB 为例。

## 类型选择

### 金额

- 需要十进制定点运算时使用合适精度的 `DECIMAL(p, s)`。
- 也可按最小货币单位存整数，但必须明确币种和单位；部分资产存在超过两位小数的最小单位。
- 不用 `FLOAT/DOUBLE` 表示需要精确相等和结算的十进制金额。
- API 可传十进制字符串或“整数 + 单位/币种”，避免 JSON number 在不同语言间产生精度歧义。

精度和范围必须从业务上限反推，例如税率、汇率、中间计算和汇总可能需要比展示更多的小数位。

### 时间

- `TIMESTAMP` 在连接时区和 UTC 之间转换，范围受类型版本限制；适合明确的时间点。
- `DATETIME` 保存日历字段本身，不自动表达时区；适合营业日、当地预约时间等需要额外时区语义的场景。
- “统一存 UTC”适合瞬时时间，但生日、酒店入住日等日历日期不应强行转换成 UTC 时间点。
- API 使用明确的 ISO 8601 offset/Z 或独立的日期类型，并单独保存业务时区标识。

### 标识、枚举和文本

- 主键可选自增整数、分布式 ID 或其他稳定标识，依据写入拓扑、暴露风险和索引成本决定。
- MySQL `BOOLEAN` 是 `TINYINT(1)` 的同义写法，数据库约束仍应限制合法值。
- `ENUM` 有存储和约束优势，也有演进、跨数据库和排序语义成本；不是一律禁止。
- 大文本与高频列表字段分离与否，要根据访问模式和行大小测试，不能只凭类型名称判断。

## 约束优先

- `NOT NULL` 表达必填，避免让每个调用方猜 NULL 含义。
- 唯一约束守住业务唯一性，应用“先查再插”无法抵抗并发。
- 外键适合由同一数据库维护的强引用完整性；跨服务引用则需要其他对账机制。
- `CHECK` 可表达简单范围，不应把复杂业务流程都塞入数据库表达式。

## 软删除与唯一性

软删除适合恢复、审计或历史查询，但会增加每个查询、唯一性、容量和隐私删除的复杂度。法律或安全要求的彻底删除不能用软删除替代。

错误做法：

```sql
UNIQUE KEY uk_business_deleted (business_key, deleted_at)
```

MySQL 唯一索引允许多个 `NULL`，因此它不能阻止同一个 `business_key` 出现多条 `deleted_at IS NULL` 的有效记录。

一种 MySQL 方案是用生成列只索引有效记录：

```sql
ALTER TABLE records
  ADD COLUMN active_business_key VARCHAR(128)
    GENERATED ALWAYS AS (
      CASE WHEN deleted_at IS NULL THEN business_key ELSE NULL END
    ) STORED,
  ADD UNIQUE KEY uk_active_business_key (active_business_key);
```

删除记录的生成列为 `NULL`，可以保留多条历史；有效记录映射为业务键，只允许一条。还要评估业务键长度、字符集和恢复已删除记录时的冲突。

单纯 `UNIQUE(business_key, is_deleted)` 也只能保留一条已删除记录，不适合多次删除历史。

## 快照与反范式

订单保存下单时的商品名、价格和地址，通常是业务快照，不是无意义重复。反范式字段要定义：

- 来源和写入时机；
- 后续是否同步更新；
- 与主数据冲突时谁是真相；
- 如何重建和对账。

没有所有权的冗余会逐渐变成无法解释的数据分叉。

## 审计与版本

常见字段包括 `created_at`、`updated_at`、创建/修改主体和乐观锁版本。审计日志与表内 `updated_by` 作用不同：后者只保存最后状态，前者记录变化过程。敏感字段的历史值也要考虑加密、访问控制和保留期。

## 索引设计

- 从真实的 WHERE、JOIN、ORDER BY、返回列和频率设计联合索引。
- 唯一索引先表达正确性，普通索引再优化访问。
- 索引数量没有通用“五个上限”；看写入成本、重复前缀、空间和实际使用。
- 上线前后用执行计划和指标验证，定期清理确认无用的重复索引。

## 接口契约

前后端至少明确：

1. 金额的币种、单位、舍入规则和传输类型；
2. 时间是时间点、当地日期还是带时区日历时间；
3. 枚举未知值和向前兼容行为；
4. 分页是 offset 还是 cursor，排序是否稳定；
5. 大整数是否以字符串传输，避免 JavaScript 安全整数范围问题；
6. 字段缺失、`null` 和空字符串的不同语义。

接口 schema 和数据库实体不应机械一一暴露。数据库迁移、API 演进和前端版本需要各自的兼容策略。
