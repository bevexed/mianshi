# Redis 数据结构与使用场景

Redis 适合低延迟的缓存、计数、临时状态和协调，但数据结构选择还要考虑持久化、内存、复制、集群和故障语义。

## 执行模型

Redis 的核心数据访问主要在内存中，事件驱动网络模型避免每连接一个线程。多数命令按顺序执行，单条命令相对于其他命令具有原子性；现代 Redis 还使用 I/O 线程和后台线程/进程处理部分工作，因此“Redis 完全单线程”并不准确。

单个慢命令、大 key 操作或长 Lua 脚本仍可能阻塞其他请求。原子不代表持久、跨节点一致或业务正确。

## 常用数据类型

| 类型       | 典型用途                   | 注意                                |
| ---------- | -------------------------- | ----------------------------------- |
| String     | 缓存、计数、位图、限流状态 | 大对象会放大网络和复制成本          |
| Hash       | 对象字段、计数集合         | 小字段很多时注意整体 key 大小       |
| List       | 简单队列、阻塞弹出         | 消费确认、重放和消费组能力有限      |
| Set        | 去重、标签、集合运算       | 大集合运算可能阻塞                  |
| Sorted Set | 排行、时间线、调度索引     | score 是 double，超大整数精度要注意 |
| Stream     | 有 ID 的消息流、消费组     | 仍需处理 pending、ACK、裁剪和幂等   |

Bitmap 适合连续 ID 的密集布尔状态；如果最大 ID 很大且稀疏，内存不一定省。HyperLogLog 提供近似基数统计，不适合需要列出成员或精确计费。GEO 底层用于地理位置近邻查询，精度和坐标范围要符合业务。

## 什么时候使用 Redis

不要从“Redis 很快”直接推出“数据应该放 Redis”。先看需求是否属于以下类型：

| 需求 | 典型例子 | 必须补充的边界 |
| --- | --- | --- |
| 热点数据缓存 | 商品详情、配置、用户摘要 | 明确数据库真相来源、不一致窗口和失效策略 |
| 带过期的临时状态 | 验证码、会话、OAuth state、任务进度 | TTL 不是精确定时器，过期数据不能是唯一业务事实 |
| 原子计数与集合 | 计数、排行榜、去重、滑动窗口限流 | 单命令原子不等于整个业务流程原子 |
| 多实例协调 | 锁、资源租约、共享限流 | 说明故障切换、锁过期和旧持有者继续写的处理 |
| 任务与消息 | BullMQ、延迟任务、轻量消息流 | 处理重复、ACK/重试、积压、持久化和容量 |

可以依次问：

1. 是否需要低延迟、高频读写或多个实例共享？
2. 是否需要 TTL、原子自增、集合运算、去重或抢占？
3. 数据丢失或过期后能否从数据库或上游重建？
4. 内存成本是否值得，是否有容量上限和清理策略？
5. 引入后的一致性、穿透、击穿、雪崩和故障降级由谁负责？

订单、支付、资产、正式业务事实和复杂关联查询通常不应只依赖 Redis。低频海量历史数据放在内存中也可能得不偿失。

### 项目表达

> 在采集服务中，BullMQ 与 Redis 负责任务派发和延迟调度，MySQL 任务表保存长期业务事实；共享出口轮换还使用 Redis TTL 和 Lua compare-and-delete 处理竞态。Redis 负责低延迟调度与协调，企业、资质和人员等正式数据仍由 MySQL 保存。快速去重只是第一层，最终结果仍靠数据库唯一约束和幂等写入兜底。

## 过期与淘汰

过期 key 通过访问时的被动过期与周期性的主动过期清理。过期时间到达不保证内存恰好在该毫秒释放，应用不应把 TTL 当成精确调度器。

达到 `maxmemory` 后，行为由 `maxmemory-policy` 决定：

- `noeviction`：不淘汰，可能拒绝会增加内存的写命令；
- `allkeys-lru` / `allkeys-lfu`：在所有 key 中按近似最近/频率策略淘汰；
- `volatile-*`：只在设置 TTL 的 key 中淘汰，没有候选时可能像 noeviction；
- random、TTL 等其他策略适合特定访问模式。

默认配置和托管服务可能不同。缓存与持久状态混在同一实例时，任何淘汰策略都更难推理，最好按数据性质隔离并用 `INFO` 命中率、eviction 和内存指标验证。

## 原子组合

多个命令需要一起判断和修改时，可使用 Lua、事务或服务端提供的原子命令。Lua 执行期间阻塞命令线程，应保持短小、确定且限制输入规模。

```lua
-- 仅锁的 token 与调用者一致时删除。
if redis.call('GET', KEYS[1]) == ARGV[1] then
  return redis.call('DEL', KEYS[1])
end
return 0
```

## 分布式锁

```text
SET resource_lock random_token NX PX 30000
```

- token 每次获取唯一；释放和续期都必须校验 token 并原子执行。
- TTL 防止持有者永久失联，但过短会让业务未完成时锁失效。
- 自动续期要有最大持有时间和进程健康判断，不能无限延长僵死任务。
- Redis 故障切换、网络暂停和客户端停顿可能破坏互斥假设。

如果过期锁的旧持有者仍能写下游，仅靠锁 token 不够；下游需要 fencing token（单调递增版本）拒绝旧持有者，或用数据库约束/状态版本保证正确性。锁应减少冲突，不应成为唯一正确性机制。

单实例锁强调简单但存在可用性和故障切换风险；多节点算法增加假设与复杂度。根据可接受故障模型选择，并通过故障注入验证，不以“用了 Redlock/看门狗”代替证明。

参考：[Redis distributed locks](https://redis.io/docs/latest/develop/use/patterns/distributed-locks/)

## Key 设计与集群

- key 包含稳定命名空间、版本和业务标识，避免把敏感信息直接放在 key 中。
- 设定 TTL 和最大集合长度，监控大 key、热 key 与每租户占用。
- Redis Cluster 的多 key 原子操作要求相关 key 位于同一 hash slot，可用 hash tag，但会形成热点。
- 扫描使用 `SCAN` 类命令而非生产环境全量 `KEYS`；遍历仍会消耗资源，应限速。
