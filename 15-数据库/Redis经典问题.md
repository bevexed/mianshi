# Redis 缓存常见问题

穿透、热点失效和大面积失效是不同故障形态。方案必须同时说明一致性、容量、失败和降级边界。

## 缓存穿透

查询不存在的数据时，缓存无法拦截请求，流量持续到达数据库。

- 先做身份、参数和对象范围校验。
- 短时间缓存“未找到”，并在数据创建时主动失效；空值也要设置容量上限。
- 大规模稳定集合可用布隆过滤器拦截明确不存在项。

布隆过滤器存在假阳性。只有在元素正确加入、位数组未丢失且删除策略正确时，才能依赖“没有假阴性”的理论性质；过滤器自身与数据库不同步会产生业务假阴性。

## 热点 key 同时回源（击穿）

热点缓存过期时，大量请求可能并发回源。

常见方案：

- singleflight/互斥重建，仅一个请求访问下游，其余等待或返回旧值；
- stale-while-revalidate，允许在受控陈旧窗口内先返回旧值并异步刷新；
- 在预计到期前刷新热点，并保留硬过期作为最终边界。

互斥锁必须用唯一 token 并在 `finally` 中原子校验释放。等待者需要超时、抖动和降级，递归轮询没有上限会把缓存故障变成请求堆积。

## 大面积失效（雪崩）

原因可能是大量 key 同时到期、Redis/网络不可用、错误清库或热门数据同时迁移。

- TTL 加抖动，避免同批数据同一毫秒过期。
- 限制回源并发，按业务优先级熔断或降级，保护数据库。
- 多级缓存只缓存允许短暂陈旧的数据，并控制本地缓存一致性和实例内存。
- Redis 使用适合目标的高可用与备份，但故障切换不能代替客户端超时、容量和降级。
- 预案中演练“缓存完全不可用”，而不只演练单个节点重启。

## Cache Aside 一致性

常见写路径是先提交数据库，再删除缓存；读路径缓存未命中时查询数据库并填充。它减少了直接更新缓存的乱序问题，但不提供强一致性。

典型竞态：慢读取得旧值，写事务随后提交并删缓存，慢读最后把旧值重新写回。还可能出现数据库已提交但删缓存失败。

根据业务要求选择补强：

- 缓存 TTL 限制单次陈旧值的最长存活，但如果旧值被持续重新写入，不能单独证明最终一致。
- 删除事件通过事务 Outbox/binlog 可靠投递并重试，消费者幂等。
- value 带数据版本，缓存写入拒绝覆盖更新版本。
- 对极短竞态窗口可做有界延迟再删，但固定延迟无法覆盖所有慢请求，只是风险降低手段。
- 强一致读绕过缓存或使用由同一一致性系统维护的方案；要接受延迟和可用性成本。

先定义允许陈旧多久、写后读是否必须看到新值、删缓存失败如何发现，再选择方案。“最终一致”必须说明促使系统收敛的机制。

## 大 key

大 key 会增加命令延迟、网络、复制、持久化和迁移成本。

- 按业务维度拆分并限制集合长度；
- 使用渐进扫描/删除，`UNLINK` 可把部分释放工作放到后台，但键从命名空间移除仍是同步动作；
- 监控 key 大小和增长率，不等故障后才抽样。

## 热 key

单个 key 的读写可能压垮一个节点或网络：

- 允许短暂陈旧时使用进程内缓存；
- 只读值可复制到多个 key/节点，但要解决更新广播和读取路由；
- 可合并的写计数按分片累加并异步汇总，不能对任意值简单加随机后缀；
- 对热点调用限流、批处理并监控单 key QPS。

## 观测指标

至少监控命中率、回源量、evicted/expired key、内存碎片、命令延迟、阻塞客户端、复制延迟、连接错误、大 key/热 key、缓存重建耗时和降级次数。命中率高也可能有严重热点，必须结合尾延迟和数据库压力判断。
